# Case studies

System design is learned by doing it out loud. This lesson gives you a method, then sketches three common systems with
the decisions an interviewer or reviewer will push on. Treat each sketch as a starting point to argue with, not an
answer key.

## A repeatable method

Walk every design in this order and say each step aloud:

1. **Requirements**: users, tasks, traffic, latency, quality bar, privacy, budget.
2. **Baseline**: the simplest version that could work.
3. **Architecture**: the components the requirements force you to add.
4. **Bottlenecks**: where latency and cost concentrate.
5. **Failure modes**: what breaks and what the user sees.
6. **Scaling**: what changes at 10x traffic or data.
7. **Trade-offs**: what you chose not to do, and why.

## Case 1: customer-support copilot

*Requirements (assumed)*: 30k conversations/day, help centre of 5k articles updated daily, account questions need
live data, answers need sources, p95 first token under 2 s.

| Concern | Decision |
|---------|----------|
| Knowledge | Hybrid RAG over articles, event-driven re-index on edit; order data via tools with session identity |
| Citations | Every answer links its article; abstain when retrieval is weak |
| Routing | Small model classifies intent; mid-tier model answers; strong model for disputes |
| Caching | Prompt caching always; semantic cache for generic FAQs only, evicted on article edit |
| Escalation | Handoff to human on low confidence, angry sentiment, or refund above a limit, with the conversation summary attached |
| Cost check | 30k × ~$0.003 ≈ $90/day before caching |

*Push-back to expect*: "What if an article is wrong?" (provenance, feedback per citation, owner per article). "What
if the provider is down?" (fallback model, then article search results).

## Case 2: coding assistant

*Requirements*: works in repositories of up to millions of lines; can edit files and run tests; tasks can take minutes.

| Concern | Decision |
|---------|----------|
| Context | Can't fit the repo; combine a code search index (symbols, file paths, embeddings), grep-style tools and a repository map |
| Tools | Read file, search, edit, run tests, all executed in a sandbox |
| Sandboxing | Isolated container per task, no production credentials, network restricted, resource and time limits |
| Models | Strong model for planning and editing; a fast model for autocomplete-style suggestions |
| Long tasks | Run as async jobs with checkpoints; stream progress; user approves before pushing a branch |
| Evaluation | Tasks with hidden tests (in the spirit of SWE-bench) on your own repos |

*Push-back*: "How do you stop it running `rm -rf` or leaking secrets?" (sandbox, allow-listed commands, no secrets in
the environment, human review of diffs).

## Case 3: deep research agent

*Requirements*: answer open questions with a cited report in under 15 minutes; budget per report capped.

| Concern | Decision |
|---------|----------|
| Planning | A lead model breaks the question into sub-questions |
| Parallelism | Sub-agents search and read sources in parallel, each with a narrow brief |
| Context management | Sub-agents return compressed findings with source links, not raw pages; the lead keeps notes |
| Citations | Each claim carries a source; a final pass checks that cited text supports the claim |
| Budgets | Caps on tokens, tool calls and wall time per report; stop early when sources repeat |
| Recovery | Durable workflow state so a crashed worker's sub-task is retried, not the whole report |

```
Budget sketch per report (example prices):
  lead model: 6 calls × 20k tokens       = 120k tokens
  5 sub-agents × 10 calls × 15k tokens   = 750k tokens
  ≈ 870k tokens × ~$3/M blended          ≈ $2.60 per report
```

*Push-back*: "Why multi-agent rather than one long loop?" (parallel speed and isolated contexts, at the price of more
tokens and harder debugging).

## Defending a choice

A good defence names the requirement, the alternative and the evidence: "We use a small model for intent because it
scores within 1 point of the large model on our 300 labelled messages at a tenth of the latency." A weak defence names
a tool: "We use X because it's popular."

## Try it

Design a meeting-notes assistant that joins video calls, produces a summary with action items, and lets users ask
questions about past meetings. Walk the seven steps briefly.

<details>
<summary>Reference</summary>

- Requirements: transcripts of 30-60 min calls, summaries within minutes after the call, Q&A across a team's history,
  strict access (only attendees/team), moderate volume.
- Baseline: transcribe, one long-context summary call, no Q&A.
- Architecture: STT with diarization → async summary job (structured output: decisions, action items with owners) →
  index transcript chunks with meeting id, date, attendees ACL → RAG Q&A with citations to timestamps.
- Bottlenecks: transcription time and long-transcript tokens; summarise per section then combine.
- Failures: bad diarization assigns tasks to the wrong person (show the quote, allow edits); STT outage (retry
  queue).
- Scaling: batch STT, prompt caching of the summary instructions, per-tenant indexes.
- Trade-offs: async summary (not live) to keep cost low; no agent, since steps are fixed.
</details>

## Check yourself

1. In the support copilot, why do account questions go to tools rather than RAG?

<details>
<summary>Answer</summary>
Account data is per-user, changes constantly and must be exact; tools query the system of record with the session's
identity, which also enforces access control.
</details>

2. What is the single most important safety control for a coding agent that runs commands?

<details>
<summary>Answer</summary>
An isolated sandbox with no production credentials and restricted network and resources, so even a bad or injected
command can't damage real systems; diff review before merge adds a second layer.
</details>

3. Why do research sub-agents return compressed findings instead of full pages?

<details>
<summary>Answer</summary>
To keep the lead agent's context small and focused; raw pages would exhaust the context window, raise cost and bury
the relevant facts.
</details>
