# A framework for AI system design

Most weak AI designs begin with a tool: "we'll use an agent framework and a vector database". Strong designs begin
with a question: what has to be true for this product to work? This lesson gives you a repeatable order of
operations, so that every box you draw later has a reason behind it.

## Step 1: requirements before boxes

Write these down before any architecture. If you are in an interview, ask for them; if nobody knows, state an
assumption out loud.

| Requirement | Example question | Why it changes the design |
|-------------|------------------|---------------------------|
| Use case | Who asks what, and what do they do with the answer? | Decides whether you need retrieval, tools or neither |
| Success criteria | What does "good" mean, and how will we measure it? | Without this you can't compare designs |
| Traffic | Requests per day, peak per second, growth | Drives cost, rate limits, caching |
| Latency | Interactive chat (seconds) or a nightly batch (hours)? | Decides model size, streaming, sync vs async |
| Quality bar | Is a wrong answer annoying or dangerous? | Decides guardrails, human review, model tier |
| Privacy | Can data leave your cloud? PII? Residency? | May rule out some providers entirely |
| Cost budget | Cents per request? Monthly cap? | Bounds model choice and context size |

## Step 2: choose the approach

There are four main tools, and they combine.

| Approach | Use when | Avoid when |
|----------|----------|------------|
| Prompting only | The model already knows enough; the task is a transformation (summarise, classify, rewrite) | Answers depend on private or fast-changing facts |
| RAG | Answers must come from your documents, with citations | The whole source fits comfortably in the prompt |
| Agents (tools in a loop) | The steps can't be known in advance; the system must act | A fixed sequence of steps would do |
| Fine-tuning | You need a consistent style/format at scale, or a smaller model to match a bigger one on a narrow task | You are trying to teach it facts that change |

A common honest answer is "RAG plus a little tool use", not "a multi-agent system".

## Step 3: the trade-off triangle

Quality, latency and cost pull against each other. A bigger model raises quality and both latency and cost. More
retrieved chunks may raise quality and certainly raise cost. Two more forces sit on top: **complexity** (every
component is something to evaluate, debug and keep running) and **reliability** (every extra call is another thing
that can fail).

Make the trade-off concrete with a back-of-envelope estimate:

```
Support assistant, 50,000 requests/day
Prompt: 3,000 tokens (system + 5 chunks + question), output: 300 tokens

Large model (example price $3 / M input, $15 / M output):
  input  50k × 3,000 = 150M tokens → $450/day
  output 50k ×   300 =  15M tokens → $225/day     ≈ $20k/month

Small model (example price $0.25 / M input, $1.25 / M output):
  ≈ $56/day                                       ≈ $1.7k/month
```

The question is no longer "which model is best?" but "is the large model's quality gain worth $18k a month for this
use case?" That is a question you answer with an eval set, not a hunch.

## Step 4: baseline first

Build the simplest thing that could meet the requirements: one model call, maybe naive retrieval. Measure it on your
eval set for quality, latency and cost. Then add components one at a time, each justified by a measured failure:

```python
baseline = {"model": "small", "retrieval": "dense top-5", "rerank": False}
results = run_eval(baseline, eval_set)     # quality 0.71, p95 2.1 s, $0.002/req

candidate = {**baseline, "rerank": True}
results = run_eval(candidate, eval_set)    # quality 0.79, p95 2.6 s, $0.0025/req
# keep it only if +0.08 quality is worth +0.5 s and +25% cost
```

A design that starts sophisticated has no way of telling which parts are earning their keep.

## Try it

A legal team wants a tool that answers questions about 20,000 internal contracts. Lawyers use it a few hundred times
a day, contracts never leave the company's cloud, and a wrong answer could cost money. Write the requirements table and
pick an approach.

<details>
<summary>Reference</summary>

- Use case: lawyers ask clause-level questions and need the exact source text.
- Success: answer correct and cited on an eval set of real lawyer questions; abstains when unsure.
- Traffic: low (hundreds/day), so per-request cost matters less than quality.
- Latency: a few seconds is fine; streaming helps.
- Quality bar: high; citations are mandatory and answers should be checkable.
- Privacy: must run inside the company cloud (a managed platform or self-hosted model).
- Approach: RAG with hybrid search (clause numbers and party names need keyword matching), a strong model because volume
  is low, citations and abstention. No fine-tuning (facts change as contracts are added), no agent unless questions
  need multi-step lookups across contracts.
</details>

## Check yourself

1. Why should you write the cost budget down before choosing a model?

<details>
<summary>Answer</summary>
Because model price per token multiplied by traffic can differ by 10x or more between tiers. Without a budget you
can't rule options out, and you may design something the business can't afford to run.
</details>

2. Name a case where fine-tuning is the wrong tool even though the model gives wrong answers.

<details>
<summary>Answer</summary>
When the wrong answers come from missing or changing facts (prices, policies, inventory). Fine-tuning bakes in a
snapshot and is poor at reliable fact recall; retrieval or tools fix this better.
</details>

3. What does a baseline give you that a sophisticated first design doesn't?

<details>
<summary>Answer</summary>
A measured reference point. Each added component can then be judged by how much quality it adds against the latency,
cost and complexity it brings; without the baseline you can't tell which parts matter.
</details>
