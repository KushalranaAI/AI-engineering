# Reliability and graceful degradation

An AI system depends on a model provider, an embedding API, a vector database and several tools, any of which can be
slow, down or wrong at any moment. The model itself can return malformed JSON or ignore an instruction. Reliable
design assumes all of this happens and decides in advance what the user gets when it does.

## Everything fails

| Failure | How it shows up | First defence |
|---------|-----------------|---------------|
| Provider outage | 5xx errors, connection timeouts | Fallback provider or model |
| Rate limit | 429 responses | Backoff, queue, quota per tenant |
| Slow response | Request hangs for a minute | Timeout, then fallback |
| Malformed output | JSON that doesn't parse or match the schema | Validate, re-ask once, then fail cleanly |
| Tool failure | API error or empty result | Retry if idempotent; tell the model the tool failed |
| Empty / weak retrieval | Low scores, no relevant chunks | Abstain or ask a clarifying question |
| Model mistake | Plausible but wrong answer | Guardrails, citations, human review |

## Timeouts, retries, circuit breakers and queues

The classic resilience patterns apply, with a few LLM-specific twists:

- **Timeouts** must fit streaming: time out on *time to first token* and on *gaps between tokens*, not only on total
  duration, because a long answer can legitimately take 30 s.
- **Retries** with exponential backoff and jitter for 429/5xx. Retry only idempotent operations: never blindly
  retry a tool call that sends an email or issues a refund.
- **Circuit breakers**: after repeated failures, stop calling the provider for a while and go straight to the
  fallback, instead of making every user wait for a timeout.
- **Queues** for work that doesn't need an immediate answer, so spikes become delays rather than errors.

```python
async def generate_with_fallback(prompt):
    for model in ["primary-large", "secondary-provider-large", "small-fast"]:
        if breaker[model].is_open():
            continue
        try:
            resp = await asyncio.wait_for(call(model, prompt), timeout=20)
            out = Answer.model_validate_json(resp.text)   # schema check
            breaker[model].record_success()
            return out, model
        except (TimeoutError, ProviderError, ValidationError) as e:
            breaker[model].record_failure()
            log.warning("model_failed", model=model, error=type(e).__name__)
    return None, None    # caller degrades
```

## Guardrails at the boundaries

Don't rely on the system prompt to keep the model safe. Put checks in code where data crosses a boundary: user input
coming in (injection patterns, PII, size limits), model output going out (schema, groundedness, banned content,
secrets), and above all **actions** (validate tool arguments against the user's permissions before executing).

## Degrade, don't die

Plan a ladder of reduced service and write it into the design:

1. Primary model unavailable → fallback model (log it, quality may differ).
2. All generation down → serve a cached answer or the top retrieved article directly as search results.
3. Retrieval down → answer only general questions and say documents are unavailable.
4. Can't help safely → hand off to a human, or say clearly what you can't do right now.

An honest "I can't check your order right now, here's the status page" beats a spinner and a 500 error.

## Humans approve risky actions

For irreversible or high-impact actions (payments, deletions, outbound messages to customers, production changes) the
model proposes and a person approves. Design the approval UI to show exactly what will happen, with the arguments,
not the model's summary of them.

## Service levels

Set targets the design must meet, and measure them:

| SLO | Example target |
|-----|----------------|
| Availability (non-error responses) | 99.5% monthly |
| Latency | p95 time to first token under 2 s |
| Quality | ≥ 90% pass rate on weekly sampled eval of live traffic |
| Safety | 0 unapproved irreversible actions |

Quality is an SLO too: a system that returns 200 OK with wrong answers is down in every way that matters to users.

## Try it

Your support assistant calls a model, a vector DB and an order-lookup tool. The primary provider is returning errors
for 30% of requests. Describe what the user experiences under your design, step by step.

<details>
<summary>Reference</summary>

- Failed calls fail fast on error (or after a TTFT timeout) and go to the fallback model; once failures pass the
  threshold the circuit opens and requests skip the primary entirely, so most users see a normal answer with slightly
  different style.
- If the fallback also fails, the user sees the most relevant help articles as links, plus a note that the assistant is
  degraded.
- Order lookups still work since the tool is independent; if it fails, the reply says the status can't be checked and
  offers a human agent.
- Alerts fire on the error rate; dashboards show the share of requests served by the fallback.
</details>

## Check yourself

1. Why is a retry dangerous for some tool calls?

<details>
<summary>Answer</summary>
Non-idempotent actions (sending email, charging a card) can execute twice if the first call actually succeeded but
the response was lost. Use idempotency keys or don't retry automatically.
</details>

2. Why time out on time-to-first-token rather than only total duration for streaming calls?

<details>
<summary>Answer</summary>
A long answer can validly take many seconds in total, but a provider that hasn't started producing tokens after a few
seconds is likely stuck; detecting that early lets you fall back sooner.
</details>

3. Why should quality be one of your service-level objectives?

<details>
<summary>Answer</summary>
An AI system can be fully "up" while giving wrong answers. Without a quality target and measurement, silent quality
failures never show on availability dashboards.
</details>
