# Model gateways and routing

If `client.chat.completions.create(model="some-model-name")` appears in thirty places in your code, you have
welded your product to one model from one vendor. Models get cheaper, better, deprecated and rate-limited every few
months. A **gateway** gives you one place to absorb that change.

## What a gateway does

A gateway is a thin service or library between application code and model providers. The app asks for a *capability*
("a cheap classifier", "the strong reasoning model"); the gateway decides which concrete model serves it.

```
app code ──► gateway ──► provider A (model x, model y)
                    ├──► provider B (model z)
                    └──► self-hosted vLLM (open-weight model)
         keys · retries · rate limits · logging · cost tracking · fallbacks
```

It can be a library (for example LiteLLM's SDK), a self-hosted proxy, a hosted router, or your cloud platform's
unified API. The design idea is the same.

## Routing rules

Route each request on properties you know before calling the model:

| Signal | Example rule |
|--------|--------------|
| Task type | Classification and extraction → small model; open-ended reasoning → large model |
| Context length | Prompt over 100k tokens → a long-context model |
| Modality | Contains an image → a vision-capable model |
| Latency | Autocomplete → fastest model available |
| Cost | Free-tier users → cheaper tier |
| Risk | Medical or legal topic → strongest model plus stricter guardrails |

```python
ROUTES = {
    "classify":  {"model": "small-fast",   "max_tokens": 50},
    "answer":    {"model": "mid-tier",     "max_tokens": 800},
    "reasoning": {"model": "large-strong", "max_tokens": 4000},
}

def route(task: str, prompt_tokens: int, has_image: bool) -> dict:
    cfg = dict(ROUTES[task])
    if has_image:
        cfg["model"] = "mid-tier-vision"
    if prompt_tokens > 100_000:
        cfg["model"] = "long-context"
    return cfg
```

The model names are config, not code, so swapping one is a deploy of a YAML file.

## Cascades

A **cascade** sends a request to a cheap model first and escalates only when needed. The hard part is deciding
"needed": common signals are a self-reported confidence, a verifier model, a failed schema check, or a cheap classifier
that predicts difficulty.

```
Worked example: 100k requests/day
  all on large model:                 100k × $0.010           = $1,000/day
  cascade: small handles 70%:          70k × $0.001 + 30k × ($0.001 + $0.010)
                                      = $70 + $330            =   $400/day
```

The saving is real only if the small model's 70% are actually right. Measure the cascade's quality on your eval set,
and note that escalated requests pay for both calls and are slower.

## Fallbacks and their risks

When the primary provider errors or throttles, fail over to another. But a fallback model is a **different model**:
it may follow your prompt differently, format JSON differently, or call tools differently. Treat every fallback route
as a production configuration: keep prompts compatible, run your eval suite against it, and log which model served
each request so you can explain odd answers later.

## One place for keys, limits and usage

Centralising in the gateway pays off once there are several teams or providers:

- Provider keys live only in the gateway; apps get scoped internal keys.
- Retries with backoff and per-provider rate limits are implemented once.
- Every call is logged with model, tokens, latency, cost and calling team.
- Budgets per team or feature stop one runaway job eating everyone's quota.

The price: the gateway is now on the critical path, so it needs its own monitoring, timeouts and redundancy. For a
single small app with one provider, a thin internal wrapper function may be all you need.

## Try it

Design routing for a support chatbot that (a) labels each incoming message by intent, (b) answers FAQs, (c) handles
refund disputes, and (d) occasionally receives screenshots. Name the model tier for each and one fallback.

<details>
<summary>Reference</summary>

- Intent labelling: small fast model with a fixed label set and structured output; fallback to another provider's
  small model.
- FAQs: mid-tier model with RAG; a cascade could try the small model first if evals show it is good enough.
- Refund disputes: strong model (higher risk, money involved), plus human approval for refunds above a threshold.
- Screenshots: route to a vision-capable model when an image is attached.
- Fallbacks are tested on the eval set; all routes log which model answered.
</details>

## Check yourself

1. What changes in your system when a fallback model answers instead of the primary?

<details>
<summary>Answer</summary>
Output quality, formatting, tool-calling behaviour and latency can all change. The fallback must be evaluated like any
other release, and requests must record which model served them.
</details>

2. What is the main design challenge in a cascade?

<details>
<summary>Answer</summary>
Deciding reliably when the cheap model's answer is good enough. A bad escalation signal either sends wrong answers to
users or escalates so often that the cascade costs more than using the strong model directly.
</details>

3. When is a separate gateway service overkill?

<details>
<summary>Answer</summary>
For a single app, one provider and one team. A small wrapper function with config-driven model names gives most of
the flexibility without adding a new critical-path service.
</details>
