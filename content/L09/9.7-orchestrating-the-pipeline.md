# Orchestrating the pipeline

By now you have parts: retrievers, models, tools, guardrails, caches. Orchestration is how they connect, what runs in
what order, who decides each step (your code or the model), and how long the user waits. Most production problems
here come from giving the model decisions that code could have made.

## The whole flow

Draw the request path end to end, including the boring parts:

```
request
  → auth + rate limit
  → input guardrail (size, injection, PII)
  → cache lookup ──hit──► respond
  → route (intent classifier: faq | account | escalate)
      faq     → retrieve → rerank → generate → output guardrail → cache write
      account → tool: order API (user id from session) → generate → output guardrail
      escalate→ create ticket → respond with handoff message
  → log trace (versions, tokens, latency, cost)
  → respond (streamed)
```

A diagram like this answers most interview follow-ups before they are asked: where is permission checked, what's
cached, what happens on failure.

## Code decides or model decides

For each decision point, ask: can a rule, a lookup or a small classifier make this reliably? If yes, let code do it.

| Decision | Usually deterministic | Usually the model |
|----------|----------------------|-------------------|
| Which user's data to load | Session identity | Never |
| Whether a refund is allowed | Business rules | Never; it may draft the explanation |
| Which pipeline branch | Small classifier or rules | Only if categories are fuzzy and many |
| Which of 5 search queries to run | Sometimes fixed | Planning in open-ended research |
| How to phrase the answer | — | Yes |

Deterministic steps are cheaper, faster, testable with ordinary unit tests and don't drift when the model changes.

## Sync, async, queued or long-running

| Style | Use when | Design notes |
|-------|----------|--------------|
| Synchronous, streamed | Chat, answers under ~30 s | Timeouts, streaming, fallbacks |
| Async job + polling/webhook | Tasks of 30 s to a few minutes (report, bulk extraction) | Return a job id; store status |
| Queue + workers | Bulk or bursty offline work | Retries, dead-letter queue, idempotent workers |
| Durable long-running workflow | Agents running for minutes to hours, waiting on humans | Checkpoint state so a crash resumes, not restarts |

```python
@app.post("/reports")
async def create_report(req: ReportRequest):
    job_id = uuid4().hex
    await jobs.put(job_id, status="queued")
    await queue.enqueue("build_report", job_id=job_id, spec=req.model_dump())
    return {"job_id": job_id, "status_url": f"/reports/{job_id}"}
```

For long agent runs, a durable workflow engine (Temporal, Step Functions or similar) persists each step, so a worker
restart doesn't throw away twenty minutes of tool calls and tokens.

## Not everything needs an agent

A useful ladder, from simplest to most flexible:

1. Single call (with retrieval if needed).
2. Fixed chain: step A then B then C.
3. Router: a classifier picks one of several fixed chains.
4. Agent: the model chooses tools in a loop until done.

Move up only when the lower rung can't handle the task. Agents cost more (many calls), are slower, harder to evaluate,
and fail in more ways. Many "agent" products are really a router plus three fixed chains, which is a good thing.

## Clean component boundaries

Give each component a clear contract (input, output, errors) so it can be swapped, evaluated and scaled alone:

- Retrieval service: `search(query, filters) → [chunk]`, evaluated with hit rate.
- Generation: `answer(question, chunks) → {text, citations}`, evaluated with faithfulness.
- Tools: typed functions with their own tests and permission checks.

When quality drops, these boundaries let you tell whether retrieval or generation broke, and upgrade one without
redeploying everything.

## Try it

A product team wants "an AI agent" that takes an uploaded invoice, extracts fields, checks the vendor against an
approved list, and posts it to the accounting system. Propose an orchestration and say where, if anywhere, a model
makes decisions.

<details>
<summary>Reference</summary>

A fixed pipeline, run as an async job: (1) extract fields with a vision/LLM call into a strict schema; (2) validate
types, totals and dates in code; (3) look up the vendor in the approved list with a deterministic query (fuzzy match
in code if needed); (4) if all checks pass and the amount is under a threshold, post via the accounting API with an
idempotency key; otherwise queue for human review. The model only does extraction (and possibly a short explanation
for reviewers). No agent loop is needed because the steps are known in advance.
</details>

## Check yourself

1. Why prefer a deterministic step over a model decision when both would work?

<details>
<summary>Answer</summary>
It is cheaper, faster, predictable, unit-testable and unaffected by model updates or prompt injection.
</details>

2. When does a task need a durable workflow rather than an in-memory async job?

<details>
<summary>Answer</summary>
When it runs long (minutes to hours), involves many costly steps or waits on humans, so a crash or deploy would
otherwise lose progress; durable workflows checkpoint and resume.
</details>

3. What do clear component boundaries buy you when answer quality drops?

<details>
<summary>Answer</summary>
You can evaluate each component on its own metric to localise the fault (e.g. retrieval hit rate fell vs generation
faithfulness fell) and fix or replace that part alone.
</details>
