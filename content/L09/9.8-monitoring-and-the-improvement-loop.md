# Monitoring and the improvement loop

Launch day is when you start learning what your users actually ask. A well-designed AI system treats production as a
source of test cases: it records what happened, notices what went wrong, and turns those failures into evals that
protect the next release. This lesson is about designing that loop into the architecture from the start.

## Evals and feedback are part of the architecture

In a system design, monitoring is a component with inputs and outputs, not a footnote:

```
request → app → response
            │
            ├─► trace store (prompt, chunks, tool calls, versions, tokens, latency, cost)
            ├─► metrics (Prometheus / provider dashboards)
            ├─► online eval sampler (LLM judge on ~1-5% of traffic)
            └─► feedback events (thumbs, edits, escalations)
                     │
                     ▼
            review queue → labelled failures → offline eval set → CI gate
```

## What to watch

| Area | Signals |
|------|---------|
| Quality | Online judge scores, groundedness, abstention rate, thumbs-down rate |
| Latency | p50/p95 TTFT and total time, per stage |
| Cost | Tokens and spend per request, per feature, per tenant |
| Errors | Provider errors, timeouts, schema failures, guardrail blocks |
| Retrieval | Top score distribution, empty-result rate, which sources get cited |
| Tools / agents | Calls per request, failure rate, steps per task, loops hitting the cap |
| Providers | Error rate and latency per model, share served by fallback |

Watch distributions and trends, not just averages: a slowly rising abstention rate often means the index is going
stale.

## Explicit and implicit feedback

Explicit feedback (thumbs, star ratings, comments) is clear but rare: often only a few percent of users click anything,
and they skew toward angry. Implicit signals are plentiful but noisy:

- The user rephrases and asks again straight away.
- They copy the answer (probably good) or edit a draft heavily (probably not).
- They click "talk to a human" after the answer.
- They abandon the session mid-stream.

Log both, linked to the trace id, so any signal leads back to the exact prompt, chunks and model that produced it.

## Failures become test cases

The most valuable artifact a production system makes is its list of real failures. A simple routine:

1. Each week, pull thumbs-down traces, escalations and low judge scores.
2. Review and label them: what was wrong (retrieval miss, hallucination, refusal, tone).
3. Add representative cases, with the expected behaviour, to the offline eval set.
4. Fix, and confirm the fix in CI without regressing older cases.

## Version everything

A regression you can't attribute is a regression you can't fix. Stamp every trace with every version that influences
behaviour:

```python
trace.update(metadata={
    "app_version": GIT_SHA,
    "prompt_id": "support-answer", "prompt_version": 14,
    "model": resp.model,                  # the exact model the provider reports
    "retrieval_config": "hybrid-k40-rerank8-v3",
    "index_version": "2026-11-01",
    "route": route_name,
})
```

Then "quality dropped on Tuesday" becomes "quality dropped for traces with prompt version 14", which is a one-line
rollback.

## The loop

Deploy → observe → collect feedback → evaluate → improve → redeploy. The design question for each turn of the loop is
how fast it can run. A team that can go from a reported failure to a gated fix in a day will outpace a team with a
better first version but a monthly release cycle.

## Try it

Users of your document assistant say "it got worse last week". You have traces with version metadata, thumbs feedback
and weekly online judge scores. Describe how you investigate.

<details>
<summary>Reference</summary>

1. Plot judge scores, thumbs-down rate, abstention rate and retrieval top scores by day; find when the change began.
2. Group traces by version fields (prompt, model, retrieval config, index version, route) and compare metrics before
   and after; look for one that changed at that time, including a provider-side model update visible in the model
   field.
3. Read a sample of bad traces to classify the failure (e.g. retrieval misses after a re-index).
4. Roll back the responsible change if possible, add the failing cases to the eval set, fix, and gate the fix in CI.
</details>

## Check yourself

1. Why log the exact model string the provider returns, not just the model you requested?

<details>
<summary>Answer</summary>
Aliases can point to new snapshots and fallbacks can serve a different model; the returned identifier tells you what
actually produced the answer.
</details>

2. Give two implicit feedback signals and why they're useful.

<details>
<summary>Answer</summary>
Immediate rephrasing of the same question and escalation to a human after an answer. Both happen far more often than
explicit ratings and correlate with unhelpful answers, though each needs review because they are noisy.
</details>

3. What turns monitoring into improvement rather than just dashboards?

<details>
<summary>Answer</summary>
A routine that reviews failures, adds them to the offline eval set and gates future changes on them, so each failure
found in production prevents a repeat.
</details>
