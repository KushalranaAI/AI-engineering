# Caching

LLM calls are slow and billed per token, so caching looks like free money. It isn't free: a cache can serve a stale
answer, leak one user's data to another, or simply never hit. Design caching deliberately, decide what is safe to
reuse, and measure what it saves.

## Four kinds of cache

| Cache | Key | What it saves | Typical risk |
|-------|-----|---------------|--------------|
| Exact-response | Hash of (model, prompt, params) | The whole LLM call | Low hit rate on free-text input |
| Prompt / prefix | Identical leading tokens, handled by the provider | Prefill cost and TTFT for repeated prefixes | Almost none; you just need a stable prefix |
| Retrieval | Normalised query → chunk ids | Embedding + search + rerank | Stale after re-indexing |
| Semantic | Embedding of the query → nearest past query | The whole call for paraphrases | Wrong answer for a "similar" but different question |

**Prompt caching** deserves special mention because it is nearly risk-free. Providers can reuse computation for a
prompt prefix they have recently seen, typically charging much less for cached input tokens. You get it by putting
stable content (system prompt, tool definitions, long reference documents) first and variable content (the user's
question) last. Some providers do this automatically; others need you to mark the cache point.

```python
messages = [
    {"role": "system", "content": SYSTEM_PROMPT + TOOL_DOCS},  # stable → cacheable prefix
    {"role": "user", "content": f"Context:\n{chunks}\n\nQuestion: {q}"},  # varies → last
]
```

## What is safe to cache

Ask three questions for each cache:

1. **Is the answer the same for everyone?** If it depends on the user (their account, permissions, language), the key
   must include those, or you must not cache it.
2. **How long does it stay true?** Set a TTL from the data's change rate, and invalidate on events (a document edit
   should evict cached retrievals and answers built from it).
3. **What does a wrong hit cost?** A stale FAQ answer is mildly bad; a cached "your refund was approved" is a
   disaster.

```python
def cache_key(q: str, user) -> str:
    norm = " ".join(q.lower().split())
    return sha256(f"{MODEL}|{PROMPT_VERSION}|{INDEX_VERSION}|{user.tenant_id}|{user.locale}|{norm}")
```

Including the prompt and index versions means a release automatically stops serving old answers.

## Semantic caching

A semantic cache embeds the incoming query, finds the nearest stored query, and returns its answer if similarity is
above a threshold. It shines for repetitive public questions ("how do I reset my password", "password reset steps").
It is dangerous when small wording differences matter: "cancel my order" vs "cancel my subscription" may sit very
close in embedding space. Mitigations: a high threshold tuned on labelled pairs, scoping by intent or tenant, and only
caching answers to questions you've classified as generic.

## Freshness against speed and cost

| Content | Suggested policy (example) |
|---------|---------------------------|
| Public FAQ answers | Semantic cache, 24 h TTL, evict on article edit |
| Answers over private docs | Exact cache keyed by tenant + permissions, short TTL |
| Live data (orders, prices) | Don't cache the answer; maybe cache the tool result for seconds |
| System prompt prefix | Always use provider prompt caching |

## Measure the hit rate

Log every lookup as hit or miss and compute savings:

```
10,000 requests/day, cost per full call $0.004, cache lookup $0.0001
Hit rate 30% → saved 3,000 × $0.004 = $12.00, lookups cost 10,000 × $0.0001 = $1.00
Net saving $11/day and ~2 s faster on 30% of requests.
Hit rate 3%  → saved $1.20, lookups cost $1.00: barely worth the complexity.
```

Also sample cache hits for quality review: a cache with a high hit rate that serves wrong answers is worse than none.

## Try it

A bank's assistant answers questions about public product terms and about the user's own transactions. Design the
caching: which caches, keys, TTLs and what you never cache.

<details>
<summary>Reference</summary>

- Prompt caching for the system prompt and tool definitions on every request.
- Semantic cache for generic product-terms questions only (route by intent first), keyed with locale and
  product-terms index version, TTL a day, evicted when terms change; high threshold.
- Retrieval cache for product-terms queries, invalidated on re-index.
- Never cache answers about the user's transactions or anything from account tools across users; at most cache the
  tool response for that user for a few seconds within one conversation.
- Track hit rate, savings and a sampled quality check of hits.
</details>

## Check yourself

1. Why should the prompt version be part of an exact-response cache key?

<details>
<summary>Answer</summary>
So that changing the prompt automatically stops serving answers produced by the old prompt; otherwise a fix would be
invisible to users until entries expire.
</details>

2. What is the main risk of semantic caching?

<details>
<summary>Answer</summary>
Returning a cached answer for a question that is worded similarly but means something different, giving a confidently
wrong reply.
</details>

3. How do you get the benefit of provider prompt caching?

<details>
<summary>Answer</summary>
Keep the stable parts of the prompt identical and at the start (system prompt, tools, reference text) and put the
variable parts at the end, and mark cache breakpoints where the provider requires it.
</details>
