# Designing the knowledge layer

A model can only answer well with the right information in front of it. The knowledge layer is the part of your system
that decides where each fact lives and how it reaches the prompt. Get this wrong and no model upgrade will save you;
get it right and a mid-sized model often does the job.

## Where should each fact come from?

Sort every kind of knowledge your product needs into one of five homes.

| Home | Good for | Example |
|------|----------|---------|
| Model weights | Stable general knowledge, language, reasoning | Grammar, what a refund is, Python syntax |
| Prompt (always present) | Small, stable, always-relevant rules | Tone guide, output format, top-level policies |
| Retrieval index | Large or private collections, cited answers | Help-centre articles, contracts, code |
| Memory / external state | Facts about this user or conversation | "Prefers metric units", open ticket id |
| Live tools / APIs | Facts that change by the minute or need exact values | Order status, stock level, today's price |

A useful test: **how big is it, how often does it change, and does it need to be exact?** A 2-page policy that changes
quarterly belongs in the prompt. Ten thousand articles belong in an index. An account balance must come from a tool,
never from an index that was built last night.

## The context pipeline

Treat everything between the raw source and the model as one designed pipeline:

```
sources → ingest (extract, clean, chunk, embed, tag metadata)
        → retrieve (dense + keyword, filtered by permissions)
        → rerank (keep the best few)
        → assemble (order, dedupe, trim to budget, add citations ids)
        → generate
```

Each stage has its own knobs and its own failure mode, so in a design you should say what each stage does and how you
would measure it (for example, hit rate at k for retrieval, faithfulness for generation).

## Mixing retrieval methods

Start with one retriever and add others only for a measured gap:

- **Dense vectors** for paraphrased, natural-language questions.
- **Keyword (BM25)** for ids, product codes, names and exact phrases. Hybrid with rank fusion is a common default.
- **Graph** retrieval when questions are about relationships ("which suppliers share a parent company?") or need
  whole-corpus summaries.
- **Structured queries** (SQL) when the answer is an aggregate over rows. Don't embed a spreadsheet.

## Freshness, permissions and provenance

These are the parts interviewers probe, because they are where real systems break.

- **Freshness**: decide an update path per source (event-driven re-index on edit, or a scheduled sync) and an
  acceptable staleness ("help articles within 15 minutes").
- **Access control**: filter at retrieval time using permissions stored with each chunk. Never retrieve everything and
  ask the model to hide what the user can't see.
- **Provenance**: keep source id, version and URL with every chunk so answers can cite and you can debug.
- **Scale**: estimate chunks × dimensions × bytes to size the index, and plan re-embedding as a migration.

```python
results = index.search(
    query_vector=embed(question),
    top_k=40,
    filter={
        "tenant_id": user.tenant_id,
        "acl_groups": {"$in": user.groups},   # permission filter in the query
        "status": "published",
    },
)
```

## Retrieve per request, or keep it in context?

Long context windows tempt teams to paste everything in. It works for small, stable sets, and it can be cheap if
the provider caches a repeated prefix. It fails when the collection is large, changes often, or needs permission
filtering per user, and models are known to use information in the middle of very long prompts less reliably.
A practical rule: keep **rules and small reference material** pinned; **retrieve** everything else.

## Try it

You are designing an internal HR assistant. Sources: a 3-page code of conduct, 800 policy pages that differ by country,
each employee's leave balance, and a weekly-changing list of public holidays. Assign each to a home and name the
access-control rule.

<details>
<summary>Reference</summary>

- Code of conduct: pinned in the system prompt (small, stable, always relevant; prefix caching makes it cheap).
- Country policies: retrieval index with metadata `country`, `effective_date`; filter by the employee's country.
- Leave balance: live tool call to the HR system with the caller's identity; never indexed.
- Holidays: a tool or a small structured table queried by country and date; indexing it risks stale answers.
- Access control: filter retrieval by country and role, and have the leave tool accept only the authenticated
  user's id, not an id from the model's arguments.
</details>

## Check yourself

1. Why is "retrieve everything, then tell the model not to reveal restricted documents" a bad design?

<details>
<summary>Answer</summary>
The restricted text is already in the prompt, so a prompt injection, a model slip or a log can leak it. Permission
checks must happen in code before content reaches the model.
</details>

2. When should a fact come from a tool rather than a retrieval index?

<details>
<summary>Answer</summary>
When it changes faster than the index refreshes, or must be exact and current (balances, order status, prices). Tools
query the system of record at request time.
</details>

3. Give one reason to add keyword search to a dense retriever.

<details>
<summary>Answer</summary>
Dense embeddings are weak at exact tokens such as product codes, ticket ids, names and rare jargon. BM25 matches these
exactly, and fusing the two lists usually improves recall on such queries.
</details>
