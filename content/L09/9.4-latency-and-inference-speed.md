# Latency and inference speed

"It's slow" is not a diagnosis. An AI request is a chain of steps, and each step is slow for a different reason with a
different fix. Before you buy a bigger GPU or switch providers, find out where the time actually goes.

## Build a latency budget

Break one request into its parts and time each from your traces:

| Stage | Typical range (example) | Driven by |
|-------|------------------------|-----------|
| Network + auth + gateway | 20-100 ms | Region, TLS, proxies |
| Embedding the query | 20-80 ms | Embedding API round trip |
| Vector + keyword search | 10-100 ms | Index size, filters |
| Reranking | 50-300 ms | Number of candidates, model size |
| Time to first token (TTFT) | 0.3-2 s | Prompt length, model size, provider load |
| Generation | output tokens ÷ tokens/s | Output length, model speed |
| Tool calls | 0.1 s to many seconds | The external system |

Generation time is mostly arithmetic:

```
500 output tokens at 50 tokens/s  = 10 s
500 output tokens at 150 tokens/s = 3.3 s
150 output tokens at 50 tokens/s  = 3 s     ← asking for a shorter answer beats a faster model here
```

Output length is often the single biggest lever. Ask for concise answers, set `max_tokens`, and avoid making the
model restate the question.

## Streaming

Streaming does not make the request finish sooner, but users judge speed by when something appears. With streaming
the perceived wait is TTFT, not total time. Stream whenever a human is reading; don't bother for machine-to-machine
calls where the caller needs the whole JSON anyway.

## Parallel instead of sequential

Many pipelines chain calls that don't depend on each other.

```python
import asyncio

async def handle(question: str):
    # independent: run together
    chunks, profile, intent = await asyncio.gather(
        retrieve(question),
        fetch_user_profile(),
        classify_intent(question),     # small model
    )
    return await generate(question, chunks, profile, intent)
```

Three 300 ms steps go from 900 ms to about 300 ms. Also question every LLM call in a chain: is a "rewrite the query"
step worth its 600 ms on every request, or only on follow-up questions?

## Smaller models where they suffice

Intent detection, extraction, routing and short summaries rarely need the largest model. A smaller model is usually
faster on both TTFT and tokens per second, and cheaper. Prove it with your eval set step by step, not system-wide.

## Shorter prompts and batching

- **Trim context**: fewer, better chunks (reranking helps) cut TTFT, since the model must process every input token.
- **Prefix caching**: keep the stable part of the prompt (system prompt, tool definitions) first and identical across
  requests so providers that cache prefixes can skip recomputing it.
- **Batch offline work**: nightly summaries or bulk classification can go through batch APIs, which trade hours of
  latency for lower prices.
- **Serving-side**: if you host models, engines like vLLM use continuous batching and paged KV caches to serve many
  requests at once; quantisation and speculative decoding can raise tokens per second.

## Throughput at scale

Latency is one request; throughput is how many per second the system sustains. On self-hosted GPUs, larger batches
raise throughput and utilisation but raise each request's latency. On APIs, your ceiling is usually the provider's
rate limit in tokens per minute:

```
Limit: 2M tokens/min.  Each request: 4,000 tokens in + 500 out = 4,500
Max sustained ≈ 2,000,000 / 4,500 ≈ 444 requests/min ≈ 7.4 req/s
```

If peak traffic is 20 req/s, no amount of autoscaling your own servers helps: you need a higher quota, a second
provider, shorter prompts or caching.

## Try it

Your RAG endpoint takes 9 s at p50. Traces show: query rewrite 0.8 s, embed 0.05 s, search 0.08 s, rerank 0.4 s, TTFT
1.2 s, generation of 400 tokens at 60 tokens/s. List three changes in order of expected impact.

<details>
<summary>Reference</summary>

Generation is about 6.7 s of the 9 s.
1. Shorten answers (target ~150 tokens, set `max_tokens`) or use a faster model for the final step: saves around 4 s.
2. Stream the response so the perceived wait drops to roughly rewrite + retrieval + TTFT (~2.5 s).
3. Make the query rewrite conditional (only for follow-up questions) or run it on a small model: saves up to 0.8 s.
Rerank (0.4 s) is worth checking last: reduce candidates if evals allow.
</details>

## Check yourself

1. Why does streaming improve user experience without reducing total latency?

<details>
<summary>Answer</summary>
Users perceive the wait as the time until something appears. Streaming makes that time-to-first-token, and the
reading happens while the rest generates.
</details>

2. Why does trimming retrieved context reduce time to first token?

<details>
<summary>Answer</summary>
The model must process every input token (the prefill) before producing the first output token. Fewer input tokens
mean a shorter prefill.
</details>

3. Your app hits a wall at 7 requests per second although your servers are idle. What is the likely cause?

<details>
<summary>Answer</summary>
The provider's rate limit (tokens or requests per minute). Fixes are quota increases, more providers, shorter prompts
or caching, not more servers.
</details>
