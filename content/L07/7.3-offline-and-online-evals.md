# Offline and online evals

Evals run in two places. **Offline** evals run a fixed test set against a candidate version before it ships. **Online** evals score real traffic after it ships. You need both: offline catches regressions you can anticipate, online catches the ones you can't.

## Offline suites

An offline suite is a versioned dataset plus checks, run on demand or in CI. Use it to:

- compare two prompts, models or retrieval settings on identical inputs;
- run experiments ("does reranking help?") with a number to show for it;
- stop regressions: a new version must not score below the current one.

Because the dataset is fixed, results are comparable over time. Its weakness is that it only contains what you thought to include.

## What breaks after launch

Real users do things your test set did not foresee:

| Risk | Example |
|---|---|
| Unexpected inputs | Pasted spreadsheets, other languages, a question about a product launched last week |
| Failures that only show at scale | 2% of answers about one product line cite a retired policy |
| Changing behaviour | Users learn the bot handles returns and start asking about warranty claims |
| Data drift | The knowledge base is updated; old chunks linger; upstream API changes field names |
| Model changes | A provider updates the model behind an alias |

None of these show up in an offline suite until you add them.

## System metrics vs quality metrics

Split what you watch in production into two kinds:

- **System metrics** come straight from logs with no judgement: latency (p50/p95), tokens in and out, cost, error and timeout rates, tool-call counts, retrieval hit counts.
- **Quality metrics** need a scorer: faithfulness, answer relevance, policy compliance, toxicity. Usually computed by an LLM judge or classifier on a **sample** of traffic.

System metrics are cheap and complete; quality metrics are costly, so you score a sample, typically a few percent of traffic plus anything flagged (thumbs down, escalations, long conversations).

## Online evaluation

The online pipeline looks like this:

```
requests ──► app ──► trace log (input, context, output, latency, tokens)
                         │
                         ├─► dashboards for system metrics (all traffic)
                         └─► sampler ──► judges ──► quality scores ──► dashboards + alerts
```

A sampling-and-scoring job can be small:

```python
import random

def score_sample(traces, judges, rate=0.05):
    flagged = [t for t in traces if t.get("user_feedback") == "down"]
    sampled = [t for t in traces if random.random() < rate]
    for t in {t["id"]: t for t in flagged + sampled}.values():
        t["scores"] = {name: fn(t) for name, fn in judges.items()}
        if t["scores"]["faithful"] is False:
            send_to_review_queue(t)
    return traces
```

Alert on changes, not single cases: "faithfulness on sampled answers dropped from 94% to 86% over 24 hours" is actionable; one bad answer is noise.

Watch privacy: production traces contain user data, so redact before storing and before sending to a judge provider.

## Closing the loop

The most valuable thing online evals produce is new offline test cases. The loop:

1. A production failure is found (alert, user report, review queue).
2. Someone confirms it and writes the expected behaviour.
3. The input (anonymised) is added to the offline dataset with that expectation.
4. The fix is developed against the suite, which now includes the case.
5. The case stays forever, so the bug cannot quietly return.

Over months this turns a generic starter dataset into one that reflects your real users.

## Try it

Your RAG assistant has an offline suite of 150 questions scoring 92% correct. After launch you notice more escalations to human agents. List two system metrics and one quality metric you would check first, and what you would do with what you find.

<details>
<summary>Reference</summary>

System metrics: retrieval empty-result rate (are many questions finding nothing?) and the distribution of topics or query lengths compared to the offline set. Also latency and error rates, in case timeouts cause fallbacks.

Quality metric: judge-scored answer relevance or faithfulness on a sample of escalated conversations versus non-escalated ones.

Then read 20-30 escalated conversations, cluster them (likely a new topic, a stale document, or a language the corpus doesn't cover), fix the cause, and add representative cases from each cluster to the offline suite so it reflects real traffic.
</details>

## Check yourself

1. Why can't an offline suite alone protect a production LLM app?

<details>
<summary>Answer</summary>

It only contains inputs someone anticipated. Real traffic brings new topics, phrasings, data changes and provider-side model updates that the fixed set never covers, so failures can grow unnoticed.
</details>

2. Why do teams usually score only a sample of production traffic for quality?

<details>
<summary>Answer</summary>

Quality metrics need a judge model or human, which costs money and time per request. Scoring a random sample plus flagged traces gives a reliable trend at a fraction of the cost, while cheap system metrics are logged for all traffic.
</details>

3. What turns a production failure into lasting protection?

<details>
<summary>Answer</summary>

Adding it, with the correct expected behaviour, to the offline dataset so every future version is tested against it and the regression can't silently return.
</details>
