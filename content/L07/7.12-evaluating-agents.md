# Evaluating agents

An agent can reach the right answer by a terrible route: twelve redundant searches, a delete it shouldn't have attempted, a lucky guess after a failed tool call. If you only grade the final answer, all of that passes. Agent evals look at **what the agent did**, not only what it said at the end.

## What to evaluate

| Dimension | Question |
|---|---|
| Tool choice | Did it pick the right tool at each step? |
| Arguments | Were the arguments correct and well-formed? |
| Trajectory | Was the sequence of actions sensible: no loops, no waste, right order? |
| Task success | Did it actually complete the user's goal? |
| Recovery | When something broke, did it notice and respond sensibly? |
| Safety | Did it stay within permissions and resist manipulation? |
| Efficiency | How many steps, tool calls, tokens, seconds and dollars did it take? |

All of this needs **traces**: a log of every model call, tool call, argument and result for each run. Most agent frameworks emit them; if yours doesn't, record them yourself before writing any evals.

## Tool choice and arguments

For single-step decisions, build cases like unit tests: given this state, the expected tool and key arguments.

```python
cases = [
    {"input": "What's the status of order ORD-123456?",
     "expected_tool": "get_order", "expected_args": {"order_id": "ORD-123456"}},
    {"input": "Refund my last order",
     "expected_tool": "lookup_recent_orders", "expected_args": {}},  # must look up before refunding
]

def score_first_step(agent, case):
    call = agent.first_tool_call(case["input"])   # run until first tool call, don't execute
    right_tool = call.name == case["expected_tool"]
    right_args = all(call.args.get(k) == v for k, v in case["expected_args"].items())
    return {"tool": right_tool, "args": right_args}
```

Check arguments by meaning, not exact strings, where formatting may vary (dates, casing). Validate them against the tool's schema too: malformed arguments are a common, easily measured failure.

## Trajectories

For multi-step tasks, compare the action sequence with what a sensible agent would do. Three approaches, in rising flexibility:

1. **Exact match** to a reference trajectory. Strict; fine for tightly scripted flows.
2. **Constraint checks** on the trace: required tools were called, forbidden tools were not, A happened before B, no tool called more than N times with identical arguments.
3. **LLM judge** reading the trace with a rubric: "Was each step justified by the previous result? Were any steps redundant?"

```python
def trajectory_checks(trace):
    calls = [(s.tool, tuple(sorted(s.args.items()))) for s in trace.tool_steps]
    names = [c[0] for c in calls]
    return {
        "looked_up_before_refund": "refund" not in names
            or names.index("lookup_recent_orders") < names.index("refund"),
        "no_repeat_calls": len(calls) == len(set(calls)),
        "within_step_budget": len(calls) <= 8,
        "finished": trace.final_answer is not None,
    }
```

Constraint checks are usually the best value: cheap, deterministic and tolerant of the many valid orders an agent might take.

## Task success

Define success by the **end state**, not the transcript. For an agent that books meetings, check the calendar; for a coding agent, run the tests; for a data agent, compare the produced table. Report success rate over realistic multi-step tasks, and run each several times, since agents are especially variable. Benchmarks such as tau-bench report pass^k (succeeding on all k tries) precisely because consistency matters for real users.

## Recovery under failure

Agents tested only on a happy path look much better than they are. Inject faults with stub tools:

| Fault | Good response |
|---|---|
| Tool times out | Retry with backoff, then try an alternative or report |
| Malformed result | Notice, don't build on it, re-query or flag |
| Service unavailable | Use fallback tool or explain clearly to the user |
| Missing information | Ask the user rather than inventing |
| Unexpected state (order already refunded) | Stop and report, don't repeat the action |

Score both whether the agent **noticed** the failure and whether its **response** was appropriate. Report success under faults separately from success in ideal conditions.

## Safety

Agents act, so safety evals test actions, using sandboxed tools and fake data:

- **Unauthorised or destructive actions**: asks that should be refused or require approval ("delete all inactive users").
- **Approval gates**: does every consequential action actually go through the human-approval step, or can phrasing skip it?
- **Prompt injection via tools**: a web page or email the agent reads contains instructions to call a different tool or send data somewhere; check that tool usage is unchanged.
- **Secret extraction and scope escape**: attempts to make the agent reveal credentials or system instructions, or use tools outside its task.
- For agents with code execution or computer use, specialised cybersecurity capability benchmarks help judge whether the agent could do dangerous things if misused.

Measure **unsafe-action rate** and **attack success rate**, and gate releases on them.

## Efficiency

Track steps, tool calls, latency, tokens and cost per task next to success. Two agents with equal success rates are not equal if one needs three times the steps. Efficiency regressions often show up first in long-tail tasks, so look at p95, not just averages.

## Try it

You have a travel agent with tools `search_flights`, `hold_booking`, `pay` (requires approval) and `email_user`. Write four trace-level checks you would run on every eval task.

<details>
<summary>Reference</summary>

1. `pay` is never called without a preceding approval event in the trace.
2. `hold_booking` is called only with a flight id returned by an earlier `search_flights` result (no invented ids).
3. No identical tool call repeats more than twice (loop detection), and total tool calls stay within budget (say 10).
4. If any tool returned an error, the next step is a retry, alternative or user message, not a call that depends on the failed result.

A good fifth: `email_user` is called at most once per task, and only after the final booking state is known.
</details>

## Check yourself

1. Why isn't grading the final answer enough for an agent?

<details>
<summary>Answer</summary>

The agent chooses its own path. A correct final answer can hide wasted steps, loops, unsafe or unauthorised actions, and lucky recoveries, all of which matter for cost, reliability and safety.
</details>

2. Why are constraint checks often better than exact trajectory matching?

<details>
<summary>Answer</summary>

Many orders of actions are valid. Exact matching fails good runs that take a different but reasonable path, while constraints (required tools, forbidden tools, ordering rules, repeat limits) check what actually matters and stay deterministic and cheap.
</details>

3. How do you test whether an agent recovers from failures?

<details>
<summary>Answer</summary>

Replace tools with stubs that time out, return malformed data, become unavailable or report unexpected state, then score whether the agent noticed and chose an appropriate response (retry, alternative, replan, ask, escalate), reporting success under faults separately.
</details>
