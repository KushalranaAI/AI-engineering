# Benchmarks and model evals

Every model launch arrives with a table of benchmark scores. Those numbers are useful for shortlisting, and easy to misread. This lesson is about what a benchmark actually measures and how to read the claims critically.

## What gets measured

Public benchmarks try to cover separate capabilities. Typical families:

| Capability | What the test looks like | Example benchmarks |
|---|---|---|
| Knowledge | Multiple-choice questions across subjects | MMLU, MMLU-Pro, GPQA |
| Reasoning and maths | Word problems, competition maths | GSM8K, MATH, AIME problem sets |
| Code | Write a function or fix a real repo issue, checked by tests | HumanEval, SWE-bench |
| Instruction following | Verifiable constraints ("answer in 3 bullets, no commas") | IFEval |
| Long context | Find or combine facts spread across very long inputs | Needle-in-a-haystack variants, RULER |
| Multimodal | Questions about images, charts, documents | MMMU |
| Tool use / agents | Multi-step tasks using APIs or a browser | tau-bench, BFCL, WebArena |
| Safety | Refusal of harmful requests, over-refusal of benign ones | Various red-team suites |

No single number captures a model. A model can lead on maths and trail on instruction following.

## How a benchmark is built

Every benchmark has five parts, and each one can change the score:

1. **Dataset** - the questions or tasks, and their answers or tests.
2. **Prompt format** - zero-shot or few-shot, chain-of-thought allowed or not, system prompt, answer template.
3. **Run configuration** - temperature, max tokens, number of attempts, whether tools or a "thinking" budget are allowed.
4. **Scoring** - exact match, regex extraction, unit tests passing, or an LLM judge.
5. **Aggregation** - mean accuracy, pass@1 vs pass@k, macro vs micro averages across subjects.

Worked example: the same model on the same coding set might report 72% "pass@1" with one attempt and 88% "pass@10" if any of ten samples passing counts. Both numbers are honest; they answer different questions. Always check which one you are reading.

```python
from math import comb

def pass_at_k(n: int, c: int, k: int) -> float:
    """Unbiased pass@k from n samples with c correct (Chen et al., 2021)."""
    if n - c < k:
        return 1.0
    return 1.0 - comb(n - c, k) / comb(n, k)

print(pass_at_k(n=20, c=8, k=1))   # 0.40
print(pass_at_k(n=20, c=8, k=10))  # ~0.9996
```

## Leaderboards

Leaderboards collect scores across models so you can compare them. They come in two broad styles:

- **Static benchmark aggregators** run (or collect) scores on fixed datasets, often with independent re-runs and price and speed data alongside.
- **Preference arenas** show anonymous pairs of answers to real users who vote for the better one; votes become an Elo-style rating. These reflect what people prefer in open-ended chat, which rewards style and length as well as correctness.

Use leaderboards to build a shortlist of three to five models, never to make the final pick. The final pick comes from testing on your task (lesson 7.6 covers how).

## Benchmark traps

| Trap | What happens | How to spot it |
|---|---|---|
| **Contamination** | Test questions leaked into training data, so the model has memorised answers | Big gap between a public set and a freshly written, similar set |
| **Saturation** | Top models all score 90%+, so differences are noise | Scores clustered at the ceiling; small deltas reported as wins |
| **Benchmark overfitting** | Training targets the benchmark's style rather than the skill | Strong benchmark scores, weak real-world reports |
| **Configuration gaming** | Favourable prompts, many attempts, or custom scaffolds for one's own model only | Footnotes reveal different settings per model |
| **Judge bias** | Scores depend on an LLM judge that prefers some styles | Check whether the scorer is a model and which one |

Benchmark designers respond with private held-out sets, regularly refreshed questions, and harder datasets. That arms race is the story of lesson 7.5.

## Try it

A vendor claims their new model "beats the competition on coding: 91% vs 84%". Write four questions you would ask before believing it matters for you.

<details>
<summary>Reference</summary>

1. Which benchmark, and is it saturated or known to be contaminated (for example, an older function-level set vs a recent repo-level one)?
2. Were both models run with the same prompt, attempts (pass@1 vs pass@k), temperature, tool access and reasoning budget?
3. Who ran it - the vendor or an independent party - and can it be reproduced?
4. Does the benchmark resemble my task (my language, framework, codebase size), and what are the latency and cost per task at that score?
</details>

## Check yourself

1. Name the five parts of a benchmark that can each change its reported score.

<details>
<summary>Answer</summary>

The dataset, the prompt format, the run configuration (temperature, attempts, tools, token budget), the scoring method, and how results are aggregated.
</details>

2. What is data contamination and why does it inflate scores?

<details>
<summary>Answer</summary>

Test items (or close copies) appear in the model's training data, so it can recall answers instead of solving them. The score then measures memory of the test, not the underlying skill.
</details>

3. Why is a preference arena rating not a direct measure of correctness?

<details>
<summary>Answer</summary>

Users vote on which answer they like better, and preference is influenced by length, formatting, tone and confidence, not only accuracy. A ranking there reflects perceived chat quality across many prompts.
</details>
