# Evaluation methods

Once you know what "good" means for your system, you need a way to score each output. There are only three scorers available: **code**, **people**, and **another model**. Picking the right one for each criterion is most of the design work.

## Code, humans and LLM judges

| Method | Good at | Weak at | Cost per case |
|---|---|---|---|
| **Programmatic** (code) | Format, exact values, JSON validity, length, latency, whether a tool was called | Meaning, tone, paraphrase | Near zero |
| **Human review** | Nuance, domain correctness, subjective quality, setting the standard | Speed, consistency between reviewers, scale | High |
| **LLM-as-a-judge** | Semantic checks at scale: faithfulness, relevance, rubric scoring | Bias (position, length, own style), subtle domain errors | Low to moderate |

Rule of thumb: use code wherever a check can be written as code. It is free, fast and never drifts. Reach for a judge only where meaning is involved, and use humans to calibrate both.

```python
import json, re

def valid_json(output: str) -> bool:
    try:
        json.loads(output)
        return True
    except json.JSONDecodeError:
        return False

def has_order_id(output: str) -> bool:
    return re.search(r"\bORD-\d{6}\b", output) is not None
```

An LLM judge is just a model call with a tight rubric and a structured verdict:

```python
JUDGE_PROMPT = """You are grading a support answer.
Question: {question}
Reference facts: {facts}
Answer: {answer}

Is every claim in the answer supported by the reference facts?
Reply with JSON: {{"supported": true|false, "reason": "<one sentence>"}}"""

def judge(client, question, facts, answer):
    resp = client.chat.completions.create(
        model="gpt-4.1-mini",  # example; use a capable model you have tested as a judge
        messages=[{"role": "user", "content": JUDGE_PROMPT.format(
            question=question, facts=facts, answer=answer)}],
        response_format={"type": "json_object"},
        temperature=0,
    )
    return json.loads(resp.choices[0].message.content)
```

Make judges reliable by asking one narrow question per call, requiring a binary or small-scale verdict with a reason, and checking agreement against 30-50 human-labelled cases before trusting the numbers. Known biases include favouring the first answer in a pair, favouring longer answers, and favouring outputs from the same model family; swap positions and control length when comparing two outputs.

## With or without a reference

- **Reference-based** scoring compares output to a known good answer: exact match for a SQL result, a list of facts that must appear, a reference summary for a judge to compare against.
- **Reference-free** scoring checks properties of the output alone, or against the input: is it valid JSON, is it polite, is every claim supported by the retrieved context, does it answer the question asked.

Reference-free checks are cheaper to set up because you don't need answer keys, so they also work on live traffic. Reference-based checks catch a failure reference-free checks miss: an answer that is fluent, grounded in the wrong document, and wrong.

## When you need a golden set

A **golden dataset** is a set of inputs with expected outputs, agreed by people who know the domain. You need one when:

- correctness depends on facts the judge can't verify on its own (your policies, your database);
- there is a single right answer (classification label, extracted field, SQL result);
- you need a stable, comparable number across releases.

You can rely on judgement alone when the criterion is about the relationship between input and output (did it follow the format, is the answer supported by the given context, is the tone appropriate) and no hidden ground truth is involved.

## Method by behaviour

Classify each criterion by the kind of behaviour, then pick the method:

| Behaviour type | Example | Method |
|---|---|---|
| Deterministic | Output parses as the schema; correct category label | Code, reference-based |
| Semantic | Answer states the right refund window in any wording | LLM judge with reference facts, or code for key values |
| Subjective | Tone fits a premium brand | LLM judge with rubric, calibrated by humans |
| Operational | p95 latency under 3 s; cost per request | Code, from logs |

Most real systems need a mix, and one test case can carry several checks.

## Try it

For a text-to-SQL assistant, list three criteria and assign each a method and say whether it needs a reference.

<details>
<summary>Reference</summary>

1. **Query runs without error** - programmatic, reference-free (execute against a test database).
2. **Result matches the expected rows** - programmatic, reference-based (compare the result set of the generated query with that of a hand-written gold query; comparing SQL text is too strict because many queries are equivalent).
3. **Explanation to the user is accurate and plain** - LLM judge with a short rubric, reference-free, spot-checked by a person.

A good extra: **query is read-only** (no `UPDATE`/`DELETE`) - programmatic, reference-free.
</details>

## Check yourself

1. Why should you prefer a code check over an LLM judge when both are possible?

<details>
<summary>Answer</summary>

Code checks are free, instant, deterministic and don't have biases or drift when the judge model changes. A judge adds cost, latency and its own error rate, so use it only where meaning has to be assessed.
</details>

2. Give one failure a reference-free faithfulness check can miss but a reference-based check would catch.

<details>
<summary>Answer</summary>

The retriever fetched the wrong (but plausible) document, and the model faithfully summarised it. The answer is fully supported by its context, so faithfulness passes, but it disagrees with the reference answer, so a reference-based correctness check fails.
</details>

3. How do you know whether your LLM judge can be trusted?

<details>
<summary>Answer</summary>

Have humans label a sample of cases, run the judge on the same cases, and measure agreement. Adjust the rubric until agreement is high, and re-check when you change the judge model or prompt.
</details>
