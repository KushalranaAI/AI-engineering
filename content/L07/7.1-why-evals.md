# Why evals

You change one line in a prompt, try three questions in a playground, the answers look fine, and you ship. A week later support tickets show the bot now invents refund rules for a whole category of orders. Nothing crashed, no test failed, because there were no tests. **Evals** are how you replace "looks fine to me" with numbers you can compare across versions.

## The trouble with vibe checks

Eyeballing a handful of outputs fails in predictable ways:

- **Tiny sample.** Five hand-picked questions say nothing about the long tail where real users live.
- **You pick easy cases.** You test what you had in mind while building, not what customers type.
- **No baseline.** Without the same questions scored on the old version, you can't tell whether a change helped or hurt.
- **Memory is unreliable.** "It seemed better yesterday" is not a measurement.

The public cost of skipping this is real. In *Moffatt v. Air Canada* (British Columbia Civil Resolution Tribunal, 2024), the airline's website chatbot told a customer he could claim a bereavement fare discount after travelling. The airline's actual policy said otherwise. The tribunal held the airline responsible for what its chatbot said and ordered it to pay the difference. The chatbot was not "broken" in any way a unit test would catch; it simply gave a confident, wrong answer about policy. That is exactly the kind of failure an eval set of policy questions with known correct answers is built to catch.

## Tests for probabilistic systems

Ordinary software tests assume the same input gives the same output, so you assert equality. LLM systems break that assumption:

| Traditional tests | LLM evals |
|---|---|
| Deterministic output | Output varies with sampling, model version, context |
| Pass/fail per case | Scores and pass rates over a dataset |
| `assert result == expected` | "Does this answer contain the right fact and no false ones?" |
| A failure is a bug | A few failures may be acceptable; the rate matters |
| Run once | Often run several times per case to measure variance |

You still write normal unit tests for the deterministic code around the model (parsers, retrievers, tool functions). Evals sit on top, measuring behaviour statistically.

## Model evals vs application evals

Two different questions get called "evals":

- **Model evals** ask how capable a base model is in general: maths, coding, knowledge. Labs and benchmark sites run these. They help you shortlist models.
- **Application evals** ask whether *your* system, with your prompts, retrieval, tools and data, does *your* job. This is where nearly all of your effort goes.

A model that tops a coding leaderboard can still do badly at extracting fields from your invoices. Only an application eval tells you.

## The eval workflow

Every useful eval effort follows the same loop:

1. **Define the task.** What should the system do, for whom, and what is out of scope?
2. **Set criteria.** Turn "good" into checkable properties: correct, grounded in sources, right format, polite, under 2 seconds.
3. **Build a dataset.** Realistic inputs, with expected outputs or reference facts where you can provide them. Start with 30-100 cases.
4. **Run.** Execute the system on every case and record outputs, latency and tokens.
5. **Score and analyse.** Apply checks, read the failures, group them into categories.
6. **Iterate.** Fix the biggest failure category, re-run, compare with the previous score.

A minimal harness is short:

```python
import json

def run_eval(system, cases, checks):
    results = []
    for case in cases:
        output = system(case["input"])
        scores = {name: fn(case, output) for name, fn in checks.items()}
        results.append({"id": case["id"], "output": output, **scores})
    for name in checks:
        rate = sum(r[name] for r in results) / len(results)
        print(f"{name}: {rate:.0%}")
    return results

checks = {
    "mentions_policy_id": lambda c, o: c["policy_id"] in o,
    "no_promise_of_refund": lambda c, o: "guaranteed refund" not in o.lower(),
}
cases = [json.loads(line) for line in open("policy_questions.jsonl")]
```

Reading failures by hand (step 5) is the part people skip and the part that teaches the most. Scores tell you *that* something is wrong; reading outputs tells you *what*.

## Check yourself

1. Why is "I tried ten prompts and they looked good" not enough evidence to ship a prompt change?

<details>
<summary>Answer</summary>

The sample is small and biased toward cases the developer thought of, there is no baseline score for the previous version to compare against, and output varies between runs. A change can fix those ten while breaking a category nobody tried.
</details>

2. What is the difference between a model eval and an application eval?

<details>
<summary>Answer</summary>

A model eval measures a base model's general capability on a standard task set. An application eval measures your whole system (prompts, retrieval, tools, data) on your own task. The first helps shortlist models; the second decides whether your product works.
</details>

3. Why do LLM evals usually report rates rather than pass/fail?

<details>
<summary>Answer</summary>

Outputs are probabilistic and some failure is expected, so a single case passing or failing says little. The meaningful signal is the pass rate across a dataset, compared between versions, often across repeated runs to account for variance.
</details>
