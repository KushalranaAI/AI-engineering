# Reviewing eval results and dashboards

You have a golden set, metrics and a judge. Running them produces numbers, and numbers are easy to misread. Reviewing
results well is a skill: it separates teams that ship improvements from teams that ship noise. This lesson covers how
to read a run, decide whether a change is real, find the cause of failures, and present results so a decision follows.

## Reading a run

Start with the aggregate, then immediately look past it.

- **Per-slice scores.** An overall 0.84 can hide 0.95 on common questions and 0.40 on refunds over ₹10,000. Slice by topic,
  difficulty, language, and answerable versus unanswerable.
- **The worst cases.** Sort rows by score and read the bottom 20. Patterns appear within minutes.
- **Distributions.** Two runs with the same mean can differ: one with uniformly decent answers and one with many perfect
  answers and a few disastrous ones. Look at histograms, not only averages.
- **Flipped cases.** Compare against the baseline row by row. Which cases went from pass to fail (regressions) and which
  from fail to pass (gains)? Net change hides churn: +10 fixed and −9 broken looks like a tiny win but is a risky change.

## Is the change real?

Eval sets are small samples, and judge scores are noisy, so differences need a sanity check.

- **Paired comparison.** Since both versions answer the same questions, compare per-question differences instead of two
  separate averages. This removes question difficulty from the noise.
- **Confidence interval.** For a pass rate p on n cases, the 95% margin is about 1.96 × √(p(1−p)/n). At p = 0.8, n = 100
  that is ±8 points; at n = 400, ±4. A 3-point gain on 100 cases is within noise.
- **Run-to-run variance.** Run the same version twice (or three times if sampling temperature is above zero). If two identical
  runs differ by 2 points, a 2-point difference between versions means nothing.
- **A sign test on flips.** If 12 cases flipped to pass and 4 to fail, that 12 to 4 split is more convincing than the
  net +8 suggests; if it is 9 to 7, it is a coin toss.

```python
from math import sqrt
def margin(p, n): return 1.96 * sqrt(p * (1 - p) / n)
def summarize(base, new):                         # lists of 0/1 per question
    gains = sum(1 for b, n in zip(base, new) if not b and n)
    losses = sum(1 for b, n in zip(base, new) if b and not n)
    return {"base": sum(base)/len(base), "new": sum(new)/len(new), "gains": gains, "losses": losses}
```

## Error analysis

Numbers tell you *that* something failed; reading tells you *why*. Take the failing cases, tag each with a cause, and count:

| Cause tag | Count |
|-----------|-------|
| retrieval missed the policy | 14 |
| answer ignored context | 6 |
| ambiguous question, should have asked | 5 |
| reference answer is wrong | 3 |
| tool timeout | 2 |

Fix the biggest group first. Note the "reference is wrong" row: sometimes the dataset is the bug. Correct it and log the
change in the dataset version.

## Dashboards that get used

A good eval dashboard answers "can we ship?" at a glance:

1. **Trend lines** per metric over time (and per version), so a slow decline is visible.
2. **A regression table** against the baseline: metric, baseline, current, change, and a pass/fail against the agreed
   threshold.
3. **Slices** for the topics or segments you care most about.
4. **Cost and latency next to quality.** A +2 point gain that doubles cost is a decision, not an automatic win.
5. **Links to the failing rows**, so anyone can click from a red number to the actual cases.

Tools: Langfuse, LangSmith and similar platforms give you experiment views; a Streamlit page, a notebook or a static
HTML report from a script is plenty for a first version (the capstone builds one).

## Deciding to ship

Agree on rules before seeing results, or the data will be bent to the wish. For example: *ship if faithfulness does not
drop by more than 2 points, no slice drops by more than 5, no new critical failures appear, and p95 latency stays under 4
seconds; hold if any critical safety case fails.* Record the decision and the evidence in the change description. When the
numbers are ambiguous, run more cases or a canary on a small share of traffic (10.13) instead of arguing.

## Check yourself

1. Why compare two versions question by question instead of comparing two averages?

<details>
<summary>Answer</summary>

Both versions answer the same questions, so a paired comparison cancels question difficulty and shows exactly which cases
improved or regressed, giving a less noisy and more informative result.
</details>

2. What is wrong with deciding the ship threshold after seeing the results?

<details>
<summary>Answer</summary>

It invites bending the criteria to justify the result you wanted. Agree on thresholds in advance so the data decides.
</details>

3. What should sit beside quality metrics on a dashboard?

<details>
<summary>Answer</summary>

Cost and latency, because a quality gain that costs far more or runs much slower may not be worth shipping.
</details>
