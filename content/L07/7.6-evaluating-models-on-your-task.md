# Evaluating models on your task

Leaderboards tell you which models are strong in general. They don't tell you which one is best at turning your users' questions into SQL against your schema, at a price you can afford. For that you run your own comparison. It takes a day or two and usually saves far more than that in cost or quality.

## Custom evals versus public benchmarks

A public benchmark answers "how does this model do on this fixed set of questions, under the benchmark's conditions?". Your
question is different: "how will it do on *my* inputs, with *my* prompt, my output format and my users?" The two diverge more
often than you would expect:

- Benchmarks measure general ability; your task may depend on a narrow skill (a particular SQL dialect, Hindi legal terms).
- Benchmark questions leak into training data, so scores can be inflated (7.5).
- Prompts, tool use and output constraints in your app change the result.
- Aggregate rank hides the failure types that matter to you (a model strong on maths but wordy and slow).

Use benchmarks for the cheap first step (a shortlist), then run a **custom eval** on your own cases, which is a small golden
set (7.7) scored with code checks and a calibrated judge (7.8). Even 50 to 100 well-chosen cases typically predicts your
real results better than a leaderboard position. When the two disagree, trust the custom eval, and update it when you
find a case it missed.

## Making a shortlist

Start broad, filter fast:

1. **Hard constraints first.** Context length, data residency, open weights vs API, structured output and tool-calling support, licence.
2. **Capability.** Use leaderboards to keep models strong on the relevant skill (code, reasoning, multilingual).
3. **Latency and price.** Aggregator sites list throughput, time to first token and price per million tokens for many providers.

Aim for three to five candidates, including at least one small, cheap model. Small models win more often than people expect on narrow tasks.

## A task dataset: text-to-SQL

Build 50-150 cases that look like real traffic. For text-to-SQL, each case holds a question, the gold SQL written by someone who knows the schema, and a tag:

```json
{"id": "q017", "question": "Top 5 customers by revenue in 2025",
 "gold_sql": "SELECT customer_id, SUM(amount) AS revenue FROM orders WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01' GROUP BY customer_id ORDER BY revenue DESC LIMIT 5",
 "tags": ["aggregation", "date-filter"]}
```

Cover the easy majority and the hard tail: joins across three tables, ambiguous column names, questions that should be refused ("delete old orders"), and questions the schema can't answer. Score by **executing** both queries on a test database and comparing result sets, since many different SQL strings are correct.

## Fair comparison

Change one thing only: the model. Keep identical:

- inputs and their order;
- system prompt and schema description (allow small per-provider formatting adjustments only if documented);
- temperature, max tokens, reasoning settings where comparable;
- scoring code.

Run each case more than once (three runs is common) if outputs vary, and report the mean and spread.

```python
import time, statistics

def compare(models, cases, generate_sql, run_query, runs=3):
    report = {}
    for model in models:
        correct, latencies, tokens = 0, [], 0
        for case in cases:
            for _ in range(runs):
                t0 = time.perf_counter()
                sql, usage = generate_sql(model, case["question"])
                latencies.append(time.perf_counter() - t0)
                tokens += usage["input"] + usage["output"]
                try:
                    correct += run_query(sql) == run_query(case["gold_sql"])
                except Exception:
                    pass  # invalid SQL counts as wrong
        n = len(cases) * runs
        report[model] = {
            "accuracy": correct / n,
            "p50_s": statistics.median(latencies),
            "p95_s": statistics.quantiles(latencies, n=20)[18],
            "avg_tokens": tokens / n,
        }
    return report
```

## Estimating cost

Translate tokens into a monthly bill:

```
cost per request = input_tokens × input_price + output_tokens × output_price
monthly cost     = cost per request × requests per month
```

Worked example (prices are illustrative): a 3,000-token prompt (mostly the schema) and 150 output tokens, 200,000 requests a month.

| Model | Input $/M | Output $/M | Cost/request | Monthly |
|---|---|---|---|---|
| Large | 3.00 | 15.00 | $0.01125 | $2,250 |
| Small | 0.40 | 1.60 | $0.00144 | $288 |

The schema is identical on every call, so **prompt caching** can cut the input cost sharply on providers that support it (cached input is typically billed at a fraction of the normal rate). Place the stable schema at the start of the prompt so it can be cached, and include caching in your estimate.

## Picking the winner

Put quality, latency and cost in one table and decide against your requirements, not the leaderboard:

| Model | Accuracy | p95 latency | Monthly cost |
|---|---|---|---|
| Large | 91% | 4.1 s | $2,250 |
| Medium | 89% | 2.0 s | $700 |
| Small | 78% | 0.9 s | $288 |

If the product needs 85%+ and answers under 3 s, Medium wins even though Large scores higher. Break accuracy down by tag too: if Small fails mostly on multi-table joins, routing just those to a larger model can be a good compromise.

## Try it

Your support classifier handles 1 million messages a month, about 800 input and 10 output tokens each. Model X costs $0.15/M input and $0.60/M output and scores 94%. Model Y costs $2.50/M and $10/M and scores 95%. Estimate both monthly costs and say which you'd pick.

<details>
<summary>Reference</summary>

X: 800 × 0.15/1M + 10 × 0.60/1M = $0.00012 + $0.000006 = $0.000126 per message, about $126 a month.
Y: 800 × 2.50/1M + 10 × 10/1M = $0.002 + $0.0001 = $0.0021 per message, about $2,100 a month.

One point of accuracy for roughly 17x the cost is rarely worth it for classification. Pick X, then check what the extra 1% of errors are: if they are costly (e.g. misrouted legal complaints), consider sending only low-confidence cases to Y.
</details>

## Check yourself

1. Why compare executed results rather than SQL text when scoring text-to-SQL?

<details>
<summary>Answer</summary>

Many different queries return the same correct result (different aliases, join order, equivalent filters). String comparison would mark correct queries wrong; result comparison measures what matters.
</details>

2. Name three things you must hold constant to compare models fairly.

<details>
<summary>Answer</summary>

Any three of: the input set, the prompt and schema description, sampling settings (temperature, max tokens, reasoning budget), the scoring code, and the number of runs per case.
</details>

3. How does prompt caching change a cost estimate?

<details>
<summary>Answer</summary>

If a large stable prefix (like a schema or instructions) repeats on every call, providers that support caching bill those cached tokens at a reduced rate, so the effective input cost can fall a lot. Estimates should use the expected cache hit rate, and prompts should put the stable content first.
</details>
