# Building golden datasets

Every eval method in this level (code checks, judges, RAG metrics, regression gates) needs the same raw material: a set
of realistic inputs with a way to say what a good answer looks like. That set is your **golden dataset**. A thoughtful
50-case dataset beats a sloppy 5,000-case one, because every later decision ("did the new prompt help?") is only as
trustworthy as the cases behind it.

## What a golden dataset is

A golden dataset is a **versioned** collection of test cases, each with:

- an **input** (the question, conversation or task);
- the **expected result**: a reference answer, the ids of the documents that should be retrieved, a list of facts that
  must appear, or a rubric describing what good looks like;
- **metadata**: topic, difficulty, language, user type, whether it is answerable, where the case came from.

It is "golden" because you trust it enough to settle an argument. That trust has to be earned by review.

```json
{
  "id": "q_0042",
  "input": "Can I return a laptop after 10 days if I opened the box?",
  "reference": "Yes. Laptops can be returned within 15 days if unused or defective; opened items incur a 10% fee.",
  "must_cite": ["policy-returns-electronics"],
  "tags": {"topic": "returns", "difficulty": "medium", "answerable": true, "source": "support_ticket"},
  "added": "2026-02-11", "reviewed_by": "asha"
}
```

## Where the cases come from

Mix several sources:

1. **Production logs and support tickets**: the most realistic inputs, including typos and half-questions. Remove
   personal data first (8.8).
2. **Domain experts**: ask the people who answer these questions today for the ten hardest and ten most common ones.
3. **Synthetic generation**: have a model write questions from your documents. It scales, but synthetic questions tend
   to be tidier and easier than real ones, so use them to widen coverage, never as the whole set, and review them.
4. **Failures**: every bug report and thumbs-down becomes a case (more on this below).

## Coverage on purpose

Random sampling over-represents the common and misses the dangerous. Build a coverage grid and fill it deliberately:
topics × difficulty × user type × language. Include cases the system **should refuse or say "I don't know"** to,
ambiguous questions where it should ask a clarifying question, adversarial inputs (8.2), and multi-turn conversations if
that is how users talk. If 20% of your traffic is in Hindi, 20% of your set should be too.

## Labelling and agreement

Whoever writes the reference answers needs written **guidelines**: what counts as correct, how much detail, what to do
when the source documents disagree. Then test the labels themselves. Have two people label the same 30-50 cases and
compute agreement, ideally with **Cohen's kappa**, which corrects for chance agreement (roughly: below 0.4 weak, 0.6-0.8
substantial, above 0.8 near-perfect). Low agreement means your guidelines are unclear, not that the labellers are
careless, and a judge model (7.8) will also be unreliable on those cases. Resolve disagreements by discussion and update
the guidelines.

## Size, splits and leakage

Choose a size you can afford to run on every change: 50-200 cases for fast checks, a larger set nightly. Keep a
**held-out split** you do not tune against; if you iterate on prompts using the whole set, your scores will creep up
without real improvement (overfitting to the test). Watch for **leakage**: if the reference answers or the test
questions appear in your prompt examples, your index metadata or your fine-tuning data, the score is meaningless.

## Versioning and growth

Store the set in git (JSONL works well) or a dataset registry such as the datasets feature of Langfuse or LangSmith. Tag
versions (`golden-v3`) and record which version every eval run used, so a score change is never ambiguous. Then grow it:
each production failure, after you fix it, is added as a test case. After six months the set is a map of everything
that has gone wrong, which is exactly what you want to guard against.

## Try it

You are building a golden set for a bank's FAQ bot. You have 400 real customer questions from last month, tagged by
topic. About 70% are about three topics (card blocks, UPI failures, statements). How do you sample 100 cases?

<details>
<summary>Reference</summary>

Do not sample proportionally; that gives 70 cases from three topics and almost none from the rest. Take 12-15 from each of
the three big topics and 3-5 from each smaller topic, tag difficulty, and add 10 deliberately hard or unanswerable
cases (for example, asking for another customer's balance, which must be refused) plus a handful of Hindi and
mixed-language questions. Have two reviewers label 30 of them and compute kappa before trusting the rest.
</details>

## Check yourself

1. Why shouldn't a golden set be made only of synthetic questions?

<details>
<summary>Answer</summary>

Synthetic questions tend to be cleaner and easier than real ones and miss real phrasing, typos and edge cases, so the
set would overstate quality. Use them to widen coverage, alongside real and expert-written cases.
</details>

2. What does low inter-annotator agreement tell you?

<details>
<summary>Answer</summary>

That the labelling guidelines or the task definition are ambiguous. Fix those first; neither humans nor a judge model
can be reliable on cases people disagree about.
</details>

3. How do you keep a golden set useful over time?

<details>
<summary>Answer</summary>

Version it, record which version each run used, keep a held-out split, and add every fixed production failure as a new
case so the set keeps covering what has gone wrong before.
</details>
