# Eval suites and regression testing

A one-off eval tells you how good a version is today. An **eval suite** runs the same checks on every change, compares against a baseline and blocks the change if quality drops. It is the LLM equivalent of a test suite in CI, and it is what lets a team change prompts and models weekly without fear.

## Component, pipeline, application

Test at the level that answers your question:

| Level | What you test | Example (RAG support bot) | Speed |
|---|---|---|---|
| **Component** | One part in isolation | Retriever: does the right chunk appear in the top 5? | Fast, cheap |
| **Pipeline** | Several parts wired together | Retrieve + generate: is the answer faithful to the context? | Medium |
| **Application** | The whole system as a user meets it | Multi-turn conversation: was the issue resolved correctly and politely? | Slow, costly |

Component tests localise failures; application tests confirm the user experience. A healthy suite has many component cases, fewer pipeline cases and a small set of end-to-end scenarios.

## Versioning everything

An eval score only means something if you can say exactly what produced it. Record, for every run:

- dataset version (a hash or git tag of the case file);
- eval config (checks, judge prompt, judge model, thresholds);
- system config (prompt version, model id, temperature, retrieval settings);
- results per case, plus the summary.

Keep datasets and judge prompts in git next to the code. A judge prompt change is a change to the ruler; re-score the baseline when you make one, or the comparison is meaningless.

## Experiments and baselines

The **baseline** is the score of what's currently in production on the current dataset. Every candidate is compared to it on identical cases. Experiment-tracking tools (Langfuse, LangSmith, Braintrust, MLflow, Weights & Biases and others) store runs and show per-case diffs, which matter more than the averages: "+2% overall" can hide ten cases that went from right to wrong.

## CI gates

Run the suite on every pull request that touches prompts, model config, retrieval or tools. Fail the build if a key metric drops past a tolerance:

```python
# eval_gate.py - run in CI after the eval job writes results.json
import json, sys

baseline = json.load(open("baselines/main.json"))
current = json.load(open("results.json"))

GATES = {                       # metric: max allowed drop (absolute)
    "answer_correct": 0.02,
    "faithfulness": 0.02,
    "valid_json": 0.0,          # never allowed to drop
}
LIMITS = {"p95_latency_s": 4.0, "cost_per_request_usd": 0.01}

failed = []
for metric, tolerance in GATES.items():
    if current[metric] < baseline[metric] - tolerance:
        failed.append(f"{metric}: {baseline[metric]:.3f} -> {current[metric]:.3f}")
for metric, limit in LIMITS.items():
    if current[metric] > limit:
        failed.append(f"{metric}: {current[metric]} over limit {limit}")

if failed:
    print("Eval gate failed:\n  " + "\n  ".join(failed))
    sys.exit(1)
print("Eval gate passed")
```

Practical tips:

- **Tolerance** absorbs run-to-run noise. Measure noise by running the baseline several times; set tolerance just above it.
- **Critical cases** (safety, legal, never-break behaviours) should be hard gates: any failure fails the build.
- Keep the PR suite fast (minutes). Run the larger, slower suite nightly or before releases.
- Cache outputs for unchanged components to cut cost.

## A dataset that grows

Your golden set should grow from three sources:

1. **Production failures** found through online evals, user feedback and support tickets.
2. **Edge cases** discovered during development and red-teaming.
3. **Coverage gaps**: categories of real traffic with few or no cases.

Tag every case (topic, difficulty, source, date added) so you can report scores by slice. Retire or fix cases whose expected answers are out of date, such as after a policy change. A stale golden answer fails good outputs and trains the team to ignore the suite.

## Quality with cost and latency

Every change trades something. Track all three together:

| Version | Correct | p95 latency | Cost/request |
|---|---|---|---|
| v12 (baseline) | 88% | 2.1 s | $0.004 |
| v13 add reranker | 91% | 2.6 s | $0.005 |
| v14 bigger model | 92% | 4.8 s | $0.019 |

v13 is a clear win; v14 buys one point for double the latency and nearly four times the cost. Without the extra columns, v14 looks best.

## Try it

Your team has 120 eval cases. A teammate's PR changes the system prompt and the summary goes from 86% to 87%. What else would you check before approving?

<details>
<summary>Reference</summary>

- The per-case diff: which cases flipped right-to-wrong and wrong-to-right. A net +1% might hide several regressions in an important category.
- Whether +1% is beyond noise: compare with the baseline's own run-to-run variation.
- Critical cases (safety, policy) all still pass.
- Latency, token count and cost per request, since a longer prompt raises both.
- That the dataset, judge prompt and judge model are the same versions used for the baseline.
</details>

## Check yourself

1. Why must the judge prompt and judge model be versioned like code?

<details>
<summary>Answer</summary>

They define how outputs are scored. Changing them changes the measurement itself, so scores before and after aren't comparable unless the baseline is re-scored with the new judge.
</details>

2. How do you choose the tolerance for a CI gate?

<details>
<summary>Answer</summary>

Run the unchanged baseline several times to see how much the metric moves from noise alone, then set the tolerance just above that range. Behaviours that must never break get zero tolerance.
</details>

3. Why keep many component tests and only a few application-level scenarios?

<details>
<summary>Answer</summary>

Component tests are fast and cheap and point to the exact part that failed. Application scenarios are slow and costly and only show that something went wrong, so a small number confirms the end-to-end experience while component tests do most of the work.
</details>
