# Versioning, cost and caching

A prompt is code that runs on someone else's computer and is billed per token. It deserves the same habits as code:
version control, a record of what ran where, and attention to how much each request costs.

## Prompts are code

Store prompts in your repository, not in a dashboard text box or scattered f-strings. A simple pattern:

```
prompts/
  ticket_classifier/
    v3.txt
    v4.txt
  CHANGELOG.md        # why v4 exists, and its test-set scores
```

At runtime, log the prompt id and version with every model call, next to the model name and version. When a user
reports a strange answer from last Tuesday, you need to know exactly which prompt and which model produced it.

```python
import hashlib, logging, time
from pathlib import Path
from anthropic import Anthropic

client = Anthropic()
log = logging.getLogger("llm")

def load_prompt(name: str, version: str) -> tuple[str, str]:
    text = Path(f"prompts/{name}/{version}.txt").read_text()
    digest = hashlib.sha256(text.encode()).hexdigest()[:8]   # catches edits made without a version bump
    return text, f"{name}@{version}#{digest}"

SYSTEM, PROMPT_ID = load_prompt("ticket_classifier", "v4")

def classify(ticket: str) -> str:
    start = time.perf_counter()
    msg = client.messages.create(
        model="claude-haiku-4-5", max_tokens=50, system=SYSTEM,   # example model id
        messages=[{"role": "user", "content": f"<ticket>{ticket}</ticket>"}],
    )
    log.info("llm_call", extra={
        "prompt": PROMPT_ID, "model": msg.model,
        "in_tokens": msg.usage.input_tokens, "out_tokens": msg.usage.output_tokens,
        "latency_ms": round((time.perf_counter() - start) * 1000),
    })
    return msg.content[0].text
```

Some teams use a prompt management tool (many observability platforms include one) so non-engineers can edit prompts.
That works if every published version is still immutable, logged, and tested before release.

## Compare the full bill

The test set from module 3.6 gives you quality. Add three more columns and you can compare prompts honestly:

| Version | Accuracy | Avg input tokens | Avg output tokens | p50 latency | Cost per 1k calls* |
|---------|----------|------------------|-------------------|-------------|--------------------|
| v3 (8 examples) | 91% | 2,400 | 6 | 0.9 s | $2.43 |
| v4 (3 examples) | 90% | 1,100 | 6 | 0.6 s | $1.13 |
| v5 (v4 + reasoning field) | 94% | 1,150 | 140 | 2.1 s | $1.85 |

\*Illustrative, at $1 per million input tokens and $5 per million output tokens. Real prices vary by model and change
often; plug in the current ones.

Here v4 gives up one point of accuracy for half the cost and lower latency. Whether that's a good trade depends on the
cost of a wrong label. Make the decision explicit rather than defaulting to the most accurate prompt.

Output tokens usually cost several times more than input tokens and dominate latency, so a prompt that makes answers
shorter often saves more than one that trims the instructions.

## Cut what isn't needed

Prompts grow by accretion. Periodically remove:

- instructions repeated in two places, or in both the system prompt and every user turn;
- examples that the test set shows make no difference;
- context the task doesn't use (the full product catalogue when only one product matters);
- politeness and filler ("You are a world-class, highly intelligent assistant...").

Each removal is a prompt change, so run the test set before and after.

## Prompt caching

Providers can cache the processed form of a prompt **prefix** and reuse it when the next request starts with exactly
the same tokens. Cached input tokens are billed at a large discount and processed faster, which mostly cuts time to
first token. Mechanics vary: OpenAI caches long prefixes automatically; Anthropic lets you mark cache breakpoints with
`cache_control`; Google offers both implicit and explicit context caching. Caches expire after minutes of inactivity
(longer options exist on some providers), and some charge extra to write the cache.

The rule that follows: **put stable content first and variable content last.**

```
[system prompt, tool definitions]   ← identical on every call
[few-shot examples, reference docs] ← identical on every call
[conversation history]              ← grows, but its start is stable
[today's user input]                ← changes every call
```

Anything that changes per request near the top (a timestamp in the first line of the system prompt, a user's name,
randomly ordered examples) breaks the match for everything after it. Check the cached token count in the usage data of
your responses to confirm caching is happening.

## Try it

Your system prompt starts with `Current time: 2026-11-06 14:32:07. You are the assistant for...`, followed by 3,000
tokens of policies and examples, then the user's question. Cached tokens in your usage logs are always zero. Explain and
fix.

<details>
<summary>Reference</summary>

The timestamp changes on every request and sits at the very start, so no two requests share a prefix and nothing can be
reused. Move the policies and examples to the top, unchanged, and pass the current time in the user turn (or at the end
of the prompt), at minute or day resolution if exact seconds aren't needed. Then confirm the usage data reports cached
tokens on the second and later calls; on providers with explicit caching, also add a cache breakpoint after the stable
block.
</details>

## Check yourself

1. What should you log with each model call so you can reproduce an odd answer later?

<details>
<summary>Answer</summary>

The prompt id and version (ideally a hash of the text), the exact model id or version, the inputs, token counts and
latency, and the output.
</details>

2. Why does shortening the output often save more than shortening the prompt?

<details>
<summary>Answer</summary>

Output tokens are usually priced several times higher than input tokens and are generated one at a time, so they
dominate both cost and latency.
</details>

3. What breaks prompt caching, and how do you structure prompts to benefit from it?

<details>
<summary>Answer</summary>

Any change near the start of the prompt, since caching matches an exact prefix. Put stable instructions, tools,
examples and reference material first, and variable content such as user input and timestamps last.
</details>
