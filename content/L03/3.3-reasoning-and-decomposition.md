# Reasoning and decomposition

A model produces its answer one token at a time, and each token can only build on what came before. If the answer
needs several steps of work, the model either does that work in tokens it writes first, or tries to jump straight to
the result. Prompting for reasoning gives it room to do the work. Decomposition goes further and splits the work across
separate steps you control.

## When to ask for reasoning

Asking a standard (non-reasoning) model to work through a problem before answering, often called **chain-of-thought**,
reliably helps on:

- multi-step arithmetic and word problems;
- planning and scheduling with many constraints;
- code that has to satisfy several requirements at once;
- logic puzzles and "which of these rules applies" decisions.

It helps little, or hurts, on:

- extraction ("pull the invoice date");
- classification with clear labels;
- rewriting, translation and short summaries.

On those tasks the extra tokens cost money and time, and the free-text reasoning can drift from the format you need.

## Doing it without breaking your parser

If your code needs a clean answer, let the model reason in one place and answer in another:

```python
from openai import OpenAI
from pydantic import BaseModel

client = OpenAI()

class Verdict(BaseModel):
    reasoning: str          # scratch space, logged but not shown to users
    eligible: bool
    reason_code: str

policy = "Refunds within 30 days of purchase, unused licences only, max 2 refunds per customer per year."
case = "Bought 2026-09-20, asked 2026-10-15, licence activated once, 1 refund earlier this year."

resp = client.responses.parse(
    model="gpt-4.1-mini",   # example non-reasoning model
    input=[
        {"role": "system", "content": "Decide refund eligibility. Check every policy condition in turn "
                                      "in `reasoning` before setting `eligible`."},
        {"role": "user", "content": f"<policy>{policy}</policy>\n<case>{case}</case>"},
    ],
    text_format=Verdict,
)
v = resp.output_parsed
print(v.eligible, v.reason_code)
```

Put the reasoning field **before** the answer fields. The model generates fields in order, so the answer can then
depend on the reasoning rather than the other way round.

## Decomposing a task

Some tasks are too much for one prompt even with reasoning: the instructions conflict, or one failure ruins
everything. Split them:

| One overloaded prompt | Decomposed |
|-----------------------|------------|
| "Read this contract, find risky clauses, rate each, and write an email to the client." | 1. Extract clauses as a list. 2. For each clause, rate risk with a focused prompt. 3. Write the email from the rated list. |

Benefits: each prompt is simpler and testable on its own; you can use a cheap model for easy steps; failures point to
a step; independent steps run in parallel. Costs: more calls, more latency, and errors can pass from step to step.
Split when a step is independently checkable or needs a different instruction set, not by reflex.

A lighter form is decomposition inside one prompt: ask the model to first list the sub-questions, then answer each,
then combine. This is often enough for medium-difficulty problems.

## Prompting reasoning models

Reasoning models (for example OpenAI's o-series and GPT-5 family with reasoning effort, Claude with extended thinking,
Gemini thinking models) already think before answering. They are trained to do it, and you control how much through a
setting such as reasoning effort or a thinking budget. With them:

- **Don't** script the thinking ("first do X, then Y, think step by step"). It rarely helps and can constrain a better
  approach the model would have found.
- **Do** state the goal, give all the relevant context, list hard constraints, and describe what a good answer looks
  like and how it will be judged.
- **Do** keep few-shot examples minimal at first; add them only if the output format needs showing.
- Raise or lower the effort setting before rewriting the prompt to get more or less depth.

The hidden reasoning tokens are billed as output, so a high effort setting on a simple task is pure waste.

## Try it

You have a prompt that asks a model to "read the attached 40-page RFP and produce a bid/no-bid decision with a
one-page summary for the sales director". Results are inconsistent. Propose a decomposition into 3-4 steps, saying
which steps need reasoning and which don't.

<details>
<summary>Reference</summary>

1. **Extract requirements** (no reasoning needed): list mandatory requirements, deadline, budget, evaluation criteria
   as structured output.
2. **Check fit per requirement** (light reasoning, can run in parallel): for each requirement, compare against a short
   capabilities document and mark met / partial / not met with a sentence of justification.
3. **Decide** (reasoning model or reasoning prompt): given the fit table, budget and deadline, decide bid or no-bid
   against explicit criteria, with reasons.
4. **Write the summary** (no reasoning needed): turn the decision and the table into a one-page summary in the house
   format.

Each step's output can be checked on its own, which is what makes the whole thing debuggable.
</details>

## Check yourself

1. Why does asking for reasoning help a standard model on multi-step maths?

<details>
<summary>Answer</summary>

Each token is produced with a fixed amount of computation and depends only on earlier tokens. Writing out intermediate
steps lets later tokens build on worked results instead of guessing the final answer in one jump.
</details>

2. In a structured output, why put the `reasoning` field before `answer`?

<details>
<summary>Answer</summary>

Fields are generated in order. If the answer comes first, the reasoning can only justify a choice already made. If the
reasoning comes first, the answer is conditioned on it.
</details>

3. What changes when you prompt a reasoning model instead of a standard one?

<details>
<summary>Answer</summary>

Stop prescribing how to think. Give the goal, context, constraints and success criteria, and control depth with the
reasoning-effort or thinking-budget setting.
</details>
