# Testing and debugging prompts

The usual way people improve a prompt: try an input, dislike the answer, add a sentence, try again, like it, ship.
Two weeks later a different input breaks, and the new sentence turns out to have broken three old cases nobody
rechecked. The fix is the same as for code: a test suite you run on every change.

## Diagnosing a failure

Before editing, name the cause. Most prompt failures fall into a few buckets.

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| Different answers to the same input | Instruction underspecified; temperature high | Define the decision rule; lower temperature |
| Follows rule A, ignores rule B | Rules conflict or B is buried | Resolve the conflict; state priority; move B up |
| Copies a phrase or label from examples too often | Examples skewed or too similar | Balance and vary examples |
| Invents facts | Needed context missing; no "I don't know" path | Supply the context; allow abstaining |
| Right content, wrong shape | Output spec vague | Tighten the spec; use structured output |
| Works in testing, fails on real users | Test inputs too clean | Add real, messy inputs to the set |

A quick diagnostic: ask yourself whether a competent new colleague, given only this prompt, would produce the answer you
want. If they'd need to ask a question, so does the model.

## A small test set

You don't need thousands of cases. Twenty to fifty well-chosen ones catch most regressions.

- **Normal cases**: the bulk of real traffic, sampled from logs where possible.
- **Edge cases**: empty input, very long input, other languages, two intents at once, sarcasm, typos.
- **Known failures**: every bug you've fixed becomes a permanent test.
- **Should-refuse cases**: out-of-scope or unsafe requests, with the expected decline.

For each case store the input and a way to judge the output: an exact expected value for classification and
extraction, or a list of checks ("mentions the 30-day limit", "under 100 words", "doesn't promise a refund") for free
text. Checks you can run in code are best; an LLM-as-judge is the subject of the evaluation level.

```python
import json, statistics
from openai import OpenAI

client = OpenAI()
cases = [json.loads(line) for line in open("cases.jsonl")]   # {"input": ..., "expected": ...}

def run(prompt_version: str, system: str, model: str = "gpt-4.1-mini", repeats: int = 3) -> dict:
    scores = []
    for case in cases:
        outs = []
        for _ in range(repeats):
            r = client.chat.completions.create(
                model=model, temperature=0,
                messages=[{"role": "system", "content": system},
                          {"role": "user", "content": case["input"]}],
            )
            outs.append(r.choices[0].message.content.strip())
        correct = sum(o == case["expected"] for o in outs) / repeats
        scores.append({"input": case["input"], "correct": correct, "consistent": len(set(outs)) == 1})
    return {
        "version": prompt_version,
        "accuracy": statistics.mean(s["correct"] for s in scores),
        "consistency": statistics.mean(s["consistent"] for s in scores),
        "failures": [s["input"] for s in scores if s["correct"] < 1],
    }
```

## Compare versions on the same cases

Run every candidate prompt on the whole set and compare the summary numbers *and* the list of failing cases. Two
versions at 88% accuracy can fail on completely different inputs. Look for:

- **Net gains**: v2 fixes five cases and breaks none.
- **Trade-offs**: v2 fixes five and breaks two. Read the two; are they more important?
- **Noise**: a one-case difference on a 30-case set may be chance. Repeat runs, or grow the set.

Change one thing at a time where you can. If you rewrite the whole prompt and accuracy rises, you won't know which
change helped, or which one quietly hurt a case that's now masked by others.

## Less variance, fewer regressions

- Lower temperature for tasks with one right answer.
- Replace soft words ("usually", "if appropriate") with concrete decision rules.
- Keep every fixed bug as a test, so it stays fixed.
- Re-run the suite when you change **model** or model version, not just the prompt. A prompt is tuned to a model.
- Keep the suite fast and cheap enough that you actually run it: a few minutes, a few cents.

## Try it

Your ticket classifier prompt v1 scores 80% on 40 cases. You add the sentence "Tickets mentioning invoices are billing."
v2 scores 85%. What do you check before shipping v2?

<details>
<summary>Reference</summary>

- **Which cases changed.** List cases v1 passed and v2 fails, and vice versa. 85% might be "fixed 3, broke 1".
- **What broke.** For example a bug report that mentions an invoice page ("the invoice page crashes") may now be
  labelled billing. If so, refine the rule ("about charges or payments, not errors on the invoice page") and add
  that case to the set.
- **Noise.** Run each version several times; on 40 cases one or two flips can be randomness.
- **Coverage.** Make sure the set includes the kind of real ticket that prompted the change, so the gain isn't only on
  synthetic cases.
</details>

## Check yourself

1. Why judge prompt versions on a fixed set instead of a few live tries?

<details>
<summary>Answer</summary>

Single outputs vary and are cherry-picked by whoever is looking. A fixed set compares versions on identical inputs,
reveals cases that a change broke, and gives numbers you can track over time.
</details>

2. What four kinds of case belong in a starter test set?

<details>
<summary>Answer</summary>

Normal cases from real traffic, edge cases, known past failures, and cases the system should refuse or decline.
</details>

3. You switch to a newer model and keep the same prompt. What should you do?

<details>
<summary>Answer</summary>

Re-run the full test set. Prompts are tuned against a particular model's behaviour, and a newer model can follow
instructions differently, sometimes more literally, which can break cases that used to pass.
</details>
