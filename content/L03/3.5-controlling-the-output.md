# Controlling the output

Users see the output; your code parses it. Both care about shape: length, tone, headings, tables, field names. Some of
that shape is a matter of taste and is best steered with words. Some of it is a contract your code depends on and
should be enforced by machinery, not requested politely.

## Steering style, length and layout

Instructions work best when they are specific and positive (say what to do, not only what to avoid).

| Vague | Specific |
|-------|----------|
| "Be brief." | "Answer in at most 3 sentences." |
| "Don't use markdown." | "Write plain prose paragraphs with no headings, bullets or bold." |
| "Make it professional." | "Write as a support engineer emailing a business customer: polite, direct, no exclamation marks." |
| "Format nicely." | "Use a table with columns Feature, Free plan, Pro plan." |

Some practical points:

- **Length** is approximate. Models count words poorly but follow sentence, bullet and paragraph counts well. Use
  `max_tokens` as a hard ceiling for cost, not as a style control; hitting it cuts the answer off mid-sentence.
- **Your prompt's own style leaks.** A prompt full of markdown bullets invites markdown back. If you want prose, write
  the prompt in prose.
- **Show the shape.** For anything unusual, one example of the exact output is clearer than a description.
- **Labels and delimiters** help both humans and parsers: "Start with `Summary:` on its own line, then `Actions:`."

## When words are not enough

"Return valid JSON with these keys" works most of the time. Most of the time isn't good enough when a parse error
crashes a pipeline that runs a million times a day. Typical failures: a friendly sentence before the JSON, a missing
key, a trailing comma, a string where you wanted a number, a label outside your allowed set.

If code consumes the output, use **structured output** from Level 2: give the API a schema and let it constrain
generation so the result always parses and matches the types.

```python
from typing import Literal
from openai import OpenAI
from pydantic import BaseModel, Field

client = OpenAI()

class TicketSummary(BaseModel):
    category: Literal["billing", "bug", "how-to", "other"]
    urgency: int = Field(ge=1, le=5)
    summary: str = Field(description="One sentence, under 25 words, no customer names")

resp = client.responses.parse(
    model="gpt-4.1-mini",   # example model
    input=[
        {"role": "system", "content": "Summarise support tickets for the triage dashboard. "
                                      "Urgency 5 means the customer cannot work at all."},
        {"role": "user", "content": "<ticket>Since this morning nobody on our team can log in. "
                                    "We have payroll due today!!</ticket>"},
    ],
    text_format=TicketSummary,
)
print(resp.output_parsed)
```

Anthropic and Google offer equivalent schema-constrained output; with Anthropic a forced tool call with an input
schema also does the job. Note that some constraints (like `ge=1, le=5` or a word limit) may not be enforced during
generation by every provider, so validate the parsed object in code as well.

## Meaning vs format

Split the responsibilities:

| Concern | Where it belongs |
|---------|------------------|
| Which fields exist, their types, allowed values | Schema (enforced) |
| What each field should contain, and how to decide it | Prompt and field descriptions |
| Tone, length, emphasis in free-text fields | Prompt |
| Range checks, cross-field rules, business limits | Your code after parsing |

A schema guarantees `category` is one of four strings. It can't guarantee it is the *right* one; that's the prompt's
job, measured by your test set. Conversely, there is no point spending prompt words begging for valid JSON once the
schema enforces it.

A caution: very rigid formats can make answers worse when the model has to squeeze reasoning into them. If quality
drops after adding a schema, give it a free-text `reasoning` field first (module 3.3), or generate freely and then
extract into the schema with a second, cheap call.

## Try it

A product page generator must return: a title (under 60 characters), three bullet-point benefits, and a price string
like "$19/month". It's displayed by a front-end component. Decide what goes in the schema, what goes in the prompt, and
what goes in code.

<details>
<summary>Reference</summary>

- **Schema:** `title: str`, `benefits: list[str]` with exactly three items (min/max length 3), `price: str`.
- **Prompt:** tone and audience, what makes a good benefit (concrete outcome, not a feature name), "title under 60
  characters", "price formatted like $19/month, using the price provided, never inventing one".
- **Code:** check `len(title) <= 60` and truncate or retry; check the price string matches a regex such as
  `^\$\d+(\.\d{2})?/(month|year)$` and equals the real price from your database; escape text before rendering.

The front end never parses free text; it receives a validated object.
</details>

## Check yourself

1. Why isn't `max_tokens` a good way to make answers shorter?

<details>
<summary>Answer</summary>

It's a hard cut-off, not an instruction. The model doesn't plan for it, so the answer simply stops mid-sentence. Ask for
a length in sentences or bullets and keep `max_tokens` as a safety ceiling.
</details>

2. Your schema forces `sentiment` to be "positive", "negative" or "neutral". Is the sentiment now correct?

<details>
<summary>Answer</summary>

No. The schema guarantees the value is one of the allowed labels, not that it's the right label. Correctness comes from
the prompt and is checked with a test set.
</details>

3. Quality dropped after you switched to strict JSON output. What could you try?

<details>
<summary>Answer</summary>

Add a reasoning or notes field before the answer fields, loosen over-tight constraints, or generate a free-text answer
first and extract it into the schema with a second call.
</details>
