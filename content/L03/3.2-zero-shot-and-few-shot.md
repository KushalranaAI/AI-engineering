# Zero-shot and few-shot

**Zero-shot** means you describe the task and give no examples. **Few-shot** means you also show a handful of worked
input-output pairs. Modern models are good at following plain instructions, so zero-shot is the right default. Examples
earn their tokens when words alone can't pin down what you want.

## When examples help

| Situation | Zero-shot enough? | Why |
|-----------|-------------------|-----|
| Translate, summarise, fix grammar | Usually | The task is familiar and "good" is widely agreed |
| Extract named fields into a schema | Usually, with a schema | The schema says more than examples would |
| Your own labels with fuzzy boundaries ("how-to" vs "bug") | Often not | Examples show where the line is |
| A house style or tone | Often not | Style is easier to show than describe |
| An unusual output format | Often not | One example beats a paragraph of format rules |
| Edge cases you keep getting wrong | No | Add an example of exactly that case |

A useful test: if two careful humans would read your instruction and still disagree on some inputs, the model will
too. Examples are how you settle the disagreement.

## Writing good examples

Good examples are **representative**, **varied** and **consistent**.

- Cover each label or branch at least once, including the awkward ones (a ticket that is both billing and bug).
- Vary length, phrasing and topic so the model learns the rule, not a surface pattern.
- Use exactly the output format you want, every time. One sloppy example teaches sloppiness.
- Keep them short. Three to five is typical; past that, returns usually shrink while cost keeps growing.

With chat APIs you can supply examples as fake previous turns, which models follow closely:

```python
from openai import OpenAI

client = OpenAI()

examples = [
    ("I was charged twice this month", "billing"),
    ("Export to CSV crashes the app", "bug"),
    ("How do I add a second user?", "how-to"),
    ("Charged twice AND now the invoice page errors", "billing"),  # tie-break rule, shown not told
]

messages = [{"role": "system", "content":
             "Label each support ticket as billing, bug, how-to or other. Reply with the label only. "
             "If money is involved, prefer billing."}]
for text, label in examples:
    messages += [{"role": "user", "content": text},
                 {"role": "assistant", "content": label}]
messages.append({"role": "user", "content": "The app logs me out every five minutes"})

resp = client.chat.completions.create(model="gpt-4.1-mini", messages=messages, temperature=0)  # example model
print(resp.choices[0].message.content)   # expected: bug
```

## Quality, variety and order

Examples are powerful, so their flaws are powerful too. Known effects:

- **Label imbalance.** If three of four examples are "billing", the model leans towards "billing".
- **Recency.** The last example tends to have the most pull. Don't always end on the same label.
- **Copying surface features.** If every positive example mentions a price, the model may treat "mentions a price" as
  the rule.
- **Wrong labels hurt.** A mislabelled example can teach the wrong boundary.

Order matters less with strong current models than it did with earlier ones, but it hasn't vanished. If results swing
when you shuffle examples, your examples are doing too much work or are inconsistent with the instructions. Measure on
a test set (module 3.6) rather than trusting one run.

For large example pools you can **select examples dynamically**: embed the incoming input and insert the few most
similar labelled examples. This is retrieval applied to prompting, and it often beats a fixed set.

## Few-shot vs fine-tuning

| | Few-shot | Fine-tuning |
|---|---|---|
| Where the knowledge lives | In the prompt, every call | In the model's weights |
| Setup | Minutes | Data collection, a training run, evaluation |
| Per-call cost | Pays for example tokens each time (caching helps) | Shorter prompts |
| Changing behaviour | Edit text | Retrain |
| Scale of teaching | A handful of examples | Hundreds to thousands |

Start with prompting. Consider fine-tuning when you have plenty of good data, the behaviour is stable, and prompt
length or consistency has become the bottleneck (covered in the fine-tuning level).

## Try it

You are building a classifier that tags customer messages as `complaint`, `question` or `praise`. Zero-shot works on
most inputs but mislabels sarcasm ("Great, the app crashed again. Love it.") as praise. Write three few-shot examples
that fix this without breaking ordinary praise.

<details>
<summary>Reference</summary>

```
User: Great, another update that deleted my settings. Fantastic.
Assistant: complaint

User: Really happy with the new dashboard, saves me an hour a week.
Assistant: praise

User: Is there a way to schedule reports?
Assistant: question
```

The first shows sarcasm labelled as a complaint. The second is genuine praise, so the model doesn't learn "positive
words mean complaint". The third covers the remaining label. Then check it on a test set that includes both sarcastic
and sincere messages, and vary which example comes last.
</details>

## Check yourself

1. You need product names extracted into a fixed JSON schema. Do you reach for few-shot first?

<details>
<summary>Answer</summary>

Usually not. A clear instruction plus a schema (ideally enforced through structured output) defines the task well. Add an
example only if a specific ambiguity keeps causing errors, such as whether to include the brand in the name.
</details>

2. Your four examples are all labelled "positive" except one. What risk does that create?

<details>
<summary>Answer</summary>

Label bias: the model is pulled towards the majority label. Balance the labels, or at least make sure each one appears
and the order isn't always the same.
</details>

3. Name two signals that it may be time to fine-tune instead of adding more examples.

<details>
<summary>Answer</summary>

You have hundreds or more high-quality labelled examples; the prompt has grown long and expensive; quality still
plateaus with good examples; or you need a smaller, cheaper model to match a larger one's behaviour.
</details>
