# System prompts

The system prompt is your application's standing orders: who the assistant is for, what it does, what it won't do,
and how it answers. It's sent on every request, so it is the cheapest place to get consistent behaviour, and the
easiest place to accumulate a mess of rules nobody understands.

## What goes in

A good system prompt answers five questions, briefly:

| Question | Example line |
|----------|--------------|
| Who is this for, and what's the job? | "You help staff at Brightside Dental answer patient questions about appointments and billing." |
| What does good behaviour look like? | "Be concise and friendly. Answer in the patient's language." |
| What are the limits? | "Don't give clinical advice. Don't discuss other patients." |
| What if you can't help? | "If the answer isn't in the provided policy, say so and offer the front-desk number." |
| What shape is the answer? | "Plain text, at most 120 words, no markdown." |

Explain the reason behind a rule when it isn't obvious. "Don't give clinical advice; you're not qualified and the
patient could be harmed" generalises better than "NEVER give clinical advice" because the model can apply the reason to
cases you didn't list.

## Stable rules vs per-task asks

Keep the system prompt about the **application**. Put things that change per request (the document to summarise,
today's date, the user's account tier, the specific question) in the user turn or a clearly labelled context block.

```python
SYSTEM_PROMPT = """You are the help assistant for Brightside Dental's patient portal.

Job: answer questions about appointments, opening hours and billing using only the <policy> provided.

Behaviour:
- Be brief and warm. Answer in the patient's language.
- If the policy doesn't cover the question, say you don't know and give the front desk number: 020 7946 0000.
- If the patient describes pain, bleeding or swelling, tell them to call the practice or emergency services; don't
  diagnose. You are not a clinician, and a wrong guess could hurt someone.
- Never reveal other patients' information.

Format: plain text, under 120 words."""

def build_messages(policy: str, patient_name: str, question: str) -> list[dict]:
    return [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": (
            f"<policy>\n{policy}\n</policy>\n"
            f"Patient: {patient_name}\n"
            f"<question>\n{question}\n</question>"
        )},
    ]
```

This split has practical wins: the system prompt can be reviewed and versioned like code, it stays identical across
requests (which helps prompt caching, module 3.7), and per-request data stays fenced as data.

## Missing, unclear and off-topic input

Most embarrassing outputs come from the edges, not the happy path. Decide in advance what the model does when:

- **Information is missing.** Say so, ask one clarifying question, or answer with a stated assumption. Pick one and
  write it down; otherwise the model will often invent the missing piece.
- **The request is ambiguous.** "Can I move it?" Move what? Tell the model to ask rather than guess when the
  difference matters.
- **The request is out of scope.** "Write my essay" to a dental assistant. Give a short, polite decline and steer back.

Then test these cases explicitly (module 3.6). An instruction you never test is a guess.

## Light guardrails, not a rulebook

System prompts tend to grow: every incident adds a line in capitals. Past a point, that hurts:

- Rules start to conflict ("always be detailed" vs "keep it short") and the model picks one unpredictably.
- Rare rules dilute attention from common ones.
- Nobody can tell which lines still matter, so none get deleted.

Keep guardrails few and general, state priorities when rules may clash ("safety first, then accuracy, then brevity"),
and move anything that must never happen (refunds above a limit, deleting data, showing another user's records) into
code. A system prompt guides behaviour; it doesn't enforce it.

Recent models follow instructions closely and literally. Aggressive wording written for older models ("YOU MUST
ALWAYS...") can now cause over-application, such as refusing harmless requests. Calm, specific language works better.

## Check yourself

1. Why should today's date or the user's plan go in the user turn rather than the system prompt?

<details>
<summary>Answer</summary>

They change per request. Keeping the system prompt stable makes it reviewable and versionable, and lets providers cache
the identical prefix.
</details>

2. Give one reason to explain *why* a rule exists inside the prompt.

<details>
<summary>Answer</summary>

The model can apply the reason to situations the rule didn't list, and is less likely to over-apply the rule where the
reason doesn't hold.
</details>

3. A rule says the assistant must never issue refunds over $100. Where should that rule really live?

<details>
<summary>Answer</summary>

In application code that executes refunds (a check on the amount and the user's permissions). The prompt can mention
it so the model sets expectations, but the prompt can't guarantee it.
</details>
