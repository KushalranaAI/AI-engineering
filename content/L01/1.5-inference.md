# Inference

Inference is everything that happens between sending a request and receiving the last token. Two phases with very
different costs explain most of what you will see in latency dashboards and on pricing pages.

## From request to response

1. Your prompt (system prompt, history, documents, question) is tokenized.
2. **Prefill**: the model processes all input tokens and builds its internal state.
3. **Decode**: it generates output tokens one at a time, each requiring a pass through the model.
4. Generation stops at an end token, a stop sequence or the max-tokens limit.

## Prefill vs decode

| | Prefill | Decode |
|---|---|---|
| Works on | All input tokens at once | One new token per step |
| Parallel? | Yes, the GPU processes the whole prompt together | No, each token depends on the previous one |
| Bottleneck | Compute | Memory bandwidth (reading the weights and cache for every token) |
| Felt as | Time before the first token appears | Speed of the text streaming out |
| Priced as | Input tokens (cheaper) | Output tokens (often several times dearer) |

Because prefill is parallel, a 10,000-token prompt might take a fraction of a second to a couple of seconds. Decode is
sequential, so 2,000 output tokens at 80 tokens per second take 25 seconds, regardless of how fast prefill was.

## Latency numbers that matter

- **TTFT (time to first token)**: network + queueing + prefill. Dominated by prompt length and server load.
- **Output speed (tokens/second)**: decode rate, mostly a property of the model, hardware and batch size.
- **Total latency** ≈ TTFT + output_tokens / tokens_per_second.

```python
def estimate_latency(output_tokens, ttft_s=0.6, tps=80):
    return ttft_s + output_tokens / tps

print(estimate_latency(50))     # ≈ 1.2 s
print(estimate_latency(2000))   # ≈ 25.6 s
```

The single biggest lever on response time is usually **how many tokens you ask the model to write**. Streaming (Level 2)
doesn't reduce total time, but it lets users read from TTFT onward.

## The KV cache

During attention every token needs the keys and values of all earlier tokens. Recomputing them for the whole sequence at
every decode step would be wasteful, so the server stores them in a **KV cache**: computed once at prefill, then extended
by one entry per new token. Each decode step only computes the new token's query, key and value and reads the rest
from the cache.

Consequences:

- Decode stays roughly constant cost per token instead of growing with each step's full recomputation.
- The cache takes GPU memory proportional to context length × layers × batch size. Long contexts limit how many requests
  a server can run at once, which is part of why long-context calls cost more.
- Providers can keep the KV cache for a common prompt prefix across requests. That is **prompt caching** (Level 3): a
  repeated system prompt or document is billed at a discount and has lower TTFT.

## Why this drives cost and speed

- **Long prompts** raise TTFT and input cost, and use cache memory.
- **Long outputs** dominate total latency and cost more per token.
- **Reasoning models** (1.7) generate many hidden thinking tokens before the answer. Those are decode tokens: you wait for
  them and you are billed for them, usually as output.
- **Throughput tricks** on the server (batching many users together, speculative decoding, paged KV memory) explain
  why the same model is faster from one provider than another.

## Try it

Call any chat API twice with the same short question: once asking for "one sentence", once for "a 600-word essay".
Measure TTFT (with streaming) and total time. Compute output tokens per second for each.

<details>
<summary>Reference</summary>

```python
import time
from openai import OpenAI
client = OpenAI()

def timed(prompt):
    t0 = time.perf_counter(); first = None; text = ""
    stream = client.chat.completions.create(
        model="gpt-4o-mini",  # any chat model you have access to
        messages=[{"role": "user", "content": prompt}], stream=True)
    for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            first = first or time.perf_counter()
            text += chunk.choices[0].delta.content
    total = time.perf_counter() - t0
    return first - t0, total, len(text.split())

print(timed("Explain DNS in one sentence."))
print(timed("Explain DNS in a 600-word essay."))
```

TTFT is similar for both because the inputs are nearly the same. Total time is many times longer for the essay, roughly
in proportion to its length, because decode is sequential. Tokens per second should be in the same range for both.
</details>

## Check yourself

1. Why does a 2,000-token answer take far longer than a 50-token one with the same prompt?

<details>
<summary>Answer</summary>

Output tokens are generated one at a time, each needing a pass through the model. Prefill time is the same; decode time
scales with the number of output tokens.
</details>

2. What does the KV cache store, and what does it cost?

<details>
<summary>Answer</summary>

The keys and values of every previous token at every layer, so they aren't recomputed each step. It costs GPU memory
that grows with context length, which limits concurrency on long contexts.
</details>

3. Users complain the app "takes forever to start answering". Which metric, and what would you try?

<details>
<summary>Answer</summary>

TTFT. Shorten or cache the prompt prefix, pick a faster model or provider, check queueing, and make sure you stream so
users see the first tokens as soon as they arrive.
</details>
