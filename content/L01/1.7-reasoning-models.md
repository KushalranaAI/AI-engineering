# Reasoning models

Some models are trained to work through a problem before they answer: they generate a long internal chain of reasoning,
check themselves, backtrack, and only then write a reply. On hard problems this can be the difference between wrong and
right. On easy ones it just makes you wait and pay more.

## Thinking before answering

A standard chat model starts producing its answer immediately. A **reasoning model** first produces **reasoning tokens**
(sometimes shown to you, often summarised or hidden), then the final answer. Labs train this behaviour mostly with
reinforcement learning on problems with checkable answers (maths, code with tests, logic puzzles): the model is rewarded
when its final answer is correct, and it learns that longer, more careful reasoning earns more reward.

The general idea is **test-time compute**: instead of only making the model bigger at training time, spend more
computation per question at inference time. Earlier, people got part of this effect by prompting "let's think step by
step" (chain-of-thought prompting). Reasoning models have the habit trained in and do it far more effectively.

## Controls and budgets

Providers expose this as a dial rather than raw sampling settings:

| Control | Example form | Effect |
|---|---|---|
| Reasoning effort | `low` / `medium` / `high` | More effort, more thinking tokens |
| Thinking budget | A max number of thinking tokens | Caps spend on reasoning |
| On/off | Hybrid models with thinking enabled or disabled per request | Same model, fast or careful mode |

Parameter names differ by provider and change between API versions; check the current docs. Two things are constant:
**reasoning tokens are billed** (usually at the output-token rate), and **they add latency** because they are generated
one by one before the answer. A response with 150 visible tokens may have used 5,000 tokens of thinking.

## Where it helps and where it doesn't

| Likely worth it | Usually not worth it |
|---|---|
| Hard maths and quantitative problems | Sentiment or topic classification |
| Debugging, multi-file code changes, algorithm design | Extracting fields from a document |
| Planning with many steps or constraints | Rewriting, translating, tone changes |
| Logic puzzles, scheduling, constraint satisfaction | Straightforward summaries |
| Ambiguous analysis where checking your own work matters | Chit-chat, simple lookups from provided text |

A quick test: if a careful human would need scratch paper, reasoning probably helps. If they'd answer at a glance, it
probably doesn't.

## The trade-off

```
quality ↑   as reasoning effort ↑
cost    ↑   (more output tokens billed)
latency ↑   (seconds to minutes of thinking before the first visible token)
```

Diminishing returns are typical: going from no reasoning to low effort often helps a lot on hard tasks; going from high
to maximum helps less and costs a lot more. Measure on your own problems; for a user-facing chat a 30-second pause may be
unacceptable even if accuracy rises.

## Prompting reasoning models

Old habits can backfire. With reasoning models:

- **Don't micromanage the thinking.** "Think step by step" or a long scripted procedure is unnecessary and can constrain
  the model's own better approach.
- **State the goal precisely.** What problem, for whom, what result.
- **Give the relevant context** and nothing extra.
- **List constraints** (time limits, libraries allowed, format).
- **Say what a good answer looks like**: acceptance criteria, tests it must pass, how it will be checked.

```python
prompt = """Goal: schedule 6 interviews (list below) into Tuesday 09:00-17:00.
Constraints: each is 45 min; 15 min gap between interviews in the same room;
rooms A and B; Priya can't do before 11:00; lunch 12:30-13:15 no interviews.
Output: a table of time, room, candidate. If impossible, say which constraint breaks."""

from openai import OpenAI
resp = OpenAI().responses.create(
    model="o4-mini",                  # an example reasoning model
    reasoning={"effort": "medium"},
    input=prompt,
)
print(resp.output_text)
print(resp.usage)                     # look for reasoning tokens in the output details
```

## Try it

Take five problems: two multi-step word problems, one tricky scheduling puzzle, and two simple sentiment labels. Run each
on a fast general model and on a reasoning model. Record correctness, latency and tokens billed.

<details>
<summary>Reference</summary>

Expected pattern: the reasoning model gets the word problems and the scheduling puzzle right more often, but takes several
times longer and bills many more output tokens (check the usage object for reasoning tokens). On the sentiment labels
both are correct and the reasoning model is simply slower and dearer. The lesson is to route: send hard tasks to a
reasoning model (or higher effort) and keep easy ones on a fast model.
</details>

## Check yourself

1. Why does a reasoning model's bill often exceed what its visible answer suggests?

<details>
<summary>Answer</summary>

It generates reasoning tokens before the answer, and those are billed (usually as output) even if hidden.
</details>

2. Give one task where you'd turn reasoning off or down, and why.

<details>
<summary>Answer</summary>

Extracting fields from an invoice, classifying tickets, or rewriting text: the answer doesn't need multi-step work, so
extra thinking adds cost and latency without improving quality.
</details>

3. How should a prompt for a reasoning model differ from an old chain-of-thought prompt?

<details>
<summary>Answer</summary>

Drop the "think step by step" scaffolding and instead state the goal, context, constraints and success criteria clearly;
let the model choose how to reason.
</details>
