# Sampling and generation settings

The model gives you a probability for every possible next token. Something still has to pick one. That choice, the
**sampling** strategy, is what the knobs on an API call control. Set them for the task, not by habit.

## From probabilities to a token

The model outputs raw scores (**logits**), which softmax turns into probabilities. Then:

- **Greedy decoding**: always take the most likely token. Repeatable, but can be dull or get stuck in loops.
- **Sampling**: draw a token at random, weighted by probability. Varied, sometimes surprising.

The settings below reshape or trim the distribution before the draw.

## The knobs

| Setting | What it does | Typical use |
|---|---|---|
| `temperature` | Divides logits before softmax. Below 1 sharpens the distribution (more predictable), above 1 flattens it (more random). 0 behaves like greedy. | 0-0.3 for extraction; 0.7-1.0 for ideas |
| `top_p` (nucleus) | Keep the smallest set of tokens whose probabilities add up to p, drop the rest | 0.9-1.0; adjust this or temperature, not both |
| `top_k` | Keep only the k most likely tokens | Exposed by some APIs and local runtimes |
| `max_tokens` | Hard cap on output length | Cost and latency control; too low truncates answers |
| `stop` | Strings that end generation when produced | Stop at a delimiter in structured or few-shot outputs |
| `frequency_penalty`, `presence_penalty`, `repetition_penalty` | Lower the score of tokens already used | Reduce repetition in long outputs |

```python
import numpy as np

logits = np.array([4.0, 3.0, 2.0, 0.5])          # scores for 4 candidate tokens
tokens = ["Paris", "Lyon", "France", "banana"]

def probs(logits, temperature):
    z = logits / temperature
    e = np.exp(z - z.max())
    return e / e.sum()

for t in (0.2, 0.7, 1.0, 1.5):
    print(t, dict(zip(tokens, probs(logits, t).round(3))))
# 0.2 → Paris ~0.99           (almost greedy)
# 1.5 → Paris ~0.53, banana ~0.05 (long tail gets a real chance)
```

Higher temperature does not make a model smarter or more creative in any deep sense; it just gives lower-ranked tokens
a better chance. Past about 1.2 that often means nonsense.

## Matching settings to the task

| Task | Suggested start | Why |
|---|---|---|
| Field extraction, classification, JSON output | temperature 0-0.2 | You want the single most likely answer every time |
| Factual Q&A over provided text | 0-0.3 | Fewer creative detours from the source |
| Summaries, rewrites | 0.3-0.7 | Some fluency, little invention |
| Brainstorming, names, marketing copy | 0.8-1.0 | Variety across runs is the point |
| Generating many diverse candidates to rank later | 1.0 with n > 1 | Spread out the samples |

Then measure. Note that **temperature 0 is not a guarantee of identical output**: batching and floating-point effects on
the server can still change results, and some providers say so explicitly. If you need reproducibility, store outputs.

## Provider differences

APIs don't expose the same controls. One may offer `top_k` and another not; some cap temperature at 1, others at 2;
penalty parameters exist on some and not others. **Reasoning models** frequently fix or ignore temperature and top-p,
since the provider tunes sampling for the hidden reasoning; you control them with reasoning-effort or thinking-budget
settings instead (next module). Always check the current API reference for the model you call, and expect a request to
be rejected if you send an unsupported parameter.

## Try it

Pick a model and ask: "Suggest a name for a budgeting app for students." Run it five times each at temperature 0, 0.7 and
1.3. Then ask "What is 17 × 23? Reply with the number only." five times at 0 and 1.3. Record distinct answers and
correctness.

<details>
<summary>Reference</summary>

```python
from openai import OpenAI
client = OpenAI()

def runs(prompt, temp, n=5):
    return [client.chat.completions.create(
        model="gpt-4o-mini", temperature=temp,
        messages=[{"role": "user", "content": prompt}],
    ).choices[0].message.content.strip() for _ in range(n)]

for t in (0, 0.7, 1.3):
    print(t, runs("Suggest a name for a budgeting app for students.", t))
```

At 0 you get the same or nearly the same name each time; at 0.7 some variety; at 1.3 lots of variety and occasionally
odd names. For the arithmetic, temperature 0 should give 391 consistently, while 1.3 may occasionally produce a wrong
number. Randomness helps where many answers are acceptable and hurts where exactly one is right.
</details>

## Check yourself

1. You're extracting invoice totals into JSON. What temperature would you start with, and why?

<details>
<summary>Answer</summary>

0 or close to it. There is one correct value, so you want the most likely token every time and as little variation as
possible.
</details>

2. What does `top_p=0.9` do?

<details>
<summary>Answer</summary>

It keeps only the most likely tokens whose probabilities together reach 90%, discards the long tail, renormalises, and
samples from what remains.
</details>

3. Your code sets `temperature=0.2` on a reasoning model and the API returns an error. What's going on?

<details>
<summary>Answer</summary>

Many reasoning models don't support traditional sampling parameters. Remove them and use the model's reasoning-effort or
thinking-budget controls instead.
</details>
