# Choosing a model

"Which model should we use?" is one of the most common questions you'll be asked, and "the one at the top of the
leaderboard" is the most common wrong answer. Model choice is an engineering decision: requirements first, measurements
second, preferences last.

## Eight things to check

| Dimension | Question | How to find out |
|---|---|---|
| Capability | Can it do the task at all? | A handful of quick tries |
| Quality | How reliably does it do *your* task? | Your own test set |
| Latency | Is TTFT and total time acceptable? | Measure p50 and p95 with real prompts |
| Cost | What does a request cost at expected volume? | Token counts × prices, measured |
| Context | Does the input fit, with room to spare? | Token-count real inputs |
| Modalities | Text only, or images, audio, PDFs, video? | Model card |
| Privacy and deployment | External API OK, or must it run in your cloud or on your hardware? | Legal, security, model availability |
| API features | Structured output, tool calling, streaming, caching, batch? | API docs |

Some are hard filters (deployment, modality, context, features): fail one and the model is out. Others are trade-offs
(quality, latency, cost) you balance.

## Reading the fine print

- **Model cards**: check training cutoff, context length, supported languages, known limitations, and for open models
  total vs active parameters and licence.
- **Benchmark tables**: note which settings were used (reasoning effort, number of attempts) and who ran them.
- **Pricing pages**: input vs output vs cached input prices; separate rates for reasoning tokens, long contexts above a
  threshold, batch discounts, and per-image or per-second audio charges.
- **Context specs**: maximum input and maximum output are different limits.
- **API docs**: which parameters are supported for this specific model; rate limits for your account tier.

## Why benchmarks aren't enough

Benchmarks (1.11) measure someone else's tasks under someone else's settings. They can't tell you how a model handles
your formats, your edge cases, your language mix or your latency budget. They're useful only to build the shortlist.

## A repeatable process

```
define task → list requirements → shortlist 3-5 → test on your examples
  → measure quality → measure latency → measure cost → read the failures → choose
```

A minimal harness:

```python
import time, statistics

def evaluate(model, examples, price_in, price_out):
    scores, latencies, cost = [], [], 0.0
    for ex in examples:
        t0 = time.perf_counter()
        resp = call_model(model, ex["input"])           # your provider wrapper
        latencies.append(time.perf_counter() - t0)
        scores.append(grade(resp.text, ex["expected"]))  # exact match, rubric, or a checker
        cost += resp.input_tokens * price_in + resp.output_tokens * price_out
    return {
        "model": model,
        "accuracy": sum(scores) / len(scores),
        "p50_s": statistics.median(latencies),
        "p95_s": statistics.quantiles(latencies, n=20)[-1],
        "cost_per_1k_requests": 1000 * cost / len(examples),
    }
```

Then **read the failures**, not just the score. Two models at 90% may fail on completely different cases; one set of
failures might be harmless formatting quirks, the other wrong numbers.

A worked example for a ticket-triage feature (illustrative numbers):

| Model | Accuracy | p95 latency | Cost / 1k requests | Notes |
|---|---|---|---|---|
| Large frontier model | 96% | 3.1 s | $4.20 | Best quality |
| Mid-size model | 94% | 1.2 s | $0.60 | Misses mostly in an ambiguous category |
| Small open model (hosted) | 88% | 0.5 s | $0.08 | Struggles with multilingual tickets |

If triage errors are cheap (a human re-routes them) and volume is high, the mid-size model is likely the pick. If
mistakes are costly, the large one may be worth seven times the price. The decision depends on the business, which is why
you measure rather than guess. Keep the harness: you'll rerun it whenever a new model or version appears.

## Try it

Choose a task (for example, turning customer emails into a JSON with `intent`, `urgency` and `order_id`). Write the
requirements for each of the eight dimensions, decide which are hard filters, and shortlist three models.

<details>
<summary>Reference</summary>

Example: Capability and quality: must extract all three fields correctly on at least 95% of real emails. Latency: under
2 s p95, since it runs in a background queue (soft). Cost: under $1 per 1,000 emails at 50k emails/day (soft but
important). Context: emails up to ~3k tokens, so any modern model passes. Modalities: text only, maybe PDF attachments
later. Privacy: customer data, so either an API with suitable data terms or a managed platform in your cloud (hard
filter). Features: native structured output strongly preferred (hard filter for reliability). Shortlist: one mid-size
closed model, one small closed model, one open model on a managed platform; then run all three through a harness like
the one above on 50+ real emails.
</details>

## Check yourself

1. Which of the eight dimensions are usually hard filters rather than trade-offs?

<details>
<summary>Answer</summary>

Privacy and deployment, modalities, context size, and required API features. Failing any of them rules a model out
regardless of quality.
</details>

2. Two models score 91% and 93% on your test set. What else do you look at before choosing?

<details>
<summary>Answer</summary>

The failures themselves (how severe and which categories), latency (especially p95), cost at expected volume, and
whether the difference is meaningful given the test set size.
</details>

3. Why keep your evaluation harness after choosing?

<details>
<summary>Answer</summary>

Models get updated, deprecated and superseded. Re-running the same harness lets you compare a new model or version
against the current one quickly and safely.
</details>
