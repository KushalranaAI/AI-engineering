# What an LLM is

Strip away the chat window and an LLM does one thing: given some text, it produces a probability for every possible next
piece of text. Everything else, from answering questions to writing code, comes from running that one step in a loop.
If you hold on to this picture, a lot of odd behaviour later in the path stops being mysterious.

## One step, repeated

The model reads a sequence of **tokens** (word pieces, covered in the next module) and outputs a probability
distribution over its whole vocabulary, often 100,000 to 250,000 entries.

```
Input:  "The capital of France is"
Output: " Paris" 0.92   " a" 0.02   " the" 0.01   " located" 0.008  ...
```

Generation is a loop around that step:

1. **Predict**: compute next-token probabilities for the text so far.
2. **Choose**: pick one token (the most likely, or a weighted random draw).
3. **Append**: add it to the text.
4. **Repeat** until a stop token or a length limit.

```python
def generate(model, prompt_tokens, max_new=50):
    tokens = list(prompt_tokens)
    for _ in range(max_new):
        probs = model.next_token_probs(tokens)   # one forward pass
        nxt = sample(probs)                      # choose
        if nxt == model.eos_id:                  # end-of-sequence token
            break
        tokens.append(nxt)                       # append and loop
    return tokens
```

There is no separate "answering" module. A reply to "Summarise this email" is just the continuation the model finds most
plausible after that request, one token at a time. Each new token is conditioned on everything before it, including the
tokens the model itself just wrote, which is why an early mistake tends to snowball.

## What it is not

| It is not... | Because... |
|---|---|
| A database | Nothing is stored as rows you can look up. Facts are smeared across billions of numeric weights and recalled imperfectly. |
| A search engine | It does not fetch documents at answer time unless your application gives it a search tool. Its knowledge stops at its training data. |
| A deterministic function | With sampling switched on, the same prompt can give different outputs. Even at temperature 0, providers do not always guarantee identical results. |
| A store of canned answers | It composes new text on every call, so it can produce fluent sentences nobody ever wrote, true or not. |

This is the engineering consequence: you treat model output as a *plausible draft* that your code may need to check, not
as a lookup result.

## Why one model does many tasks

Predicting the next token well, across trillions of tokens of web pages, books, code and dialogue, forces the model to
pick up grammar, facts, styles, translation pairs, programming patterns and common reasoning moves. All of those help with
prediction. So a single model can:

- summarise (the continuation of "TL;DR:" is a summary),
- translate (the continuation of "In French:" is French),
- classify (the continuation of "Sentiment:" is a label),
- write code, answer questions, extract fields.

The task is specified by the text you give it, not by a different program. That is why the prompt matters so much.

## Where capability comes from

Models have improved along four levers that tend to compound:

- **Data**: more tokens, and above all better-filtered, more diverse and higher-quality tokens (including code and
  synthetic data).
- **Compute**: more training compute lets a model learn more from the data.
- **Size**: more parameters give more capacity to store patterns.
- **Training method**: better post-training (instruction tuning, preference and reinforcement learning) turns raw
  capability into useful behaviour.

Scaling-law research showed that loss falls predictably as data, parameters and compute grow together, and that many
early models were too big for the amount of data they were trained on. For you as an engineer, the useful takeaway is:
a newer, smaller model trained on better data can beat an older, larger one, so size alone tells you little.

## Try it

Ask any chat model the same open prompt five times, for example "Give me a name for a coffee shop run by robots."
Then, before sending "The opposite of hot is", write down the next word you expect. Explain what you observe.

<details>
<summary>Reference</summary>

The coffee-shop names differ across runs because the model samples from a distribution with many reasonable options;
no single continuation dominates. For "The opposite of hot is" almost every run says "cold": the distribution is so
peaked on one token that sampling nearly always picks it. Variation is therefore a property of how spread out the
distribution is, not a sign the model is "confused". You predicted the word the same way the model does, from patterns
you have seen many times.
</details>

## Check yourself

1. Describe in one sentence how an LLM produces a 100-word answer.

<details>
<summary>Answer</summary>

It repeatedly predicts a probability distribution for the next token given everything so far, picks one token, appends
it and repeats until it emits a stop token or hits a length limit.
</details>

2. Why is it risky to treat an LLM like a database of facts?

<details>
<summary>Answer</summary>

It has no exact records to look up. It generates likely text from patterns in its weights, so it can produce a fluent,
specific and wrong answer, and its knowledge stops at its training cutoff.
</details>

3. A colleague says "we need a separate model for summarising and another for classification." What would you check
   first?

<details>
<summary>Answer</summary>

Whether one general model, prompted for each task, already meets the quality, cost and latency needs. A single LLM
handles both because the task is defined by the input text. Separate models only make sense if measurement shows a
cheaper or specialised one does better.
</details>
