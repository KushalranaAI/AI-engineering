# Inside the model: embeddings, attention, transformers

You don't need the matrix maths to be a good AI engineer, but you do need a clear picture of the pipeline. It explains
why context is expensive, what "70B" means for your hosting bill, and why some huge models run cheaply.

```
text → tokens → embeddings → [transformer layer × N] → next-token probabilities
```

## From token ids to vectors

Each token id indexes a row in an **embedding table**: a learned vector of a few thousand numbers. Think of the vector
as coordinates in a space where related meanings sit near each other. A position signal is added (modern models
usually use rotary position encodings) so the model knows word order.

The vectors then pass through dozens of identical **transformer layers**. Each layer updates every token's vector by
mixing in information from other tokens (attention) and then transforming it (a feed-forward network). Early layers
capture surface features such as syntax; later layers carry more abstract meaning. At the end, the last token's vector
is projected onto the vocabulary to give next-token probabilities.

## Parameters and size

**Parameters** are the learned numbers: embedding tables, attention weights, feed-forward weights. "8B" means about
8 billion of them. Size drives memory directly:

| Model size | Memory for weights at 16-bit (2 bytes) | At 4-bit quantisation |
|---|---|---|
| 8B | ~16 GB | ~4-5 GB |
| 70B | ~140 GB | ~35-40 GB |
| 400B | ~800 GB | ~200 GB |

(Plus extra memory for the KV cache during inference, covered in 1.5.)

More parameters mean more capacity, but not automatically a better model. Training data quality, amount of training,
and post-training matter as much. A well-trained 8B model can beat an older 70B one on many tasks, and it is far cheaper
to run.

## Attention, intuitively

Consider: *"The animal didn't cross the street because it was tired."* To understand "it", the model needs to connect it
to "animal", not "street". **Attention** lets each token look at the other tokens and pull in information from the ones
that matter for its meaning.

Mechanically, each token's vector produces three vectors:

- **Query**: what am I looking for?
- **Key**: what do I contain, for others searching?
- **Value**: what do I pass on if someone attends to me?

A token compares its query with every key; high matches get high weights (via softmax), and the token takes a weighted
mix of the values. Many **attention heads** run in parallel, each learning different relationships (grammar, coreference,
position).

```python
import numpy as np

def attention(Q, K, V):
    scores = Q @ K.T / np.sqrt(K.shape[-1])          # how well each query matches each key
    n = scores.shape[0]
    scores[np.triu_indices(n, k=1)] = -np.inf         # causal mask: no peeking at later tokens
    w = np.exp(scores - scores.max(axis=-1, keepdims=True))
    w /= w.sum(axis=-1, keepdims=True)                # softmax → weights per row sum to 1
    return w @ V                                      # weighted mix of values
```

**Causal** attention means a token can only see itself and earlier tokens, which matches generation: when predicting
token 10, tokens 11 onward don't exist yet. Because every token attends to every earlier token, the work grows roughly
with the square of the sequence length, one reason long contexts are costly.

## Dense vs mixture-of-experts

In a **dense** model every parameter is used for every token. In a **mixture-of-experts (MoE)** model, each layer's
feed-forward block is split into many "experts" and a small **router** sends each token to only a few of them (say 2 of
64). Attention is usually still shared.

This separates two numbers you will see on model cards:

- **Total parameters**: everything that must sit in memory.
- **Active parameters**: what is actually computed per token.

An MoE with 400B total and 17B active needs memory like a 400B model but spends compute per token closer to a 17B model.
Names like "8x7B" mean 8 experts built on a 7B-sized design; the total is less than 56B because attention and embeddings
are shared. Practical upshot: MoE models are fast and cheap per token once loaded, but hard to self-host because you
still need enough GPU memory for all the experts. Most frontier and many open-weight models now use MoE.

## Try it

Open an attention visualiser (for example BertViz in a notebook, or any online transformer explainer) on *"The animal
didn't cross the street because it was tired."* Then change "tired" to "wide". What should "it" attend to in each case?

<details>
<summary>Reference</summary>

With "tired", "it" should attend mainly to "animal" (animals get tired). With "wide", it should shift towards "street".
In real models you'll find some heads in middle layers that show this clearly and many that do something else entirely;
attention is spread across many heads and layers, so no single map is "the" explanation. The exercise shows that a
token's meaning is built from context, and that a single word later in the sentence can change which earlier tokens matter.
</details>

## Check yourself

1. Why does a model's attention cost grow so quickly with prompt length?

<details>
<summary>Answer</summary>

Each token compares its query against the keys of every earlier token, so the number of comparisons grows roughly with
the square of the sequence length.
</details>

2. A model card says 120B total, 5B active. What does that tell you about hosting and speed?

<details>
<summary>Answer</summary>

It is an MoE. You must hold all 120B parameters in memory, but each token only uses about 5B worth of compute, so
generation is fast and cheap per token relative to its size.
</details>

3. What does "causal" mean in causal attention, and why is it needed?

<details>
<summary>Answer</summary>

Each token can only attend to itself and earlier tokens. The model is trained to predict the next token, so letting it
see future tokens would let it cheat, and at generation time those tokens don't exist yet.
</details>
