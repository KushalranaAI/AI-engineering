# Tokens

You pay for tokens, your context window is measured in tokens, and latency grows with tokens. Yet a token is neither a
character nor a word. Knowing what it actually is explains your API bill and a handful of strange model failures.

## Characters, words, tokens

A **tokenizer** converts text into a list of integers (token ids) from a fixed vocabulary before the model sees anything.
Most modern tokenizers use a variant of **byte-pair encoding (BPE)**: start from bytes, then repeatedly merge the most
frequent adjacent pairs found in training text into new vocabulary entries. Common words become one token; rare words
are split into several pieces.

```python
import tiktoken   # pip install tiktoken

enc = tiktoken.get_encoding("o200k_base")   # an OpenAI encoding
for text in ["hello", "unbelievably", "Kubernetes", "1234567", "  indent"]:
    ids = enc.encode(text)
    print(f"{text!r:16} {len(ids)} tokens  {[enc.decode([i]) for i in ids]}")
```

Typical output looks like `'unbelievably' 2 tokens ['un', 'believably']`. The exact splits depend on the tokenizer, and
**every model family has its own**. The same paragraph might be 100 tokens for one model and 120 for another, so token
counts and prices are not directly comparable across providers. Use the provider's own token-counting endpoint or library
when you need exact numbers.

Why not just use characters or words? Characters make sequences very long (slow and expensive, since cost grows with
length). Whole words make the vocabulary huge and can't handle new words. Sub-word tokens are the compromise: short
sequences, a bounded vocabulary, and any string can still be encoded.

## How different text tokenizes

Tokenizers are trained mostly on English and code, so other content is less efficient. A rough picture:

| Text | Rough tokens per word or item | Why |
|---|---|---|
| Plain English prose | ~1.3 per word (about 4 characters per token) | Common words are single tokens |
| Rare or technical words | 2-4 per word | Split into fragments |
| Numbers | Varies; long numbers split into chunks of digits | Digits grouped inconsistently |
| Source code | Often more than prose | Whitespace, symbols and identifiers |
| Emoji | Several tokens each | Multi-byte characters |
| Hindi, Tamil, Amharic and many non-Latin scripts | Often 2-5x English for the same meaning | Less training text, so fewer merges |
| Mixed Hindi-English (Hinglish) | Between the two | Latin-script parts compress better |

Newer tokenizers have larger vocabularies and treat non-English text better than older ones, but the gap rarely
disappears. Measure your own data.

## Why tokens matter to an engineer

- **Cost**: APIs charge per input token and per output token (output usually costs several times more). A product used
  in a language that needs 3x the tokens costs about 3x as much to serve.
- **Context**: limits like "200k tokens" include the system prompt, history, documents and the answer. Token-hungry text
  fills it faster.
- **Latency**: output tokens are generated one at a time, so longer outputs mean slower responses.
- **Odd failures**: the model sees `"strawberry"` as a few tokens, not ten letters, so counting letters or reversing a
  string is surprisingly hard. Numbers split into arbitrary digit groups make arithmetic error-prone.

A quick estimate you can do in your head:

```
monthly cost ≈ requests × (input_tokens × input_price + output_tokens × output_price)

e.g. 100,000 requests × (1,500 in × $1/M + 300 out × $4/M)
   = 100,000 × ($0.0015 + $0.0012) = $270 / month       (example prices only)
```

## Try it

Using `tiktoken` (or a provider's token counter), count tokens for: an English paragraph of about 100 words, a Hindi
translation of it (use any translator), a 15-line Python function, and a list of 50 random 6-digit numbers. Compute tokens
per character for each.

<details>
<summary>Reference</summary>

```python
import tiktoken
enc = tiktoken.get_encoding("o200k_base")
samples = {"english": en, "hindi": hi, "code": code, "numbers": nums}
for name, text in samples.items():
    n = len(enc.encode(text))
    print(f"{name:8} chars={len(text):5} tokens={n:5} tokens/char={n/len(text):.2f}")
```

Expect English to be the most efficient (roughly 0.25 tokens per character), code and numbers somewhat worse, and Hindi
noticeably worse in tokens per unit of meaning, though modern large-vocabulary tokenizers narrow the gap. The exact
figures depend on the encoding, which is the point: measure with the tokenizer of the model you will actually use.
</details>

## Check yourself

1. Two support replies have 200 words each, one in English and one in Hindi. Why might the Hindi one cost more?

<details>
<summary>Answer</summary>

The tokenizer was trained on mostly English text, so it learned fewer merges for Devanagari and splits Hindi into more,
smaller tokens. Pricing is per token, so the same meaning costs more.
</details>

2. Why does an LLM sometimes miscount the letters in a word?

<details>
<summary>Answer</summary>

It never sees individual letters, only token ids for multi-character chunks. Spelling details have to be inferred
indirectly, which is unreliable.
</details>

3. Can you compare two providers' prices per million tokens directly?

<details>
<summary>Answer</summary>

Only roughly. Each uses a different tokenizer, so the same text yields different token counts. Compare the cost of
processing a sample of your real inputs and outputs instead.
</details>
