# The context window

The context window is the model's entire working view for one request: every token it can see while producing an
answer. It is not memory and not knowledge, and a bigger one is not automatically better. Most of your design choices
around LLM features are really choices about what goes into this window.

## What fills it

A limit such as "200k tokens" covers everything in the request and the response:

| Occupant | Typical size | Notes |
|---|---|---|
| System prompt | 200-3,000 tokens | Sent on every call |
| Tool definitions | 100-500 per tool | Easy to forget; dozens of tools add up |
| Conversation history | Grows each turn | The API is stateless, so you resend it all |
| Retrieved documents or files | 1,000-100,000+ | Usually the biggest item |
| Few-shot examples | 200-2,000 | |
| Tool results | Anything; a raw API response can be huge | |
| The model's output (and reasoning tokens) | Up to max output | Counts against the same window |

```python
def fits(system, history, docs, question, max_output, window=200_000, count=lambda s: len(s) // 4):
    used = count(system) + sum(count(m) for m in history) + sum(count(d) for d in docs) + count(question)
    return used + max_output <= window, used

ok, used = fits(sys_prompt, chat_history, retrieved, user_q, max_output=4_000)
print(ok, used)   # rough estimate; use the provider's token counter for exact numbers
```

## Context, knowledge and memory

Three different things often get blurred:

- **Model knowledge**: what was learned in training and lives in the weights. Fixed, possibly stale, recalled imperfectly.
- **Context**: what is in this request right now. Precise and current, but gone after the call.
- **Long-term memory**: anything your application stores (database, vector index, user profile) and chooses to put back
  into context later. The model itself remembers nothing between calls.

If you want the model to "know" a customer's order history, it has to be in the context of that call. Products that
appear to remember you are simply re-inserting saved information.

## What goes wrong with long contexts

- **Truncation**: exceed the limit and the API either errors or (in some frameworks) silently drops the oldest
  messages, often including important instructions.
- **Lost in the middle**: models tend to use information at the beginning and end of a long input more reliably than
  information buried in the middle.
- **Dilution and distraction**: irrelevant text competes for attention. Adding 50 loosely related documents can make
  answers worse than adding the 3 right ones.
- **Cost and latency**: every token is processed (and billed) on every call. A 100k-token prompt on each turn of a chat
  adds up fast.

## Big window, uneven use

Advertised windows of hundreds of thousands to millions of tokens tell you what the model *accepts*, not how well it
*uses* it. Simple "needle in a haystack" tests (find one planted sentence) are passed by most modern models; harder tests
that require combining several facts spread through a long input, or reasoning over them, show performance dropping as
length grows. Effective context is usually much shorter than the maximum.

So the engineering question is rarely "which model has the biggest window?" but "what is the smallest set of tokens
that lets the model do this task well?" That is the seed of retrieval (Level 4) and context engineering (Level 6).

## Try it

Take a long document (30-50k tokens, such as a long report). Insert a specific fact ("The project codename is BLUE
HERON.") at 5%, 50% and 95% of the way through. Each time ask "What is the project codename?" plus a second question that
requires combining the codename with another detail elsewhere in the document. Compare.

<details>
<summary>Reference</summary>

Current strong models will usually find the single fact in all three positions; the simple lookup is no longer a hard
test. The combined question is where differences show: accuracy tends to drop when the fact is in the middle, and drops
further with longer documents or weaker models. Repeat each case a few times since results vary. The takeaway: a model
that accepts your whole document may still use parts of it poorly, so put critical instructions and facts at the start or
end, and prefer sending less, better-chosen text.
</details>

## Check yourself

1. Your chatbot "forgets" the user's name after a long conversation. What are two likely causes?

<details>
<summary>Answer</summary>

The history was truncated to fit the window (dropping the early turn with the name), or the name is still present but
buried in the middle of a long context where the model attends to it less reliably.
</details>

2. What's the difference between context and model knowledge?

<details>
<summary>Answer</summary>

Knowledge is learned into the weights during training and is fixed and possibly outdated. Context is the text in the
current request: up to date and exact, but only present for that call.
</details>

3. A model supports 1M tokens. Why might you still send only 20k?

<details>
<summary>Answer</summary>

Cost and latency scale with input size, and quality often drops with more irrelevant text. Choosing the relevant 20k
usually gives better, cheaper, faster answers.
</details>
