# The model landscape

There are hundreds of models and new ones every week. You don't need to track them all; you need a map of the
categories and the trade-offs each one carries, so you can place any new release on it in a minute.

## Three ways to get a model

| | Closed API models | Open-weight, self-hosted | Managed platforms and hosted open models |
|---|---|---|---|
| Examples (illustrative) | OpenAI GPT, Anthropic Claude, Google Gemini via their APIs | Llama, Qwen, Mistral, DeepSeek, Gemma weights on your GPUs | Bedrock, Vertex AI, Azure AI Foundry; inference providers such as Together or Fireworks |
| Capability | Usually the frontier | Strong and closing the gap, especially per dollar | Whatever they host, closed or open |
| Effort to start | An API key | GPUs, a serving stack (vLLM, SGLang, llama.cpp), ops | An account; often inside your existing cloud |
| Data control | Leaves your network (with contractual protections) | Never leaves | Stays in your cloud account or the host's |
| Customisation | Prompting, some fine-tuning | Full: fine-tune, quantise, modify | Varies |
| Cost shape | Pay per token | Pay for hardware whether busy or idle | Per token, sometimes reserved capacity |
| Main risk | Vendor lock-in, model changes you don't control | Operational burden, under-used GPUs | Lag behind newest releases, platform quirks |

"Open-weight" means the trained weights are downloadable. It does not necessarily mean the training data or code are
open, nor that you may use it for anything.

## Other ways to slice models

- **Small vs large**: small models (1-15B parameters) are fast, cheap and can run on a laptop or phone; large ones handle
  harder tasks.
- **Dense vs mixture-of-experts**: covered in 1.3; affects memory needs and speed.
- **General vs specialised**: coding models, embedding models, rerankers, speech, vision, domain-tuned models.
- **Reasoning vs non-reasoning**: whether the model thinks before answering (1.7).
- **Text-only vs multimodal**: accepts images, audio, video or PDFs, and possibly produces them.

There is **no best model**, only a best model for a given workload, budget and constraint set. A small open model
classifying tickets at a tiny fraction of the cost can be the right answer even when a frontier model is slightly more
accurate.

## Knowledge cutoffs

Every model's knowledge stops at its **training cutoff**. Ask about anything later (a new library version, this
quarter's prices, yesterday's news) and it will either say it doesn't know or, worse, confidently describe an older
state of the world. Recent information has to come in through the prompt, retrieval or tools. Also note that a model may
not know its own cutoff precisely.

## Versions, snapshots and deprecations

Model names come in two flavours:

```python
# An alias: convenient, but the provider may point it at a newer model at any time.
model = "claude-sonnet-latest"   # illustrative alias form

# A pinned snapshot: same weights until it is retired.
model = "gpt-4o-2024-08-06"      # illustrative dated snapshot
```

In production, **pin a snapshot**, store the model id with every logged output, and re-run your tests before moving to a
new one. Providers retire old models on published schedules, typically with months of notice; subscribe to their
deprecation pages and plan migrations rather than discovering them in an outage. Behaviour can shift noticeably between
versions, even when benchmark scores improve.

## Licences

Before building on open weights, read the licence. Broadly:

| Licence type | Examples | What to watch |
|---|---|---|
| Permissive | Apache 2.0, MIT | Few restrictions; commercial use fine |
| Custom community licences | Some large-lab model licences | Usage policies, user-count thresholds, naming requirements |
| Non-commercial / research only | Various research releases | Can't ship in a paid product |

Also check rules on using a model's outputs to train other models. When in doubt, involve whoever handles legal review.

## Try it

You need a model to summarise internal HR documents for employees of a European company. Data must not leave your cloud
account in the EU, volume is moderate, and the team has no GPU experience. List which of the three access routes fit, and
what you'd check about any candidate model.

<details>
<summary>Reference</summary>

A managed platform in your existing cloud (for example Bedrock, Vertex AI or Azure AI Foundry, in an EU region) fits best:
data stays in your account and region, and nobody has to run GPUs. A closed API directly may be acceptable if its data
processing terms and EU residency options satisfy your legal team, but that needs checking. Self-hosting open weights
satisfies data control but adds operational burden the team isn't ready for. For any candidate check: availability in
your EU region, quality on a sample of your documents, multilingual support if staff write in several languages, context
length for long policies, licence (if open-weight), pricing at your volume, and the snapshot and deprecation policy.
</details>

## Check yourself

1. What does "open-weight" guarantee, and what doesn't it?

<details>
<summary>Answer</summary>

You can download and run the weights. It doesn't guarantee open training data or code, and the licence may still restrict
commercial use or how you use outputs.
</details>

2. Why should production code use a pinned model version rather than an alias?

<details>
<summary>Answer</summary>

An alias can be moved to a different model without notice, changing behaviour under you. A pinned snapshot stays the
same until retirement, so you can test before upgrading.
</details>

3. A model confidently describes a library's API incorrectly. What's a likely reason, and how do you fix it?

<details>
<summary>Answer</summary>

The library changed after the model's training cutoff. Put current documentation in the context (or give the model a docs
lookup tool) instead of relying on its memory.
</details>
