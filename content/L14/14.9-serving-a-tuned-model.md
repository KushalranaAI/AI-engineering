# Serving a tuned model

A tuned adapter on your laptop proves nothing to users. Serving it means choosing how the adapter and base model are packaged, putting it behind the same gateway as your other models, rolling it out carefully, and knowing when it needs retraining. The most common production failure here is boring: a template mismatch that makes a good tune behave badly.

## Separate adapter or merged weights

| | Keep adapter separate | Merge into base |
|-|----------------------|-----------------|
| Storage | Base once + small adapter per task | Full model copy per task |
| Loading | Base + adapter at runtime | Single model |
| Many tasks on one GPU | Yes (multi-LoRA) | No, one model per copy |
| Swapping versions | Load a new adapter | Redeploy the model |
| Inference overhead | Small | None |
| Needed for | vLLM multi-LoRA, serverless adapter hosts | GGUF export, runtimes without LoRA support |

## Save, load and merge

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

base = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B-Instruct", torch_dtype="bfloat16")
model = PeftModel.from_pretrained(base, "out/extract-v3")     # load adapter
merged = model.merge_and_unload()                              # fold B·A into W
merged.save_pretrained("models/extract-v3-merged")
AutoTokenizer.from_pretrained("out/extract-v3").save_pretrained("models/extract-v3-merged")
```

Merge onto a base loaded in 16-bit, not 4-bit. Then **re-run the eval** on the merged model and confirm it matches the adapter's numbers.

## Many adapters on one base with vLLM

vLLM can keep one copy of the base model in GPU memory and apply a different LoRA per request:

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --enable-lora --max-loras 4 --max-lora-rank 32 \
  --lora-modules extract-v3=./out/extract-v3 tone-v1=./out/tone-v1
```

Clients pick the adapter by model name through the OpenAI-compatible API (`model="extract-v3"`). Many tasks share one GPU instead of one GPU each. vLLM also supports loading adapters at runtime, which lets you add a new version without a restart (check the docs for the setting that enables it).

## Quantised export for local runtimes

For Ollama or llama.cpp, merge first, convert to GGUF, and quantise (for example a 4- or 5-bit variant). Quantisation can undo part of a fine-tune's gain, especially on precise formats, so **evaluate the quantised file** on the same test set, not just the 16-bit original.

## Managed adapter hosting

Several inference providers host LoRA adapters on shared base models and bill per token, often close to the base model's price. Compare with your own GPU:

- Low or bursty traffic: per-token hosting is usually cheaper than an idle GPU.
- Steady high traffic, strict data residency or custom runtimes: your own GPUs can win.

## Template, tokenizer and versions

Serve with exactly the tokenizer and chat template used in training. Ship the tokenizer files with the adapter, and add a startup check that renders a known example and compares it with the training-time rendering.

Version these together, as one release: base model revision, adapter, dataset version, training config, chat template, and eval results. Keep the previous release deployable so rollback is a config change.

## Rollout through the gateway

Your gateway already routes between providers. Add the tuned model as another route:

1. **Shadow**: send copies of real requests to the tune, log outputs, don't show them.
2. **Canary**: 5% of traffic, compare online metrics and sampled eval scores with the baseline.
3. **Ramp** to 25%, 50%, 100%, with a one-line rollback.

Track latency and cost per request against the prompted baseline it replaces; that's the business case.

## Retraining triggers

Write down in advance what causes a retrain:

- A new base model is clearly better on your eval.
- Input drift: the share of inputs unlike the training data grows.
- New failure cases accumulate past a threshold.
- The spec changes (new fields, new categories).

Every retrained version passes the same eval gate before rollout.

## Try it

Serve two adapters on one base model with vLLM. Send ten requests to each by model name. Then train or copy a "v2" of one adapter and swap it in without restarting the server.

<details>
<summary>Reference</summary>

Start vLLM with `--enable-lora` and both `--lora-modules`. Requests with `model="extract-v3"` and `model="tone-v1"` hit the same process and GPU. For the swap, enable runtime LoRA updating and use the load/unload adapter endpoints (or restart with the new path if runtime loading is off). Confirm by sending the same request before and after and checking eval output, and note that GPU memory barely changed.

## Check yourself

1. Why might you keep adapters separate instead of merging?

<details>
<summary>Answer</summary>

To serve many tasks or versions from one base model on one GPU, to swap versions without redeploying a full model, and to save storage.
</details>

2. The tuned model scored 91% offline but behaves erratically in production. What's the first thing to check?

<details>
<summary>Answer</summary>

That the serving stack uses the same chat template and tokenizer as training (and the same base revision and adapter version). Then check generation settings and any quantisation applied only at serving time.
</details>

3. Name two signals that should trigger retraining.

<details>
<summary>Answer</summary>

Any two of: a clearly better base model, drift in input distribution, accumulating new failure cases, or a changed task specification.
</details>
