# Supervised fine-tuning

Supervised fine-tuning (SFT) is the plain, workhorse kind of tuning: show the model inputs paired with the outputs you want, and adjust its weights so those outputs become more likely. Nearly every other technique in this level either builds on SFT or is compared against it.

## What SFT changes

A pretrained or instruction-tuned model already predicts the next token well. SFT runs the same next-token training on your examples, computing loss only on the target (assistant) tokens. Each step nudges the weights so the model assigns higher probability to your answers. It doesn't install a new skill from nothing; it shifts which of the model's existing behaviours comes out by default.

## The hyperparameters that matter first

| Setting | What it controls | Sensible start (LoRA on a 7-8B model) |
|---------|------------------|---------------------------------------|
| Learning rate | Size of each update | 1e-4 to 2e-4 for LoRA; ~1e-5 for full tuning |
| Epochs | Passes over the data | 1-3; more on tiny datasets risks memorising |
| Batch size | Examples per update | Whatever fits; raise effectively with accumulation |
| Gradient accumulation | Steps summed before an update | Effective batch = batch x accumulation, aim for 16-64 |
| Max sequence length | Tokens per example | Just above your longest real example; longer costs memory |

Leave the rest at library defaults until you have a reason to change them.

## Full vs parameter-efficient

Full fine-tuning updates every weight. For a 7B model that means storing gradients and optimizer states for billions of parameters, so it needs several large GPUs and produces a full new copy of the model. Parameter-efficient methods (next lesson: LoRA) freeze the base and train a tiny fraction of new weights. For a narrow task they usually reach similar quality, which is why full tuning is rarely the first choice.

## A first run with TRL

```python
from datasets import load_dataset
from peft import LoraConfig
from trl import SFTConfig, SFTTrainer

ds = load_dataset("json", data_files={"train": "train.jsonl", "validation": "val.jsonl"})

config = SFTConfig(
    output_dir="out/extract-v1",
    num_train_epochs=3,
    learning_rate=2e-4,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,
    eval_strategy="steps", eval_steps=50,
    save_strategy="steps", save_steps=50,
    logging_steps=10,
    bf16=True,
)
trainer = SFTTrainer(
    model="Qwen/Qwen2.5-7B-Instruct",       # example base model
    args=config,
    train_dataset=ds["train"],
    eval_dataset=ds["validation"],
    peft_config=LoraConfig(r=16, lora_alpha=32, target_modules="all-linear"),
)
trainer.train()
```

Argument names shift between TRL releases, so check the current docs, but the shape stays the same: a dataset of `messages`, a config, a model, a trainer.

## Reading the curves

| Pattern | Diagnosis | Action |
|---------|-----------|--------|
| Train and validation loss both high and flat | Underfitting | More epochs, higher LR, check data/template |
| Train keeps falling, validation turns up | Overfitting | Stop earlier, fewer epochs, more varied data |
| Loss spikes or goes to NaN | Unstable | Lower LR, add warmup, check for bad examples |
| Both fall, then flatten together | Healthy | Pick a checkpoint near the flat start |

## Catastrophic forgetting

A model trained hard on one narrow task can lose general ability: it stops following unrelated instructions, or answers everything in your task's format. Signs show up on prompts outside your dataset, not in your validation loss. Mitigations: fewer epochs, lower LR, LoRA rather than full tuning, and mixing a small share of general instruction data into training.

## Read outputs, not just loss

Lower loss means the model is more confident about your exact reference tokens. It doesn't guarantee better answers; a model can lower loss by memorising phrasing. At each saved checkpoint, generate answers for 10-20 validation inputs and read them. Choose the checkpoint with the best validation *behaviour* (your task metric), not the last one saved.

## Try it

Train the same dataset for 1, 3 and 8 epochs. Plot validation loss for each run and read ten outputs from each final checkpoint.

Usually 1 epoch is slightly undertrained, 3 is close to best, and 8 shows validation loss rising while training loss keeps falling. The best checkpoint is often mid-run, which is why you save several and choose on validation.

## Check yourself

1. Training loss keeps falling but validation loss started rising at step 300. What happened and what do you keep?

<details>
<summary>Answer</summary>

The model began overfitting around step 300. Keep the checkpoint near the validation minimum (around step 300), confirmed by reading outputs and scoring the task metric, not the final checkpoint.
</details>

2. What is the effective batch size with batch 4 and gradient accumulation 8 on one GPU?

<details>
<summary>Answer</summary>

32. Gradients from 8 steps of 4 examples are summed before each weight update.
</details>

3. After tuning, the model extracts invoices well but now answers "what's 2+2?" with a JSON invoice. What is this called, and name one fix.

<details>
<summary>Answer</summary>

Catastrophic forgetting (or over-specialisation). Fixes: fewer epochs or a lower learning rate, mixing general instruction data into training, or using LoRA with a smaller rank.
</details>
