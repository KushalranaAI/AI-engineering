# Evaluating a fine-tune

A fine-tune is a claim: "this model is better for our task than what we had, by enough to justify owning it." Evaluation is how you test the claim. Done carelessly, it produces a flattering number that hides regressions. Done well, it sometimes tells you the tune wasn't worth it, which is a perfectly good result.

## Baselines before training

Before any training, score at least three baselines on your held-out test set:

1. **The base model** you will tune, with a simple prompt.
2. **The best prompted version** of that base model: full instructions, few-shot examples, retrieval if relevant.
3. **A stronger model** with that same best prompt.

The tune must beat (2) to be worth anything, and you need (3) to know whether "just use a bigger model" is cheaper overall.

## Same test set, same judge

Every candidate (baselines, each checkpoint, merged and quantised versions) runs on the **same held-out test set**, with the **same metrics**, scored by the **same judge** with the same prompt and settings. Change any of those and the comparison is meaningless. Your eval harness from earlier levels should make this one command:

```python
CANDIDATES = {
    "base_simple":   ("qwen2.5-7b-instruct", "prompts/simple.txt"),
    "base_best":     ("qwen2.5-7b-instruct", "prompts/best_fewshot.txt"),
    "stronger_best": ("frontier-model",      "prompts/best_fewshot.txt"),
    "tuned_v3":      ("qwen2.5-7b+extract-v3", "prompts/short.txt"),
}
results = {name: run_eval(model, prompt, test_set="data/test-v3.jsonl", judge="judge-v2")
           for name, (model, prompt) in CANDIDATES.items()}
```

## More than one number

| Candidate | Field accuracy | Valid JSON | p50 latency | Tokens in / req | $ / 1k req |
|-----------|----------------|-----------|-------------|-----------------|-----------|
| Base, simple prompt | 71% | 93% | 300 ms | 400 | 0.10 |
| Base, best prompt | 82% | 98% | 450 ms | 3,200 | 0.45 |
| Stronger model, best prompt | 90% | 99.5% | 1,100 ms | 3,200 | 4.00 |
| Tuned v3 | 91% | 99.8% | 280 ms | 350 | 0.12 |

(Illustrative numbers.) A table like this lets a reader see quality, consistency, speed and cost together. Also record the variance: run each candidate more than once if sampling is on, and look at per-category scores, not only the overall average.

## Regressions outside the task

The test set measures the thing you trained for. Also run a **regression set** of prompts the tune never saw:

- General instruction-following ("summarise this in two sentences").
- Safety behaviour: harmful requests should still be refused as before.
- Formats outside training: if users sometimes ask for a table, does it still produce one?
- Edge inputs: empty input, a different language, extremely long input.

A tuned model that answers everything with your task's JSON has regressed, even if its task score is excellent.

## Read individual failures

Averages hide new failure modes. Diff the tuned model's failures against the best-prompted baseline's:

- Cases both fail: hard cases, possibly bad labels.
- Cases only the baseline fails: what the tune fixed.
- **Cases only the tune fails**: new failures it introduced. Read every one.

Twenty minutes reading these often changes the decision.

## One last look at the simple options

Before writing it up, ask honestly: does the best-prompted model, or the stronger model, get close enough at an acceptable cost? If the stronger model is within a point and the volume is low, the tune may not be worth its maintenance.

## Write the decision down

A short decision record:

- **Target failure and metric**, and the threshold set in advance.
- **Results table** as above.
- **Regressions found**, and whether they are acceptable.
- **Cost to own**: serving, monitoring, retraining.
- **Decision**: ship, don't ship, or ship behind a flag for a subset of traffic.

## Try it

Score three contenders on your eval set: the untouched base model, the base model with your best prompt, and your tuned model. Then throw in ten prompts that have nothing to do with the task (general questions, a refusal test, a request for a different format) and see which model holds up.

<details>
<summary>Reference</summary>

The tuned model usually wins clearly on-task. On the off-task prompts, a narrowly tuned model often fails a few: it forces the task format onto unrelated questions or answers in a fixed style. If it fails safety prompts the base handled, that is a blocking regression. Fixes include mixing general data into training, fewer epochs, or routing only on-task traffic to the tune.
</details>

## Check yourself

1. Why is "tuned model vs base model with a simple prompt" a misleading comparison?

<details>
<summary>Answer</summary>

It flatters the tune. The real alternative is the best prompted version (and possibly a stronger model). The tune has to beat what you could get without training.
</details>

2. The tune improves average accuracy by 6 points. What else do you check before shipping?

<details>
<summary>Answer</summary>

Regressions on off-task prompts and safety behaviour; new failures that only the tune makes; latency and cost per request; consistency across runs; and whether a simpler option comes close.
</details>

3. You re-ran the eval for the tuned model with a newer judge model and got higher scores. Can you compare them with last month's baseline scores?

<details>
<summary>Answer</summary>

No. Changing the judge changes the measuring instrument. Re-score all candidates with the same judge before comparing.
</details>
