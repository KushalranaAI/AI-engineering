# Should you fine-tune?

Fine-tuning feels like the "real" machine learning move: you have a problem, so you train the model on it. In practice it is the most expensive fix on the menu, and most problems that look like they need it are solved more cheaply further up the list. This lesson is about making that call deliberately.

## The ladder

Think of the options as rungs. Climb only when the rung below has failed in a way you measured.

| Rung | What it changes | Typical cost to try |
|------|-----------------|---------------------|
| 1. Better prompt (instructions, few-shot examples) | What the model is told | Hours |
| 2. Retrieval | What the model can see | Days |
| 3. Tools / structured output | What the model can do and how output is constrained | Days |
| 4. Stronger base model | The model's raw capability | Minutes to change, more per request |
| 5. Fine-tuning | The model's weights | Weeks, plus ongoing ownership |

Rungs combine. A tuned small model with retrieval is a common end state; a tuned model *instead of* retrieval for changing facts is a common mistake.

## What tuning is good at

- **Consistent behaviour and style.** A tone, a persona, a refusal policy that a long prompt only holds 90% of the time.
- **Formats a prompt can't hold.** A strict domain-specific output format, especially on small models that drift.
- **Narrow, structured tasks.** Classification, extraction, routing, rewriting into a house style.
- **Shorter prompts.** If every request carries 3,000 tokens of instructions and examples, baking them in cuts cost and latency.
- **Specialising a small model.** Getting an 8B open-weight model to match a frontier model on one job, so you can host it cheaply.

## What tuning is bad at

- **Facts that change.** Prices, policies, inventory. Training them in means retraining whenever they change, and the model will still blend them with what it already "knew". Retrieval supplies them fresh, with citations.
- **Teaching broad new knowledge.** Small tunes shape behaviour far more reliably than they add knowledge.
- **Undefined tasks.** If you can't write down what a good output looks like and score it, you can't build a dataset or tell whether the tune worked.

## Start from a measured failure

A good reason to tune sounds like: "On our 300-example test set, the best prompt we could write with a frontier model gets 81% field accuracy on contract extraction; a 4,000-token prompt makes it slow and costly; we need 92% at under 500 ms." A bad reason sounds like: "Our chatbot should know our company better."

Before training, write down three things:

1. The failure, with a number.
2. The metric and threshold that will count as success.
3. What you already tried on rungs 1-4, and how much of the gap it closed.

## Count the full cost

A rough cost sheet for one tune:

```python
costs = {
    "data_creation_hours": 60,       # writing, reviewing, cleaning examples
    "training_runs_gpu_hours": 20,   # several runs, not one
    "eval_hours": 15,                # baselines, regressions, reading outputs
    "serving_per_month": 400,        # dedicated GPU or per-token adapter hosting
    "retrain_per_base_upgrade": 0.5, # fraction of the original effort, each time
}
```

The last line is the one people forget. A tune is tied to one base model version. When a better base model ships next quarter, switching is not a config change: you rebuild the dataset in the new chat template, retrain, re-evaluate and redeploy. With prompting, you change a model name and rerun your evals.

## Try it

Pick a task where a prompt is struggling (for example, extracting five fields from messy support emails). Spend one hour improving only the prompt: clearer instructions, three to five worked examples, an output schema. Score before and after on 30 examples and record how much of the gap closed.

<details>
<summary>Reference</summary>

A typical result is that the hour closes half or more of the gap, which is exactly why this step comes first. Record the remaining failures by type. If what remains is "the model formats dates three different ways" or "it ignores rule 7 one time in ten", that is the kind of consistency problem tuning can fix. If what remains is "it doesn't know our new pricing", that is a retrieval problem, and tuning would be the wrong tool.
</details>

## Check yourself

1. Your support bot gives outdated refund amounts after a policy change. A colleague proposes fine-tuning on the new policy. What do you suggest instead, and why?

<details>
<summary>Answer</summary>

Retrieval over the current policy document. The facts will change again; retrieval picks up changes immediately and lets the answer cite its source, while a tune would need retraining each time and may still mix old and new amounts.
</details>

2. Name two situations where fine-tuning is a reasonable choice.

<details>
<summary>Answer</summary>

Any two of: enforcing a consistent style or behaviour a prompt can't hold; a strict output format on a small model; a narrow high-volume task like classification or extraction where a small tuned model can replace a costly large one; cutting a very long prompt to reduce cost and latency.
</details>

3. Why does a better base model next quarter hurt a fine-tuned system more than a prompted one?

<details>
<summary>Answer</summary>

The adapter or tuned weights only work with the base model they were trained on. Upgrading means rebuilding data in the new template, retraining and re-evaluating, while a prompted system can switch models and rerun its eval suite in an afternoon.
</details>
