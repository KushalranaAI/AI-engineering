# LoRA and QLoRA

LoRA is the reason fine-tuning stopped requiring a cluster. It trains a tiny add-on instead of the whole model, and QLoRA shrinks the frozen model further so a useful tune fits on a single rented GPU. This is the method you will actually use, and the one interviewers ask about.

## How LoRA works

Take one weight matrix `W` in the model, say 4096 x 4096. Full tuning learns a full-size update `ΔW`. LoRA bets that the useful update is **low-rank** and writes it as the product of two thin matrices:

```
W' = W + (alpha / r) · B · A        A: r x 4096,  B: 4096 x r,  r = 16
full update:  4096 x 4096 = 16.8M parameters
LoRA update:  2 x 4096 x 16 = 131K parameters   (about 0.8%)
```

`W` stays frozen. Only `A` and `B` are trained, and `B` starts at zero so the model begins exactly as the base. The trained `A` and `B` for all chosen layers form an **adapter**, usually tens to a few hundred megabytes.

## QLoRA

QLoRA loads the frozen base in **4-bit** precision (the NF4 format) while training the LoRA matrices in 16-bit. The base's memory drops roughly 4x compared with 16-bit, with little quality loss for most tasks. Paged optimizers and double quantisation squeeze a bit more. The cost is somewhat slower training, because weights are de-quantised on the fly.

## The settings

| Setting | Meaning | Typical start |
|---------|---------|---------------|
| `r` (rank) | Capacity of the adapter | 8-32; raise if underfitting |
| `lora_alpha` | Scale on the update | Often r or 2r |
| `target_modules` | Which layers get adapters | All linear layers usually beats attention-only |
| `lora_dropout` | Regularisation | 0-0.1 |
| Compute precision | bf16 on modern GPUs | bf16 |
| Quant type (QLoRA) | 4-bit format | nf4 |

## Adapters vs full tuning

| | LoRA / QLoRA | Full fine-tuning |
|-|--------------|------------------|
| Trainable params | ~0.1-2% | 100% |
| GPU memory | One GPU for 7-8B models | Several large GPUs |
| Output | Small adapter file | Full model copy |
| Quality on narrow tasks | Usually close | Sometimes slightly better |
| Swapping tasks | Load a different adapter | Load a different model |

## Estimating GPU memory

Rough rule before renting hardware:

```python
def est_gb(params_b, bits_base, seq_len, batch, lora_frac=0.01):
    base = params_b * bits_base / 8                 # frozen weights
    lora = params_b * lora_frac * (2 + 2 + 8)        # bf16 weights, grads, Adam states (GB per B params)
    acts = 0.5 * batch * seq_len / 1024             # very rough activation term with checkpointing
    return round(base + lora + acts + 2, 1)          # +2 GB overhead

print(est_gb(8, 16, 2048, 4))   # LoRA on an 8B model in bf16  -> ~23 GB
print(est_gb(8, 4, 2048, 4))    # QLoRA                          -> ~11 GB
```

Treat the numbers as a sanity check, not a guarantee; activation memory varies with the model and settings. Gradient checkpointing trades some speed for much lower activation memory.

## Running it

Libraries such as **Unsloth** (fast single-GPU training, memory savings) and **Axolotl** (YAML-configured runs) wrap PEFT, TRL and bitsandbytes. The important habit is that every run is defined by a **config file** checked into git:

```yaml
base_model: meta-llama/Llama-3.1-8B-Instruct   # example
load_in_4bit: true
adapter: qlora
lora_r: 16
lora_alpha: 32
lora_target_linear: true
datasets: [{ path: data/train-v3.jsonl, type: chat_template }]
num_epochs: 2
learning_rate: 0.0002
```

## Tracking runs

Log every run to an experiment tracker (Weights & Biases, MLflow or similar) with: dataset version, config hash, base model revision, final eval scores, peak memory and wall time. Two weeks later "the good run" will otherwise be unfindable.

## Do it yourself or managed

Managed fine-tuning (from model providers and cloud platforms) takes a dataset and returns a hosted tuned model. Ask: which base models are offered, which methods (SFT, DPO, reinforcement), can you **download the weights**, and what does serving cost? Self-run tuning gives full control and portability; managed tuning saves infrastructure work but may lock you to one provider's serving.

## Try it

Run the same dataset as LoRA r=8, LoRA r=32 and QLoRA r=16. For each run, write down how much GPU memory it peaked at, how long it took, how big the adapter file is, and how it scored on held-out data.

<details>
<summary>Reference</summary>

Expect QLoRA to use clearly the least memory and train somewhat slower; r=32 produces an adapter about four times larger than r=8. Held-out scores are often within a point or two of each other for narrow tasks, which shows that rank is rarely the bottleneck. If r=8 is clearly worse, the task needs more adapter capacity or more data.
</details>

## Check yourself

1. Why does LoRA initialise one of its matrices to zero?

<details>
<summary>Answer</summary>

So `B·A` is zero at the start and the model initially behaves exactly like the base. Training then moves away from a known-good starting point instead of adding random noise.
</details>

2. What does QLoRA quantise, and what stays in higher precision?

<details>
<summary>Answer</summary>

The frozen base weights are stored in 4-bit (NF4). The LoRA adapter weights, their gradients and computation run in 16-bit.
</details>

3. A managed service offers cheap tuning but no weight export. What risk does that create?

<details>
<summary>Answer</summary>

Lock-in: you can only serve the tune on that provider, at its prices, and lose it if the base model or service is retired. You can't move it to your own vLLM deployment or another host.
</details>
