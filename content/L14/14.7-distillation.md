# Distillation

You have a task that a frontier model does well, but at a volume where its price or latency hurts. Distillation uses the big model as a **teacher**: it produces outputs on realistic inputs, and those outputs train a small **student** model that handles just that one task. You give up a little quality and get a model that is cheaper, faster and possibly self-hosted.

## How it works for LLM teams

Classic distillation trains the student to match the teacher's full probability distribution over tokens. With API models you usually can't see those probabilities, so the common form is simpler: **use the teacher's text outputs as SFT data**. Everything from the data lesson applies; the teacher just writes the examples.

```python
from openai import OpenAI
import json

client = OpenAI()
SYSTEM = "Classify the support ticket into one of: billing, bug, how_to, account, other. Reply as JSON."

def teach(ticket: str) -> dict:
    r = client.chat.completions.create(
        model="gpt-4.1",                       # example teacher
        messages=[{"role": "system", "content": SYSTEM}, {"role": "user", "content": ticket}],
        response_format={"type": "json_object"},
    )
    return {"messages": [
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": ticket},
        {"role": "assistant", "content": r.choices[0].message.content},
    ]}

with open("distill.jsonl", "w") as f:
    for t in real_tickets:                    # sampled from production, PII scrubbed
        f.write(json.dumps(teach(t)) + "\n")
```

## Generating good teacher data

- **Use inputs that look like real traffic.** Sample from production logs (cleaned), not from inputs the teacher invented. A student trained on tidy synthetic questions fails on messy real ones.
- **Give the teacher your best prompt.** Few-shot examples, detailed rules, even reasoning steps; the student will only see the final answer, so the teacher's prompt can be as long as you like.
- **Filter with your evals.** Drop teacher outputs that fail validation, disagree with known labels, or get a low judge score. Where you have ground truth, keep only correct ones.

## The trade

A worked example for a ticket classifier at 2 million requests a month (illustrative numbers):

| Option | Accuracy on test set | p50 latency | Cost / 1,000 requests |
|--------|----------------------|-------------|-----------------------|
| Frontier model, long prompt | 94% | 900 ms | $3.00 |
| Small model, same prompt (no tuning) | 83% | 250 ms | $0.20 |
| Small model, distilled | 92% | 200 ms | $0.15 (short prompt) |

The distilled student loses two points to the teacher but costs a fraction as much, and the prompt shrinks because the instructions are baked in. Whether two points matters is a product decision; measure it, don't assume it.

## The risks

- **Copied mistakes.** The student learns the teacher's errors as faithfully as its successes. Filtering and a human-checked test set catch the worst.
- **Low diversity.** If the inputs or the teacher's phrasings are narrow, the student handles a narrow world. Watch for inputs outside the training distribution failing badly.
- **A ceiling.** The student rarely beats the teacher on the teacher's own outputs. If you need better than the teacher, you need better labels, not more distillation.
- **Terms of use.** Some providers restrict using their outputs to build models that compete with them. Read the teacher's terms before you start, and prefer open-weight teachers with permissive licences when in doubt.

## Try it

Pick a narrow task. Generate 500 teacher outputs on real-looking inputs, filter them, and tune a small open model (1-8B) with LoRA. Compare teacher, untuned student and distilled student on the same 100-example test set: accuracy, latency and cost per 1,000 requests.

## Check yourself

1. Why should teacher inputs come from real traffic rather than synthetic questions?

<details>
<summary>Answer</summary>

The student learns the distribution it trains on. Synthetic inputs are usually cleaner and narrower than real ones, so the student would fail on the messy, varied requests it will actually see.
</details>

2. Your distilled student is 2 points below the teacher. A colleague suggests generating 10x more teacher data to beat the teacher. Will it?

<details>
<summary>Answer</summary>

Unlikely. The student imitates the teacher, errors included, so the teacher is roughly a ceiling. More data may close the remaining gap but won't surpass it; better (human-checked) labels could.
</details>

3. What should you check before using a commercial API model as a teacher?

<details>
<summary>Answer</summary>

Its terms of use, which may forbid using outputs to train competing models; and your data policy, since sending production inputs to the API must be allowed.
</details>
