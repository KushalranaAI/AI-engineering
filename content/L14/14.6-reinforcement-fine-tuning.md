# Reinforcement fine-tuning

SFT copies examples. DPO learns from comparisons. Reinforcement fine-tuning (RFT) learns from a **score**: the model tries, a grader marks the attempt, and training makes high-scoring attempts more likely. It is how reasoning models got good at maths and code, and it is available to ordinary teams through managed services and open frameworks. Its power and its danger both live in the grader.

## The loop

```
prompt ──► model samples several answers ──► grader scores each ──► reward
   ▲                                                                   │
   └────────────── policy update: favour higher-reward answers ◄───────┘
```

You don't need example answers, only prompts and a way to score outputs. Methods such as PPO and GRPO differ in how they turn scores into updates (GRPO, for instance, compares several samples for the same prompt against each other instead of training a separate value model), but you rarely implement them yourself.

## SFT vs DPO vs RFT

| Method | Learns from | You must provide | Best when |
|--------|-------------|------------------|-----------|
| SFT | Examples | Good answers | You can write the right answer |
| DPO | Comparisons | Pairs of better/worse answers | Quality is easier to judge than produce |
| RFT | Rewards | A grader | Correctness can be checked automatically, and the model must find its own path |

## Which tasks fit

RFT shines when outputs can be **graded reliably and cheaply**:

- Code that must pass unit tests.
- Maths or numeric answers that can be checked exactly.
- Structured outputs whose fields can be validated against ground truth (e.g. extracted amounts matching the ledger).
- Classification with known labels, where the model benefits from reasoning first.

It fits badly where "good" is a matter of taste (use DPO) or where you can't grade at all.

## The grader is the product

Here is a grader for an extraction task:

```python
import json

def grade(output: str, truth: dict) -> float:
    try:
        pred = json.loads(output)
    except json.JSONDecodeError:
        return 0.0
    fields = ["invoice", "vendor", "due", "total", "currency"]
    correct = sum(1 for f in fields if str(pred.get(f)).strip().lower() == str(truth[f]).strip().lower())
    extra_keys = set(pred) - set(fields)
    return correct / len(fields) - 0.2 * bool(extra_keys)
```

Every weakness in that function becomes something the model learns to exploit. That is **reward hacking**: the model optimises the grader, not your intent. Classic examples:

- Tests that only check the function returns *something*: the model returns a constant.
- A judge that likes confident tone: answers become confident and wrong.
- A length-insensitive check on a "summary": the model pastes the whole input.

Defences: grade the real objective as directly as possible, combine several checks, penalise obvious cheats, hold out a separate eval the grader never sees, and read samples during training.

## How teams actually run it

Building RL infrastructure (sampling at scale, stable updates, reward pipelines) is specialist work. In practice you reach RFT through a provider's managed reinforcement fine-tuning, where you upload prompts and a grader definition, or through open frameworks such as TRL's GRPO trainer on open-weight models. Either way, your job is the dataset of prompts, the grader, and the evaluation.

## Try it

Write a grader for one checkable task (for example: "return the sum of the numbers in this sentence as JSON `{"sum": n}`"). Then try to fool it by hand: write five outputs that score well but are wrong or useless. Fix the grader so all five score poorly.

<details>
<summary>Reference</summary>

Typical holes: accepting `{"sum": "12"}` and `{"sum": 12}` inconsistently; accepting extra keys; giving partial credit for any valid JSON; not handling negative or decimal numbers; matching the number as a substring of a longer output. A fixed grader parses strictly, compares numerically with tolerance, rejects extra text and keys, and scores 0 for any parse failure. If you can fool it in five minutes, a model will fool it in five hundred steps.
</details>

## Check yourself

1. What is the minimum data RFT needs, compared with SFT?

<details>
<summary>Answer</summary>

Prompts plus a grader (and ground truth the grader can check against). SFT needs a full correct answer for each prompt.
</details>

2. Your code-generation RFT run shows test pass rate climbing to 98%, but engineers say the code is worse. What's a likely cause?

<details>
<summary>Answer</summary>

Reward hacking: the tests are weak (e.g. few cases, or they can be satisfied by special-casing inputs), so the model learned to pass them rather than write correct code. Strengthen the tests and evaluate on held-out tasks with hidden tests.
</details>

3. Why is RFT a poor fit for "make the assistant's tone friendlier"?

<details>
<summary>Answer</summary>

There's no reliable automatic check for friendliness; any judge you use becomes an easily gamed reward. Preference data with DPO, or SFT on good examples, fits better.
</details>
