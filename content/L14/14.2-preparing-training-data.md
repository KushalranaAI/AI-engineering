# Preparing training data

The dataset *is* the fine-tune. Hyperparameters move results by a few points; a dataset with contradictions, truncated answers or the wrong template can wreck the run entirely. Most of the effort in a successful tune goes here.

## Write the spec before the examples

Write one page describing the target behaviour: the input it receives, the exact output format, the rules for edge cases, and what it must never do. Every example must pass this spec. Without it, two people writing examples will teach the model two different behaviours, and the model will learn the average of both.

## Where examples come from

| Source | Strength | Bias to watch |
|--------|----------|---------------|
| Production logs (corrected) | Real inputs, real distribution | Inherits past mistakes; may contain PII |
| Expert-written demonstrations | High quality, follows the spec | Slow; experts write "clean" inputs real users don't |
| Synthetic (a strong model generates) | Fast and cheap at volume | Repetitive phrasing, narrow variety, teacher's errors |

A good mix: real inputs from logs, outputs written or corrected by experts, and synthetic examples only to fill gaps in edge cases, always filtered.

## Format it the way the model was trained

Instruction-tuned models expect a specific chat template: special tokens marking where the system, user and assistant turns begin and end. Store your data as messages and let the tokenizer apply the template, rather than hand-building strings.

```python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")  # example model
example = {"messages": [
    {"role": "system", "content": "Extract fields as JSON."},
    {"role": "user", "content": "Invoice 4471 from Acme, due 3 March, total EUR 1,200"},
    {"role": "assistant", "content": '{"invoice": "4471", "vendor": "Acme", "due": "2026-03-03", "total": 1200, "currency": "EUR"}'},
]}
print(tok.apply_chat_template(example["messages"], tokenize=False))
```

If you train with one template and serve with another, the model sees unfamiliar token patterns and quality drops with no error message.

## Train on the answer, not the question

Each example contains prompt tokens and response tokens. Usually you want the model to learn to *produce* responses, not to predict users' questions. So you **mask the loss** on prompt tokens (set their labels to -100 in PyTorch-style training). In TRL's `SFTTrainer`, the conversational dataset format plus its assistant-only loss option handles this; check your library's docs for the current flag name.

## Few clean examples beat many noisy ones

For a narrow task, a few hundred carefully checked, representative examples often outperform thousands of scraped ones. Every bad example teaches something you didn't want. Start small, train, read the failures, then add examples aimed at those failures.

## Cleaning checklist

- Exact and near-duplicate removal (normalise whitespace and case, then hash; use embeddings or MinHash for near-duplicates).
- Contradictions: same input, different outputs.
- Wrong labels and outputs that break the spec.
- Truncated responses (often from logs with length limits).
- Synthetic examples that reuse the same opening phrase; the model will copy it.
- **Balance:** if 90% of examples are the easy case, the model learns that the easy answer is always right. Over-represent hard and important edge cases.

## Splits that don't leak

Split into train (~80%), validation (~10%) and a held-out test set (~10%) that you only touch for final comparisons. Group near-duplicates *before* splitting, so paraphrases of one ticket don't end up on both sides and inflate your test score.

```python
import hashlib, random

def group_key(text: str) -> str:
    norm = " ".join(text.lower().split())[:200]
    return hashlib.sha1(norm.encode()).hexdigest()

groups = {}
for ex in examples:
    groups.setdefault(group_key(ex["messages"][1]["content"]), []).append(ex)
keys = sorted(groups); random.Random(42).shuffle(keys)
n = len(keys)
train = [e for k in keys[: int(0.8 * n)] for e in groups[k]]
val   = [e for k in keys[int(0.8 * n): int(0.9 * n)] for e in groups[k]]
test  = [e for k in keys[int(0.9 * n):] for e in groups[k]]
```

## Privacy, licences and versions

Scan for names, emails, phone numbers and account ids, and anything licensed you can't redistribute. A tuned model can repeat training text word for word. Then version the dataset (a content hash, a DVC or Hugging Face dataset revision) next to the training config, so any model can be traced to exactly what it learned from.

## Try it

Write 50 examples for one narrow task by hand, generate 50 with a strong model from a short prompt, then review all 100 against your spec. Count how many of each you keep.

<details>
<summary>Reference</summary>

Expect to keep most hand-written examples and noticeably fewer synthetic ones. Typical synthetic rejects: the same opening sentence repeated, inputs far cleaner than real traffic, subtle spec violations, and very little variety in edge cases. The lesson is to generate more than you need and filter hard, or use synthetic data only to fill named gaps.
</details>

## Check yourself

1. Why should you mask the loss on prompt tokens?

<details>
<summary>Answer</summary>

So the gradient comes only from the assistant's responses. Otherwise training also spends capacity learning to predict system prompts and user text, which isn't the behaviour you want and can dilute the signal.
</details>

2. Your test score is suspiciously high. What leak would you check first?

<details>
<summary>Answer</summary>

Near-duplicates across splits: paraphrased or templated versions of the same input in both train and test. Group by a normalised key or embedding similarity before splitting.
</details>

3. What goes wrong if 90% of your examples are the "no issue found" case?

<details>
<summary>Answer</summary>

The model learns that "no issue found" is almost always correct and under-reports the rare cases you care about. Rebalance so hard and important cases are well represented, and measure per-class results.
</details>
