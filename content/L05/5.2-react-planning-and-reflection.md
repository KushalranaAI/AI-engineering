# ReAct, planning and reflection

An agent loop on its own just repeats "model, tool, model, tool". Three ideas make that loop behave sensibly:
**ReAct** (decide, act, observe, repeat), **planning** (think about the whole route before or while walking it) and
**reflection** (check your own work and try again). Each one buys quality with extra tokens and latency, so you add
them on purpose, not by default.

## ReAct

The ReAct paper (Yao et al., 2022) showed that interleaving short reasoning with actions works better than either
alone. The model writes what it's trying to do, takes one action, sees the result, and decides again:

```
Thought: I need the order status before I can answer.
Action: get_order(order_id="A-1093")
Observation: {"status": "shipped", "carrier": "DHL", "tracking": "JD0142..."}
Thought: It's shipped. The user asked when it will arrive, so I need tracking.
Action: track_parcel(carrier="DHL", tracking="JD0142...")
Observation: {"eta": "2026-11-09"}
Answer: Your order shipped with DHL and should arrive on 9 November.
```

Modern APIs do this natively: the "Action" is a structured tool call and the "Observation" is a tool-result
message. Reasoning models may keep the "Thought" internal. The pattern is the same.

## Write the loop by hand first

Before using any framework, build one yourself. It takes about 30 lines and makes every framework readable
afterwards. This version uses the OpenAI Chat Completions shape; Anthropic and Google APIs differ only in field names.

```python
import json
from openai import OpenAI

client = OpenAI()

def react(goal, tools, impls, max_steps=8):
    msgs = [{"role": "system", "content": "Use tools when needed. Answer when you have enough."},
            {"role": "user", "content": goal}]
    seen = set()
    for step in range(max_steps):
        r = client.chat.completions.create(model="gpt-4.1-mini", messages=msgs, tools=tools)
        m = r.choices[0].message
        msgs.append(m)
        if not m.tool_calls:
            return m.content
        for call in m.tool_calls:
            key = (call.function.name, call.function.arguments)
            if key in seen:                                    # loop guard
                out = "You already ran this exact call. Try something different or answer."
            else:
                seen.add(key)
                args = json.loads(call.function.arguments)
                out = impls[call.function.name](**args)
            msgs.append({"role": "tool", "tool_call_id": call.id, "content": str(out)[:4000]})
    return "Stopped after max_steps without an answer."
```

(The model name is an example; use whatever you have access to.)

## Step by step or plan first

| Style | How it works | Good for | Weak at |
|-------|--------------|----------|---------|
| Step by step (ReAct) | Decide one action at a time | Exploratory tasks, surprises | Long tasks: loses the thread, wanders |
| Plan first | Write a list of subtasks, then execute | Tasks with clear structure, reporting progress | Plans go stale when reality differs |
| Plan and revise | Plan, execute, re-plan after each result | Long, uncertain tasks | Costs an extra call per re-plan |

A plan-first agent typically has a **planner** call that outputs a list, an **executor** that works through it,
and a **replanner** that sees completed steps plus results and returns either the remaining plan (edited) or a final
answer. Keep the plan in state, not only in the chat history, so you can show it to users and check progress.

Decomposition tips: ask for subtasks that each end in a checkable result ("list the three largest tables" rather
than "understand the database"), and cap plan length so the model doesn't produce 25 steps for a 3-step job.

## Reflection

Reflection means checking a result before accepting it. Forms you'll use:

- **Error-driven retry**: the tool returned an error; feed it back and let the model fix its arguments.
- **Self-critique**: a second call (same or different model) grades the draft against the goal and lists problems;
  the agent revises. Reflexion (Shinn et al., 2023) stores those critiques as memory for later attempts.
- **External checks**: tests, schema validation or a SQL dry-run. These beat self-critique whenever they exist,
  because the model grading itself tends to approve its own work.

## Stopping

Every agent needs several stop conditions, not one:

1. the model returns an answer with no tool call;
2. a hard **step limit** and a **time/token budget**;
3. a **repeat detector**: same tool, same arguments, or the same failing error several times in a row;
4. optionally a "no progress" check: the plan hasn't advanced in N steps.

When a limit triggers, return a useful partial result ("here's what I found before stopping") rather than nothing.

## What it costs

Each planning or reflection call adds a full model round trip and re-sends the growing context. A reflect-and-revise
cycle can easily double the tokens of a task. Measure: run the same 20 tasks with and without planning or
reflection and compare success rate, latency and cost. Keep the extra machinery only where it moves success.

## Check yourself

1. What does ReAct add compared with letting the model call one tool and answer?

<details>
<summary>Answer</summary>

Repeated cycles of reasoning, acting and observing, so later actions depend on earlier results. The model can
gather information in several steps and change direction based on what it sees.
</details>

2. When is plan-first execution a bad fit?

<details>
<summary>Answer</summary>

When the environment is highly uncertain and early results change what later steps should be, so a fixed plan
goes stale. Use step-by-step or plan-and-revise instead.
</details>

3. Why prefer an external check over self-critique when one exists?

<details>
<summary>Answer</summary>

External checks (tests, validators, dry runs) are objective and cheap; a model critiquing its own output often
misses its own mistakes or approves them, and costs an extra model call.
</details>
