# Tools for agents

In Level 2 you used tool calling once: the model asked for a function, you ran it, done. In an agent the model
chooses among tools again and again, and the quality of those tools decides most of what the agent can do. A tool is
an interface designed for a very particular user: a model that reads only the name, description and schema, and
can't ask you what you meant.

## Designing a good tool

```python
tools = [{
    "type": "function",
    "function": {
        "name": "search_orders",
        "description": (
            "Find a customer's orders. Use when the user mentions an order, purchase or delivery. "
            "Returns at most 10 orders, newest first. Does NOT return payment details."
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "customer_email": {"type": "string", "description": "Exact email on the account"},
                "status": {"type": "string", "enum": ["pending", "shipped", "delivered", "cancelled"]},
                "since": {"type": "string", "description": "ISO date, e.g. 2026-10-01"},
            },
            "required": ["customer_email"],
            "additionalProperties": False,
        },
    },
}]
```

Rules that pay off:

| Do | Why |
|----|-----|
| Name tools by intent: `search_orders`, `refund_order` | Model maps user goals to names |
| Say **when** to use it and what it **doesn't** do | Cuts wrong-tool choices between similar tools |
| Use enums, formats and required fields | Fewer malformed arguments; enable strict schema mode where supported |
| Return compact, labelled data (JSON or short text) | Model can read it; you save tokens |
| Return ids the next tool needs | Enables chaining (`order_id` → `refund_order`) |
| Prefer a few task-shaped tools over many thin API wrappers | `get_customer_summary` beats five raw CRUD calls |

## Better choices and arguments

When the agent picks the wrong tool or fills arguments badly, look at the tool definitions before the prompt:

- two tools with overlapping descriptions? Merge them or state the difference explicitly;
- free-text arguments where a closed set exists? Use an enum;
- ambiguous units or formats? Put an example in the description;
- too many tools? Selection accuracy drops as the list grows; group or filter them per task (covered in Level 6).

Then build a small test set: 30 user requests with the expected tool and arguments, and measure the hit rate after
each change.

## Sequential, parallel and repeated calls

- **Sequential**: the second call needs the first's output (find order, then refund it). The loop handles this
  naturally across turns.
- **Parallel**: independent calls in one turn (weather in three cities). Most APIs return several tool calls in one
  response; run them concurrently and return all results before the next model call. You can turn this off if
  your tools must run one at a time.
- **Repeated**: the same tool many times (paging through results). Give the tool a `cursor` or `page` argument and
  have it say whether more results exist.

```python
import asyncio

async def run_calls(calls, impls):
    async def one(c):
        try:
            return c.id, await impls[c.name](**c.args)
        except Exception as e:
            return c.id, {"error": type(e).__name__, "message": str(e)[:300]}
    return await asyncio.gather(*(one(c) for c in calls))
```

## When a tool fails

Never let an exception kill the loop, and never return a bare stack trace. Return an error the model can act on:

```json
{"error": "not_found", "message": "No customer with email ana@exmple.com. Check spelling or ask the user."}
```

Good error messages name the problem, hint at the fix and stay short. Combined with a retry cap, this lets the
agent correct a typo, try a different tool, or ask the user, instead of inventing an answer.

## Keeping results small

A tool that returns a 2 MB JSON blob will blow the context and drown the useful part. Defences: return only the fields
the agent needs, cap rows (`limit`, with a "more available" flag), truncate long text with a note saying so, and
for large data save the full result somewhere and return a handle plus summary.

## Read-only vs side effects

Sort every tool into one of two groups:

| Read-only | Consequential |
|-----------|---------------|
| `search_orders`, `get_invoice`, `read_file` | `refund_order`, `send_email`, `delete_record`, `run_sql_write` |
| Safe to retry and run in parallel | Needs authorisation checks in code, idempotency keys, often human approval |

Enforce this in your code, not the prompt: the tool implementation checks the user's permissions, validates
amounts against limits, and for anything irreversible returns "awaiting approval" until a person confirms. The model
should never hold credentials broader than the user it acts for.

Rewrite this weak tool definition: name `do_db`, description "Database tool", one argument `q: string` (raw SQL).
The agent needs to look up a product's price and stock by SKU.

Replace it with a narrow, read-only tool: name `get_product`, description "Look up one product by SKU. Returns name,

## Check yourself

1. Two tools, `search_kb` and `search_docs`, keep getting confused. What do you change first?

<details>
<summary>Answer</summary>

Their names and descriptions: say exactly what each covers and when not to use it, or merge them into one tool with
a `source` enum. Then measure selection on a small test set.
</details>

2. What should a tool return when its input is invalid?

<details>
<summary>Answer</summary>

A short structured error naming the problem and a likely fix (e.g. "not_found: check the email spelling"), not a
stack trace or empty string, so the model can correct itself.
</details>

3. Why enforce permissions inside the tool instead of in the system prompt?

<details>
<summary>Answer</summary>

Prompts can be ignored or overridden (including through injected text). Code checks run every time regardless of
what the model decided.
</details>
