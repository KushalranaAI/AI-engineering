# Running generated code safely

Letting an agent write and run code unlocks a lot: data analysis, file conversion, quick calculations, fixing its own
scripts. It also means running a program that nobody reviewed, written by a model that may have been steered by text
it read on a web page five minutes ago. The rule is simple: **generated code never runs in your application's
process or on your application's host with its credentials.** It runs somewhere disposable, with as little access as
possible.

## Why not just `exec()`?

```python
exec(model_output)   # never do this in a server
```

Code run this way has everything your app has: environment variables with API keys, database connections, the
filesystem, the internal network, and unlimited CPU. Even without malice, model code can `rm` the wrong directory,
loop forever, fill the disk or allocate 50 GB. Python-level "restricted" interpreters are not a security boundary;
they have a long history of escapes. You need isolation at the operating system or VM level.

## Sandbox options

| Option | Isolation | Notes |
|--------|-----------|-------|
| Hosted code sandboxes (E2B, Modal sandboxes, Daytona and similar) | Separate microVM or container per session, off your hosts | Fast to adopt; pay per use; data leaves your network |
| Provider code tools (e.g. a model API's built-in code execution) | Runs on the model provider's infrastructure | Simplest; limited packages and control |
| Containers you run (Docker + gVisor, or Firecracker microVMs) | Strong if configured carefully | Full control; you own the hardening |
| Plain Docker with defaults | Weaker; shares the host kernel | Acceptable only with the restrictions below and nothing sensitive on the host |

For most teams starting out, a hosted sandbox is the quickest safe choice.

## Limits to set

Whatever you use, set every one of these:

- **Filesystem**: a scratch directory only; mount input files read-only; nothing from the host.
- **Network**: off by default. If needed, allow specific domains through an egress proxy. Open network plus
  private data equals an exfiltration path.
- **Credentials**: no secrets in the sandbox environment. If code must call an API, route it through a narrow
  service you control.
- **Time**: wall-clock timeout per execution (e.g. 30 s) and per session.
- **Resources**: memory, CPU, process count and disk quotas.
- **Lifetime**: destroy the sandbox after the task; never reuse one across users.

A locked-down local container as a sketch:

```python
import subprocess, tempfile, pathlib

def run_python_sandboxed(code: str, timeout_s: int = 30) -> dict:
    with tempfile.TemporaryDirectory() as work:
        pathlib.Path(work, "main.py").write_text(code)
        cmd = [
            "docker", "run", "--rm",
            "--network=none",                 # no network
            "--memory=512m", "--cpus=1", "--pids-limit=128",
            "--read-only", "--tmpfs", "/tmp:size=64m",
            "--cap-drop=ALL", "--security-opt", "no-new-privileges",
            "--user", "65534:65534",          # nobody
            "-v", f"{work}:/work:ro", "-w", "/work",
            "python:3.12-slim", "python", "main.py",
        ]
        try:
            p = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout_s)
            return {"exit_code": p.returncode, "stdout": p.stdout[-4000:], "stderr": p.stderr[-2000:]}
        except subprocess.TimeoutExpired:
            return {"exit_code": None, "error": f"Timed out after {timeout_s}s"}
```

(If you add `--runtime=runsc` with gVisor installed, the container also gets a user-space kernel, a much stronger
boundary.)

## Returning output

The sandbox result goes back into the model's context, so treat it like any tool result:

- return exit code, the **tail** of stdout and stderr (errors are usually at the end), truncated to a budget;
- for files (charts, CSVs), store them and return a name, size and short preview, not the bytes;
- label output as data. Code output can contain text an attacker planted in an input file, so don't let it be
  read as instructions.

A good error return is what makes the "write, run, read error, fix" loop work: the model needs the traceback line,
not 300 lines of pip logs.

## Blast radius

Ask "if this code were written by an attacker, what is the worst it could do?" and design until the answer is "waste
a little compute in a throwaway box". Concretely: no secrets inside, no network or allow-listed network, per-task
sandboxes, resource caps, and human approval before any code result is used to change real systems (for example,
a generated SQL migration is reviewed before it runs against production).

## Try it

An agent analyses an uploaded CSV with pandas and must produce a chart. List the sandbox settings you'd use and what
the tool returns to the model.

<details>
<summary>Reference</summary>

Fresh sandbox per task with pandas and matplotlib preinstalled (so no network needed for `pip`), network disabled,
CSV mounted read-only, writable scratch directory for the chart, 60 s timeout, ~1 GB memory, no credentials. The tool
returns exit code, the last ~2,000 characters of stdout/stderr, and for the chart a stored file id plus dimensions
(and perhaps a one-line description). The app shows the chart to the user from the stored file.
</details>

## Check yourself

1. Why isn't a "safe" Python interpreter with blocked builtins enough?

<details>
<summary>Answer</summary>

Language-level restrictions are routinely bypassed (introspection, imports through other paths). Real isolation
comes from the OS/VM layer: separate filesystem, network, process and resource limits.
</details>

2. Which single sandbox setting most reduces data exfiltration risk?

<details>
<summary>Answer</summary>

Disabling network access (or allow-listing only specific domains through a proxy), combined with keeping secrets
out of the sandbox.
</details>

3. Why return the tail of stderr rather than the head?

<details>
<summary>Answer</summary>

Tracebacks put the actual exception at the end; the tail gives the model the line it needs to fix the code while
staying within the output budget.
</details>
