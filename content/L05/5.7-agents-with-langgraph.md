# Agents with LangGraph

A hand-written `while` loop is perfect for learning and fine for small agents. It gets painful when you need to
survive a crash halfway through a 20-minute run, pause for a human to approve a refund, or explain to a colleague
why the agent took path B instead of path A. **LangGraph** is a low-level runtime for exactly that: you describe the
agent as a graph over explicit state, and it handles persistence, resumption and interrupts. It doesn't write your
prompts or hide the loop; it makes the loop explicit.

## State, nodes and edges

- **State**: a typed object (usually a `TypedDict`) that every step reads and updates. Fields can have
  **reducers** that say how updates merge; `add_messages` appends to the message list instead of replacing it.
- **Nodes**: plain Python functions `state -> partial update`. A node can call a model, run tools, transform
  data or make a decision.
- **Edges**: which node runs next. Normal edges are fixed; **conditional edges** call a function on the state
  to choose.

## A tool-using agent as a graph

```python
from typing import Annotated, TypedDict
from langchain.chat_models import init_chat_model
from langchain_core.tools import tool
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import InMemorySaver

@tool
def get_invoice(invoice_id: str) -> dict:
    """Look up an invoice by id, e.g. INV-2207."""
    return {"id": invoice_id, "amount": 129.0, "status": "failed", "reason": "card_expired"}

class State(TypedDict):
    messages: Annotated[list, add_messages]
    steps: int

llm = init_chat_model("openai:gpt-4.1-mini").bind_tools([get_invoice])   # example model

def agent(state: State):
    return {"messages": [llm.invoke(state["messages"])], "steps": state.get("steps", 0) + 1}

def route(state: State):
    last = state["messages"][-1]
    if state["steps"] >= 8:
        return END                      # loop guard lives in the graph, not the prompt
    return "tools" if last.tool_calls else END

g = StateGraph(State)
g.add_node("agent", agent)
g.add_node("tools", ToolNode([get_invoice]))
g.add_edge(START, "agent")
g.add_conditional_edges("agent", route, ["tools", END])
g.add_edge("tools", "agent")            # the loop: tools always go back to the model

app = g.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "ticket-881"}}
out = app.invoke({"messages": [("user", "Why did INV-2207 fail?")], "steps": 0}, config)
print(out["messages"][-1].content)
```

The shape `agent → (tools → agent)* → END` is the ReAct loop from lesson 5.2, drawn as a graph. The difference is
that every hop is a recorded step.

## Checkpoints and resuming

When you compile with a **checkpointer**, LangGraph saves the state after every step under the `thread_id`. Use
`InMemorySaver` for tests and a durable one (Postgres, SQLite, Redis) in production. That gives you:

- **resume after failure**: if the process dies at step 6, invoke again with the same `thread_id` and it continues
  from the last checkpoint instead of starting over;
- **multi-turn conversations**: the next user message on the same thread sees the previous state;
- **time travel**: load an earlier checkpoint, change something, and replay from there.

## Human approval with interrupts

For consequential actions, pause the graph and wait for a person:

```python
from langgraph.types import interrupt, Command

def issue_refund(state: State):
    proposal = state["messages"][-1].tool_calls[0]["args"]
    decision = interrupt({"action": "refund", "args": proposal})   # pauses here, state is saved
    if decision != "approve":
        return {"messages": [("user", "Refund rejected by reviewer.")]}
    # ... perform the refund with an idempotency key ...
```

The first `invoke` returns with the interrupt payload. Your UI shows it to a reviewer, maybe hours later, and you
continue with `app.invoke(Command(resume="approve"), config)`. Because state is checkpointed, nothing is held in memory
while waiting.

## Debugging with state

`app.get_state(config)` shows the current values and which node runs next. `app.get_state_history(config)` lists every
checkpoint, so you can see exactly what the model saw at step 4 and which edge it took. Paired with a tracing tool
such as LangSmith or an OpenTelemetry-based tracer, this answers "why did it do that?" without guesswork.

## Graph or plain loop?

| Use a plain loop when | Use a graph when |
|----------------------|------------------|
| Short runs, seconds long | Runs take minutes or hours |
| No approval steps | People must approve or edit mid-run |
| One path: model ↔ tools | Distinct phases (plan, execute, verify) with branches |
| Losing a run is fine | Runs must survive restarts |
| You're prototyping | Several people maintain and debug it |

LangGraph also has prebuilt agents (one function that builds the standard tool loop). Use them, but know the graph
underneath so you can customise it.

## Try it

Add a `verify` node to the graph above that runs after the agent produces a final answer. It checks that the answer
mentions the invoice id and a reason; if not, it adds a message asking the agent to fix it and routes back to `agent`.
Limit verification to two retries.

<details>
<summary>Reference</summary>

Add `verify_attempts: int` to `State`. Change `route` to return `"verify"` instead of `END` when there are no tool
calls. In `verify`, check the last message's content; on success return `{}` and route to `END`; on failure return
`{"messages": [("user", "Your answer must include the invoice id and the failure reason.")], "verify_attempts":
n + 1}`. A conditional edge from `verify` goes to `END` if passed or `verify_attempts >= 2`, else back to `agent`.
</details>

## Check yourself

1. What does a reducer like `add_messages` do?

<details>
<summary>Answer</summary>

It defines how a node's update merges into existing state: here, new messages are appended (or matched by id)
instead of replacing the whole list.
</details>

2. What do you need for a run to resume after the process crashes?

<details>
<summary>Answer</summary>

A durable checkpointer (e.g. Postgres) and the same `thread_id`; invoking again continues from the last saved
checkpoint.
</details>

3. How does an interrupt differ from asking for approval in the prompt?

<details>
<summary>Answer</summary>

An interrupt actually halts execution in code and saves state until a resume command arrives; the action can't run
without it. A prompt instruction only asks the model to wait, which it may not do.
</details>
