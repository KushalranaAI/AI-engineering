# Agent frameworks compared

By now you can write an agent loop, tools, memory, multi-agent delegation and checkpointing yourself. Frameworks
package those pieces. They save time, but each one makes different choices about how much it hides, and switching
later is painful. The best way to choose is to build the **same small agent** in a few of them and compare what you had
to write, what you could control and what you could see when it broke.

## The reference agent

Use one task for every framework: "Given a GitHub repo name, fetch its open issues, group them by theme and draft a
short triage note." Tools: `list_issues(repo)`, `get_issue(number)`. Requirements: a step limit, one approval before
posting the note, and a trace you can inspect.

Here it is with the OpenAI Agents SDK, one of the lightest options:

```python
from agents import Agent, Runner, function_tool

@function_tool
def list_issues(repo: str) -> list[dict]:
    """List open issues for a GitHub repo like 'owner/name'. Returns number and title."""
    return github.list_open_issues(repo)[:50]

@function_tool
def get_issue(repo: str, number: int) -> dict:
    """Get one issue's title, labels and first 1,000 characters of body."""
    return github.get_issue(repo, number)

triager = Agent(
    name="Triager",
    instructions="Group open issues into 3-6 themes and write a short triage note with issue numbers.",
    tools=[list_issues, get_issue],
    model="gpt-4.1-mini",            # example; any supported model
)

result = Runner.run_sync(triager, "Triage open issues in acme/widgets", max_turns=12)
print(result.final_output)
```

Rebuild it in two or three others and keep notes on the table below.

## The main options

**LangGraph.** Low-level graph of nodes and edges over explicit, typed state, with checkpointing, interrupts and
time travel built in. Strongest when control flow, durability and human-in-the-loop matter. More code for simple
agents; you design the graph yourself (prebuilt agents help).

**Google Agent Development Kit (ADK).** Open-source, code-first framework with agents, sessions and state, tools,
multi-agent composition (including workflow agents that run sub-agents in sequence, parallel or loops), plus a
local dev UI, evaluation tooling and deployment paths, notably to Google Cloud. Supports A2A for talking to remote
agents. Works with Gemini first but can use other models.

**CrewAI.** Built around role-based collaboration: you define agents with roles and goals, tasks, and a **Crew**
that runs them. **Flows** add event-driven, more deterministic orchestration around crews when you need tighter
control. Quick to get a multi-agent prototype; the role metaphor can hide what prompts actually run.

**Agno.** Python framework with three levels: **Agents** (one model plus tools, memory and knowledge), **Teams**
(agents coordinating) and **Workflows** (deterministic, code-defined steps). Puts emphasis on performance and a
runtime that serves agents as an API.

**OpenAI Agents SDK.** A thin, code-first loop: agents with tools, **handoffs** between agents, sessions for history,
**guardrails** that run checks on input and output, and built-in **tracing**. Works with non-OpenAI models through
adapters. Close to the hand-written loop, so easy to reason about; less built-in durable execution than a graph
runtime.

## Comparing them

Fill this in from your own builds rather than from marketing pages; the honest answers change with each release.

| Dimension | Questions to ask |
|-----------|------------------|
| Abstraction level | How much of the loop and prompts can I see and change? |
| Control over execution | Can I force fixed steps, branches, loops and limits in code? |
| State and persistence | Is state typed and explicit? Can a run resume after a crash? |
| Multi-agent support | Handoffs, supervisors, parallel workers? How is context passed? |
| Tool integrations | How do I define tools? Is there a library of ready ones? |
| MCP and A2A | Can it consume MCP servers? Expose or call A2A agents? |
| Debugging and observability | Built-in tracing? OpenTelemetry export? A local UI? |
| Deployment | Library only, or a server/runtime? Tied to a cloud? |
| Model flexibility | Easy to swap providers or use open-weight models? |

A rough first impression many engineers report:

| Need | Usually a good starting point |
|------|------------------------------|
| Long-running, resumable, approval-heavy workflows | LangGraph |
| Simple single agent or handoffs, fast to write | OpenAI Agents SDK or Agno |
| Google Cloud deployment, Gemini, A2A | Google ADK |
| Role-based multi-agent prototype | CrewAI |

Treat that as a hypothesis to test, not a rule.

## What not to choose on

GitHub stars, the number of integrations listed, or a demo that looks impressive. Choose on the dimensions above for
your actual architecture, and on how quickly you can debug a failing run at 2 a.m. Whatever you pick, keep your tools
and prompts in plain modules you own so a framework change doesn't mean a rewrite.

## Try it

Build the reference agent in two frameworks. For each, record lines of code, how you added the step limit and the
approval step, and what the trace showed when you made `get_issue` fail on purpose.

A typical result: the Agents SDK version is the shortest; the step limit is `max_turns`, approval needs your own
check (or a tool that only returns a "pending approval" result) and the trace shows the failed tool call with its

## Check yourself

1. Why build the same agent in several frameworks instead of reading comparisons?

<details>
<summary>Answer</summary>

You see directly what each hides, how much control you keep, and how debuggable it is on your own task; published
comparisons go stale quickly and reflect other people's needs.
</details>

2. Which framework features matter most for an agent that waits days for approval?

<details>
<summary>Answer</summary>

Durable persistence of state, resumption by thread or session id, and first-class interrupts or human-in-the-loop
support.
</details>

3. How do you limit lock-in whatever framework you choose?

<details>
<summary>Answer</summary>

Keep tools, prompts and business logic in plain modules you own, use standards like MCP for tools, and treat the
framework as the orchestration layer only.
</details>
