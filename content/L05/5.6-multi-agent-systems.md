# Multi-agent systems

A multi-agent system is several agent loops, each with its own instructions, tools and context, that cooperate on one
job. It's an appealing idea ("a team of specialists"), and sometimes the right one. It's also the easiest way to
multiply your cost, latency and debugging time. The skill is knowing which situation you're in.

## Good reasons to split

Split work across agents when the pieces genuinely need something different:

- **different tools or permissions**: a researcher that browses the web shouldn't also hold the tool that writes
  to your production database;
- **different instructions** that conflict if merged into one prompt (a strict reviewer vs a creative writer);
- **different models**: a cheap fast model for triage, a stronger one for hard reasoning;
- **context isolation**: a subtask needs to read 200 pages, and only the 1-page conclusion should reach the main
  agent;
- **parallelism**: independent subtasks can run at the same time.

"It feels more organised" is not on the list.

## The common shapes

| Pattern | How it works | Fits |
|---------|-------------|------|
| Orchestrator and workers | One agent plans and delegates subtasks to workers, then combines results | Research, report writing, broad investigations |
| Sequential handoff | Agent A finishes its part and passes control to agent B | Triage then specialist (support: router → billing agent) |
| Parallel specialists | Several agents look at the same input from different angles; results are merged or voted | Code review (security, style, performance), document checks |
| Hierarchical | Supervisors manage teams that have their own supervisors | Very large tasks; rarely needed in practice |

## An orchestrator

The simplest robust implementation treats each worker as a **tool** of the orchestrator. The orchestrator's model
decides which worker to call with what brief; each worker is its own agent loop and returns a short result.

```python
from dataclasses import dataclass

@dataclass
class WorkerResult:
    ok: bool
    summary: str           # short, for the orchestrator's context
    sources: list[str]
    detail_ref: str | None # where the full output is stored

def make_worker_tool(name, system_prompt, tools, model):
    def run(brief: str) -> dict:
        try:
            out = run_agent(system_prompt, brief, tools, model, max_steps=12)
            ref = save_artifact(name, out.full_text)
            return WorkerResult(True, out.summary[:1500], out.sources, ref).__dict__
        except Exception as e:
            return WorkerResult(False, f"{name} failed: {e}", [], None).__dict__
    return run

worker_tools = {
    "research_web": make_worker_tool("researcher", RESEARCH_PROMPT, [web_search, fetch_page], "strong-model"),
    "analyse_data": make_worker_tool("analyst", ANALYST_PROMPT, [run_sql_readonly], "strong-model"),
}
# The orchestrator is a normal agent whose tools are worker_tools.
```

Key details:

- **Briefs, not transcripts.** Send each worker a self-contained task: goal, constraints, what to return. Workers don't
  see the orchestrator's whole history.
- **Short returns.** Workers return a summary plus a reference to full output, so the orchestrator's context stays
  small.
- **Structured results** with an `ok` flag make failure handling explicit.

## When a worker fails

Decide the policy in code: retry once with the error appended to the brief; if it fails again, try an alternative
worker or a simpler approach; if the subtask is essential, stop and escalate to a human with what you have. Give
each worker its own step and token budget, and give the whole run a total budget, so one stuck worker can't drain
everything.

## The usual problems

| Problem | What you see | Mitigation |
|---------|-------------|-----------|
| Duplicate work | Two workers search the same thing | Orchestrator keeps a task list in state; workers get distinct briefs |
| Coordination overhead | More tokens spent talking than working | Fewer, broader workers; summaries only |
| Context growth | Orchestrator context fills with worker outputs | Return summaries plus references |
| Conflicting results | Workers disagree | Explicit merge step that compares sources; flag conflicts to the user |
| Latency and cost | Several model calls per worker, multiplied | Parallelise independent work; cap workers |
| Hard debugging | "Which agent made this mistake?" | Trace every agent call with a shared run id |

## A2A and MCP

**MCP** connects an agent to tools, data and prompts. **A2A** (Agent2Agent, an open protocol started by Google and
now under the Linux Foundation) connects agents to *other agents*, possibly built by different teams or vendors, using
published "agent cards" that describe what an agent can do and an interface for sending it tasks and getting
results. Inside one codebase you rarely need A2A: a function call or a framework handoff is enough. It matters when
independently deployed agents have to cooperate across team or company boundaries.

## One agent is often enough

A single capable agent with a well-designed set of tools is easier to build, cheaper to run and simpler to debug. Move
to several agents when you can name the concrete benefit (isolation, permissions, parallelism, different models) and
measure it. A good test: build the single-agent version first, then check whether the split version beats it on your
eval set by enough to justify the extra cost.

## Try it

You're building a "weekly competitor report": find news about five competitors, summarise each, then write one report.
Sketch the single-agent and multi-agent designs and say which you'd ship first.

<details>
<summary>Reference</summary>

Single agent: tools `web_search`, `fetch_page`; it loops through competitors and writes the report. Simple, but its
context fills with five companies' raw pages. Multi-agent: an orchestrator spawns five parallel researcher workers
(one per competitor) that each return a 200-word summary with sources, then a writer step composes the report. The
split is justified by context isolation and parallelism. Ship the single agent first if it fits comfortably; switch
once you see context bloat or slow runs, and compare both on quality and cost.
</details>

## Check yourself

1. Give two legitimate reasons to split one agent into several.

<details>
<summary>Answer</summary>

Any two of: different tools or permissions, conflicting instructions, different models, context isolation for big
subtasks, and parallel execution of independent work.
</details>

2. Why should workers return summaries plus a reference rather than full output?

<details>
<summary>Answer</summary>

To keep the orchestrator's context small and focused; the full output stays available for later steps that need
details.
</details>

3. How do MCP and A2A differ?

<details>
<summary>Answer</summary>

MCP standardises how an agent reaches tools, resources and prompts. A2A standardises how independent agents discover
each other and exchange tasks and results.
</details>
