# What an agent is

"Agent" gets used for almost anything that calls an LLM. A more useful definition: an **agent** is a system where the
model decides what happens next. It picks an action, your code runs it, the model reads the result and picks again,
until it decides the job is done. That one property, the model controlling the flow, is what makes agents powerful,
and also what makes them slow, expensive and hard to test.

## The loop

Every agent, however fancy, is a variation on this:

```
goal ──► model decides ──► run action (tool) ──► observe result ──┐
              ▲                                                    │
              └────────────────── not done yet ◄──────────────────┘
                                   done ──► final answer
```

In code, the skeleton is short:

```python
def run_agent(goal: str, tools: dict, max_steps: int = 10) -> str:
    messages = [{"role": "user", "content": goal}]
    for _ in range(max_steps):
        reply = call_model(messages, tools=list(tools))   # model chooses
        if reply.tool_call is None:                       # model says "done"
            return reply.text
        result = tools[reply.tool_call.name](**reply.tool_call.args)
        messages += [reply.as_message(), tool_result(reply.tool_call.id, result)]
    return "Stopped: step limit reached."
```

Everything else in this level (planning, memory, multi-agent, LangGraph) is about making that loop smarter, safer or
more durable.

## Call, chain, workflow, agent

The cleanest way to tell these apart is to ask **who decides the next step**.

| Shape | Who decides the next step | Example |
|-------|---------------------------|-------|
| Single LLM call | Nobody, there is one step | Summarise this ticket |
| Chain | Your code, fixed order | Extract fields, then translate, then format |
| Workflow | Your code, with branches | Classify the ticket; if billing, run billing prompt, else FAQ prompt |
| Agent | The model, at run time | "Find why invoice 4411 failed and fix it if it's safe" |

Workflows can still use the model for decisions (a router is an LLM call that picks a branch), but the set of
possible paths is written in your code. In an agent, the path is discovered while running.

## Where agents earn their keep

Agents fit tasks that are **open-ended** and **multi-step**, where you can't list the steps in advance because they
depend on what earlier steps reveal:

- debugging: read the error, open the file it points to, run the test, try a fix, re-run;
- research: search, notice a gap, search again with a better query, compare sources;
- operations: check a dashboard, query logs for the spike, look up the deploy that preceded it.

The common thread: the next useful action depends on the last observation.

## When a workflow is better

If you can draw the flowchart, build the flowchart. A fixed workflow is:

- **cheaper**: a known number of model calls instead of 3 to 30;
- **faster**: steps can run in parallel and you skip "thinking" turns;
- **testable**: each step has a defined input and output you can evaluate;
- **predictable**: it can't wander into an unrelated tool or loop forever.

Many "agent" projects in production are really workflows with one LLM-powered router, and they're better for it.
A good habit: start with the simplest shape that works and promote to an agent only when the fixed version keeps
failing on cases where the path genuinely varies.

## The parts of an agent

| Part | What it does | Typical failure if missing or weak |
|------|--------------|-----------------------------------|
| Model | Chooses actions and writes answers | Bad tool choices, poor reasoning |
| Instructions | Role, goal, rules, output format | Off-task actions, wrong tone |
| Tools | The actions it can take | Can't finish, or invents answers |
| State / memory | What it knows so far | Repeats steps, forgets constraints |
| Control loop | Runs model and tools in turn | (the loop is the agent) |
| Stop conditions | Done signal, step/time/cost limits | Runs forever, burns budget |

Notice that only one row is the model. Most of the engineering is in the other five.

## Try it

For each task, say whether you would build a chain, a workflow or an agent, and why:

1. Turn every new support email into a JSON record (customer, product, sentiment).
2. Given a GitHub issue, reproduce the bug in the repo and propose a patch.
3. Answer HR policy questions from a fixed handbook.

<details>
<summary>Reference</summary>

1. **Chain** (or a single structured-output call). The steps never change: extract, validate, store.
2. **Agent.** Reproducing a bug requires reading code, running commands and reacting to what comes back; the
   path differs for every issue.
3. **Workflow**: retrieve, then answer with citations, perhaps with a router for "not in the handbook". RAG with
   fixed steps is enough; an agent would add cost and unpredictability with no benefit.
</details>

## Check yourself

1. What single question distinguishes a workflow from an agent?

<details>
<summary>Answer</summary>

Who decides the next step. In a workflow your code defines the possible paths (even if an LLM picks a branch). In
an agent the model chooses actions at run time and the path isn't fixed in advance.
</details>

2. Give three reasons to prefer a workflow when both would work.

<details>
<summary>Answer</summary>

Lower and more predictable cost, lower latency (fewer calls, parallel steps), easier testing of each step, and no
risk of loops or wandering into unrelated tools.
</details>

3. Your agent sometimes runs for 40 steps and never answers. Which component is missing or weak?

<details>
<summary>Answer</summary>

Stop conditions: a step limit, time and cost budgets, and a clear done criterion in the instructions. Weak state can
contribute too (it repeats actions because it forgot it already did them).
</details>
