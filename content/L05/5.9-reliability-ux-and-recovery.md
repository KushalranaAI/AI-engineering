# Reliability, UX and recovery

A demo agent succeeds when everything goes right. A production agent is judged by what happens when things go wrong:
the API times out, the model picks the wrong tool, the user closes the tab, the process restarts mid-refund. This
lesson is about making failure boring: bounded, recoverable and visible to the user.

## How agents fail

| Failure | Symptom | First fix |
|---------|---------|-----------|
| Wrong tool | Searches docs when it should query orders | Sharper tool descriptions; fewer overlapping tools |
| Bad arguments | Invalid ids, wrong date format | Enums and formats in the schema; actionable error messages |
| Tool unavailable | Timeouts, 5xx | Retries with backoff, then a fallback or a clear failure |
| Repeated actions | Same call over and over | Repeat detector in the loop |
| Incomplete plan | Stops after step 2 of 5 | Plan in state; check all steps are done before finishing |
| Infinite loop | Never answers | Step, time and token budgets |
| Context growth | Gets slower, forgets the goal | Truncate tool results; summarise history (Level 6) |

Log every model call and tool call with a run id so you can tell which of these happened.

## Budgets

Put hard limits in code, checked before every step:

```python
import time
from dataclasses import dataclass, field

@dataclass
class Budget:
    max_steps: int = 15
    max_seconds: float = 120
    max_tokens: int = 200_000
    max_cost_usd: float = 0.50
    max_retries_per_tool: int = 2
    started: float = field(default_factory=time.monotonic)
    steps: int = 0
    tokens: int = 0
    cost: float = 0.0

    def check(self) -> str | None:
        if self.steps >= self.max_steps:              return "step limit"
        if time.monotonic() - self.started > self.max_seconds: return "time limit"
        if self.tokens >= self.max_tokens:            return "token limit"
        if self.cost >= self.max_cost_usd:            return "cost limit"
        return None
```

When a budget trips, stop cleanly: save state, tell the user what was done and what wasn't, and offer to continue.

## Idempotent actions

Retries are only safe if repeating an action doesn't repeat its effect. A "send invoice" call that times out may have
succeeded; retrying blindly sends two. Make consequential tools idempotent:

- generate an **idempotency key** per intended action (e.g. hash of run id, step and arguments) and pass it to
  the downstream API (most payment APIs support this) or check it in your own table before acting;
- prefer "set" over "increment" operations (`set_status("closed")` rather than `toggle_status()`);
- record completed actions in run state so a resumed run skips them.

```python
def refund_order(order_id: str, amount_cents: int, run_id: str, step: int):
    key = f"{run_id}:{step}:refund:{order_id}:{amount_cents}"
    if actions.exists(key):
        return actions.get(key)                     # already done: return the same result
    result = payments.refund(order_id, amount_cents, idempotency_key=key)
    actions.save(key, result)
    return result
```

## Persist to resume

Save run state (goal, plan, completed steps, results, pending approvals) after every step to a durable store. Then a
crash, deploy or approval that takes two days doesn't lose work. LangGraph checkpointers do this for you; in a
hand-written loop, write a row per step.

## Fallbacks and escalation

Decide in advance what happens when the agent can't continue:

1. retry the step (bounded);
2. try an alternative tool or a simpler deterministic path;
3. return a partial result with an honest explanation;
4. hand off to a human, with the run's state and log attached so they don't start from zero.

Some cases should always escalate: low confidence on a consequential action, repeated failures, a policy
boundary, or the user asking for a person.

## Showing progress

Long-running agents feel broken if the screen is blank for 40 seconds. Stream structured events, not raw tokens:

```json
{"type": "step",   "label": "Searching orders for ana@example.com"}
{"type": "result", "label": "Found 3 orders", "sources": ["order A-1093"]}
{"type": "approval_needed", "action": "refund_order", "args": {"order_id": "A-1093", "amount": "€42.00"}}
```

Show the current task, the tool being used in plain words, key results and sources, and approval requests with
exactly what will happen.

## User control

Give people buttons that map to real operations:

- **Cancel**: set a flag the loop checks before every step; don't start new actions; report what already happened.
- **Pause / resume**: stop after the current step and resume from saved state later.
- **Redirect**: let the user add an instruction ("skip the EU customers") that is injected into state before the
  next model call.

## Clear without oversharing

Users need to understand what the agent did, not read its raw internal reasoning. Raw reasoning is verbose, can
contain half-formed or wrong ideas presented as facts, and may expose system prompt details. Prefer short, written-for-
users step labels and a final summary of actions taken with sources. Keep detailed traces for your engineers.

## Try it

Your agent processes expense reports and calls `approve_expense(report_id)`. The call timed out, the worker
restarted, and the run resumed. Describe what must be true so the expense isn't approved twice and the user sees the
right status.

<details>
<summary>Reference</summary>

The run state was saved before the call with the step marked "in progress" and an idempotency key (run id + step +
report id). On resume, the agent retries with the same key; the expense system (or your action table) recognises the
key and returns the original result instead of approving again. Approval being a "set status" operation also makes it
safe. The UI subscribes to run events, so after resume it shows "Expense R-551 approved" once, plus a note that a
retry happened.
</details>

## Check yourself

1. Why isn't a step limit alone enough?

<details>
<summary>Answer</summary>

A few steps can still take a long time or cost a lot (huge contexts, slow tools). You also need time, token and
cost budgets, plus repeat detection.
</details>

2. What makes a retry safe for a consequential action?

<details>
<summary>Answer</summary>

Idempotency: an idempotency key or a check of completed actions so repeating the call returns the original result
instead of repeating the side effect.
</details>

3. What should the user see when the agent hits its budget?

<details>
<summary>Answer</summary>

A clear stop with a summary of what was completed, what wasn't, any partial results with sources, and an option to
continue or hand off, with state saved so continuing doesn't redo work.
</details>
