# Memory basics

LLMs are stateless: each API call knows only what you send in that call. Everything that looks like memory (the
assistant remembering your name, an agent recalling a decision from yesterday) is your code storing information and
putting the right parts back into the prompt. This lesson covers the basic kinds of memory and the four operations
you need. Advanced compression and offloading come in Level 6.

## Four things people call "memory"

| Kind | What it holds | Lifetime | Where it lives |
|------|---------------|----------|----------------|
| Conversation history | The raw messages so far | One session | The message list |
| Task state | Plan, steps done, intermediate results | One task/run | A typed object or DB row |
| Short-term memory | What matters for this session, possibly condensed | One session | History + a running summary |
| Long-term memory | Facts, preferences, past outcomes | Across sessions | Database or vector store, per user |

Keeping these separate in your code makes each one easier to inspect, test and delete.

## Short-term memory

The simplest version is the message list itself. It works until the conversation grows past what you want to pay
for or the model handles well. Two basic fixes:

- **Trim**: keep the system prompt, the first user message (often the goal) and the last N turns.
- **Summarise**: when history passes a threshold, replace older turns with a summary that keeps decisions,
  constraints and open questions.

```python
def build_short_term(messages, summary, keep_last=8):
    head = [messages[0]]                                  # system prompt
    if summary:
        head.append({"role": "system", "content": f"Summary of earlier conversation:\n{summary}"})
    return head + messages[-keep_last:]
```

When trimming, don't split a tool call from its tool result; most APIs reject an orphaned result.

## Long-term memory

Long-term memory needs a store keyed by user (or tenant) and a way to find relevant entries. A common pattern is
small text facts plus embeddings, the same machinery as RAG:

```python
from datetime import datetime, timezone

class MemoryStore:
    def __init__(self, db, embed):
        self.db, self.embed = db, embed

    def write(self, user_id, text, kind="fact"):
        self.db.insert(user_id=user_id, text=text, kind=kind,
                       vector=self.embed(text), updated=datetime.now(timezone.utc))

    def search(self, user_id, query, k=5):
        return self.db.top_k(vector=self.embed(query), k=k, filter={"user_id": user_id})

    def update(self, memory_id, new_text):
        self.db.update(memory_id, text=new_text, vector=self.embed(new_text),
                       updated=datetime.now(timezone.utc))

    def forget(self, memory_id):
        self.db.delete(memory_id)
```

Always filter by `user_id`. A memory store without strict per-user filtering is a data leak waiting to happen.

## Deciding what to keep

Storing every message is cheap to build and expensive to live with: retrieval returns noise and stale facts. Store
distilled items instead:

- **facts**: "Works in the Berlin office", "Uses Postgres 16";
- **preferences**: "Prefers answers in bullet points", "Wants metric units";
- **summaries** of finished tasks: "Migrated the billing job to the new queue on 3 Nov; rollback plan in DOC-88";
- **outcomes**: what worked or failed last time.

A cheap way to get these: after each session (or every few turns), ask a model to extract candidate memories as JSON
with a type and a confidence, and only write ones above a threshold.

## Write, read, update, forget

1. **Write**: extract and store a new item.
2. **Read**: retrieve the few items relevant to the current request (semantic search plus filters such as type or
   recency), not the whole store.
3. **Update**: when a new fact contradicts an old one ("I moved to the Munich office"), change or replace the old
   item rather than storing both. A simple approach: on write, search for similar memories and ask a model whether the
   new one adds, updates or duplicates them.
4. **Forget**: delete on user request, expire stale items, and support full deletion for privacy obligations.

## Putting it together

Per request: load the user's top-k relevant memories, add them to the prompt in a clearly labelled section ("Known
about this user"), build short-term context from history, call the model, then extract and write new memories in the
background so the user doesn't wait.

## Try it

Design the memory for a cooking assistant. A user said last week "I'm vegetarian" and today says "I've started eating
fish again". List what is stored after each session and what gets retrieved when they ask "What should I cook tonight?"

<details>
<summary>Reference</summary>

After week 1: `{kind: preference, text: "Vegetarian"}`. Today the extractor finds a contradicting fact; the update
step finds the similar memory and replaces it with `"Pescatarian: vegetarian plus fish (since Nov 2026)"` rather than
adding a second, conflicting entry. For "What should I cook tonight?", retrieval returns the diet preference and any
other cooking preferences (spice level, equipment), and the prompt includes them in a labelled section. The raw chat
transcripts are not injected.
</details>

## Check yourself

1. Why shouldn't you inject the full conversation history into every request?

<details>
<summary>Answer</summary>

It grows cost and latency with every turn, eventually exceeds the window, and fills the context with noise that can
distract the model. Retrieve or summarise what matters instead.
</details>

2. What goes wrong if long-term memory only ever appends?

<details>
<summary>Answer</summary>

Contradicting and stale facts pile up, retrieval returns both old and new versions, and the model may act on
outdated information. You need update and forget operations.
</details>

3. What is the most important filter on every memory query?

<details>
<summary>Answer</summary>

The user (or tenant) id, so one person's memories can never be retrieved for another.
</details>
