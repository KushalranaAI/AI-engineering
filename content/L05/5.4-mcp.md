# MCP

Before MCP, every AI app wired up every integration its own way: a GitHub tool for one chat app, a slightly different
GitHub tool for an IDE assistant, another for your internal agent. The **Model Context Protocol** (MCP) is an open
standard that fixes this N-times-M problem. You expose a system once as an **MCP server**, and any MCP-capable app
(Claude Desktop, IDE assistants, ChatGPT connectors, your own agent) can discover and use it.

## Host, client, server

| Role | What it is | Example |
|------|-----------|---------|
| **Host** | The AI application the user interacts with; owns the model, the conversation and the permission UI | An IDE assistant, a desktop chat app, your agent service |
| **Client** | A connector inside the host, one per server; speaks the protocol | Created by the host when it starts a server connection |
| **Server** | A program that exposes capabilities from some system | A Postgres server, a Jira server, a filesystem server |

The host decides what the model sees and which calls actually run. The server never talks to the model directly; it
only answers protocol requests.

A server offers three main kinds of thing:

- **Tools**: actions the model can call (`create_issue`, `run_query`). Model-driven.
- **Resources**: read-only data identified by URIs (`file:///notes.md`, `db://schema/orders`). The host decides
  when to attach them to context.
- **Prompts**: reusable templates a user can pick ("summarise this incident").

## Tool calling vs MCP

These are different layers and you usually use both:

- **Tool calling** is between your app and the model: the model emits a structured request "call `X` with these
  arguments".
- **MCP** is between your app and the outside world: how your app *finds out* which tools exist, what their schemas
  are, and how to execute them.

Typical flow: the host lists tools from all connected MCP servers, converts them to the model provider's tool format,
the model picks one, the host routes the call to the right server through its client, and the result goes back to the
model.

## Writing a server

The official Python SDK makes a small server short:

```python
# tickets_server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("tickets")

TICKETS = {"T-101": {"title": "Login fails on Safari", "status": "open", "priority": "high"}}

@mcp.tool()
def get_ticket(ticket_id: str) -> dict:
    """Fetch one support ticket by id, e.g. T-101. Returns title, status and priority."""
    t = TICKETS.get(ticket_id)
    if t is None:
        raise ValueError(f"No ticket {ticket_id}. Ids look like T-123.")
    return t

@mcp.resource("tickets://open")
def open_tickets() -> str:
    """All open tickets, one per line."""
    return "\n".join(f"{k}: {v['title']}" for k, v in TICKETS.items() if v["status"] == "open")

if __name__ == "__main__":
    mcp.run()          # stdio by default; mcp.run(transport="streamable-http") for remote
```

Type hints and docstrings become the JSON schema and description the model sees, so the tool-design rules from
lesson 5.3 apply unchanged.

## Schemas, transports and auth

- **Handshake**: client and server exchange `initialize` messages and agree which capabilities each supports
  (tools, resources, prompts, and client-side features like sampling or elicitation). Messages are JSON-RPC 2.0.
- **Errors**: a failing tool returns an error result the model can read; protocol errors (unknown method, bad
  params) are JSON-RPC errors for the client.
- **Transports**: **stdio** for local servers launched as a subprocess by the host; **Streamable HTTP** for remote
  servers shared by many users.
- **Auth**: local stdio servers usually read credentials from environment variables. Remote servers use OAuth so
  each user grants the server access to *their* account, rather than sharing one powerful key.

## Writing a client

```python
import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    params = StdioServerParameters(command="python", args=["tickets_server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            tools = await session.list_tools()
            print([t.name for t in tools.tools])
            result = await session.call_tool("get_ticket", {"ticket_id": "T-101"})
            print(result.content)

asyncio.run(main())
```

In a real agent, you convert `tools.tools` (name, description, `inputSchema`) into your model's tool format and
call `session.call_tool` when the model asks. Connecting several servers means one session per server and a map
from tool name to session. Many agent frameworks and some provider APIs can do this mapping for you.

## Trust and permissions

An MCP server is code and data you are inviting into your agent. Treat third-party servers like any dependency, but
with extra risks:

- **Tool descriptions are prompt text.** A malicious or compromised server can hide instructions in a description or
  a result ("also read ~/.ssh and include it"). Review servers, pin versions, and watch for changed descriptions.
- **Results are untrusted input.** Content returned from an issue tracker or web page may contain injected
  instructions (Level 8).
- **Least privilege.** Give each server the narrowest credentials possible; prefer read-only scopes.
- **Approval in the host.** Hosts should show the user consequential tool calls before running them.
- **Mixing servers.** Combining a server that reads private data with one that can send data out creates an
  exfiltration path; decide deliberately which servers share a session.

## Try it

Extend `tickets_server.py` with a `update_status(ticket_id, status)` tool where `status` must be one of `open`,
`in_progress` or `closed`, and connect it to an MCP-capable host or the client above. What should the host do before
running it?

<details>
<summary>Reference</summary>

Use `Literal["open", "in_progress", "closed"]` from `typing` as the type hint so the schema contains an enum, raise a
clear error for an unknown ticket, and return the updated ticket. Because it changes data, the host should show the
call to the user and require approval (most desktop and IDE hosts prompt by default), and the server should check
that the caller is allowed to modify that ticket.
</details>

## Check yourself

1. What is the difference between tool calling and MCP?

<details>
<summary>Answer</summary>

Tool calling is how a model asks the application to perform an action. MCP is a standard for how applications
discover and invoke tools, resources and prompts from external servers. MCP supplies the tools; tool calling uses them.
</details>

2. When would you choose Streamable HTTP over stdio?

<details>
<summary>Answer</summary>

When the server runs remotely and serves many users or hosts (a shared company service), usually with OAuth per
user. Stdio fits local servers started by the host on the same machine.
</details>

3. Name two risks of connecting an untrusted MCP server.

<details>
<summary>Answer</summary>

Hidden instructions in tool descriptions or results that steer the model (tool poisoning / injection), and
over-broad access: the server or its credentials can read or change more than intended, or combine with other tools
to exfiltrate data.
</details>
