# Load testing with Locust

The app works for you and for the three colleagues who tried it. What happens with 200 people at once? You can guess, or
you can **load test**: simulate many concurrent users and watch latency, errors and throughput. For LLM apps this matters
more than usual, because requests are slow (seconds, not milliseconds), hold a connection for a long time (streaming) and
often hit a provider rate limit before they hit your CPU. **Locust** is a Python load-testing tool where you describe user
behaviour in code.

## What to learn from a load test

You are looking for the **knee**: the concurrency at which latency starts climbing faster than throughput. Along the way
answer:

- Which limit do we hit first: our code, the database, the provider's rate limit (429 errors) or GPU capacity (12.4)?
- What is p95 and p99 latency, and time to first token, at expected peak?
- How do errors behave beyond the knee: graceful 429s and queueing, or timeouts and crashes?

The load-test simulator in the Practice area (and the latency tail ideas in 12.4) show why p99 explodes past ~70% utilisation.

## Writing a locustfile

Install with `pip install locust`. A locustfile defines a user class with tasks:

```python
# locustfile.py
import json, random, time
from locust import HttpUser, task, between

QUESTIONS = [json.loads(l)["input"] for l in open("golden.jsonl")]

class ChatUser(HttpUser):
    wait_time = between(5, 15)            # think time between messages, like a real person

    @task
    def ask(self):
        q = random.choice(QUESTIONS)
        self.client.post("/chat", json={"message": q}, name="/chat")
```

`wait_time` is crucial: real users read and type. With no wait, 100 "users" behave like thousands. Draw questions from a real
distribution (your golden set from 7.7 or sampled logs), because identical prompts hit caches and give flattering numbers.

## Streaming endpoints

A `200 OK` returned after the full stream tells you total time but not what the user feels. Measure **time to first token
(TTFT)** and total time yourself, and report them to Locust as custom metrics:

```python
    @task
    def ask_stream(self):
        q = random.choice(QUESTIONS)
        start = time.perf_counter()
        first = None
        with self.client.post("/chat/stream", json={"message": q}, stream=True,
                              name="/chat/stream", catch_response=True) as r:
            for chunk in r.iter_lines():
                if chunk and first is None:
                    first = time.perf_counter() - start
            total = time.perf_counter() - start
            if r.status_code != 200 or first is None:
                r.failure(f"bad response {r.status_code}")
            else:
                r.success()
        if first is not None:
            self.environment.events.request.fire(
                request_type="TTFT", name="/chat/stream", response_time=first * 1000,
                response_length=0, exception=None, context={})
```

(Locust's API evolves; check the current docs for the event fields.) Now the statistics table shows a separate TTFT row.

## Ramp shapes

Run with the web UI (`locust -f locustfile.py --host http://localhost:8000`) and set **users** and **spawn rate**, or run
headless for CI:

```bash
locust -f locustfile.py --host https://staging.example.com \
  --headless -u 200 -r 5 -t 10m --csv results --exit-code-on-error 1
```

`-u` is peak users, `-r` is users added per second, `-t` the duration. Use different **shapes** for different questions:

- **Ramp**: increase steadily to find the knee.
- **Spike**: jump to a high load for a minute to see how fast autoscaling reacts (10.11).
- **Soak**: moderate load for hours to expose leaks, rate-limit resets and cost.

A custom `LoadTestShape` class can script these (stages with a user count and duration).

## Reading results

Locust reports requests per second, percentile response times (50/90/95/99) and failures, and plots users, RPS and latency
over time. Read them together:

1. RPS rises with users, then flattens: that flat point is capacity.
2. p95 and p99 rise before RPS flattens: the tail warns you first.
3. Failures starting at some user count: note the type (429 from the provider, 502/504 from the load balancer, timeouts).

Record the result as a sentence you can put in a README: "1 replica sustains 18 concurrent users at p95 TTFT under 1.5
s; at 25 users p95 TTFT is 6 s and 3% of requests time out."

## Real provider or mock

A load test against the real model costs money and may trip rate limits. Decide what you are testing:

- **Mock provider** (a stub returning a canned stream after a fixed delay): tests *your* code, database, networking and
  autoscaling cheaply and repeatably. Most load tests should use this.
- **Real provider** for a short run: finds the provider's actual limits and latency under concurrency. Cap spend and tell the
  provider if you will hit them hard.

## Try it

A single pod handles 10 concurrent chats with p95 TTFT of 1.2 s. At 30 concurrent chats the p95 TTFT is 9 s, and RPS has not
risen. The pod's CPU is at 20%. What is likely happening, and what do you test next?

<details>
<summary>Reference</summary>

The service is not CPU-bound; requests are waiting for something else: a worker pool or connection limit in the app (for
example too few Uvicorn workers or a small HTTP client pool), or the provider rate limit queueing requests. Check the app's
concurrency settings and the provider's 429s and latency, raise the limits or add replicas, and rerun the ramp. CPU is the
wrong signal to scale on here.
</details>

## Check yourself

1. Why does `wait_time` matter in a locustfile?

<details>
<summary>Answer</summary>

It models the pause real users take between actions. Without it each simulated user sends requests continuously, which
overstates the load per user and gives misleading capacity numbers.
</details>

2. Why measure time to first token separately for a streaming endpoint?

<details>
<summary>Answer</summary>

Users feel how soon text starts appearing, not just when the stream ends, and a successful status code says nothing about
either, so TTFT must be measured explicitly.
</details>

3. When should you load test against a mock provider instead of the real one?

<details>
<summary>Answer</summary>

When you are testing your own code, infrastructure and autoscaling: it is cheap, repeatable and avoids rate limits. Use the
real provider only for short runs that discover its actual limits.
</details>
