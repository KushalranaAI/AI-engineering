# Evals as a release gate

In Level 7 you built an evaluation suite and ran it by hand. A suite you run by hand gets skipped the week it matters.
This lesson turns it into a **gate**: an automated check that every change must pass before it can ship, exactly like
unit tests. The rule is that a prompt edit, a model swap and a retrieval tweak go through the same gate as a code change.

## Evals as ordinary tests

DeepEval lets you write eval cases as pytest tests. Each test builds a test case (input, actual output, retrieved
context, optionally the expected answer) and asserts that metrics clear a threshold.

```python
# tests/evals/test_rag.py
import json, pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import (
    FaithfulnessMetric, AnswerRelevancyMetric, ContextualPrecisionMetric,
)
from app.rag import answer_with_context   # returns (answer, list_of_chunk_texts)

CASES = json.load(open("evals/rag_eval_v3.json"))   # the fixed Level 7 set

@pytest.mark.parametrize("case", CASES, ids=lambda c: c["id"])
def test_rag_case(case):
    answer, chunks = answer_with_context(case["question"])
    tc = LLMTestCase(
        input=case["question"],
        actual_output=answer,
        expected_output=case["expected"],
        retrieval_context=chunks,
    )
    assert_test(tc, [
        FaithfulnessMetric(threshold=0.80),
        AnswerRelevancyMetric(threshold=0.75),
        ContextualPrecisionMetric(threshold=0.70),
    ])
```

Run it with `deepeval test run tests/evals/test_rag.py` (or plain `pytest`). The metrics use an LLM judge under the
hood, so the judge model is itself something to pin.

For the agent, score behaviour rather than prose: did it pick the right tools (DeepEval has a tool-correctness metric
that compares called tools with expected ones), did it finish the task, and how many steps did it take. Step count is
easy to compute yourself from the trace and catches loops that a quality metric would miss.

## Setting thresholds

Per-case asserts are strict. Many teams gate on **aggregate** scores instead, compared to the recorded baseline:

| Metric | Baseline | Tolerance | Gate fails below |
|---|---|---|---|
| Faithfulness (mean) | 0.86 | 0.03 | 0.83 |
| Answer relevance (mean) | 0.82 | 0.03 | 0.79 |
| Context precision (mean) | 0.74 | 0.04 | 0.70 |
| Agent task completion | 0.90 | 0.05 | 0.85 |
| Agent mean steps | 4.2 | +1.0 | above 5.2 |

The tolerance exists because of noise. Set it from data: run the unchanged baseline five times and look at how much
the mean moves. If it wobbles by 0.02, a 0.01 tolerance will fail random builds and people will learn to ignore the gate.

## Living with non-determinism

- **Fix sampling where you can**: temperature 0 (or low) for the app under test when the product allows it, and for the
  judge always.
- **Repeat runs** on small or high-variance sets and average.
- **Tolerance bands**, as above, rather than exact equality.
- **Look at flips**: a case that passes and fails alternately is telling you the prompt or retrieval is fragile.

## Fast subset, full suite

Evals cost money and time. A back-of-envelope for a 300-case suite with three judged metrics:

```
300 cases × (1 app call + 3 judge calls) = 1,200 LLM calls
~2,500 tokens each                       ≈ 3M tokens per run
at an example blended $1 per 1M tokens   ≈ $3 per run, 5-10 minutes with modest concurrency
```

Cheap per run, but not something to run on every keystroke. A common split:

- **On every pull request**: a fast subset of 30-50 cases covering each category and every past regression.
- **Before release** (merge to main, or nightly): the full suite.

## Synthetic cases, checked by a person

DeepEval's synthesizer can generate question-and-answer cases from your documents, which helps cover topics your
hand-written set missed. Treat generated cases as drafts: a person reads each one, fixes or deletes bad ones, and only
then adds them to a new version of the dataset. An unreviewed synthetic case can encode a wrong answer and fail
correct behaviour forever.

## Record every gated run

Log each gate run to MLflow with the commit, prompt version and model as parameters and the aggregate scores as
metrics. Over months this becomes a history of each metric, and when faithfulness slowly erodes you can see which
release started it.

## Try it

Deliberately weaken your RAG prompt (for example, remove "answer only from the context") and run the gate. Confirm it
fails and that the output names the failing metric.

<details>
<summary>Reference</summary>

Removing the grounding instruction usually lets the model fill gaps from its own knowledge, so faithfulness drops while
relevance may stay the same or even rise. The DeepEval report should show failing cases with `FaithfulnessMetric`
below threshold and the judge's reason ("the output contains claims not present in the retrieval context"). If the gate
passes anyway, your eval set lacks questions whose answers are missing from the corpus: add a few, as a new dataset
version, so the gate can see this class of regression.
</details>

## Check yourself

1. Why should a prompt-only change go through the same gate as a code change?

<details>
<summary>Answer</summary>

Because a prompt change can alter behaviour across every request just as much as code can, and nothing else (types,
unit tests) will catch it. The gate is the only automatic check on behaviour.
</details>

2. How do you choose a tolerance band for a metric?

<details>
<summary>Answer</summary>

Run the unchanged baseline several times and measure how much the score varies by chance. Set the tolerance a little
wider than that noise so the gate fails on real regressions, not random variation.
</details>

3. Why is mean step count a useful agent gate metric?

<details>
<summary>Answer</summary>

It catches loops and wasted calls that output-quality metrics can miss: the agent may still finish correctly but take
twice as many steps, which doubles cost and latency.
</details>
