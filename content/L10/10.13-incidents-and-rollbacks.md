# Incidents and rollbacks

Every production system has incidents. LLM applications have the usual ones (a bad deploy, a full disk) plus a set of
their own, and some of those don't throw a single error: the service is up, latency is fine, and the answers are
quietly worse. This lesson is about recognising those incidents and reaching for the right lever quickly.

## The LLM-shaped incidents

| Incident | How it shows up | Signal that catches it |
|---|---|---|
| Provider outage | 5xx or timeouts from the model API | Error-rate alert, readiness check failing |
| Silent model update | Same code, different tone or format; more refusals; parse failures | Online eval scores drop, schema re-ask rate rises |
| Prompt regression | Quality drop right after a prompt label moved | Online evals and feedback split by prompt version |
| Stale index | Answers cite old policies, "not found" for new docs | Freshness metric (age of newest indexed doc), user feedback |
| Runaway agent | One task makes dozens of calls | Steps-per-task metric, spend spike per request |
| Cost spike | Spend climbs faster than traffic | Daily spend alert, cost-per-request panel |

## Match the lever to the cause

The most common mistake in an incident is pulling the wrong lever, for example redeploying the previous image when the
problem was a prompt that lives in a registry and was never part of the image.

| Cause | Lever | Time to effect |
|---|---|---|
| Provider outage | Switch to fallback model/provider (gateway config or feature flag) | Seconds to minutes |
| Prompt regression | Move the `production` label back to the previous prompt version | Seconds, plus cache TTL |
| Bad code or dependency | Redeploy the previous image tag | Minutes |
| Stale or corrupted index | Re-run ingestion, or point config at the previous index build | Minutes to hours |
| Runaway agent / cost spike | Lower step and spend caps, disable the offending tool, rate-limit the client | Minutes |
| Silent model update | Pin back to the previous snapshot if still available; otherwise adjust prompt and re-evaluate | Hours |

A fallback model is useful only if you prepared it: the fallback has been run through your eval suite, its prompt
variant exists, and switching is a config flag rather than a code change.

```python
# a minimal kill switch read on every request (from config service, flag tool or env)
def pick_model(flags) -> str:
    if flags.get("force_fallback"):
        return flags["fallback_model"]        # evaluated ahead of time, not picked during the incident
    return flags["primary_model"]
```

## Runbooks

A runbook is a short page per incident type, written calmly in advance so nobody improvises at 2 a.m.

```markdown
## Runbook: provider outage
Signal:   HighErrorRate alert AND provider status page shows incident, OR >20% timeouts to provider for 5 min
First action: set force_fallback=true; confirm error rate falls within 5 minutes on the dashboard
Who decides: on-call engineer flips the flag; product owner is told if fallback quality is noticeably lower
Afterwards: unset the flag once provider errors are < 1% for 30 minutes; write the incident note
```

Keep it short enough to read under pressure: the signal, the first move, who decides, how to undo.

## Re-evaluate on model changes

Providers announce deprecations and new snapshots ahead of time. Treat each announcement as a change request: run the
full eval suite against the new model in staging, compare with the current baseline, adjust prompts if needed, and
only then switch. If you rely on an alias, schedule a periodic eval run anyway, because aliases can move without a
release note that reaches you.

## Blameless reviews

After each incident, write a short review: timeline, impact, cause, what detected it, what fixed it, what will change.
Blameless means asking "what made this easy to get wrong?" rather than "who did it?", because people hide mistakes
from a process that punishes them, and hidden mistakes repeat.

One LLM-specific rule: every incident that involved a wrong answer adds at least one case to the eval suite. The
question that broke production should never be able to break it again unnoticed.

## Try it

In staging, simulate a provider outage and time how long the app takes to fall back and then recover.

<details>
<summary>Reference</summary>

Simulate the outage by pointing the primary provider's base URL at a non-routable address, injecting failures in your
gateway, or revoking the staging key. Record timestamps for: first failed request, alert fired, fallback active
(errors stop), primary restored, fallback switched off. If falling back is manual, the dominant delay is usually the
time to notice and act; consider automatic fallback after N consecutive failures (a circuit breaker) and compare the
timings. Also check what users saw during the gap: a clear message is acceptable, a spinner that hangs for 60 seconds
is not.
</details>

## Check yourself

1. Answer quality dropped right after a prompt label was moved. Should you redeploy the previous image?

<details>
<summary>Answer</summary>

No. The prompt is not in the image. Move the `production` label back to the previous prompt version; that is faster
and actually reverses the change.
</details>

2. Which LLM incident is most likely to produce no errors at all, and how would you catch it?

<details>
<summary>Answer</summary>

A silent model update or a stale index. Both keep the service healthy while answers get worse. Online evals on sampled
traffic, freshness metrics and user feedback are what catch them.
</details>

3. What should every incident involving a wrong answer leave behind?

<details>
<summary>Answer</summary>

A runbook update if the response was slow or unclear, and at least one new eval case reproducing the failure, so the
gate catches it next time.
</details>
