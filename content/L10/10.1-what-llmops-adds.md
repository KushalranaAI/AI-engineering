# What LLMOps and AgentOps add

You already know how to ship ordinary software: write code, test it, deploy it, watch it. An LLM application looks
like ordinary software from the outside, a web service that takes requests and returns responses. Inside, it behaves
differently in ways that break the usual habits. **LLMOps** is the set of practices for shipping, running and improving
LLM applications safely. This lesson is about what it adds on top of what you already do.

## LLMOps and MLOps

Classic MLOps grew up around models you train yourself: data pipelines, feature stores, training runs, model
registries, drift detection. Some of that carries straight over (experiment tracking, versioned artifacts, monitoring
for drift). But most teams building with LLMs never train a model. They call someone else's.

| | Classic MLOps | Application LLMOps |
|---|---|---|
| Main artifact | Trained weights | Prompts, config, retrieval setup, code |
| Who changes the model | You, when you retrain | The provider, sometimes without telling you |
| Testing | Accuracy on a held-out set | Evals with graders, often LLM judges |
| Cost driver | Training compute | Tokens on every single request |

That gives two flavours. **Model LLMOps** is training, fine-tuning and hosting models: GPU clusters, checkpoints,
serving stacks. **Application LLMOps** is running products on top of models that already exist. This level is about the
second, because that is what most AI engineers do every day.

## Why LLM apps are harder to operate

- **Output is not deterministic.** The same input can produce different answers, so "the test passed once" proves less.
- **Prompts are behaviour.** Changing one sentence in a system prompt can change answers across thousands of queries,
  and no compiler or type checker notices.
- **The model can change under you.** An alias like `latest` may point to a new snapshot next month. Even pinned
  versions get retired.
- **Every request costs money.** A bug that loops an agent is a bug that spends money, fast.

## What a release actually contains

In a normal service, a release is a commit. In an LLM app, the thing that decides behaviour is wider:

```
release = code
        + prompts (system prompt, templates, few-shot examples)
        + model id and sampling settings
        + retrieval config (chunk size, top-k, reranker)
        + index contents (which documents, embedded with which model)
        + tool definitions (names, descriptions, schemas)
```

Every one of those can change an answer. If you only version the code, you cannot tell why Tuesday's answers differ
from Monday's. The rule for the rest of this level: all six parts are versioned, recorded with each request, and
changed through the same checks.

## Operating RAG vs operating agents

The two apps you carry into this level fail differently.

| | RAG app | Agent |
|---|---|---|
| Typical silent failure | Stale index, retrieval quietly returning worse chunks | Loops, wrong tool picked, tool errors swallowed |
| Cost profile | Predictable per request | Variable; one task can take 3 calls or 40 |
| Key metrics | Faithfulness, context precision, freshness | Task completion, steps per task, tool error rate |
| Main safety lever | Grounding checks | Step, spend and permission limits |

## AgentOps: what agents add on top

**AgentOps** is LLMOps for systems that take multiple steps and use tools. Everything above still applies, and these
things become more important:

- **Run-level tracing.** One user request can be 20 model calls and 10 tool calls. You need the whole tree, with timing,
  tokens and cost per step, to see where a run went wrong (10.12).
- **Trajectory evals.** Judge the path (tool choice, order, wasted steps), not only the final answer (7.12).
- **Hard limits.** Caps on steps, wall-clock time and spend per run, with a clear failure when they trigger (5.9).
- **Replay.** Re-run a saved trace against a new prompt or model to see what would change.
- **Action audit.** A log of every consequential action, who or what approved it, and with which inputs (8.6).
- **Memory operations.** Stores that need their own versioning, deletion and decay jobs (6.14).

The same release discipline applies: version the prompts, tools and memory policies together, gate on evals, and have a
rollback.

## The lifecycle

This level walks through one loop, in order:

**track** experiments and prompts, **evaluate** every change, **guard** requests at runtime, **serve** behind an API,
**ship** through CI/CD, **deploy** to the cloud, **monitor** in production, then **improve** by turning failures into
new eval cases and going round again.

## Try it

Your RAG app's code is frozen. Write down everything that could still make its answers different tomorrow. For each one,
say whether you could currently detect it.

<details>
<summary>Reference</summary>

A typical list:

- The provider updates the model behind an unpinned alias. Detectable only if you log the exact model version returned.
- Someone edits a prompt stored in a registry or config. Detectable if prompts are versioned and logged per request.
- New or edited documents are ingested, or old ones deleted. Detectable if index builds are versioned.
- The embedding model behind the API changes. Rarely detectable unless you record the model per vector.
- A dependency upgrade changes chunking or parsing. Detectable only with pinned dependencies and eval runs.
- A provider changes safety filtering or default parameters.

Most teams starting out can detect almost none of these. That is the gap this level closes.
</details>

## Check yourself

1. Why is "the release is a git commit" not true for an LLM application?

<details>
<summary>Answer</summary>

Because behaviour also depends on prompts, the model version, retrieval settings, index contents and tool definitions,
which often live outside the code repository and can change independently. All of them have to be versioned together.
</details>

2. What is the difference between application LLMOps and model LLMOps?

<details>
<summary>Answer</summary>

Application LLMOps runs products on top of existing models (prompts, retrieval, evals, deployment, monitoring). Model
LLMOps covers training, fine-tuning and hosting the models themselves. Most teams only do the first.
</details>

3. Name one failure that is typical of an agent but rare in a RAG app.

<details>
<summary>Answer</summary>

A runaway loop, where the agent keeps calling tools without finishing, burning tokens and time. Others: calling the
wrong tool, or passing bad arguments to a tool that has side effects.
</details>
