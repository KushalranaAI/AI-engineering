# Deploying on AWS

Your images are built and tagged by CI. Now they need somewhere to run that survives a crashed machine, a bad release
and a traffic spike. This lesson uses plain building blocks on AWS (EC2, IAM, Secrets Manager, CodeDeploy, an
Application Load Balancer and Auto Scaling) because they show every moving part. Container services like ECS or a
managed platform hide some of these, but the ideas are identical.

## The shape

```
users → ALB (HTTPS, idle timeout raised) → target group → EC2 instances in an Auto Scaling group
                                                           each runs your container
                                                           IAM role → Secrets Manager, ECR/Docker Hub, CloudWatch
CI → CodeDeploy → rolls new image tag onto instances, health checks decide go/rollback
```

## EC2 with a role, not keys

Launch instances from a launch template whose user data installs Docker and the CodeDeploy agent. Attach an **IAM
instance role** that allows exactly what the app needs: read one secret, pull images, write logs. Never copy access
keys onto the machine; the role gives the instance short-lived credentials automatically, and they cannot leak from a
config file because there is none.

## Secrets Manager

Store provider API keys in AWS Secrets Manager and fetch them at container start:

```python
import json, os, boto3

def load_secrets(secret_id: str = "support-rag/prod") -> None:
    sm = boto3.client("secretsmanager")             # credentials come from the instance role
    values = json.loads(sm.get_secret_value(SecretId=secret_id)["SecretString"])
    for k, v in values.items():
        os.environ.setdefault(k, v)                 # e.g. OPENAI_API_KEY, LANGFUSE_SECRET_KEY

load_secrets()
```

Rotating a key becomes "update the secret, restart the containers", with no image rebuild.

## Releases with CodeDeploy

CodeDeploy runs a release on each instance by following an `appspec.yml` with lifecycle hooks. The last hook,
`ValidateService`, is where you decide whether the release is healthy.

```yaml
# appspec.yml
version: 0.0
os: linux
hooks:
  ApplicationStop:
    - location: scripts/stop.sh          # docker stop the old container
      timeout: 60
  ApplicationStart:
    - location: scripts/start.sh         # docker pull $IMAGE_TAG && docker run ...
      timeout: 180
  ValidateService:
    - location: scripts/validate.sh      # curl /readyz and one canned question; exit 1 on failure
      timeout: 120
```

If validation fails, CodeDeploy marks the deployment failed and, with automatic rollback enabled, redeploys the last
successful revision.

| Release style | How it works | Pros | Cons |
|---|---|---|---|
| In-place (rolling) | Replace containers instance by instance | Cheap, simple | Capacity dips during rollout; mixed versions briefly |
| Blue/green | Start a new set of instances, shift ALB traffic, keep the old set for a while | Instant rollback by shifting back | Doubles instances during the switch |

## The load balancer and streaming

An ALB closes a connection if no data passes for its **idle timeout**, 60 seconds by default. A streamed answer
usually sends tokens often enough, but an agent that thinks for 70 seconds before its first token, or a long tool call,
gets cut off. Raise the idle timeout above your longest expected silence (for example 180 s), and send a periodic SSE
comment line (`: keep-alive`) during long pauses. Point the target group health check at `/readyz`.

## Scaling on the right signal

An LLM app spends most of its time waiting on the provider. CPU stays low even when every worker is busy, so CPU-based
scaling never triggers. Scale on **load per instance** instead: the ALB's request-count-per-target metric, or better, a
custom CloudWatch metric for in-flight requests.

Back-of-envelope:

```
peak traffic             = 20 requests/s
average request duration = 6 s (mostly streaming)
in-flight requests       = 20 × 6 = 120            (Little's law)
safe concurrency/instance = 40 (measured in a load test)
instances needed         = 120 / 40 = 3, run 4 for headroom
```

Now check the provider side. If each request uses about 3,000 tokens, 20 requests/s is 3.6M tokens per minute. If your
account's limit for that model is, say, 2M tokens per minute, you will hit 429 errors long before your instances are
busy. **Provider rate limits usually cap throughput first.** Size scaling with them in view, ask for higher limits
ahead of launches, and add a fallback model for overflow.

## Try it

Load-test the deployed app until it scales out. Find out whether the bottleneck was your instances or the provider.

<details>
<summary>Reference</summary>

Use a load tool such as Locust or k6 against the ALB, ramping concurrency slowly. Watch three things together: the
Auto Scaling group's instance count, your in-flight-requests metric, and the rate of provider 429/rate-limit errors in
your logs. If instances are added and latency recovers, the instances were the bottleneck. If errors climb while
instance concurrency is moderate and adding instances does not help, you hit the provider's tokens-per-minute or
requests-per-minute limit. The fix there is a quota increase, a cheaper/smaller model for some traffic, caching, or a
second provider, not more EC2.
</details>

## Check yourself

1. Why scale an LLM app on concurrency rather than CPU?

<details>
<summary>Answer</summary>

Because instances are mostly idle waiting on network I/O to the model provider. CPU stays low even when every worker
slot is occupied, so it never signals the real load.
</details>

2. What does raising the ALB idle timeout fix?

<details>
<summary>Answer</summary>

Long-running streamed or agent requests with gaps of silence longer than the default timeout being cut off by the load
balancer mid-response.
</details>

3. What makes blue/green rollback faster than in-place rollback?

<details>
<summary>Answer</summary>

The old version is still running on its own instances, so rollback just shifts load balancer traffic back, with no
redeploy needed.
</details>
