# Getting your apps production-ready

You do not need a new project to learn LLMOps. You already have two: the RAG app from Level 4 and the agent from
Level 5. This lesson gets both into a shape that the rest of the level can work with. The goal is simple to state:
every setting that changes behaviour is explicit, versioned, and written into the record of every request.

## Configuration, not code

Most notebook-era apps have the model name in one file, the prompt in a string literal in another, and `top_k = 5`
somewhere in the middle. Pull all of it into one config object that is loaded at startup.

```yaml
# config/rag.yaml
app: support-rag
config_version: 7
model:
  id: gpt-4.1-mini-2025-04-14     # example: a dated snapshot, not an alias
  temperature: 0.2
  max_output_tokens: 600
prompt:
  name: rag-answer
  label: production              # resolved from the prompt registry (next lesson)
retrieval:
  embedding_model: text-embedding-3-small
  index: docs-2026-10-30
  chunk_size: 800
  chunk_overlap: 100
  top_k: 8
  reranker: none
```

```python
from pathlib import Path
import yaml
from pydantic import BaseModel

class ModelCfg(BaseModel):
    id: str
    temperature: float
    max_output_tokens: int

class RetrievalCfg(BaseModel):
    embedding_model: str
    index: str
    chunk_size: int
    chunk_overlap: int
    top_k: int
    reranker: str

class AppCfg(BaseModel):
    app: str
    config_version: int
    model: ModelCfg
    retrieval: RetrievalCfg
    prompt: dict

def load_config(path: str) -> AppCfg:
    return AppCfg.model_validate(yaml.safe_load(Path(path).read_text()))
```

Validating with Pydantic means a typo in the YAML fails at startup, not on the hundredth request. For the agent, the
same file also lists which tools are enabled and the step and spend limits.

## Pin everything that can drift

- **Model snapshots.** Use the dated model id where the provider offers one. An alias is convenient in a notebook and
  dangerous in production, because it can point somewhere new without a deploy.
- **Dependencies.** Lock exact versions (`uv lock`, `pip-tools`, or Poetry). A minor bump in a PDF parser or a
  text splitter can change every chunk in your index.
- **Index builds.** Name each index build (`docs-2026-10-30`) and record which embedding model and chunking produced it.
- **Container base images.** Pin a tag or digest rather than `python:latest`.

The test: if you rebuild from the same commit and config next month, you should get the same system.

## Traceable from the first request

Give every request an id and attach the versions that shaped it. Log it with every model call, retrieval and tool call.

```python
import uuid, time, logging, json

log = logging.getLogger("app")

def answer(question: str, cfg: AppCfg, prompt_version: int) -> str:
    request_id = str(uuid.uuid4())
    ctx = {
        "request_id": request_id,
        "config_version": cfg.config_version,
        "model": cfg.model.id,
        "prompt": f"{cfg.prompt['name']}@{prompt_version}",
        "index": cfg.retrieval.index,
    }
    t0 = time.perf_counter()
    chunks = retrieve(question, cfg.retrieval)          # your Level 4 code
    reply = generate(question, chunks, cfg.model)       # your Level 4 code
    ctx["latency_ms"] = round((time.perf_counter() - t0) * 1000)
    log.info(json.dumps(ctx))
    return reply
```

When an answer goes wrong later, this record tells you exactly which combination produced it. Later in the level the
same fields flow into traces and dashboards.

## A fixed yardstick

Bring the evaluation set you built in Level 7 along, unchanged. It is the ruler every later change is measured with:
a new prompt, a new model, a bigger chunk size. If you edit the ruler and the change at the same time, you cannot tell
which one moved the score. Store it in the repo (or a dataset registry) with its own version number, and only add cases
in deliberate, recorded steps.

| Item | Where it lives | Versioned by |
|---|---|---|
| Code | Git | Commit SHA |
| Config | Git (YAML) | `config_version` + commit |
| Prompts | Prompt registry | Prompt version / label |
| Index | Vector DB | Build name |
| Eval set | Git or dataset store | Dataset version |

## Try it

Without touching code, switch your RAG app to a different chunk size and a different model using only config. Rebuild the index, run five questions,
and confirm no Python file changed.

<details>
<summary>Reference</summary>

1. Copy `rag.yaml` to `rag-v8.yaml`; set `chunk_size: 500`, `index: docs-2026-11-06-c500` and a different model id;
   bump `config_version` to 8.
2. Run your ingestion script with `--config config/rag-v8.yaml` so it builds the new index under the new name.
3. Start the app with `APP_CONFIG=config/rag-v8.yaml` and ask your five questions.
4. `git diff --stat` should show only the YAML file. The request logs should show `config_version: 8`, the new model
   and the new index name. If you had to touch code, that setting was still hard-coded: move it into config.
</details>

## Check yourself

1. Why pin a dated model snapshot instead of using the provider's latest alias?

<details>
<summary>Answer</summary>

An alias can be repointed by the provider to a new model, changing your app's behaviour with no deploy and no record.
A dated snapshot only changes when you change it, and you can evaluate the change first.
</details>

2. What should be attached to every request record, at minimum?

<details>
<summary>Answer</summary>

A request id, the model id, the prompt name and version, the config version, and the index build (plus enabled tools
for an agent). With those you can reproduce or explain any answer.
</details>

3. Why keep the eval set fixed while you change the system?

<details>
<summary>Answer</summary>

Because it is the measuring stick. If both the eval set and the system change, a score difference cannot be attributed
to either one. Add new cases deliberately, as a new dataset version.
</details>
