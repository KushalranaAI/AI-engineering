# Monitoring and observability

Once real users arrive, three questions never go away: is it up, is it fast and affordable, and are the answers any
good? The first two are classic monitoring. The third is new, and needs traces and online evaluation. This lesson
builds all three layers.

| Layer | Question | Tool in this lesson |
|---|---|---|
| Infrastructure | Are the machines healthy? | Prometheus + Node Exporter |
| Application | Requests, latency, errors, tokens, blocks? | Prometheus client in the app, Grafana |
| Behaviour | What happened inside this request, and was the answer good? | Langfuse traces, online evals, feedback |

## Infrastructure metrics

Run **Node Exporter** on every instance; it exposes CPU, memory, disk and network on port 9100. **Prometheus** scrapes
those endpoints on a schedule and stores the time series. On AWS, Prometheus can discover instances by tag through its
EC2 service discovery, so new instances from Auto Scaling appear automatically.

## Application metrics

Machine metrics will not tell you that token spend tripled. Export your own from the backend:

```python
from prometheus_client import Counter, Histogram, make_asgi_app

REQUESTS = Counter("app_requests_total", "Requests", ["route", "status"])
LATENCY = Histogram("app_request_seconds", "End-to-end latency", ["route"],
                    buckets=(0.5, 1, 2, 4, 8, 16, 32))
TOKENS = Counter("llm_tokens_total", "Tokens used", ["model", "kind"])        # kind=input|output
COST = Counter("llm_cost_usd_total", "Estimated spend", ["model"])
BLOCKS = Counter("guardrail_blocks_total", "Guardrail blocks", ["guard"])

app.mount("/metrics", make_asgi_app())   # Prometheus scrapes this

def record_llm_usage(model: str, usage, price_in: float, price_out: float):
    TOKENS.labels(model, "input").inc(usage.input_tokens)
    TOKENS.labels(model, "output").inc(usage.output_tokens)
    COST.labels(model).inc(usage.input_tokens * price_in + usage.output_tokens * price_out)
```

Keep label values low-cardinality: model names and routes, never user ids or request ids, or Prometheus memory explodes.

## Dashboards and alerts

A useful first Grafana dashboard has one row per concern: traffic (requests/s), latency (p50 and p95 from the
histogram), error rate, token spend per hour by model, guardrail blocks by guard, and instance CPU and memory. Seeing
spend next to traffic tells you whether a cost rise is "more users" or "each request got more expensive".

Alert only on things a human must act on:

```yaml
groups:
- name: llm-app
  rules:
  - alert: HighErrorRate
    expr: sum(rate(app_requests_total{status=~"5.."}[5m])) / sum(rate(app_requests_total[5m])) > 0.05
    for: 10m
  - alert: LatencyOverBudget
    expr: histogram_quantile(0.95, sum by (le) (rate(app_request_seconds_bucket[10m]))) > 8
    for: 15m
  - alert: DailySpendHigh
    expr: sum(increase(llm_cost_usd_total[24h])) > 200
```

Also alert when Auto Scaling fails to launch instances. Everything else belongs on a dashboard, not in someone's pager.

## Tracing

Metrics say "p95 latency went up". A **trace** says why: this request spent 300 ms in retrieval, 5.8 s in the model and
2 s in a tool. Langfuse records each request as a trace with nested spans for retrieval, generations and tool calls,
including tokens, cost, latency and the prompt version.

```python
from langfuse import observe   # older SDK versions: from langfuse.decorators import observe

@observe()
def retrieve(question): ...

@observe(as_type="generation")
def generate(question, chunks): ...

@observe()
def answer(question):
    chunks = retrieve(question)
    return generate(question, chunks)
```

With the provider integrations (for example Langfuse's OpenAI wrapper), token counts and costs are captured
automatically.

## Online evals and feedback

Offline evals use your fixed set. Production brings questions you never wrote. Two ways to judge them:

- **Online evaluation**: run an LLM judge (faithfulness, relevance) on a sample of live traces, say 5%, and chart the
  scores over time. A drop is often the first sign of a stale index or a silent model change.
- **User feedback**: thumbs up/down, plus implicit signals like rephrasing the same question or copying the answer.
  Attach them to the trace id.

Then close the loop: each week, pull low-scoring or thumbs-down traces, confirm the failure, and add the best ones to
the eval suite as a new dataset version. Production failures become tomorrow's gate.

## Try it

Open yesterday's traces, sort by cost, and take the top request apart: which step spent the tokens, and was that spend necessary?

<details>
<summary>Reference</summary>

Sort traces by total cost in Langfuse (or query your logs by cost). Open the top one and read the spans. Common
culprits: an agent that looped through many tool calls, each resending the whole growing history; a retrieval step
that returned many long chunks; a huge pasted input; or a retry storm after malformed output. Write down the input
tokens per span. The fix follows from the cause: a step cap, smaller top-k or chunk trimming, an input length limit, or
better structured output so re-asks stop.
</details>

## Check yourself

1. Why must user ids never be Prometheus label values?

<details>
<summary>Answer</summary>

Each distinct label value creates a new time series. Unbounded values like user ids create millions of series and
overload Prometheus. Put per-user detail in traces or logs instead.
</details>

2. What can a trace tell you that a latency histogram cannot?

<details>
<summary>Answer</summary>

Where the time and tokens went inside one specific request: which step (retrieval, model, tool) was slow or costly,
with the actual inputs, outputs and prompt version.
</details>

3. Why run online evals on a sample rather than every request?

<details>
<summary>Answer</summary>

Judge calls cost money and add load. A small sample is enough to track quality trends over time while keeping eval
spend a small fraction of serving spend.
</details>
