# Horizontal Pod Autoscaling and vertical scaling

Your load test (10.10) found that one pod handles about 18 concurrent chats. Traffic is 5 at 3 am and 120 at 8 pm. Running
7 pods all night wastes money; running 2 at the evening peak makes users wait. **Autoscaling** adjusts capacity to
demand automatically. Kubernetes has two main forms: **horizontal** (more pods) and **vertical** (bigger pods). For
LLM apps, choosing the right *signal* matters more than the mechanics.

## The HPA control loop

The **HorizontalPodAutoscaler (HPA)** is a control loop. Every 15 seconds or so it reads a metric, compares it with a target, and
sets the replica count with this formula from the Kubernetes docs:

**desiredReplicas = ceil( currentReplicas × currentMetricValue / targetMetricValue )**

Example: 3 replicas, average CPU 75%, target 50% → ceil(3 × 75 / 50) = ceil(4.5) = **5** replicas. If load drops to 20%:
ceil(5 × 20 / 50) = ceil(2) = 2. The metric is an average across pods, so it self-corrects as pods are added.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: chat-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: chat-api}
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 60}}
```

CPU utilisation is measured against the pod's CPU **request**, so the request must be sensible (10.9). The resource metrics
come from the **metrics-server** add-on, which you must install.

## Choosing the metric

CPU is the default and often the wrong choice for LLM apps. A FastAPI service that mostly awaits a model API can hold 50
open streams at 5% CPU. It becomes slow because of concurrency (workers, connections, provider limits), not CPU. Better
signals:

- **In-flight requests per pod** (a gauge your app exports): scale to keep about 15 per pod, below the knee from your load
  test.
- **Queue depth** for worker-based designs (jobs waiting per worker).
- **Requests per second per pod** or p95 latency, though latency reacts after users already feel it.

Custom metrics reach the HPA through a **metrics adapter** (for example the Prometheus adapter, using the metrics from
10.12), or through **KEDA**, an add-on that scales on event sources such as queue length or Prometheus queries and can even
scale to zero.

```yaml
  metrics:
    - type: Pods
      pods:
        metric: {name: inflight_requests}
        target: {type: AverageValue, averageValue: "15"}
```

## Stability

An autoscaler that reacts to every blip flaps: scale up, scale down, scale up. Controls:

- **minReplicas** keeps a floor for availability and quick response; **maxReplicas** caps cost and protects downstream
  limits such as the provider's rate limit or your database connections.
- **Stabilisation windows**: the HPA looks back over recent recommendations before acting. By default scale-down waits
  several minutes (300 s) while scale-up reacts immediately; tune with `behavior`.
- **Policies** limit how fast it moves.

```yaml
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies: [{type: Percent, value: 100, periodSeconds: 60}]   # at most double per minute
    scaleDown:
      stabilizationWindowSeconds: 300
      policies: [{type: Pods, value: 1, periodSeconds: 120}]       # drop one pod per 2 minutes
```

Scale up fast, scale down slowly: users notice a slow scale-up immediately and a slow scale-down never.

## Vertical scaling

The **Vertical Pod Autoscaler (VPA)** adjusts a pod's CPU and memory **requests** instead of the count. Its recommender
is valuable even if you never let it act. Run it in `Off` (recommendation-only) mode, read the suggestions, and set
requests yourself. Rules of thumb: do not let HPA and VPA both scale on the same metric (they fight), and remember that
resizing a pod usually restarts it. Vertical scaling suits workloads that cannot be split, such as an embedding model
that needs more memory.

## Nodes and cold starts

New pods need somewhere to run. If the cluster is full, pods wait **Pending** until new nodes join, which is the job of the
**Cluster Autoscaler** or **Karpenter**. A node takes minutes to start; then the image must be pulled and the app (and any
model files) loaded. So scaling is always later than the spike. Mitigate: keep headroom (`minReplicas`, or CPU target lower
than you think), use small images, pre-pull images, keep a little spare node capacity, and scale on a leading metric
(queue depth) instead of a lagging one (latency). For GPU model servers (12.10) cold starts can take many minutes, so
headroom matters even more.

## Prove it with a load test

Autoscaling configuration is a hypothesis until you test it. Run a Locust ramp (10.10), in a staging cluster, and capture
three charts on one timeline: users, replica count, and p95 latency or errors. A good result shows replicas rising shortly
after load, latency staying inside budget with a brief bump, and replicas falling back after the test. Bad results look
like a long Pending period, flapping, or latency blowing out while replicas are capped at `maxReplicas`.

## Try it

Pods each handle 15 concurrent chats before latency degrades. Peak is 240 concurrent chats. You use an in-flight-requests
HPA with a target of 12 per pod, min 3 and max 25. How many pods at peak, and what could still go wrong?

<details>
<summary>Reference</summary>

At 240 chats, 240 / 12 = 20 pods (within the 25 cap). Risks: scale-up lag (nodes and pull time) means the first minutes of a
spike run under-provisioned, so latency rises before replicas arrive; the provider's rate limit may bind before 20 pods do;
and if all pods start together they may hit the secrets and database endpoints at once. Mitigate with headroom, a gentler
spike ramp, and a load test that includes a sudden jump.
</details>

## Check yourself

1. Apply the HPA formula: 4 replicas, average in-flight per pod is 30, target is 10. What is the new replica count?

<details>
<summary>Answer</summary>

ceil(4 × 30 / 10) = 12 replicas, subject to maxReplicas and the scaling policies.
</details>

2. Why is CPU often a poor scaling signal for an LLM API service?

<details>
<summary>Answer</summary>

The service spends most of its time waiting on the model, so CPU stays low while concurrency and latency climb. In-flight
requests or queue depth track the real limit.
</details>

3. Why scale up quickly but scale down slowly?

<details>
<summary>Answer</summary>

Under-capacity hurts users at once, while extra capacity costs only a little money for a few more minutes. A slow
scale-down also prevents flapping when traffic dips briefly.
</details>
