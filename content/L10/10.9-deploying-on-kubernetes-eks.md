# Deploying on Kubernetes with Amazon EKS

In 10.8 you put the app on EC2 with CodeDeploy. That works, and for one service it can be enough. When you have several
(an API, a worker, an embedding service, a guardrail sidecar), each with its own scaling and rollout needs, you want one
consistent way to run all of them. **Kubernetes** is that layer, and **Amazon EKS** is AWS's managed Kubernetes. This lesson
deploys the FastAPI backend from 10.6 on EKS with health-checked rollouts and a way back. Commands and versions change;
check the current EKS and Kubernetes documentation before running them.

## Why Kubernetes

You describe the **desired state** ("run 3 copies of this image, reachable on this address, with these settings") and
Kubernetes continually works to make reality match. A crashed container is replaced; a new image is rolled out gradually;
a failed rollout stops itself. The price is complexity (new concepts, YAML, cluster upkeep), so it earns its place when you
run multiple services, need fast rollbacks or autoscaling (10.11), or your team already knows it. For a single small app,
EC2 or a managed container service is simpler.

## EKS building blocks

- **Control plane**: the Kubernetes API and scheduler, run and patched by AWS.
- **Nodes**: the machines your pods run on, as **managed node groups** (EC2 instances AWS helps manage) or **Fargate**
  (serverless, per-pod).
- **Pods** (one or more containers), **Deployments** (keep N pods running and roll out updates), **Services** (a stable
  address for a set of pods), **Ingress** (HTTP routing from outside).

The quickest start is `eksctl`:

```bash
eksctl create cluster --name llm-prod --region ap-south-1 \
  --nodegroup-name general --node-type t3.large --nodes 2 --managed
aws eks update-kubeconfig --name llm-prod --region ap-south-1
kubectl get nodes
```

A cluster costs money while it exists (a control-plane fee plus the nodes), so delete practice clusters:
`eksctl delete cluster --name llm-prod`.

## Deployments, Services and Ingress

```yaml
# k8s/app.yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: chat-api}
spec:
  replicas: 3
  selector: {matchLabels: {app: chat-api}}
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxUnavailable: 0, maxSurge: 1}   # never drop below 3 healthy pods
  template:
    metadata: {labels: {app: chat-api}}
    spec:
      serviceAccountName: chat-api            # linked to an IAM role (below)
      containers:
        - name: api
          image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/chat-api:2026-03-09-a1b2c3d
          ports: [{containerPort: 8000}]
          envFrom: [{configMapRef: {name: chat-config}}]
          resources:
            requests: {cpu: "250m", memory: "512Mi"}
            limits:   {memory: "1Gi"}
          readinessProbe: {httpGet: {path: /healthz, port: 8000}, periodSeconds: 5}
          livenessProbe:  {httpGet: {path: /livez,  port: 8000}, periodSeconds: 10, failureThreshold: 3}
---
apiVersion: v1
kind: Service
metadata: {name: chat-api}
spec:
  selector: {app: chat-api}
  ports: [{port: 80, targetPort: 8000}]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: chat-api
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/load-balancer-attributes: idle_timeout.timeout_seconds=300   # long streams
spec:
  ingressClassName: alb
  rules:
    - http: {paths: [{path: /, pathType: Prefix, backend: {service: {name: chat-api, port: {number: 80}}}}]}
```

The **AWS Load Balancer Controller** (installed once in the cluster) watches the Ingress and creates an Application Load
Balancer. Raising the idle timeout is the same streaming lesson as in 10.8: a model reply can pause longer than the
default 60 seconds.

## Config and secrets

Put non-secret settings in a **ConfigMap** (model name, feature flags). Do not put the API key in the manifest or the
image. Give the pod an AWS identity through **IAM roles for service accounts (IRSA)**, so the application can read the key
from Secrets Manager at start-up, exactly as in 10.8, with no static credentials. The service account carries an annotation
naming the IAM role, and the role's policy allows only `secretsmanager:GetSecretValue` on that one secret. (EKS Pod Identity is
a newer alternative; check the docs for which fits your cluster version.)

## Probes and resources

- **Readiness probe**: Kubernetes sends traffic to a pod only when this passes. During a rollout it is what stops traffic
  reaching a pod that has not finished loading. Make `/healthz` check what the app really needs (config loaded, vector store
  reachable), but not the LLM provider, or a provider blip will take every pod out at once.
- **Liveness probe**: restarts a pod that is stuck. Keep it cheap and conservative; an over-eager liveness probe causes
  restart storms.
- **Requests and limits**: requests tell the scheduler how much to reserve; limits cap use. Without a memory limit a
  leaking pod can starve its neighbours; setting a CPU limit too low causes throttling and latency spikes, so many teams set
  CPU requests but no CPU limit.

## Rolling updates and rollback

```bash
kubectl apply -f k8s/app.yaml
kubectl set image deployment/chat-api api=123456789012.dkr.ecr.ap-south-1.amazonaws.com/chat-api:2026-03-10-d4e5f6a
kubectl rollout status deployment/chat-api        # waits until new pods are ready
kubectl rollout undo deployment/chat-api          # one command back to the previous revision
```

With `maxUnavailable: 0` and a working readiness probe, a bad image never replaces healthy pods: the new pod fails its probe,
the rollout stalls, and users stay on the old version. Tie this to your CI/CD pipeline (10.7): the pipeline pushes a tagged
image and runs `kubectl set image` (or applies a Helm chart or Kustomize overlay), then waits on `rollout status` and calls
`rollout undo` if it times out.

## Try it

A new release starts but a config error makes the app crash at start-up. Describe what users experience with
(a) no readiness probe and `maxUnavailable: 1`, and (b) the manifest above.

<details>
<summary>Reference</summary>

(a) Without a readiness probe Kubernetes sends traffic as soon as the container starts, and one old pod is removed per step,
so some requests fail until the pods crash-loop and the rollout is noticed. (b) The new pod never becomes ready, so it
receives no traffic; with `maxUnavailable: 0` the old pods stay in service, `rollout status` times out, and the pipeline runs
`rollout undo`. Users see nothing.
</details>

## Check yourself

1. What does `maxUnavailable: 0` guarantee during a rolling update?

<details>
<summary>Answer</summary>

Kubernetes never removes a healthy pod before a new one is ready, so capacity does not dip below the desired replica count
during the rollout.
</details>

2. Why give pods IAM roles (IRSA) instead of storing AWS keys in a Secret?

<details>
<summary>Answer</summary>

The pod receives short-lived, scoped credentials automatically, so there are no long-lived keys to leak or rotate, and the
role can be limited to exactly the secrets the app needs.
</details>

3. Why should a readiness probe not depend on the LLM provider being up?

<details>
<summary>Answer</summary>

A provider outage would fail every pod's probe at once and remove all of them from service, turning a degraded dependency
into a total outage. Handle provider failures in the application (retries, fallback) instead.
</details>
