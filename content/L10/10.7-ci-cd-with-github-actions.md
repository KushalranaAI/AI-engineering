# CI/CD with GitHub Actions

You now have tests, an eval gate and a Dockerfile. CI/CD wires them into one automatic path so that every change,
including a one-line prompt change, travels the same road to production:

```
push → unit tests → eval gate → build & tag image → push to registry → deploy staging → approve → production
```

Each arrow only fires if the step before it passed. Nothing reaches users without passing the gate.

## The pipeline

```yaml
# .github/workflows/release.yml
name: release
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.lock
      - run: pytest tests/unit -q

  eval-gate:
    needs: test
    runs-on: ubuntu-latest
    # Fork PRs don't receive secrets; skip the gate there rather than fail confusingly
    if: github.event_name == 'push' || github.event.pull_request.head.repo.full_name == github.repository
    env:
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      EVAL_SUBSET: ${{ github.event_name == 'pull_request' && 'fast' || 'full' }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.lock
      - run: python -m evals.gate --subset "$EVAL_SUBSET" --baseline evals/baseline.json

  build:
    needs: eval-gate
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USER }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: ./backend
          push: true
          tags: myorg/support-rag:${{ github.sha }}

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: ./scripts/deploy.sh staging myorg/support-rag:${{ github.sha }}

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production        # configured to require a reviewer
    steps:
      - run: ./scripts/deploy.sh production myorg/support-rag:${{ github.sha }}
```

A few deliberate choices in that file:

- **`needs:`** makes the order strict. The build job cannot start until the eval gate succeeds.
- **The fast subset runs on pull requests and the full suite on merges to main**, balancing feedback speed against
  eval cost.
- **Images are tagged with the commit SHA**, not `latest`. A SHA tag says exactly what code is inside, never moves,
  and makes rollback unambiguous.
- **Only the push to `main` builds and pushes images**, so experimental branches never land in the registry.

## Secrets in pipelines

Store provider keys and registry tokens as repository or environment secrets. GitHub masks them in logs, but you can
still leak them by printing derived values or writing them into artifacts, so never echo them. Workflows triggered by
pull requests from forks do not receive secrets by default, which is a protection, not a bug: otherwise anyone could
open a PR that prints your key. Do not "fix" this by switching to `pull_request_target` with a checkout of the fork's
code; that combination is a well-known way to hand your secrets to strangers.

Use a scoped key for CI with its own spend limit, separate from production. An eval loop gone wrong should hit the CI
budget, not the production one.

## Approval before production

GitHub **environments** can require a named reviewer before a job that targets them runs. Staging deploys
automatically, someone checks it (a smoke test, a glance at the dashboards), then approves production. The approval
is logged with who approved and when, which auditors like.

## Rollback by tag

Because every released image is tagged with its commit and kept in the registry, rolling back is redeploying the
previous tag:

```bash
./scripts/deploy.sh production myorg/support-rag:3f9c2a1   # last known good SHA
```

No rebuild, no waiting for the eval gate, no chance that a rebuild pulls a newer dependency. Keep a retention policy
that holds at least the last several production images.

Remember that prompts in a registry roll back separately, by moving a label. Your runbooks (later in this level) should
say which lever to pull for which problem.

## Try it

Make a PR whose only change is a prompt (the file itself, or the version pinned in config). Follow it through the pipeline.

<details>
<summary>Reference</summary>

On the PR: `test` runs (and passes, since no code changed), then `eval-gate` runs the fast subset against the new
prompt. If scores stay within tolerance, the PR shows green checks; `build` and the deploy jobs are skipped because the
event is a pull request. After merge, the push to `main` reruns tests and the full suite, builds an image tagged with
the merge commit SHA, deploys to staging, and waits for approval before production. The key observation: a "text only"
change still had to prove itself on the eval set. If the prompt lives in a registry instead of the repo, add a
separate workflow (or registry webhook) that runs the gate when the staging label moves.
</details>

## Check yourself

1. Why tag images with the commit SHA instead of `latest`?

<details>
<summary>Answer</summary>

A SHA tag is immutable and identifies the exact code inside. `latest` moves, so you cannot tell what is running and
cannot reliably roll back to it.
</details>

2. Why don't fork pull requests get your secrets, and what should the pipeline do about it?

<details>
<summary>Answer</summary>

Because untrusted code from the fork could read and exfiltrate them. The pipeline should skip secret-dependent steps
such as the eval gate for fork PRs, and run them after a maintainer merges or re-runs the branch internally.
</details>

3. What makes rollback fast in this design?

<details>
<summary>Answer</summary>

The previous gated image already exists in the registry under its SHA tag, so rollback is a redeploy of a known
artifact, with no rebuild and no new risk.
</details>
