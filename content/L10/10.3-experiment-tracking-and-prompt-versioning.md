# Experiment tracking and prompt versioning

Two weeks into tuning a RAG app, someone asks "which settings gave us that 0.86 faithfulness score?" and nobody knows.
The notebook was overwritten, the prompt was edited in place, and the model has since changed. Two tools stop this:
an **experiment tracker** that records every run, and a **prompt registry** that versions every prompt.

## Tracking experiments with MLflow

An experiment is a question ("does a reranker help?"). A **run** is one attempt at answering it with specific
settings. For each run, log three kinds of thing:

| Kind | Examples | MLflow call |
|---|---|---|
| Parameters (inputs) | chunk size, top-k, model, temperature, tool set, prompt version | `log_params` |
| Metrics (scores) | faithfulness, answer relevance, p95 latency, cost per query | `log_metrics` |
| Artifacts (files) | the rendered prompt, the full config, sample outputs | `log_text`, `log_dict` |

```python
import mlflow

mlflow.set_experiment("support-rag")

def run_experiment(cfg: dict, prompt_text: str, prompt_version: int):
    with mlflow.start_run(run_name=f"k{cfg['top_k']}-c{cfg['chunk_size']}"):
        mlflow.log_params({
            "model": cfg["model"],
            "temperature": cfg["temperature"],
            "chunk_size": cfg["chunk_size"],
            "top_k": cfg["top_k"],
            "prompt_version": prompt_version,
        })
        results = evaluate_on_eval_set(cfg, prompt_text)   # your Level 7 harness
        mlflow.log_metrics({
            "faithfulness": results.faithfulness,
            "answer_relevance": results.relevance,
            "p95_latency_ms": results.p95_latency_ms,
            "cost_per_query_usd": results.cost_per_query,
        })
        mlflow.log_dict(cfg, "config.json")
        mlflow.log_text(prompt_text, "prompt.txt")
        mlflow.log_text("\n\n".join(results.sample_outputs[:10]), "samples.txt")
```

Run `mlflow ui` and you can sort runs by any metric and compare them side by side. The first run you log for each app
should be the **baseline**: the current settings, unchanged. Every later run is judged against it.

A typical comparison table after an afternoon of work:

| Run | top_k | reranker | Faithfulness | p95 latency | Cost/query |
|---|---|---|---|---|---|
| baseline | 5 | none | 0.81 | 2.1 s | $0.0021 |
| k10 | 10 | none | 0.82 | 2.6 s | $0.0034 |
| k20-rerank | 20 → 5 | cross-encoder | 0.88 | 2.4 s | $0.0024 |

The table makes the decision: the reranker run wins on quality at almost the same cost, while simply raising k paid
more for nearly nothing. (Numbers here are illustrative.)

## Versioning prompts in a registry

A prompt in a Python string ships only with a code deploy and has no history beyond git blame. A **prompt registry**,
such as Langfuse, stores prompts as numbered, immutable versions. Labels like `staging` and `production` point at a
version. You never edit a version; you create a new one and move the label.

```python
from langfuse import Langfuse

langfuse = Langfuse()   # reads keys and host from environment variables

# Create a new version and put it on staging only
langfuse.create_prompt(
    name="rag-answer",
    prompt="Answer using only the context below. If it is not there, say so.\n\n"
           "Context:\n{{context}}\n\nQuestion: {{question}}",
    labels=["staging"],
)
```

At runtime the app fetches whatever the `production` label points at:

```python
FALLBACK = "Answer using only the context.\n\nContext:\n{{context}}\n\nQuestion: {{question}}"

prompt = langfuse.get_prompt(
    "rag-answer",
    label="production",
    cache_ttl_seconds=300,   # serve from local cache between refreshes
    fallback=FALLBACK,       # used if the registry cannot be reached on first fetch
)
text = prompt.compile(context=context, question=question)
# record prompt.version with the request so traces show which version answered
```

Three properties matter here:

- **Caching** keeps the registry off the hot path; most requests never make a network call for the prompt.
- **A pinned fallback** means a registry outage degrades to a known-good prompt instead of an error.
- **Version on every trace.** When quality drops, you filter traces by prompt version and see exactly when it started.

Promotion and rollback are the same move: point `production` at a different version. Rolling back a bad prompt takes
seconds and needs no deploy, which is the main reason to keep prompts out of code.

## Try it

Create a second version of your RAG prompt with the `staging` label. Evaluate staging and production on your eval set
as two MLflow runs, then decide whether to promote.

<details>
<summary>Reference</summary>

1. `create_prompt(name="rag-answer", prompt=new_text, labels=["staging"])` creates, say, version 4.
2. Fetch both with `get_prompt("rag-answer", label="staging")` and `label="production"`.
3. Run the eval harness twice inside two `mlflow.start_run` blocks, logging `prompt_version` as a param.
4. Compare in the MLflow UI. If staging is better on the key metric and not meaningfully worse on latency or cost,
   move the `production` label to version 4 (in the Langfuse UI or via the SDK's prompt update call). Otherwise leave
   production alone and record why staging was rejected in the run's notes.
</details>

## Check yourself

1. What belongs in parameters versus metrics versus artifacts?

<details>
<summary>Answer</summary>

Parameters are the inputs you chose (model, chunk size, top-k, prompt version). Metrics are numeric results (scores,
latency, cost). Artifacts are files worth keeping for inspection (the prompt text, full config, sample outputs).
</details>

2. Why move a label instead of editing a prompt in place?

<details>
<summary>Answer</summary>

Versions stay immutable, so every past trace still points at the exact text that produced it, and rollback is just
moving the label back. Editing in place destroys that history.
</details>

3. What happens to a well-built app if the prompt registry goes down?

<details>
<summary>Answer</summary>

It keeps serving: cached prompts are used until they expire, and if nothing is cached it uses the pinned fallback.
The registry should never be a single point of failure for answering requests.
</details>
