# Grounding, citations and saying "I don't know"

A RAG answer is only useful if people can trust it. That means three things: the claims come from the retrieved text, each claim points to where it came from, and the system declines when the text doesn't support an answer. Models do none of these reliably by default; you have to design for them and check them.

## Answers built from evidence

A model has two sources of information in a RAG prompt: the context you supplied and everything it absorbed in training. Ungrounded answers come from the second. They are often right, which is what makes them dangerous: when your policy differs from the common practice the model learned, it will confidently state the common practice.

Ways to push the model toward the evidence:

- Instruct it plainly to use only the sources, and to say when they are insufficient.
- Keep context focused (reranked, fewer chunks), so the relevant text is easy to find.
- Ask for an extract-then-answer structure: first quote the relevant sentences, then answer from the quotes.
- Use temperature 0 or low for factual Q&A.

## Citing sources

Give every chunk a short, stable id and require citations in a format your code can parse. Structured output makes this robust:

```python
from pydantic import BaseModel

class Claim(BaseModel):
    text: str
    source_ids: list[str]
    quote: str               # exact supporting text from the source

class GroundedAnswer(BaseModel):
    answerable: bool
    claims: list[Claim]

# e.g. with the OpenAI SDK's structured output helper
resp = client.beta.chat.completions.parse(
    model="gpt-4.1-mini",    # example
    messages=messages,
    response_format=GroundedAnswer,
)
answer = resp.choices[0].message.parsed
```

Some provider APIs (Anthropic's citations feature, for example) can return citations pointing at exact spans of documents you pass in, which saves you building the format yourself.

## A citation is not proof

Models cite the wrong chunk, cite a chunk that is merely on-topic, or attach a real citation to an invented detail. Verify mechanically before showing the answer:

1. **The id exists** in the retrieved set (catches made-up ids).
2. **The quote appears** in that chunk (exact or fuzzy string match).
3. **The quote supports the claim**, checked with a natural language inference model or a small LLM judge prompt: "Does this passage support this statement? yes/no".

```python
from rapidfuzz import fuzz

def quote_ok(claim: Claim, chunks: dict[str, str]) -> bool:
    return any(
        sid in chunks and fuzz.partial_ratio(claim.quote, chunks[sid]) >= 90
        for sid in claim.source_ids
    )
```

Drop or flag claims that fail. Track the share of supported claims over time; it is one of the most useful RAG quality metrics (often called faithfulness or groundedness).

## Abstaining

Saying "I don't know" is a feature. Abstain when:

- Retrieval is weak: top scores below a threshold calibrated on your data, or no chunk passes the reranker cut-off.
- The model sets `answerable: false`, or produces no claims that pass verification.
- The question is out of scope for the corpus (a classifier or simple prompt can detect this).

A good abstention says what was searched and offers a next step: "I couldn't find anything about contractor parental leave in the HR policies. You could ask HR directly." Measure both sides: how often it wrongly answers unanswerable questions, and how often it wrongly refuses answerable ones. Tuning only one makes the other worse.

## Try it

Take ten answers from your baseline RAG app. For each claim, check by hand: does the cited chunk exist, does it contain the quoted text, and does it actually support the claim? Count each failure type.

Common results: most citations point at real chunks, but a noticeable share of claims are only partially supported, typically adding a number, condition or detail that isn't in the chunk. Fabricated ids are rarer when ids are short and clearly delimited. The partially supported claims are the ones an automated support check (quote match plus an entailment judge) is built to catch.

## Check yourself

1. Why are ungrounded answers dangerous even when they are often correct?

<details>
<summary>Answer</summary>

They come from the model's general knowledge, which can contradict your specific documents, and they look exactly as confident as grounded ones, so users can't tell the difference.
</details>

2. Name three checks that turn a citation into evidence.

<details>
<summary>Answer</summary>

The cited id is in the retrieved set, the quoted text is actually in that chunk, and the passage entails the claim (checked by an NLI model or an LLM judge).
</details>

3. Why measure wrong refusals as well as wrong answers?

<details>
<summary>Answer</summary>

Tightening abstention reduces invented answers but increases refusals on answerable questions; you need both numbers to find a sensible balance.
</details>
