# Chunking

You almost never retrieve whole documents. You split them into **chunks**, embed each chunk, and retrieve the few that best match a question. How you split decides what the model gets to read, so chunking is one of the highest-leverage choices in a RAG system.

## Why split at all

Three limits force it:

- **Embedding input length.** Embedding models accept a limited number of tokens; anything beyond is truncated, often silently.
- **Retrieval precision.** One vector for a 40-page document is an average of everything in it. It matches every question vaguely and none precisely.
- **Prompt budget.** You want to send the model the three relevant paragraphs, not three whole manuals. More text costs more, is slower, and can bury the answer.

## Four ways to split

| Strategy | How it works | Good for |
|----------|--------------|----------|
| Fixed size | Every N tokens, regardless of content | Uniform text, quick baselines |
| Recursive | Try to split on paragraphs, then lines, then sentences, then characters, until pieces fit | General prose; a solid default |
| Structural | Split on the document's own structure: Markdown headings, HTML sections, code functions | Docs, manuals, code, anything with headings |
| Semantic | Embed sentences and cut where meaning shifts between neighbours | Long unstructured text such as transcripts |

A recursive splitter is easy to write by hand:

```python
def recursive_split(text: str, max_chars: int = 1200,
                    seps=("\n\n", "\n", ". ", " ")) -> list[str]:
    if len(text) <= max_chars:
        return [text]
    for sep in seps:
        parts = text.split(sep)
        if len(parts) > 1:
            chunks, buf = [], ""
            for p in parts:
                candidate = (buf + sep + p) if buf else p
                if len(candidate) <= max_chars:
                    buf = candidate
                else:
                    if buf:
                        chunks.append(buf)
                    buf = p
            if buf:
                chunks.append(buf)
            # recurse on anything still too big
            return [c for ch in chunks for c in recursive_split(ch, max_chars, seps)]
    return [text[i:i + max_chars] for i in range(0, len(text), max_chars)]
```

In practice you would count tokens, not characters, and use a library splitter, but writing one shows there is no magic.

## Size, overlap and metadata

**Size.** Common starting points are 200 to 800 tokens. Smaller chunks match narrow facts sharply; larger ones carry more context per hit. The right size depends on your questions, so test two or three sizes against a set of real questions.

**Overlap.** Repeating 10-20% of each chunk at the start of the next stops a sentence or definition being cut in half at a boundary. Too much overlap wastes storage and returns near-duplicate results.

**Metadata.** Attach the document title, section heading path, source URL, page and date to every chunk. Two cheap tricks pay off well:

- Prepend the heading path to the chunk text before embedding ("Leave policy > Annual leave > Carry-over"). A chunk that says "up to 5 days may be carried over" now carries its topic.
- Keep `doc_id` and position so you can fetch neighbours later.

## Small precise chunks vs large rich ones

You don't have to pick one size. **Small-to-big retrieval** indexes small chunks (a sentence or a short paragraph) for sharp matching, then returns their larger parent section to the model. A variant, sentence-window retrieval, returns the matched sentence plus a few sentences either side. You get precise matching and enough context to answer.

## Try it

Take one long, structured document (an API reference or policy). Chunk it two ways: fixed 300-token chunks, and structural chunks by heading. Write five questions whose answers you know, and for each check which chunk set contains the full answer in a single chunk.

<details>
<summary>Reference</summary>

Structural chunks usually win on questions about a specific section, because each chunk is one coherent topic with its heading attached. Fixed chunks often split a definition or table across two chunks, so neither contains the full answer. Fixed chunks can win when a section is very long and the answer is a small detail buried in it; the fix is structural splitting with a size cap that falls back to recursive splitting inside oversized sections.
</details>

## Check yourself

1. Why is one embedding per whole document usually a bad idea?

<details>
<summary>Answer</summary>

The vector averages everything in the document, so it matches many questions loosely and few precisely; it may also exceed the embedding model's input limit and be truncated.
</details>

2. What problem does chunk overlap solve, and what does too much of it cost?

<details>
<summary>Answer</summary>

It keeps sentences and ideas that straddle a boundary intact in at least one chunk. Too much overlap inflates storage and embedding cost and returns near-duplicate chunks that waste prompt space.
</details>

3. How does small-to-big retrieval get both precision and context?

<details>
<summary>Answer</summary>

It searches over small chunks, which match narrowly, then hands the model the larger parent section that each match belongs to.
</details>
