# Advanced RAG patterns

Papers and blog posts describe dozens of RAG variants. Most are combinations of a few ideas: decide whether to retrieve, judge what came back, try again when it's weak, and break hard questions into steps. Learn the ideas, then pick a pattern only when it fixes a failure you have measured.

## From naive to adaptive

| Stage | Behaviour | Fixes |
|-------|-----------|-------|
| Naive | Always retrieve once, stuff top k, generate | (baseline) |
| Improved | Hybrid search, reranking, query rewriting | Poor recall and precision |
| Self-checking | Grade the evidence or the answer; retry or refuse | Confident answers from weak evidence |
| Adaptive / iterative | Choose a strategy per question; loop until enough evidence | Mixed question types, multi-step questions |
| Structured (graph) | Retrieve over entities and relations | Connected data, whole-corpus questions |

Each stage adds model calls, latency and code paths. Move up only with evidence.

## Self-RAG and Corrective RAG

**Self-RAG** trains a model to decide when to retrieve and to emit reflection tokens that judge whether passages are relevant and whether its own output is supported. You rarely train such a model yourself, but the idea carries over with prompts: ask "is retrieval needed?" first, and grade support afterwards.

**Corrective RAG (CRAG)** adds a grader after retrieval. If the evidence looks relevant, proceed. If it looks wrong, fall back to another source (web search, a different index) or rewrite the query. If ambiguous, refine and combine.

```python
def corrective_rag(question: str, max_tries: int = 2) -> str:
    query = question
    for attempt in range(max_tries + 1):
        chunks = rerank(question, hybrid_search(query, k=30))
        verdict = grade(question, chunks)   # small LLM: "relevant" | "partial" | "irrelevant"
        if verdict == "relevant":
            return generate(question, chunks)
        if attempt < max_tries:
            query = rewrite(question, feedback=verdict)
    return "I couldn't find enough reliable information to answer that."
```

The grader is the weak point: if it is too strict you loop and refuse; too lenient and you gain nothing. Evaluate it on its own.

## Adaptive, iterative and multi-hop

**Adaptive routing** classifies the question first and sends it down the cheapest path that works: no retrieval for chit-chat or general knowledge, single-shot RAG for simple lookups, a heavier path for complex questions, a SQL tool for numeric questions.

**Iterative retrieval** loops: retrieve, read, decide what is still missing, retrieve again, with a hard cap on rounds.

**Multi-hop** questions need one answer to form the next query. "Who manages the team that owns the billing service?" needs "which team owns billing?" first, then "who manages that team?". Decompose into sub-questions, answer each with retrieval, then combine. At this point your RAG system is effectively a small agent with a search tool, and agent techniques (step limits, tracing) apply.

## Graph RAG

Some questions aren't about any single passage: "What are the main themes across all customer complaints this year?" or "Which suppliers are connected to the delayed projects?". Vector search returns similar chunks, not structure.

Graph RAG uses a model to extract entities and relationships from the corpus into a knowledge graph. Microsoft's GraphRAG approach also clusters the graph into communities and writes summaries of each, so global questions can be answered from summaries. Queries can then walk relationships or read community summaries.

Costs: indexing runs a model over the whole corpus (expensive and slow), extraction errors propagate, and updates are harder. Use it when data is genuinely relational or global summary questions matter; most document Q&A doesn't need it.

## Choose by failure, not fashion

| Measured failure | Pattern to try first |
|------------------|----------------------|
| Right chunk not retrieved, vague queries | Query rewriting, RAG-Fusion |
| Right chunk retrieved but ranked low | Reranking |
| Confident answers when evidence is weak | Evidence grading, corrective loop, abstention |
| Questions needing facts from several places | Decomposition, multi-hop |
| Mix of trivial and hard questions, cost too high | Adaptive routing |
| "Across everything" questions, relational data | Graph RAG |

Write down the failure, its frequency on your eval set, the pattern's expected gain, and its added latency and cost. Then measure.

## Check yourself

1. What does Corrective RAG add to a basic pipeline?

<details>
<summary>Answer</summary>

A step that grades retrieved evidence and, when it is weak, rewrites the query, falls back to another source, or abstains instead of generating from it.
</details>

2. Why is a multi-hop question hard for single-shot retrieval?

<details>
<summary>Answer</summary>

The query needed for the second step depends on the answer to the first, which isn't known until the first retrieval and reading have happened.
</details>

3. What kind of question is Graph RAG built for, and what does it cost?

<details>
<summary>Answer</summary>

Questions about relationships and whole-corpus themes that no single chunk answers. It costs heavy model-based indexing, extraction errors and harder updates.
</details>
