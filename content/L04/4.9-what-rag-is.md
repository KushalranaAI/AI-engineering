# What RAG is, and when not to use it

Retrieval-augmented generation (RAG) is a simple idea: before asking a model a question, look up relevant text and put it in the prompt. The model answers from that text instead of from memory. You now have the search half; this module is about the whole loop and, just as important, when to leave it out.

## The pipeline

| Step | What happens | Typical failure |
|------|--------------|-----------------|
| 1. Query | Take the user's question, maybe rewrite it into a better search query | Vague or conversational question retrieves nothing useful |
| 2. Retrieve | Search the index for the top k chunks | Right answer not in the top k |
| 3. Assemble context | Order, trim and format the chunks with their sources into a prompt | Too much noise, answer buried, budget exceeded |
| 4. Generate | The model writes an answer grounded in the context, ideally with citations | Model ignores context, invents details, or misreads it |

In code the skeleton is short:

```python
def answer(question: str) -> str:
    chunks = search(question, k=5)
    context = "\n\n".join(f"[{c.id}] {c.text}" for c in chunks)
    prompt = (f"Answer using only the sources below. Cite source ids.\n\n"
              f"Sources:\n{context}\n\nQuestion: {question}")
    return llm(prompt)
```

Everything else in this level is about making each of those four lines better.

## What it solves

- **Private data.** The model never saw your contracts, tickets or wiki.
- **Fast-changing facts.** Prices, stock levels, policies updated last week. Update the index and answers change immediately, without retraining anything.
- **Collections too big for a prompt.** Even with very long context windows, sending thousands of documents per question is slow and expensive, and quality drops when the relevant passage is buried.
- **Answers you can check.** Retrieved chunks give you sources to cite, which users and auditors can verify.

## When to skip it

RAG adds an index to maintain, latency and new failure modes. Skip it when:

- **The model already knows it.** General knowledge and well-known public docs often need no retrieval. Test the plain model first.
- **The task is a transformation.** Summarising, translating or extracting fields from a document the user just supplied needs that document in the prompt, not a search.
- **Everything fits in the prompt.** A 30-page handbook fits comfortably in a modern context window. Putting all of it in, with prompt caching to cut repeat cost, is simpler and often more accurate than retrieving pieces of it.
- **The data is structured.** "What were sales in March?" belongs in SQL or an API call, not a vector search over text.

## Retrieval failure or generation failure?

When a RAG answer is wrong, find out which half failed before changing anything. Look at the retrieved chunks:

1. **The answer is not in the retrieved chunks** → retrieval failure. Fix chunking, embeddings, hybrid search, query rewriting or k.
2. **The answer is in the chunks, but the response is wrong** → generation failure. Fix the prompt, the context ordering or size, or use a stronger model.
3. **The answer is not in the corpus at all** → the right behaviour is to say so. If the model answered anyway, that is a grounding failure.

Logging the retrieved chunk ids with every answer makes this triage a two-minute job instead of guesswork.

## Check yourself

1. Name the four steps of a RAG pipeline.

<details>
<summary>Answer</summary>

Take the query (possibly rewritten), retrieve relevant chunks, assemble them into context, and generate the answer from that context.
</details>

2. Why might you put a whole document in the prompt rather than use RAG?

<details>
<summary>Answer</summary>

If it fits in the context window, sending it all avoids retrieval misses and an index to maintain; prompt caching keeps repeated cost down.
</details>

3. The correct passage was retrieved but the answer is still wrong. Which half failed, and what would you try?

<details>
<summary>Answer</summary>

Generation. Try a clearer grounding prompt, fewer or better-ordered chunks so the passage isn't buried, or a stronger model.
</details>
