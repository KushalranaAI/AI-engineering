# Scheduled ingestion pipelines with Airflow

In 4.1 you wrote a script that turns a folder of documents into clean records. It works the day you run it. Then the
help centre changes on Tuesday, a PDF is replaced on Thursday, and nobody remembers to run the script. The index
goes stale and the bot starts quoting last quarter's refund policy. A RAG system is only as fresh as its
ingestion, and ingestion needs to run itself, retry itself and complain when it breaks. That is what a workflow
orchestrator is for, and Apache Airflow is the most widely used one.

## Why a script is not a pipeline

A cron job running `python ingest.py` fails in quiet ways: the source site is down and the job exits with an empty
index; one bad PDF kills the whole run; a second run starts before the first ends; nobody can say which documents
were indexed last night. An orchestrator gives you a schedule, retries with back-off, a log per step, a record of
every run, and a place to see what failed.

## DAGs, tasks and dependencies

Airflow describes a pipeline as a **DAG** (directed acyclic graph): boxes (tasks) joined by arrows (dependencies),
with no loops. A task is one unit of work, written either as an operator or, more simply today, as a Python function
with the `@task` decorator.

For ingestion the graph is usually: **list changed documents → parse → chunk → embed → upsert into the index →
verify**. Each arrow means "run only after the previous one succeeded".

```python
from datetime import datetime
from airflow.sdk import dag, task      # Airflow 3. In Airflow 2 use: from airflow.decorators import dag, task

@dag(
    schedule="0 2 * * *",              # every night at 02:00
    start_date=datetime(2025, 1, 1),
    catchup=False,                     # say it explicitly; do not rely on the default
    max_active_runs=1,                 # never let two ingestions overlap
    default_args={"retries": 3},
    tags=["rag"],
)
def ingest_help_centre():
    @task
    def list_changed() -> list[str]:
        """Return ids of documents whose content hash differs from the one stored last time."""
        return find_changed_document_ids()

    @task(retries=1)
    def process(doc_id: str) -> int:
        doc = load_document(doc_id)
        chunks = chunk(doc.text, doc.metadata)
        vectors = embed([c.text for c in chunks])
        upsert(chunks, vectors)         # keyed by f"{doc_id}#{n}", so a re-run overwrites, not duplicates
        return len(chunks)

    @task
    def verify(counts: list[int]) -> None:
        if sum(counts) == 0 and expected_changes() > 0:
            raise ValueError("Documents changed but no chunks were written")

    verify(process.expand(doc_id=list_changed()))   # one parallel task per changed document

ingest_help_centre()
```

Two details matter. Tasks pass small values (ids, counts), not document text, because Airflow stores returned values
in its metadata database. And `.expand()` creates one task instance per document, so a single bad file fails alone
and retries alone.

## Scheduling, logical dates and backfills

A schedule can be a cron string, a preset like `@daily`, or an asset-based trigger that runs the DAG when upstream
data is updated. Each run has a **logical date** that says which slice of time it covers, not when it happened to
start. That lets you **backfill**: re-run a past range (for example, after fixing a parser bug) and get the same
result as if the pipeline had always been correct. Set `catchup` explicitly; whether missed intervals run
automatically depends on that flag and on the version you use.

## Idempotent tasks and change detection

Every task must be safe to run twice. Three habits get you there:

- **Hash the content.** Store a SHA-256 of each source document. Skip it when the hash is unchanged. This turns a
  nightly job over 50,000 documents into a run over the 40 that changed.
- **Upsert by a stable id.** Chunk ids derived from the document id and position mean a retry overwrites instead of
  duplicating.
- **Delete what disappeared.** If a source document is gone, remove its chunks too, or the bot will keep answering
  from a page that no longer exists.

## Re-indexing without downtime

Switching embedding model or chunk size means every vector changes, and vectors from different models cannot be
mixed (see 4.4). Build the new index under a new name (`help_v2`), run the verification checks against it, then
repoint an **alias** (`help_live → help_v2`) in one step. If answers get worse, point the alias back.

## Retries, alerts and quality gates

Set retries with exponential back-off for flaky sources, and a timeout so a hung download cannot block the night.
Add **data-quality gates** as tasks: fail the run if a source returns zero documents, if the chunk count drops by
more than 30% from yesterday, or if more than 2% of documents fail to parse. Route failures to a channel a person
reads. A pipeline that fails silently is worse than no pipeline.

## Try it

Your help centre has 8,000 articles; about 60 change each day. A nightly full re-embed costs $4 and takes 50
minutes, and twice last month the source site was down at 02:00. Sketch the DAG and the checks you would add.

<details>
<summary>Reference</summary>

Tasks: `list_changed` (compare stored hashes with today's fetch) → `process` mapped over changed ids (parse, chunk,
embed, upsert, delete removed ids) → `verify`. Cost drops to roughly 60/8,000 of the full run, about 3 cents and a
minute or two. For the outage: `retries=3` with a 10-minute delay and a fetch timeout, plus a gate that fails the
run (and alerts) when the fetch returns zero documents rather than deleting the whole index. For a model change:
build a new index and swap the alias after checks pass.
</details>

## Check yourself

1. Why should ingestion tasks be idempotent, and how do you achieve it?

<details>
<summary>Answer</summary>

Retries, backfills and overlapping runs all execute tasks more than once, and a non-idempotent task would create
duplicate chunks or corrupt the index. Use content hashes to skip unchanged documents and upsert by a stable id
(document id plus chunk position), so a second run overwrites instead of adding.
</details>

2. Your pipeline "succeeded" but the bot is answering from an empty index. What quality gate was missing?

<details>
<summary>Answer</summary>

A check that fails the run on suspicious results: zero documents fetched, a large drop in chunk count, or a high
parse-failure rate. Without it, an upstream outage looks like a successful run that deleted or never wrote data.
</details>

3. How do you change the embedding model without downtime?

<details>
<summary>Answer</summary>

Build a complete new index with the new model beside the old one, run retrieval checks on it, then switch an alias
from the old index to the new one. Keep the old index until you are confident, so you can switch back.
</details>
