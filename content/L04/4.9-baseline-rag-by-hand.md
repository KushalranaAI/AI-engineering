# Baseline RAG by hand

Frameworks make RAG look like one function call. Build it yourself first, on top of the search engine you already have. When something goes wrong later (and it will), you will know exactly which line to look at.

## Wiring it yourself

```python
from openai import OpenAI

client = OpenAI()
MODEL = "gpt-4.1-mini"   # example; any capable chat model works

SYSTEM = """You answer questions using only the provided sources.
Rules:
- Use only facts stated in the sources. Do not use outside knowledge.
- After each sentence, cite the source id in square brackets, e.g. [doc3#2].
- If the sources do not contain the answer, reply exactly:
  "I can't find that in the available documents."
"""

def build_context(chunks) -> str:
    return "\n\n".join(
        f"<source id=\"{c['id']}\" title=\"{c['title']}\">\n{c['text']}\n</source>"
        for c in chunks
    )

def rag_answer(question: str, k: int = 5, min_score: float = 0.3) -> dict:
    hits = hybrid_search(question, k=k)          # from your search engine
    hits = [h for h in hits if h["score"] >= min_score]
    if not hits:
        return {"answer": "I can't find that in the available documents.", "sources": []}

    resp = client.chat.completions.create(
        model=MODEL,
        temperature=0,
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": f"{build_context(hits)}\n\nQuestion: {question}"},
        ],
    )
    return {"answer": resp.choices[0].message.content,
            "sources": [h["id"] for h in hits]}
```

That is the whole baseline: retrieve, filter weak hits, format context with ids, instruct, generate, and return the sources you used for logging.

## Prompts that stay on the evidence

Models will happily fill gaps from memory. Make the rules explicit and checkable:

- **Say what counts as evidence**: "only the sources below".
- **Give an exact refusal string**, so your code and your eval can detect it.
- **Require citations**, which forces the model to anchor each claim and gives you something to verify.
- **Delimit sources clearly** with tags and ids, so the model can tell where one ends and the next begins, and so instructions hidden in a document are visibly data.
- Put the question **after** the context; models tend to attend well to the end of the prompt.

## Weak or empty retrieval

Not every question has an answer in your corpus. Signs that retrieval came back weak:

- Top scores below a threshold you chose by looking at real data (scores are model-specific; never copy a threshold).
- Top results from unrelated documents, or keyword hits that matched only a common word.
- Hybrid lists that disagree completely.

Options: refuse with the fixed message, ask the user to clarify, or retry with a rewritten query. A refusal is a good answer when the data isn't there; a confident invention is the worst outcome.

## k, order and context size

These are measurable, so measure them rather than guess. With a set of 30-50 questions and known answers, try:

| Setting | Try | What you usually see |
|---------|-----|----------------------|
| k | 3, 5, 10, 20 | Accuracy rises then flattens or drops; cost rises linearly |
| Order | Best first; best at both ends | Models can miss facts buried in the middle of long contexts |
| Chunk size | Small vs parent section | Small chunks retrieve precisely but may lack context to answer |
| Dedup | On / off | Overlapping chunks waste budget |

Track tokens and latency alongside accuracy for every setting. A configuration that is 2% better and three times the cost is rarely the right one.

## Check yourself

1. Why give the model an exact refusal string?

<details>
<summary>Answer</summary>

So code and evals can reliably detect a refusal, rather than parsing many different phrasings of "I don't know".
</details>

2. Why filter retrieved chunks by score before calling the model?

<details>
<summary>Answer</summary>

Irrelevant chunks invite the model to answer from weak evidence or noise; dropping them lets you refuse early and saves tokens.
</details>

3. You raise k from 5 to 20 and accuracy drops slightly. What is a likely explanation?

<details>
<summary>Answer</summary>

Extra chunks add noise and push the relevant passage into the middle of a long context, where models use information less reliably.
</details>
