# Getting documents in

Every RAG demo starts with a tidy folder of Markdown. Real projects start with a shared drive: PDFs exported from slide decks, scanned contracts, HTML pages wrapped in navigation, Word files with tracked changes, and three copies of the same policy with different dates. Retrieval can only be as good as the text you feed it, so ingestion is where most quality is won or lost.

## Extracting text by format

| Format | Typical tool | What goes wrong |
|--------|--------------|-----------------|
| Digital PDF | PyMuPDF, pdfplumber, Docling, Unstructured | Columns read in the wrong order, headers and footers repeated on every page, tables flattened into word soup |
| Scanned PDF / image | OCR (Tesseract) or a vision-capable model | No text layer at all; OCR mistakes on numbers and names |
| HTML | BeautifulSoup, trafilatura | Menus, cookie banners and footers swamp the real content |
| Word (.docx) | python-docx, MarkItDown | Tracked changes and comments mixed into body text |

A quick test for "does this PDF need OCR?": extract text from each page and count characters. A page with an image but almost no text is almost certainly scanned.

```python
import fitz  # PyMuPDF

def extract_pdf(path: str) -> list[dict]:
    pages = []
    with fitz.open(path) as doc:
        for i, page in enumerate(doc):
            text = page.get_text("text")
            pages.append({
                "page": i + 1,
                "text": text,
                "needs_ocr": len(text.strip()) < 50 and len(page.get_images()) > 0,
            })
    return pages
```

Tables deserve special care. If users will ask "what is the late fee for plan B?", the answer lives in a table cell, and a flattened table loses the link between "plan B" and the number. Prefer tools that emit tables as Markdown or HTML, or convert each row into a sentence ("Plan B: late fee 5%").

## Cleaning without losing structure

Cleaning means removing what hurts retrieval while keeping what helps it.

**Remove:** repeated headers and footers, page numbers, navigation, legal boilerplate that appears on every page, hyphenation at line ends ("retriev-\nal"), and stray whitespace.

**Keep:** headings (they tell you what a passage is about), list structure, table layout, and metadata such as title, author, URL, section path and last-modified date. Converting to Markdown is a good middle ground: it is plain text, but `#` headings and `|` tables survive.

Store each document as a record, not a bare string:

```python
record = {
    "doc_id": "hr-policy-leave",
    "source": "sharepoint://hr/leave-policy.pdf",
    "title": "Leave policy",
    "updated_at": "2026-03-14",
    "content_hash": "9f2c…",
    "text": "# Leave policy\n## Annual leave\n...",
}
```

The metadata you keep here becomes the filters you can apply later ("only HR documents", "only this year").

## Duplicates, edits and re-indexing

Exact duplicates are easy: hash the cleaned text and skip anything already seen. Near-duplicates (the same policy with a new date in the footer) need fuzzier tools such as MinHash or comparing embeddings, and a rule for which copy wins, usually the newest.

Edits are the operational problem. Re-embedding the whole corpus every night is wasteful and slow. Instead:

1. Give every document a stable `doc_id` (path or URL, not a random number).
2. Store a `content_hash` of its cleaned text.
3. On each run, compare hashes. Unchanged: skip. Changed: delete its old chunks and index new ones. Missing from the source: delete its chunks.

That last step matters: a deleted policy that still answers questions is worse than no answer.

## Check yourself

1. Why is it worth keeping headings and metadata rather than extracting plain text only?

<details>
<summary>Answer</summary>

Headings tell you what a passage is about, which helps both chunking and retrieval, and metadata (source, date, type) becomes the filters and citations you need later. Plain text throws that away.
</details>

2. How can you detect that a PDF page needs OCR?

<details>
<summary>Answer</summary>

Extract its text layer. If a page has little or no text but contains images, it is probably scanned and needs OCR or a vision model.
</details>

3. A source document was deleted, but users still get answers from it. What is missing from the pipeline?

<details>
<summary>Answer</summary>

A deletion step in re-indexing: compare the current set of source ids with the indexed ones and remove chunks for documents that no longer exist.
</details>
