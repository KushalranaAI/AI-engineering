# Vector databases and approximate search

Your NumPy search engine compares the query with every vector. That is exact and simple, and it is the right choice for small corpora. A vector database adds three things you will soon need: storage that survives restarts and supports updates, filters on metadata, and indexes that stay fast at millions of vectors.

## Storing vectors with their metadata

Store each chunk as one row or point: an id, the vector, the text, and metadata. With Postgres and pgvector:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id         text PRIMARY KEY,          -- e.g. "hr-policy-leave#7"
  doc_id     text NOT NULL,
  tenant_id  text NOT NULL,
  doc_type   text,
  updated_at date,
  content    text NOT NULL,
  embedding  vector(1536) NOT NULL
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
```

Dedicated engines (Qdrant, Weaviate, Milvus, Pinecone) offer the same idea through an API, with the metadata called a payload or properties. If you already run Postgres and have up to a few million chunks, pgvector keeps everything in one database with transactions and joins. Dedicated engines tend to win on very large indexes, advanced filtering and built-in hybrid search.

## Filtered top-k queries

Real queries almost always carry filters: this tenant only, documents from this year, only manuals.

```python
import psycopg

def search(conn, query_vec, tenant: str, k: int = 5):
    sql = """
        SELECT id, content, 1 - (embedding <=> %s::vector) AS score
        FROM chunks
        WHERE tenant_id = %s AND updated_at >= '2025-01-01'
        ORDER BY embedding <=> %s::vector
        LIMIT %s
    """
    vec = str(list(query_vec))
    return conn.execute(sql, (vec, tenant, vec, k)).fetchall()
```

(`<=>` is pgvector's cosine distance operator.) Filtering interacts with approximate indexes: if the filter removes most vectors, an index that first finds nearest neighbours and then filters can return fewer than k results. Engines handle this differently (pre-filtering, filter-aware graph search, iterative scans), so test filtered queries specifically, especially multi-tenant ones. Tenant filters are also a security boundary: never rely on the prompt to keep tenants apart.

## Why approximate search exists

Exact search costs one distance computation per vector per query:

| Vectors | Dims | Multiply-adds per query | Rough feel |
|---------|------|-------------------------|------------|
| 100k | 1,024 | 0.1 billion | fine |
| 10M | 1,024 | 10 billion | slow per query, painful under load |
| 100M | 1,024 | 100 billion | impractical |

Approximate nearest neighbour (ANN) indexes look at a small fraction of vectors and return results that are *almost* always the true top k. You trade a little **recall** (the share of true neighbours found) for a large gain in speed.

## HNSW and IVF intuition

**HNSW** (Hierarchical Navigable Small World) builds a layered graph where each vector links to its near neighbours. A search starts at a sparse top layer, hops greedily toward the query, and descends to denser layers. It is fast with high recall, but uses a lot of memory for the graph and builds slowly. Key knobs: `m` (links per node) and `ef_search` (how many candidates to explore; higher means better recall, slower queries).

**IVF** (inverted file) clusters vectors into, say, 1,000 groups with k-means. A query compares against cluster centres, then searches only the closest few clusters (`nprobe`). It builds faster and uses less memory, often combined with compression (product quantisation), but recall drops when an answer sits in a cluster you did not probe.

Rule of thumb: HNSW is the common default; IVF with compression appears when memory cost dominates at very large scale.

## OpenSearch k-NN

If your company already runs **OpenSearch** (or Elasticsearch) for keyword search and logs, it can store vectors too. You
declare a `knn_vector` field and an approximate-search method on the index:

```json
PUT help-v1
{
  "settings": {"index": {"knn": true, "knn.algo_param.ef_search": 100}},
  "mappings": {"properties": {
    "text":      {"type": "text"},
    "tenant":    {"type": "keyword"},
    "embedding": {"type": "knn_vector", "dimension": 384,
                  "method": {"name": "hnsw", "space_type": "cosinesimil", "engine": "lucene",
                             "parameters": {"m": 16, "ef_construction": 128}}}
  }}
}
```

A query asks for the k nearest vectors, optionally with a filter:

```json
POST help-v1/_search
{"size": 5, "query": {"knn": {"embedding": {"vector": [0.12, -0.03, "..."], "k": 5,
                                            "filter": {"term": {"tenant": "acme"}}}}}}
```

The engine (Lucene, Faiss) and which filtering modes it supports depend on the version; check the OpenSearch k-NN
documentation. The attraction is that BM25, filters, aggregations and vectors live in one cluster, which makes hybrid search
(4.7) straightforward.

## Choosing a store

| Situation | Reasonable choice |
|-----------|-------------------|
| Already on Postgres, up to a few million chunks, want transactions and joins | **pgvector** |
| Already run OpenSearch, need strong keyword search, facets and vectors together | **OpenSearch k-NN** |
| Hundreds of millions of vectors, heavy filtering, need managed scale | a dedicated vector database |
| A prototype | whatever you can run locally in ten minutes |

Decide with data: load a realistic sample into two candidates and compare recall@10 against exact search, filtered-query
latency and the operational effort for your team. The cheapest store is often the one your team already knows how to run.

## Updates and deletes

Live data changes. Plan for:

- **Upserts by stable id**, so re-indexing a document replaces its chunks.
- **Deletes**, which many ANN indexes handle by marking entries as deleted; periodic compaction or rebuilds reclaim space and restore speed.
- **Re-indexing after big changes**, since an index built on old data can lose recall as the data drifts.
- **Backups and a model version column**, so a re-embedding migration can run side by side.

## Try it

Load 50,000 chunks into pgvector or Qdrant. Run 100 queries with exact search and with an HNSW index. Measure recall@10 of HNSW against exact results, and latency for both. Then raise `ef_search` (or the equivalent) and measure again.

<details>
<summary>Reference</summary>

Exact search at this size might take tens of milliseconds; HNSW a few milliseconds. With default settings recall@10 is often above 0.9; raising `ef_search` pushes it closer to 1.0 at some latency cost. Recall is computed per query as the overlap between the HNSW top 10 and the exact top 10, divided by 10, then averaged. If recall is low with a tenant filter on, you have found the filtering interaction.
</details>

## Check yourself

1. What does an ANN index trade away, and for what?

<details>
<summary>Answer</summary>

It gives up guaranteed exact results (some recall) in exchange for much faster queries at large scale.
</details>

2. Why can a filtered query on an ANN index return fewer than k results?

<details>
<summary>Answer</summary>

If the index finds approximate neighbours first and filters afterwards, a restrictive filter can remove most of them. Filter-aware search or pre-filtering is needed.
</details>

3. When is pgvector a sensible choice over a dedicated vector database?

<details>
<summary>Answer</summary>

When you already run Postgres and the corpus is moderate (up to a few million vectors), so you benefit from one database with transactions, joins and familiar operations.
</details>
