# Reranking

First-stage retrieval has to be fast, so it compares a query vector with precomputed chunk vectors and never looks at query and chunk together. That speed costs precision: the right chunk is often in the top 50 but not the top 5. A **reranker** reads each candidate alongside the query and reorders them, so the few chunks you send the model are the best ones.

## Retrieve wide, rerank, keep the best

```
query → hybrid search (top 50, ~20 ms) → reranker (50 pairs, ~100-300 ms) → top 5 → LLM
```

Why not just send 20 chunks instead? Because more chunks cost more tokens, add latency to generation, and dilute the context with near-misses. Reranking spends a little compute up front so the prompt stays small and sharp.

## Cross-encoders

An embedding model is a **bi-encoder**: it encodes the query and the chunk separately and compares vectors. A **cross-encoder** feeds the query and the chunk into the model together, so attention can connect "cancel" in the query with "terminate the agreement" in the chunk, and notice negation or a mismatch of detail. It outputs one relevance score per pair. It is much more accurate, but it can't precompute anything, so you only run it on a short candidate list.

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")  # small example model

def rerank(query: str, candidates: list[dict], keep: int = 5) -> list[dict]:
    pairs = [(query, c["text"]) for c in candidates]
    scores = reranker.predict(pairs)
    for c, s in zip(candidates, scores):
        c["rerank_score"] = float(s)
    return sorted(candidates, key=lambda c: -c["rerank_score"])[:keep]

candidates = hybrid_search("how do I terminate my contract early", k=50)
top = rerank("how do I terminate my contract early", candidates)
```

Options in practice:

| Type | Examples | Notes |
|------|----------|-------|
| Small open cross-encoder | MiniLM-based MS MARCO models | Runs on CPU; good English baseline |
| Larger open rerankers | BGE reranker family, other multilingual models | Better quality and languages; want a GPU |
| Hosted rerank APIs | Cohere Rerank, Voyage, Jina and others | One API call; per-search pricing; data leaves your network |
| LLM as reranker | Ask a chat model to score or order candidates | Flexible, slow and expensive; useful for small lists |

## Quality versus latency

Measure both on your eval set:

| Pipeline | Hit@5 | p95 latency | Extra cost |
|----------|-------|-------------|------------|
| Hybrid, top 5 | 0.72 | 40 ms | none |
| Hybrid top 50 + small reranker | 0.84 | 180 ms (CPU) | compute |
| Hybrid top 50 + hosted reranker | 0.87 | 250 ms | per-call fee |

(The numbers are illustrative; yours will differ.) Two knobs drive the trade-off: how many candidates you rerank (latency grows roughly linearly) and the reranker's size. Reranking 20 instead of 100 candidates often keeps most of the gain at a fraction of the time. Because generation usually takes a second or more, a 150 ms rerank is often invisible to users, but it matters for autocomplete-style search.

## When it adds little

- First-stage hit@5 is already very high on your eval: there is little left to reorder.
- The right chunk isn't in the candidate list at all: a reranker can't promote what wasn't retrieved. Fix recall first (hybrid search, query rewriting, chunking).
- Your context window strategy sends whole documents anyway.
- The domain or language is far from what the reranker was trained on; it may even hurt. Always compare against no reranking.

## Try it

Take 30 questions with known answer chunks. Retrieve the top 50 with your hybrid search, then compare hit@5 before and after reranking with a small cross-encoder. Time the rerank step for 20, 50 and 100 candidates.

<details>
<summary>Reference</summary>

You should usually see hit@5 rise by several points, mostly on questions where the right chunk was ranked 6th to 30th. Rerank time grows roughly linearly with candidate count; on CPU a small model might take tens of milliseconds for 20 pairs and a few hundred for 100. Questions that are still wrong after reranking almost always had the answer missing from the top 50, which is a recall problem, not a ranking one.
</details>

## Check yourself

1. Why is a cross-encoder more accurate than a bi-encoder, and why can't you use it for first-stage search?

<details>
<summary>Answer</summary>

It reads query and chunk together, so it can model their interaction directly. Nothing can be precomputed, so scoring every chunk in a large corpus per query would be far too slow.
</details>

2. Why prefer reranking to simply raising k?

<details>
<summary>Answer</summary>

It keeps the prompt small and focused on the best evidence, avoiding the token cost, latency and dilution of sending many near-miss chunks.
</details>

3. Your reranker didn't help on a set of failing questions. What should you check first?

<details>
<summary>Answer</summary>

Whether the correct chunk was in the candidate list at all. If not, it is a recall problem to fix in first-stage retrieval.
</details>
