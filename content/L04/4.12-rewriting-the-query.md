# Rewriting the query

Users write questions for people, not for search engines. "And what about for contractors?" means nothing without the previous turn. "Why is my bill higher and can I change plans?" is two searches. Query rewriting uses a model (or rules) to turn the user's words into queries that retrieve well, before retrieval runs.

## Why the user's question is a poor query

| User wrote | Problem | Better query |
|------------|---------|--------------|
| "And for contractors?" | Depends on chat history | "Parental leave policy for contractors" |
| "it keeps crashing lol" | Vague, no product or symptom | "App crashes on launch after update, iOS" |
| "Why is my bill higher and can I switch plans?" | Two questions in one | "Reasons for bill increase"; "How to change subscription plan" |
| "PTO rollover" | Jargon the docs don't use | "Annual leave carry-over" |

## Four techniques

**Rewrite.** Ask a small model to turn the latest message plus history into one standalone search query. This is the most important one for chat apps.

**Expand.** Add synonyms or related terms ("PTO rollover" → "paid time off, annual leave, carry over unused days"). Helps keyword search especially.

**Multi-query / decompose.** Generate several queries, either different phrasings of the same need or sub-questions of a compound question, and retrieve for each.

**HyDE (Hypothetical Document Embeddings).** Ask the model to write a short, plausible answer, then embed that answer and search with it. A fake answer often looks more like the real document than the question does. The fake answer is never shown to the user, and it can mislead retrieval if the model's guess is wrong in a way that pulls in the wrong documents.

```python
import json
from openai import OpenAI

client = OpenAI()
SMALL = "gpt-4.1-mini"  # example small model

def rewrite_queries(history: list[str], message: str, n: int = 3) -> list[str]:
    prompt = (
        "Rewrite the user's latest message as standalone search queries for a "
        f"company knowledge base. Return a JSON object {{\"queries\": [...]}} with up to {n} "
        "queries: one faithful rewrite, plus sub-questions if the message asks several things.\n\n"
        f"Conversation so far:\n{chr(10).join(history)}\n\nLatest message: {message}"
    )
    resp = client.chat.completions.create(
        model=SMALL, temperature=0,
        response_format={"type": "json_object"},
        messages=[{"role": "user", "content": prompt}],
    )
    return json.loads(resp.choices[0].message.content)["queries"]
```

## RAG-Fusion

RAG-Fusion combines multi-query with rank fusion: generate several queries, retrieve a ranked list for each, and merge the lists with Reciprocal Rank Fusion. Chunks that show up across several phrasings rise to the top, and you are less dependent on any one wording.

```python
def rag_fusion(history, message, k=5):
    queries = [message] + rewrite_queries(history, message)
    rankings = [[h["id"] for h in hybrid_search(q, k=20)] for q in queries]
    return rrf(rankings)[:k]      # rrf() as in hybrid search
```

Keeping the original message in the list is a cheap safety net in case the rewrites drift.

## Paying for extra calls

Every technique adds at least one model call before retrieval can start:

| Technique | Extra LLM calls | Extra retrievals | Typical added latency |
|-----------|-----------------|------------------|-----------------------|
| Standalone rewrite | 1 (small model) | 0 | a few hundred ms |
| Multi-query / RAG-Fusion | 1 | 3-5 (run in parallel) | a few hundred ms |
| HyDE | 1 (writes a passage) | 0-1 | more, since it generates more text |

Use a small, fast model for rewriting, run retrievals in parallel, and skip rewriting when it isn't needed: a single-turn, specific question can go straight to search. Measure on your eval set; if baseline retrieval already finds the right chunk, rewriting only adds cost and a chance of drifting from what the user meant.

## Try it

Collect ten real follow-up questions from a chat log (or write ones that depend on the previous turn). Retrieve with the raw message, then with a standalone rewrite, then with RAG-Fusion. Record hit@5 and added latency.

<details>
<summary>Reference</summary>

Raw follow-ups usually retrieve badly because they lack the subject ("and for contractors?"). A standalone rewrite fixes most of them for one small-model call. RAG-Fusion adds smaller further gains, mainly on compound or ambiguous questions, and costs more retrieval time. If a rewrite made results worse, read it: it probably added an assumption the user never made, which is why keeping the original message in the fused list helps.
</details>

## Check yourself

1. Why does HyDE embed a generated answer instead of the question?

<details>
<summary>Answer</summary>

A plausible answer is phrased like the documents that contain the real answer, so its embedding lands closer to them than a short question does.
</details>

2. What is RAG-Fusion?

<details>
<summary>Answer</summary>

Generating several queries for one question, retrieving a ranked list for each, and merging the lists with Reciprocal Rank Fusion.
</details>

3. When should you skip query rewriting?

<details>
<summary>Answer</summary>

When questions are already specific and standalone and the baseline retrieves well; rewriting then only adds latency, cost and risk of drift.
</details>
