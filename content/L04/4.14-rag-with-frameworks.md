# RAG with frameworks

You have built every piece of a RAG pipeline by hand. Now port it to a framework. LlamaIndex and LangChain are the two most common in Python; both give you loaders for many file types, splitters, vector store integrations, retrievers and rerankers that plug together. The goal is speed without losing the understanding you just built.

## Rebuilding in LlamaIndex

```python
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, Settings
from llama_index.core.node_parser import SentenceSplitter
from llama_index.embeddings.openai import OpenAIEmbedding
from llama_index.llms.openai import OpenAI

Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")   # example
Settings.llm = OpenAI(model="gpt-4.1-mini", temperature=0)               # example

docs = SimpleDirectoryReader("./docs").load_data()
index = VectorStoreIndex.from_documents(
    docs, transformations=[SentenceSplitter(chunk_size=512, chunk_overlap=64)]
)

query_engine = index.as_query_engine(similarity_top_k=5)
response = query_engine.query("How many days of leave can I carry over?")
print(response)
for node in response.source_nodes:
    print(node.score, node.metadata.get("file_name"))
```

A dozen lines give you loading, chunking, embedding, an in-memory index and a query engine with sources. Swapping in a persistent vector store, a hybrid retriever or a reranker postprocessor is a few more lines each.

## Rebuilding in LangChain

LangChain composes the same steps from separate pieces: a document loader, a text splitter, an embeddings object, a vector store, a retriever (`vectorstore.as_retriever()`), a prompt template and a chat model, chained together. For multi-step or looping flows (corrective RAG, multi-hop), its sister library LangGraph models the pipeline as an explicit graph of steps with state, which is easier to debug than hidden loops.

## Framework building blocks

| Your hand-built piece | LlamaIndex | LangChain |
|-----------------------|------------|-----------|
| Extraction | Readers (`SimpleDirectoryReader`, LlamaHub) | Document loaders |
| Chunking | Node parsers (`SentenceSplitter`, Markdown parsers) | Text splitters |
| Vector store | `VectorStoreIndex` + store integrations | `VectorStore` integrations |
| Retrieval (dense, BM25, hybrid) | Retrievers, fusion retriever | Retrievers, ensemble retriever |
| Reranking | Node postprocessors | Document compressors |
| Prompt + generate | Query engine, response synthesizer | Prompt template + chat model chain |

Names change between releases; the concepts don't. If you can map each block to the code you wrote by hand, you can read any framework's docs quickly.

## Hand-built versus framework

| | Hand-built | Framework |
|--|-----------|-----------|
| Time to first working version | Slower | Much faster |
| Breadth (file types, stores, models) | Only what you write | Huge integration catalogue |
| Control over prompts and formatting | Total | Good, but defaults hide in layers |
| Debugging | Read your own code | Step into abstractions; turn on tracing |
| Upgrades | Stable | API changes between versions can break code |

A common, sensible split: use the framework's loaders and integrations, but keep the parts that define quality (chunking rules, the grounding prompt, the citation format, abstention logic) explicit and visible in your own code. Whatever you choose, inspect the actual prompt sent to the model at least once. Framework defaults sometimes include instructions you would never have written.

## Try it

Port your baseline RAG app to LlamaIndex or LangChain. Run your existing eval questions through both versions, and print the exact final prompt the framework sends to the model for one question.

## Check yourself

1. What is the main benefit of a RAG framework over hand-built code?

<details>
<summary>Answer</summary>

Speed and breadth: ready-made loaders, splitters, store integrations, retrievers and rerankers that plug together with little code.
</details>

2. Why print the final prompt a framework sends?

<details>
<summary>Answer</summary>

Default templates and settings are hidden in layers; seeing the real prompt shows what instructions and context the model actually got, which is where many quality differences come from.
</details>

3. Which parts are worth keeping explicit in your own code even when using a framework?

<details>
<summary>Answer</summary>

The parts that define quality: chunking rules, the grounding prompt, citation format and verification, and abstention logic.
</details>
