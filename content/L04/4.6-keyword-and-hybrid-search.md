# Keyword and hybrid search

Vector search is good at meaning and bad at exact strings. Keyword search is the opposite. Most production RAG systems run both and merge the results, because real users type both kinds of query, sometimes in the same sentence.

## BM25

BM25 is the classic keyword ranking function behind Elasticsearch, OpenSearch and most search engines. For each query term it scores a document on three ideas:

- **Term frequency**: the term appears in the document, more often is better, but with diminishing returns (the tenth mention adds little).
- **Inverse document frequency**: rare terms matter more. "E-4021" appearing in 3 of 100,000 chunks is strong evidence; "the" is worthless.
- **Length normalisation**: a short chunk mentioning the term is more focused than a long one that mentions it once.

Two parameters tune it: `k1` (how fast term frequency saturates, usually around 1.2-2) and `b` (how much to penalise length, usually 0.75). The defaults are fine to start.

```python
from rank_bm25 import BM25Okapi
import re

def tokenize(text: str) -> list[str]:
    return re.findall(r"[a-z0-9\-_.]+", text.lower())

corpus = ["Error E-4021: payment gateway timeout",
          "Error E-4012: invalid card number",
          "How to retry a failed payment"]
bm25 = BM25Okapi([tokenize(c) for c in corpus])
print(bm25.get_scores(tokenize("E-4021 timeout")))
```

Note the tokenizer keeps hyphens, so "E-4021" stays one token. Tokenisation choices make or break keyword search on codes and identifiers.

## Sparse versus dense

BM25 vectors are **sparse**: one dimension per vocabulary word, almost all zero. Embeddings are **dense**: a few hundred to a few thousand dimensions, all non-zero. (Learned sparse models such as SPLADE sit in between, expanding terms with related words.)

| Query type | Dense | Sparse (BM25) |
|------------|-------|---------------|
| Paraphrase, synonyms | Strong | Weak |
| Exact ids, codes, names | Weak | Strong |
| Rare jargon | Weak | Strong |
| Typos | Moderate | Weak |
| Multilingual | Strong with multilingual models | Weak |

## Fusing results with RRF

You now have two ranked lists whose scores are on different scales (cosine near 0.8, BM25 around 12). Don't add the scores. **Reciprocal Rank Fusion** uses ranks only:

```
RRF(d) = Σ over lists  1 / (k + rank_in_list(d))      k is usually 60
```

```python
def rrf(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

dense = ["c7", "c2", "c9", "c4"]
sparse = ["c2", "c5", "c7", "c1"]
print(rrf([dense, sparse]))   # c2 and c7 rise to the top: both lists liked them
```

A document ranked well by both lists beats one ranked first by only one. The constant k dampens the advantage of first place. RRF needs no tuning and no score calibration, which is why it is the usual default. Weighted score fusion (after normalising scores) can do slightly better if you have an eval set to tune the weight.

## When hybrid pays off

Hybrid clearly helps when queries contain identifiers, product names, people, error messages, version numbers or quoted phrases, which describes most support, engineering and enterprise search. It helps little on purely conversational questions over prose, where dense alone already wins. Decide with numbers: run the same question set through dense, BM25 and hybrid and compare hit rate.

## Try it

Build a 30-question test set for a docs corpus: 15 natural-language questions and 15 containing an exact identifier. Run dense, BM25 and RRF hybrid, and report hit@5 for each group.

<details>
<summary>Reference</summary>

A typical pattern: dense wins the natural-language group, BM25 wins the identifier group, and hybrid is close to the best of both on each, giving the highest overall score. If hybrid underperforms one of the components on a group, check that both lists are long enough (fuse the top 20-50 from each, not the top 5) and that the tokenizer isn't splitting identifiers.

## Check yourself

1. Why shouldn't you combine dense and BM25 results by adding their raw scores?

<details>
<summary>Answer</summary>

They are on unrelated scales and distributions, so one score would dominate. RRF uses ranks, which are comparable across lists.
</details>

2. What does inverse document frequency contribute to BM25?

<details>
<summary>Answer</summary>

It weights rare terms more heavily than common ones, so a distinctive term like an error code counts far more than a frequent word.
</details>

3. Give two query types where hybrid search clearly beats dense-only.

<details>
<summary>Answer</summary>

Queries with exact identifiers (error codes, SKUs, ticket numbers) and with names or rare jargon the embedding model handles poorly.
</details>
