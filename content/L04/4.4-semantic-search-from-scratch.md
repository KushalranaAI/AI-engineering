# Semantic search from scratch

Before you reach for a vector database, build semantic search with nothing but NumPy. It takes about twenty lines, and afterwards you will know exactly what a database adds (speed at scale, filters, persistence) and what it doesn't (better relevance).

## Three ways to measure closeness

| Measure | Formula | Higher or lower is closer? |
|---------|---------|----------------------------|
| Dot product | `a · b` | Higher |
| Cosine similarity | `(a · b) / (‖a‖ ‖b‖)` | Higher (range -1 to 1) |
| Euclidean distance | `‖a − b‖` | Lower |

The useful fact: **if every vector is normalised to length 1, all three give the same ranking.** Cosine becomes the plain dot product, and Euclidean distance is a simple function of it (`‖a − b‖² = 2 − 2 a·b`). Many embedding APIs already return normalised vectors; if yours doesn't, normalise once at index time and use the dot product, which is the cheapest to compute.

When vectors are not normalised, the dot product rewards long vectors, so a chunk can rank high partly because of its magnitude. Use cosine unless the model card says the model was trained for dot product.

## A search engine in a few lines

```python
import numpy as np

class TinySearch:
    def __init__(self, embed_fn):
        self.embed = embed_fn
        self.texts: list[str] = []
        self.vecs: np.ndarray | None = None

    def add(self, texts: list[str]) -> None:
        v = self.embed(texts)
        v = v / np.linalg.norm(v, axis=1, keepdims=True)   # normalise once
        self.vecs = v if self.vecs is None else np.vstack([self.vecs, v])
        self.texts.extend(texts)

    def search(self, query: str, k: int = 5) -> list[tuple[float, str]]:
        q = self.embed([query])[0]
        q = q / np.linalg.norm(q)
        scores = self.vecs @ q                  # one dot product per chunk
        top = np.argsort(-scores)[:k]
        return [(float(scores[i]), self.texts[i]) for i in top]
```

That is a complete, exact semantic search engine. On a laptop it scores 100,000 chunks of 768 dimensions in tens of milliseconds. It stops being fine at millions of vectors, when you need filters, or when several processes must share and update the index; those are the problems vector databases solve.

## Meaning versus exact words

Compare it with a keyword search on the same questions and you will see a clear pattern:

| Query | Semantic search | Keyword search |
|-------|-----------------|----------------|
| "cancel my subscription" vs doc "ending your plan" | Finds it | Misses (no shared words) |
| "laptop won't turn on" vs doc "device fails to power up" | Finds it | Misses |
| "error E-4021" | Returns other error codes that look similar | Finds the exact code |
| "invoice 2024-118" | Returns any invoice | Finds that invoice |

## Where it breaks

Semantic search struggles with text the model never learned to place precisely:

- **Identifiers and codes**: SKUs, error codes, ticket numbers. To an embedding, "E-4021" and "E-4012" look nearly the same.
- **Names**: people, products and internal project names that are rare or new.
- **Numbers and dates**: "orders over $500" will not filter by amount.
- **Rare jargon and acronyms**: internal abbreviations the model has never seen.
- **Negation and small qualifiers**, as with embeddings in general.

The usual fixes are keyword search alongside (hybrid search) and metadata filters for structured fields like dates and amounts.

## Check yourself

1. When do cosine similarity and dot product give the same ranking?

<details>
<summary>Answer</summary>

When all vectors are normalised to unit length; cosine then equals the dot product, and Euclidean distance ranks identically too.
</details>

2. What does a vector database give you that the NumPy version doesn't?

<details>
<summary>Answer</summary>

Fast approximate search at large scale, metadata filtering, persistence, concurrent updates and deletes. It does not by itself make results more relevant.
</details>

3. Why does semantic search do poorly on queries like "error E-4021"?

<details>
<summary>Answer</summary>

Embeddings capture general meaning, so similar-looking codes land close together; the model has no reason to separate E-4021 from E-4012 precisely. Exact keyword matching does this better.
</details>
