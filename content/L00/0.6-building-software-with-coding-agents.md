# Building software with coding agents

Coding agents can read a repository, edit files, run commands and react to the results. Used well, they make you much
faster. Used blindly, they produce plausible broken code at the same speed. The difference is the engineering process
you wrap around them.

## Three generations of tools

| Tool | What it does | Your role |
|------|--------------|-----------|
| Autocomplete | suggests the next line or block | accept or ignore |
| Chat assistant | answers questions, writes snippets you paste in | integrate and test |
| Coding agent (Claude Code, Codex, Cursor, Copilot, Gemini CLI) | explores files, edits many of them, runs tests, iterates | specify, plan, review, verify |

**AI-assisted engineering** means you direct the work and check it. **Vibe coding** means accepting whatever comes out
because it seems to run. The second is fine for a throwaway prototype and dangerous for anything you'll maintain.

## The verification loop

Every meaningful change goes through the same loop:

```
context → generate → read the diff → run tests → debug → review → accept (commit)
```

```bash
git switch -c feat/csv-export          # agent works on a branch, never directly on main
# ...agent makes the change...
git diff --stat                        # how big is it? touching files you didn't expect?
git diff                               # read it, all of it
uv run pytest && uv run mypy src       # does it actually work?
```

Red flags in a diff: new dependencies you didn't ask for, deleted or weakened tests, broad `except` blocks, hardcoded
secrets, and edits far from the task.

## Context: less, but the right less

The agent's context window is finite and everything it reads costs attention. Point it at what the task needs:
"the bug is in `client.py`'s retry logic; the failing test is `test_retry_on_503`" beats "fix the app".

Keep long-lived knowledge in a **project memory file** (for Claude Code, `CLAUDE.md`; other tools use `AGENTS.md` or
similar) that loads automatically:

```markdown
# Expense API
- Python 3.12, FastAPI, PostgreSQL via psycopg. Run: `uv run fastapi dev app/main.py`
- Tests: `uv run pytest`. Types: `uv run mypy src`. Both must pass before you finish.
- Errors use {"detail": str}. Never return raw exceptions.
- Do not add dependencies without asking.
```

Task-specific details go in the prompt, not in this file.

## Spec first, then plan

For anything bigger than a one-line fix: write what you want (behaviour, inputs, outputs, edge cases, what not to
touch), ask the agent for a plan, review and correct the plan, and only then let it edit. Fixing a wrong plan costs a
sentence; fixing a wrong 400-line diff costs an afternoon.

## Reusable pieces

| Piece | What it is | Example |
|-------|-----------|---------|
| Custom command | a saved prompt you trigger by name | `/review` runs your review checklist on the current diff |
| Skill | instructions, scripts and examples the agent loads only when relevant | "how we write migrations in this repo" |
| Subagent | a separate agent with its own context and narrow job | a test-writer or reviewer that reports back a summary |
| MCP server | a standard connector to outside systems | query the dev database, read issue tracker tickets, search docs |
| Hook | a script that runs automatically on agent events | run the formatter and linter after every file edit |
| Plugin | a bundle of the above you can share | your team's commands, hooks and skills in one install |

The key idea behind **hooks**: anything that must always happen (formatting, lint, tests, blocking edits to `.env`)
should be enforced by a script, not by hoping the model remembers an instruction. A hook in Claude Code's settings
looks like this:

```json
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "uv run ruff format . && uv run ruff check --fix ." }] }
    ]
  }
}
```

**Subagents** help because one context stuffed with exploration, implementation and review gets muddled; a fresh
reviewer with only the diff is more critical. **MCP** (Model Context Protocol) is an open standard, so one server
works across many agents.

## What carries over

Tools change every few months. The durable skills don't: giving precise context, writing specs, reviewing plans,
delegating focused work, automating checks, and verifying results. They transfer to whichever agent your team uses.
Remember that correctness, security, architecture and maintainability remain your responsibility.

## Try it

Pick a small repo of yours. Write a `CLAUDE.md` (or equivalent) with run and test commands, then ask an agent to add
one feature using spec, plan, implement. Add one hook that formats code after edits. Record one thing the agent got
wrong and how you caught it.

<details>
<summary>Reference</summary>

A good outcome looks like: a 10-20 line memory file; a written spec with at least two edge cases; a plan you edited
before approving (for example, removing an unneeded new dependency); a diff under a few hundred lines with new tests;
and a note such as "agent made the export endpoint `async def` but used a blocking file write; caught it reading the
diff; moved the write to a thread". If you didn't find any mistake, review again with a fresh-context reviewer
subagent given only the diff.
</details>

## Check yourself

1. Why enforce formatting with a hook instead of a line in `CLAUDE.md`?

<details>
<summary>Answer</summary>

An instruction can be forgotten or ignored; a hook runs deterministically every time. Rules that must always hold
belong in code.
</details>

2. What's the benefit of reviewing the agent's plan before it edits code?

<details>
<summary>Answer</summary>

Misunderstandings are cheap to fix in a plan and expensive to fix in a large diff. It also keeps the change scoped.
</details>

3. Name two warning signs in an agent-generated diff.

<details>
<summary>Answer</summary>

Any two of: tests deleted or loosened, unrequested dependencies, broad exception swallowing, hardcoded secrets,
changes to unrelated files, much larger diff than the task needs.
</details>
