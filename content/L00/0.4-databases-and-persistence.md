# Databases and persistence

An API that forgets everything on restart is a demo. PostgreSQL is the default home for application data, and it
matters doubly here: with the pgvector extension it is also one of the most common places to store embeddings later in
this path.

## Modelling the data

A **table** holds rows of one kind of thing. Each row has a **primary key** that identifies it. A **foreign key**
points at a row in another table, which is how relationships are stored.

```sql
CREATE TABLE users (
    id         BIGSERIAL PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE expenses (
    id        BIGSERIAL PRIMARY KEY,
    user_id   BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    amount    NUMERIC(10, 2) NOT NULL CHECK (amount > 0),
    category  TEXT NOT NULL,
    spent_on  DATE NOT NULL
);
```

**Normalisation** in practice: store each fact once. Don't copy the user's email into every expense row; store
`user_id` and join when you need it. Use constraints (`NOT NULL`, `UNIQUE`, `CHECK`) so the database rejects bad data
even if your code has a bug.

## SQL you'll use every week

```sql
INSERT INTO expenses (user_id, amount, category, spent_on)
VALUES (1, 12.50, 'food', '2026-11-01') RETURNING id;

SELECT category, SUM(amount) AS total, COUNT(*) AS n
FROM expenses
WHERE user_id = 1 AND spent_on >= '2026-11-01'
GROUP BY category
ORDER BY total DESC;

SELECT u.email, e.amount
FROM expenses e JOIN users u ON u.id = e.user_id
WHERE e.amount > 100;

UPDATE expenses SET category = 'travel' WHERE id = 7;
DELETE FROM expenses WHERE id = 7;
```

Always include a `WHERE` on updates and deletes. Running one without it is a classic production incident.

## Indexes

Without an index, finding rows means reading the whole table. An **index** (by default a B-tree) is a sorted lookup
structure that lets Postgres jump to matching rows.

```sql
CREATE INDEX idx_expenses_user_date ON expenses (user_id, spent_on);
EXPLAIN ANALYZE SELECT * FROM expenses WHERE user_id = 1 AND spent_on >= '2026-11-01';
```

| Situation | Effect |
|-----------|--------|
| Filtering or joining on an indexed column | fast lookup instead of a full scan |
| Wrapping the column in a function (`WHERE lower(email) = ...`) | the plain index can't be used |
| Many indexes on a write-heavy table | every insert pays to update each one |

Primary keys and `UNIQUE` columns get an index automatically. Foreign keys do not, so index them if you filter by them.

## Connecting from Python

Use a driver such as psycopg, or an ORM such as SQLAlchemy or SQLModel. Always pass values as parameters, never by
string formatting, which invites SQL injection.

```python
import os
import psycopg

DSN = os.environ["DATABASE_URL"]     # e.g. postgresql://app:secret@localhost:5432/expenses

def add_expense(user_id: int, amount: float, category: str, spent_on: str) -> int:
    with psycopg.connect(DSN) as conn:
        row = conn.execute(
            "INSERT INTO expenses (user_id, amount, category, spent_on) "
            "VALUES (%s, %s, %s, %s) RETURNING id",
            (user_id, amount, category, spent_on),
        ).fetchone()
        return row[0]            # the with-block commits on success, rolls back on error
```

In FastAPI, create a connection pool at startup (lifespan) and hand each request a connection through a dependency.
For schema changes over time, use a migration tool such as Alembic rather than editing tables by hand.

## Credentials stay out of code

The connection string contains a password, so it comes from an environment variable or a secret manager. Locally,
keep it in a `.env` file that is listed in `.gitignore`. A quick local database:

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:17
```

## Try it

Using the schema above, write one query that returns, for each user, their email and total spend in the current
month, including users who spent nothing (show 0).

<details>
<summary>Reference</summary>

```sql
SELECT u.email, COALESCE(SUM(e.amount), 0) AS total
FROM users u
LEFT JOIN expenses e
  ON e.user_id = u.id
 AND e.spent_on >= date_trunc('month', now())::date
GROUP BY u.email
ORDER BY total DESC;
```

The `LEFT JOIN` keeps users with no matching expenses, and putting the date filter in the `ON` clause (not `WHERE`)
stops it from dropping them again. `COALESCE` turns their `NULL` sum into 0.
</details>

## Check yourself

1. Why store `user_id` in `expenses` instead of the user's email?

<details>
<summary>Answer</summary>

Each fact lives in one place: if the email changes you update one row, not thousands, and the foreign key guarantees
every expense points at a real user.
</details>

2. Why is `f"SELECT * FROM users WHERE email = '{email}'"` dangerous?

<details>
<summary>Answer</summary>

It lets user input become SQL. An input like `' OR '1'='1` changes the query's meaning (SQL injection). Parameterised
queries send the value separately so it is never parsed as SQL.
</details>

3. A query filtering on `user_id` is slow on a large table. What do you check first?

<details>
<summary>Answer</summary>

Run `EXPLAIN ANALYZE` to see whether it does a sequential scan, and if so add an index on `user_id` (or a composite
index matching the filter columns).
</details>
