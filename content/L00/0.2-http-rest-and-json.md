# HTTP, REST and JSON

Every LLM provider, vector database and SaaS tool you'll integrate speaks HTTP and JSON. If you can read a raw request
and response, most "the SDK is broken" mysteries become five-minute fixes.

## One request, end to end

```
POST /v1/tickets?notify=true HTTP/1.1          ← method, path, query string
Host: api.example.com
Authorization: Bearer sk-abc123                ← headers
Content-Type: application/json

{"title": "Login broken", "priority": "high"}  ← body

HTTP/1.1 201 Created                           ← status code
Content-Type: application/json
Location: /v1/tickets/42

{"id": 42, "title": "Login broken", "priority": "high"}
```

The client picks a **method** and **URL**, adds **headers** (metadata: auth, content type, caching), optionally a
**body**, and the server answers with a **status code**, headers and a body.

Where data lives:

| Piece | Example | Typical use |
|-------|---------|-------------|
| Path parameter | `/tickets/42` | which resource |
| Query parameter | `?status=open&limit=20` | filtering, paging |
| Body | JSON object | data to create or update |
| Header | `Authorization`, `Content-Type` | metadata about the request |
| Cookie | `session=...` | browser session state |

## Methods and idempotency

| Method | Meaning | Safe to repeat? |
|--------|---------|-----------------|
| GET | read | yes (no side effects) |
| POST | create / trigger an action | no: two calls may create two records |
| PUT | replace a resource | yes: same result every time |
| PATCH | partial update | depends on the patch |
| DELETE | remove | yes: second call finds nothing to delete |

**Idempotent** means doing it twice leaves the same state as doing it once. It matters because networks fail and
clients retry. Retrying a POST blindly can charge a card twice, which is why some APIs accept an idempotency key header.

## Status codes you'll meet daily

| Code | Meaning | What you do |
|------|---------|-------------|
| 200 OK / 201 Created | success | read the body |
| 400 Bad Request | your input is malformed | fix the request, don't retry |
| 401 Unauthorized | missing or bad credentials | check the key |
| 403 Forbidden | authenticated but not allowed | check permissions |
| 404 Not Found | no such resource | check the id or path |
| 409 Conflict | clashes with current state (duplicate, version mismatch) | re-read, then decide |
| 429 Too Many Requests | rate limited | back off and retry, respect `Retry-After` |
| 500 / 502 / 503 | server-side problem | often worth a retry with backoff |

4xx means "your fault", 5xx means "their fault". That split drives retry logic later in the path.

## Designing resources

REST names **things** with nouns and uses methods for verbs:

```
GET    /tickets             list (with ?status=open)
POST   /tickets             create
GET    /tickets/42          read one
PATCH  /tickets/42          update some fields
DELETE /tickets/42          delete
GET    /tickets/42/comments sub-resource
```

Avoid `/getTicket` or `/tickets/42/delete`. Return the created object with 201, and use consistent field naming.

## Auth basics

Most APIs authenticate with a key or token in a header: `Authorization: Bearer <token>` or a custom header like
`x-api-key`. Never put secrets in the URL (URLs end up in logs, browser history and proxies), and never ship a
server-side key to a browser or mobile app, where anyone can read it.

## Poking at APIs

```bash
curl -i https://api.github.com/repos/python/cpython          # -i shows status and headers
curl -s -X POST https://httpbin.org/post \
  -H "Content-Type: application/json" -d '{"q": "hello"}' | python -m json.tool
```

The same in Python:

```python
import httpx

r = httpx.get("https://api.github.com/repos/python/cpython", timeout=10)
r.raise_for_status()                 # turns 4xx/5xx into an exception
repo = r.json()
print(repo["stargazers_count"], r.headers.get("x-ratelimit-remaining"))
```

API clients such as Bruno or Postman are handy for saving and sharing collections of requests.

## Try it

Using only curl, call the GitHub REST API to (a) fetch a public repo, (b) request a repo that doesn't exist, and
(c) find how many unauthenticated requests you have left this hour. Note the status code and the header that told
you each answer.

<details>
<summary>Reference</summary>

(a) `curl -i https://api.github.com/repos/python/cpython` returns `200` and a JSON body.
(b) `curl -i https://api.github.com/repos/python/no-such-repo-xyz` returns `404` with a JSON `message`.
(c) The `x-ratelimit-remaining` and `x-ratelimit-limit` headers on any response show your remaining budget;
`x-ratelimit-reset` is a Unix timestamp for when it refills. When it hits zero you get a `403` or `429`.
</details>

## Check yourself

1. Your client times out after sending a POST that creates an order. Is it safe to retry? What would make it safe?

<details>
<summary>Answer</summary>

Not automatically: the server may have created the order before the timeout, so a retry could create a duplicate.
An idempotency key (the server remembers the key and returns the first result) or a "check before create" step makes
it safe.
</details>

2. What's the difference between 401 and 403?

<details>
<summary>Answer</summary>

401: the server doesn't know who you are (missing or invalid credentials). 403: it knows who you are, and you aren't
allowed to do this.
</details>

3. Why shouldn't an API key go in a query string?

<details>
<summary>Answer</summary>

Full URLs are routinely logged by servers, proxies and browsers and can leak through history or referrer headers.
Headers are far less likely to be recorded or shared.
</details>
