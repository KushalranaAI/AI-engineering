# Containers and deployment

"Works on my machine" usually means the code is fine and the environment is different: another Python version, a
missing system library, an unset variable. Containers package the environment with the code so it runs the same on
your laptop, in CI and in production.

## Three layers

| Layer | Examples | Who controls it |
|-------|----------|-----------------|
| Application | your Python package, its dependencies | you, in the repo |
| Environment | Python version, OS libraries, env vars, files | the image + runtime config |
| Machine | CPU, memory, network, the host OS kernel | the platform |

A Docker **image** is a read-only template of the application plus environment. A **container** is a running
instance of an image. You build an image once and run it anywhere Docker runs.

## A Dockerfile for a FastAPI app

```dockerfile
FROM python:3.12-slim

COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
WORKDIR /app

# dependencies first: this layer is cached until the lockfile changes
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project

# then the code, which changes often
COPY . .
RUN uv sync --frozen --no-dev

EXPOSE 8000
CMD ["uv", "run", "fastapi", "run", "app/main.py", "--host", "0.0.0.0", "--port", "8000"]
```

Each instruction creates a **layer**. Docker reuses unchanged layers, so ordering matters: copy rarely changing files
(the lockfile) before frequently changing ones (your code) and rebuilds take seconds. Pin the uv tag to a specific
version in real projects. Add a `.dockerignore` so junk and secrets never enter the image:

```
.venv
.git
.env
__pycache__
tests/
```

## Build, run, inspect

```bash
docker build -t expenses-api .
docker run --rm -p 8000:8000 --env-file .env expenses-api
docker ps                         # running containers
docker logs -f <container-id>     # follow stdout/stderr
docker exec -it <container-id> sh # look around inside
```

`-p 8000:8000` maps host port to container port. `--env-file` passes configuration at run time, so the image itself
holds no secrets.

## Common startup failures

| Symptom | Likely cause |
|---------|-------------|
| Container exits immediately | crash on import or missing env var; read `docker logs` |
| Works in container, unreachable from host | server bound to `127.0.0.1` instead of `0.0.0.0`, or port not published |
| Can't reach the database | `localhost` inside a container means the container itself; use the service name |
| `ModuleNotFoundError` | dependency missing from the lockfile or wrong working directory |

## App plus database with Compose

```yaml
# compose.yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/expenses
    depends_on: [db]
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: expenses
    volumes: [pgdata:/var/lib/postgresql/data]
volumes:
  pgdata:
```

`docker compose up --build` starts both. The API reaches the database at host `db`. The volume keeps data across
restarts. These hardcoded credentials are for local development only.

## Going live

Container-friendly platforms (for example Render, Railway, Fly.io, Google Cloud Run, AWS App Runner) take an image or a
repo with a Dockerfile and give you a public HTTPS URL. The usual steps:

1. Create a managed PostgreSQL instance on the platform or a provider like Neon or Supabase.
2. Set production env vars and secrets in the platform's settings, never in the image or repo.
3. Make the app listen on the port the platform provides (often via a `PORT` variable).
4. Deploy, then check logs and hit `/docs` and a health endpoint on the public URL.

Keep production and local config separate: different database, different keys, debug features off.

## Try it

Containerise the FastAPI app from module 0.3, run it with `docker run`, and confirm `/docs` loads from your browser.
Then deliberately break it by binding to `127.0.0.1`, observe the symptom, and fix it.

<details>
<summary>Reference</summary>

Use the Dockerfile above, `docker build -t bookmarks .`, `docker run --rm -p 8000:8000 bookmarks`, and open
`http://localhost:8000/docs`. With `--host 127.0.0.1` the container starts and the logs look healthy, but the browser
can't connect, because the server only accepts connections from inside the container's own network namespace.
Binding to `0.0.0.0` accepts connections on all interfaces, including the one Docker forwards the published port to.
</details>

## Check yourself

1. Why copy `pyproject.toml` and `uv.lock` before the rest of the code?

<details>
<summary>Answer</summary>

So the dependency-install layer stays cached when only code changes. Rebuilds then skip reinstalling packages.
</details>

2. Your API container can't connect to `localhost:5432`, but Postgres is running in another container. Why?

<details>
<summary>Answer</summary>

Inside a container, `localhost` is that container. Use the other container's service name on the shared network
(for example `db:5432`).
</details>

3. Where should production secrets live?

<details>
<summary>Answer</summary>

In the platform's secret or environment settings (or a secret manager), injected at run time. Not in the image, the
Dockerfile or the repository.
</details>
