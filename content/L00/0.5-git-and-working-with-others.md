# Git and working with others

Git is how your work becomes something a team can review, run and roll back. With coding agents writing large diffs
for you, it is also your main safety net: you can only review what you can see as a diff.

## The core model

| Concept | What it is |
|---------|-----------|
| Working tree | the files on disk right now |
| Staging area (index) | the changes you've picked for the next commit |
| Commit | a snapshot plus a message, author and parent pointer |
| Branch | a movable name pointing at a commit |
| Remote | another copy of the repo, usually on GitHub or GitLab |

```bash
git status                      # what changed, what's staged
git diff                        # unstaged changes
git diff --staged               # what the next commit will contain
git add src/app.py              # stage one file (avoid blind `git add .`)
git commit -m "Validate amount is positive on expense create"
```

## The everyday flow

```bash
git switch main && git pull                  # start from the latest main
git switch -c feat/expense-categories        # one branch per change
# ...edit, test, commit in small steps...
git push -u origin feat/expense-categories
gh pr create --fill                          # or open the PR in the web UI
```

A reviewer reads the pull request, CI runs the tests, you address comments, and the branch is merged into `main`.
Teams usually **protect** `main` so nobody can push to it directly or merge without a passing build and an approval.
Review isn't bureaucracy: it catches bugs, spreads knowledge, and keeps one person's assumptions from shipping
unchecked.

## History you can read

A good commit is one logical change with a message that says what and why:

```
Add retry with backoff to weather client

The upstream API returns 503 under load. Retry up to 3 times
with exponential backoff; give up and return 502 after that.
```

Not `fix`, `wip` or `changes`. When something breaks, history is your search tool:

```bash
git log --oneline --graph -15
git log -p -- src/client.py          # every change to one file
git blame src/client.py              # who last touched each line, and in which commit
git bisect start                     # binary-search for the commit that introduced a bug
```

## Merge conflicts

A conflict means two branches changed the same lines and Git won't guess which wins.

```
<<<<<<< HEAD
TIMEOUT_SECONDS = 10
=======
TIMEOUT_SECONDS = 30
>>>>>>> feat/slow-upstream
```

Resolve it: decide what the code should be (sometimes a combination), delete the markers, run the tests, then
`git add` the file and continue the merge or rebase. Pull `main` into your branch often and conflicts stay small.

## Keep junk and secrets out

```gitignore
.venv/
__pycache__/
.env
*.log
dist/
.DS_Store
```

`.gitignore` only stops untracked files from being added. If a secret was already committed, deleting it in a new
commit doesn't remove it from history: **rotate the key** first, then clean history if needed. Commit a
`.env.example` with placeholder values so others know which variables to set.

## A README that works

Test your README by imagining a colleague with a fresh laptop. It should answer:

1. What does this do, in two sentences?
2. How do I install it? (`uv sync`)
3. How do I configure it? (which env vars, copy `.env.example`)
4. How do I run it? (`docker compose up` or `uv run fastapi dev`)
5. How do I test it? (`uv run pytest`)
6. How do I call it? (a curl example or link to `/docs`)

## Try it

Create a repo, commit a file on `main`, then create two branches that each change the same line differently. Merge
both into `main` and resolve the conflict. Then show the final history as a graph.

<details>
<summary>Reference</summary>

```bash
git init demo && cd demo
echo "TIMEOUT = 10" > config.py && git add config.py && git commit -m "Add config"
git switch -c a && sed -i 's/10/20/' config.py && git commit -am "Raise timeout to 20"
git switch main && git switch -c b && sed -i 's/10/30/' config.py && git commit -am "Raise timeout to 30"
git switch main && git merge a          # fast-forward, no conflict
git merge b                              # CONFLICT in config.py
# edit config.py to the value you want, remove markers
git add config.py && git commit          # completes the merge
git log --oneline --graph --all
```

The graph shows the two branches and the merge commit joining them.

## Check yourself

1. What's the difference between `git diff` and `git diff --staged`?

<details>
<summary>Answer</summary>

`git diff` shows changes in the working tree that are not staged yet; `git diff --staged` shows what is staged and
will go into the next commit.
</details>

2. You accidentally pushed an API key in a commit. Is deleting it in the next commit enough?

<details>
<summary>Answer</summary>

No. It's still in history and possibly already scraped. Revoke and rotate the key immediately, then rewrite history if
the repo policy requires it.
</details>

3. Why do teams protect the `main` branch?

<details>
<summary>Answer</summary>

So every change arrives through a pull request with passing checks and a review, which keeps `main` deployable and
stops unreviewed or broken code from landing.
</details>
