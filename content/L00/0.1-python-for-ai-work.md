# Python for AI work

Almost every model SDK, eval tool and data library is Python-first. You don't need to be a language lawyer, but you
do need to write Python that another engineer can read, install, test and trust. This lesson is the checklist.

## Pick the right container

| Type | Use it when | Watch out for |
|------|-------------|---------------|
| `list` | ordered items you append to | `x in big_list` is a linear scan |
| `tuple` | fixed records, dict keys | immutable, so "editing" means rebuilding |
| `set` | membership tests, de-duplication | unordered |
| `dict` | lookup by key, JSON-shaped data | keys must be hashable |
| generator | streaming large or endless data | can only be consumed once |

Generators matter in AI work because you often process files too big for memory: `(line for line in f if line.strip())`
yields one line at a time.

## Types make interfaces explicit

Type hints don't change runtime behaviour, but a checker such as mypy or pyright reads them and catches mistakes
before you run anything. For data that crosses a boundary (an API response, a config file, model output) use a
**Pydantic** model, which validates at runtime too.

```python
from pydantic import BaseModel

class Ticket(BaseModel):
    id: int
    title: str
    tags: list[str] = []

Ticket.model_validate({"id": "7", "title": "Login broken"})   # id coerced to 7
Ticket.model_validate({"title": "no id"})                      # raises ValidationError
```

Use a plain `@dataclass` for internal records that don't need validation.

## Classic traps

- **Mutable defaults**: `def add(x, items=[])` shares one list across every call. Use `items: list | None = None`.
- **Aliasing**: `b = a` copies a reference, not the list. Mutating `b` mutates `a`.
- **Swallowed errors**: a bare `except: pass` hides the bug you'll spend a day hunting. Catch specific exceptions.
- **Leaked resources**: open files and connections with `with` so they close even when an exception fires.

## Concurrency with async

Calling an API is mostly waiting on the network. `asyncio` lets one thread wait on many requests at once:

```python
import asyncio, httpx

async def fetch(client: httpx.AsyncClient, url: str) -> int:
    r = await client.get(url, timeout=10)
    return r.status_code

async def main() -> None:
    urls = [f"https://httpbin.org/delay/1?i={i}" for i in range(10)]
    async with httpx.AsyncClient() as client:
        codes = await asyncio.gather(*(fetch(client, u) for u in urls))
    print(codes)   # ~1 second total, not ~10

asyncio.run(main())
```

You will use exactly this shape later to send hundreds of LLM requests. One rule: never call a blocking function
(like `requests.get` or `time.sleep`) inside `async def`, or the whole event loop stalls.

## Projects with uv

`uv` creates environments, resolves dependencies and writes a lockfile, fast.

```bash
uv init ticket-tool && cd ticket-tool
uv add httpx pydantic
uv add --dev pytest mypy
uv run pytest
```

`pyproject.toml` lists what you depend on; `uv.lock` pins exact versions so a teammate gets the same environment.
Commit both.

## Packages, tests and debugging

Once a script passes a few hundred lines, split it: `src/ticket_tool/models.py`, `client.py`, `cli.py`. Each module
gets one job. Test with pytest:

```python
# tests/test_models.py
import pytest
from pydantic import ValidationError
from ticket_tool.models import Ticket

def test_rejects_missing_id():
    with pytest.raises(ValidationError):
        Ticket.model_validate({"title": "x"})
```

When something breaks, read the stack trace bottom-up (the last frame is where it failed), add `logging` rather than
scattered prints, and drop `breakpoint()` in to inspect live state.

## Try it

Write an async script that takes five city names, fetches each one's current weather from a free API (for example
Open-Meteo) concurrently, parses the result into a Pydantic model, and prints a sorted table. Add one pytest test for
the parsing.

<details>
<summary>Reference</summary>

Structure: `models.py` with `class Weather(BaseModel): city: str; temp_c: float`; `client.py` with an
`async def get_weather(client, city, lat, lon) -> Weather` that calls
`https://api.open-meteo.com/v1/forecast?latitude=..&longitude=..&current=temperature_2m` and builds the model from
`r.json()["current"]["temperature_2m"]`; `main.py` runs `asyncio.gather` over the cities and sorts by `temp_c`. The
test feeds a saved JSON sample into the parsing function, so it runs without the network. Total runtime should be
roughly one request's latency, not five.
</details>

## Check yourself

1. Why is `def f(items=[])` a bug waiting to happen?

<details>
<summary>Answer</summary>

The default list is created once, when the function is defined, and every call that omits `items` shares and mutates
that same list. Default to `None` and create a new list inside.
</details>

2. When does `asyncio.gather` make a program faster, and when doesn't it?

<details>
<summary>Answer</summary>

It helps when the tasks spend their time waiting on I/O (network, disk), because the waits overlap. It doesn't help
CPU-bound work, and it is ruined by any blocking call inside the coroutines.
</details>

3. What is the difference between `pyproject.toml` and `uv.lock`?

<details>
<summary>Answer</summary>

`pyproject.toml` states your direct dependencies and allowed version ranges. `uv.lock` records the exact resolved
versions of everything, including transitive dependencies, so installs are reproducible.
</details>
