# Designing tools

Once tool calling works, the next problems are subtler: the model picks the wrong tool, fills in arguments badly, or is persuaded to do something it should not. Most of these are design problems, not model problems. A tool definition is an interface for a reader that only has the name, the description and the schema to go on.

## Descriptions are part of the prompt

Every tool definition is sent to the model as context on every call. The model chooses tools by reading them, the way a new colleague would read a function list with no access to the source code. That means:

- Vague descriptions produce vague choices.
- Long lists of tools cost tokens on every request and make selection harder.
- Wording in a description changes behaviour as much as wording in the system prompt.

## Weak vs strong definitions

```python
# Weak
{"name": "search", "description": "Searches stuff.",
 "input_schema": {"type": "object", "properties": {"q": {"type": "string"}, "opts": {"type": "object"}}}}

# Strong
{"name": "search_orders",
 "description": (
     "Find a customer's orders. Use when the user mentions a purchase but no order id. "
     "Returns at most 10 orders, newest first, with id, date, total and status. "
     "Does not return payment details."
 ),
 "input_schema": {
     "type": "object",
     "properties": {
         "customer_email": {"type": "string", "description": "Exact email on the account"},
         "status": {"type": "string", "enum": ["any", "pending", "shipped", "delivered", "refunded"]},
         "since": {"type": "string", "description": "ISO date YYYY-MM-DD; omit for all time"},
     },
     "required": ["customer_email"],
 }}
```

What makes the second one better:

| Property | Why it helps |
|----------|--------------|
| Specific name with a verb and noun | Distinct from other tools at a glance |
| When to use it, what it returns, what it doesn't | The model can plan the next step |
| Few parameters | Fewer chances to fill something wrongly |
| Enums and formats | Invalid values become impossible or obvious |
| No catch-all `opts` object | Nothing the model has to guess about |

## Overlap and overload

Two tools that sound alike (`get_customer` and `lookup_user`) force the model to guess. Fix it by merging them or by stating in each description when to use it rather than the other.

Fifty near-identical tools (`get_sales_jan`, `get_sales_feb`, ...) are worse than one tool with a `month` parameter. The opposite extreme, one `run_sql` tool that can do anything, is flexible but hard to make safe. Aim for tools that match the tasks users actually ask for.

## Errors that help the model recover

A tool result is read by the model, so make errors actionable:

```python
# Unhelpful
return "Error 400"

# Helpful
return ("No customer with email 'priya@exmaple.com'. "
        "Check the spelling or ask the user for the email on their account.")
```

Return compact, relevant data too. A 5,000-line JSON dump wastes context and buries the field the model needs.

## Arguments are untrusted input

The model writes the arguments, and the model can be wrong or manipulated (a user message or a fetched web page might contain instructions). Treat arguments exactly as you would a form submitted by an anonymous user.

```python
from pydantic import BaseModel, Field, ValidationError

class RefundArgs(BaseModel):
    order_id: str = Field(pattern=r"^[A-Z]-\d{4}$")
    amount: float = Field(gt=0, le=500)

def refund_tool(raw_args: dict, user) -> str:
    try:
        args = RefundArgs.model_validate(raw_args)
    except ValidationError as e:
        return f"Invalid arguments: {e.errors()[0]['msg']}"
    order = db.get_order(args.order_id)
    if order is None or order.customer_id != user.id:      # permission check in code
        return "Order not found for this customer."
    if args.amount > order.total:
        return "Refund cannot exceed the order total."
    if args.amount > 100:
        return queue_for_human_approval(order, args.amount)  # risky action: human in the loop
    return issue_refund(order, args.amount)
```

Rules of thumb:

- **Validate** types, formats and ranges.
- **Authorise** with the real user's identity from your session, never with an id the model supplied.
- **Limit blast radius**: read-only tools by default, scoped database users, no tool that deletes in bulk.
- **Confirm** destructive or costly actions with a person, or require an extra step.

A prompt that says "never refund more than $100" is a suggestion. The `if` statement is the rule.

## Try it

Here is a tool definition: `{"name": "do_user", "description": "Does user things", "input_schema": {"type": "object", "properties": {"action": {"type": "string"}, "data": {"type": "object"}}}}`. Rewrite it as one or more well-designed tools for a support bot that can look up a user's plan and change their email address.

<details>
<summary>Reference</summary>

Split into two tools with clear purposes:

- `get_user_plan` - "Return the current plan name, renewal date and seat count for the signed-in user. Read-only." No parameters at all: the user comes from the session, not from the model.
- `request_email_change` - "Start an email change for the signed-in user. Sends a confirmation link to the new address; nothing changes until it is clicked." Parameter `new_email` (string, format email, required).

Server-side, validate the email format, take the user id from the session, and keep the confirmation step so a manipulated call cannot hijack the account.
</details>

## Check yourself

1. Why can editing a tool's description change behaviour even if no code changes?

<details>
<summary>Answer</summary>

The description is sent to the model as context and is the main thing it uses to decide whether and how to call the tool.
</details>

2. A model calls `delete_account(user_id="42")`. Where should the check that user 42 is the signed-in user live?

<details>
<summary>Answer</summary>

In your application code, using the session's identity. Better still, the tool should not accept a user id at all and should act only on the authenticated user.
</details>

3. What is wrong with exposing fifty narrowly different tools?

<details>
<summary>Answer</summary>

They consume context on every call and make correct selection harder because the options look alike. Consolidate them into fewer tools with parameters.
</details>
