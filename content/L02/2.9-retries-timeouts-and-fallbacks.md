# Retries, timeouts and fallbacks

LLM APIs fail more often than the databases and services you are used to. Providers get overloaded at peak hours, rate limits bite during traffic spikes, a long generation hangs, a tool's upstream API times out. A feature that works in a demo and falls over in production usually lacks a clear answer to one question: for each kind of failure, what should happen?

## A map of failures

| Failure | Typical signal | Retry? | Instead |
|---------|----------------|--------|---------|
| Bad or missing API key | 401 / 403 | No | Fail fast, alert |
| Invalid request (bad params, unknown model) | 400 / 404 | No | Fix the code; log the request |
| Prompt too long for the context window | 400 with a context-length message | No (not as-is) | Trim or summarise input, then retry |
| Rate limited | 429, often with a `retry-after` header | Yes, after waiting | Slow down, queue |
| Provider error or overloaded | 500, 502, 503, 529 | Yes, a few times | Fall back if it persists |
| Network error, connection reset | Connection exception | Yes | |
| Request took too long | Timeout | Usually yes, once or twice | Smaller output, faster model |
| Output fails your schema or checks | Your validation error | Yes, with feedback (module 2.4) | Reject or route to a human |
| Tool's own API fails | Exception in your tool code | Depends on that API | Return an error result to the model |

The split that matters: **transient** errors may succeed if you try again; **permanent** errors never will, and retrying them just burns time and money.

## Backoff with jitter

Retrying immediately makes overload worse. Wait longer after each failure (exponential backoff), and add randomness (jitter) so thousands of clients do not all retry at the same instant.

```python
import random, time
import anthropic

client = anthropic.Anthropic(max_retries=0, timeout=30.0)   # we handle retries ourselves here

def is_retryable(e: Exception) -> bool:
    if isinstance(e, anthropic.APIConnectionError):           # network errors and timeouts
        return True
    if isinstance(e, anthropic.APIStatusError):
        return e.status_code == 429 or e.status_code >= 500   # rate limit, server error, overloaded
    return False                                              # 400, 401, 403, 404: fail fast

def call_with_retry(max_attempts: int = 4, **kwargs):
    for attempt in range(max_attempts):
        try:
            return client.messages.create(**kwargs)
        except Exception as e:
            if not is_retryable(e) or attempt == max_attempts - 1:
                raise
            delay = min(30, 2 ** attempt) * random.uniform(0.5, 1.5)   # ~1, 2, 4 s, jittered
            if isinstance(e, anthropic.APIStatusError):
                retry_after = e.response.headers.get("retry-after")
                if retry_after:
                    delay = max(delay, float(retry_after))
            time.sleep(delay)
```

The official SDKs already retry some transient errors with backoff (a couple of attempts by default) and accept `max_retries` and `timeout` options. Know those defaults; otherwise your own loop multiplies with the SDK's and one request quietly becomes twelve.

## Timeouts

A default timeout of many minutes is not a plan. Set one per use case:

- Interactive chat: a short connect timeout and a total budget the user will tolerate; stream so progress is visible.
- Background extraction: longer, but still bounded.
- Reasoning models and long outputs: genuinely slow; give them more time or move them to a background job.

Remember that the user's wait is the sum of all attempts. Three retries of a 30-second timeout is a 90-second worst case.

## Graceful degradation and fallbacks

When retries run out, choose what the user sees:

- **Fallback model or provider.** Try a different model, or the same model through another provider or cloud platform.
- **Reduced feature.** Return search results without the AI summary; show a cached answer.
- **Honest failure.** "The assistant is unavailable, please try again", plus an alert for you.

```python
from langchain.chat_models import init_chat_model

primary = init_chat_model("anthropic:claude-sonnet-4-5", max_retries=2, timeout=30)   # example ids
backup = init_chat_model("openai:gpt-5-mini", max_retries=2, timeout=30)
model = primary.with_fallbacks([backup])
```

Fallbacks are not free. The backup model may format output differently, follow instructions less well, or handle tools differently. Test your prompts, schemas and tool definitions against it too, and log which model actually answered so you can tell when quality dips because of fallback.

## Two levels: model calls and tool calls

In a tool loop, failure can come from the model API or from the tool. Handle them separately. A model API failure is retried by your call wrapper. A tool failure is usually returned to the model as an error result, so it can choose another approach, with your own retry inside the tool only for that API's transient errors.

## Where the logic lives

| Layer | Good for |
|-------|----------|
| Provider SDK | Basic transient retries, timeouts |
| Framework (`with_retry`, `with_fallbacks`) | Cross-provider fallbacks, retry policies on chains |
| Your code | Business decisions: what to show the user, validation retries, degradation, alerts |

Pick one owner for each policy and write it down.

For each of these, decide retry / do not retry / change input and retry: (a) 401, (b) 429 with `retry-after: 20`, (c) 400 "prompt is too long", (d) 503, (e) valid JSON missing a required field.

<details>
<summary>Reference</summary>

(a) Do not retry: credentials are wrong; alert. (b) Retry after at least 20 seconds, and reduce your concurrency. (c) Change input: trim history or documents, then retry once. (d) Retry with backoff; fall back if it persists. (e) Retry with the validation error as feedback, a limited number of times, then reject.

## Check yourself

1. Why add jitter to backoff?

<details>
<summary>Answer</summary>

Without it, many clients that failed at the same moment retry at the same moment, causing another spike. Randomness spreads retries out.
</details>

2. Your wrapper retries 3 times and the SDK also retries 2 times. What is the worst case?

<details>
<summary>Answer</summary>

Up to 4 x 3 = 12 HTTP attempts for one logical call (each of your 4 attempts includes the SDK's original try plus 2 retries), with latency and cost to match. Decide which layer owns retries.
</details>

3. What should you check before relying on a fallback model?

<details>
<summary>Answer</summary>

That your prompts, output schemas and tools work acceptably on it, since behaviour and quality differ between models. Log which model served each request.
</details>
