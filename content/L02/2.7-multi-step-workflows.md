# Multi-step workflows

Real features are rarely one prompt and one answer. A support reply might need to classify the message, fetch the customer's data, draft a reply, then check the draft for policy problems. You can cram all of that into one huge prompt, or you can build a **workflow**: several focused steps (model calls, tools and plain code) joined by control flow that you write.

## Workflows vs agents

| | Workflow | Agent |
|---|----------|-------|
| Who decides the next step | Your code | The model, in a loop |
| Predictability | High: same path for same kind of input | Lower: path varies |
| Debugging | Step by step, like normal code | Harder: you inspect the model's choices |
| Good for | Known processes | Open-ended tasks |

The tool loop from module 2.5 is already a small step towards an agent, since the model chooses tools. This module is about the other end: you own the flow. Start here; reach for agents only when the steps genuinely cannot be known in advance.

## Four common shapes

**Chain (sequential).** Each step's output feeds the next. Example: extract facts -> draft -> polish.

**Router.** A cheap call classifies the input, then code sends it to the right handler. Example: billing questions to one prompt, bug reports to another, everything else to a human.

**Conditional branch / gate.** Code checks an intermediate result and decides whether to continue. Example: if the draft fails a check, revise it once, otherwise send.

**Fan-out / fan-in.** Run independent calls in parallel, then combine. Example: summarise ten documents separately, then merge the summaries.

## Built by hand

```python
import asyncio
from enum import Enum
from pydantic import BaseModel
from langchain.chat_models import init_chat_model

fast = init_chat_model("anthropic:claude-haiku-4-5", temperature=0)   # example ids
strong = init_chat_model("anthropic:claude-sonnet-4-5", temperature=0)

class Route(str, Enum):
    billing = "billing"
    bug = "bug"
    other = "other"

class Classified(BaseModel):
    route: Route
    reason: str

class Check(BaseModel):
    ok: bool
    problems: list[str]

async def handle(message: str) -> str:
    # 1. route (cheap model, structured output)
    c = await fast.with_structured_output(Classified).ainvoke(
        f"Classify this support message:\n{message}")
    if c.route == Route.other:
        return "ESCALATE_TO_HUMAN"

    # 2. draft with a route-specific prompt
    system = {"billing": "You resolve billing questions. Never promise refunds.",
              "bug": "You collect reproduction steps for bugs politely."}[c.route.value]
    draft = (await strong.ainvoke([("system", system), ("human", message)])).content

    # 3. gate: check the draft, revise once if needed
    check = await fast.with_structured_output(Check).ainvoke(
        f"Does this reply promise a refund or share internal info? Reply:\n{draft}")
    if not check.ok:
        draft = (await strong.ainvoke([("system", system), ("human", message),
                  ("ai", draft), ("human", f"Revise to fix: {check.problems}")])).content
    return draft
```

Everything about the flow is visible in ordinary Python: the order of steps, which model each uses, and what happens when a check fails.

## Fan-out / fan-in

```python
async def summarise_all(docs: list[str]) -> str:
    parts = await asyncio.gather(*[
        fast.ainvoke(f"Summarise in 3 bullets:\n{d}") for d in docs])
    joined = "\n\n".join(p.content for p in parts)
    return (await strong.ainvoke(f"Merge these summaries into one brief:\n{joined}")).content
```

## The same with LangChain composition

LangChain's runnables express these shapes declaratively: `|` for chains, `RunnableParallel` for fan-out, and `RunnableBranch` or a plain function for routing.

```python
from langchain_core.runnables import RunnableParallel
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

pros = ChatPromptTemplate.from_template("List pros of {idea}") | fast | StrOutputParser()
cons = ChatPromptTemplate.from_template("List cons of {idea}") | fast | StrOutputParser()
verdict = ChatPromptTemplate.from_template("Pros:\n{pros}\nCons:\n{cons}\nGive a verdict.")

flow = RunnableParallel(pros=pros, cons=cons) | verdict | strong | StrOutputParser()
print(flow.invoke({"idea": "moving our cron jobs to a queue"}))
```

Build a flow by hand first so you know what the composed version does.

## When to split a task

Split one prompt into several when:

- The prompt asks for unrelated things and quality drops on some of them.
- Parts need different models (cheap classifier, strong writer).
- You need to check or act on an intermediate result in code.
- You want to see which step fails.

Keep one call when the steps are tightly linked and a split would mean passing large context around repeatedly. Every extra call adds latency and cost.

## Try it

Design a workflow that turns a meeting transcript into (a) a summary and (b) a list of action items with owners, then emails only the action items whose owner is in a given list. Sketch the steps, say which are model calls and which are code, and mark what can run in parallel.

<details>
<summary>Reference</summary>

1. Model call: summary (free text).
2. Model call, in parallel with step 1: extract action items with structured output (`list[{task, owner, due}]`).
3. Code: filter items whose owner is in the allowed list; normalise names.
4. Code: send emails through your email API. No model involved, so no risk of the model emailing the wrong person.
5. Optional gate: if step 2 returns zero items for a long transcript, re-run with a stricter prompt or flag for review.

Steps 1 and 2 are a fan-out; steps 3 and 4 are deterministic code, which is exactly where decisions with side effects belong.
</details>

## Check yourself

1. What is the key difference between a workflow and an agent?

<details>
<summary>Answer</summary>

In a workflow your code decides the sequence of steps. In an agent, the model decides what to do next in a loop.
</details>

2. Why use a small, cheap model for routing?

<details>
<summary>Answer</summary>

Classification into a few categories is easy, runs on every request, and its output is short, so a fast cheap model keeps latency and cost down while the strong model is saved for the hard step.
</details>

3. Give one cost of splitting a task into many calls.

<details>
<summary>Answer</summary>

More latency and more tokens, since each call has its own overhead and often repeats context. Errors can also compound across steps.
</details>
