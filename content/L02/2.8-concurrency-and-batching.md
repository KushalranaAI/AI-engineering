# Concurrency and batching

Say you need to classify 5,000 support tickets and each call takes 2 seconds. One at a time, that is almost three hours, nearly all of it spent waiting on the network. Your CPU is idle. LLM calls are I/O-bound, so running many at once is the obvious fix. The catch is that providers limit how fast you can go, and blasting 5,000 requests at once gets you a wall of 429 errors.

## Where the speed comes from

| Approach | 5,000 calls x 2 s | Notes |
|----------|-------------------|-------|
| Sequential | ~10,000 s (2.8 h) | Simple, slow |
| 20 concurrent | ~500 s (8 min) | If rate limits allow 20 in flight |
| 100 concurrent | ~100 s | Will likely hit tokens-per-minute limits first |
| Batch API | Minutes to hours, async | Usually much cheaper; results arrive later |

Concurrency improves **throughput** (calls finished per minute). It does not make any single call faster.

## Concurrent calls with asyncio

Both major SDKs ship async clients. `asyncio.gather` starts many calls; a **semaphore** caps how many are in flight.

```python
import asyncio
import anthropic

client = anthropic.AsyncAnthropic()
MODEL = "claude-haiku-4-5"  # example id
LIMIT = asyncio.Semaphore(20)          # at most 20 requests in flight

async def classify(ticket: str) -> str:
    async with LIMIT:
        resp = await client.messages.create(
            model=MODEL, max_tokens=10,
            system="Reply with one word: billing, bug, account or other.",
            messages=[{"role": "user", "content": ticket}],
        )
        return resp.content[0].text.strip()

async def main(tickets: list[str]) -> list[str]:
    return await asyncio.gather(*(classify(t) for t in tickets))

labels = asyncio.run(main(tickets))
```

Without the semaphore, `gather` fires all 5,000 requests immediately. With it, you get steady throughput under your limit.

For robustness, add `return_exceptions=True` to `gather` (or use `asyncio.TaskGroup` with per-task error handling) so one failure does not throw away the other 4,999 results. Module 2.9 covers retries.

## Know your limits

Providers enforce several limits at once, per model and per account tier:

- **Requests per minute** (RPM)
- **Input tokens per minute** and **output tokens per minute** (or a combined TPM)
- Sometimes a cap on concurrent requests

Back-of-envelope: each ticket call uses about 300 input tokens. A 200,000 input-tokens-per-minute limit allows about 660 calls a minute, or 11 per second. At 2 s per call, about 22 in flight sustains that, so a semaphore of 20 is sensible. Pushing to 100 just produces 429s and retries.

Rate-limit responses usually include headers telling you how much budget remains and when it resets. Read them rather than guessing.

## Framework batching

LangChain runnables have `batch` and `abatch`, with a concurrency cap:

```python
results = chain.batch(inputs, config={"max_concurrency": 20})
```

This is the same semaphore idea, packaged.

## Provider batch APIs

When nobody is waiting for the answer (nightly enrichment, backfills, evaluation runs), use the provider's batch endpoint. You submit many requests at once; the provider processes them when it has capacity, typically within 24 hours and often much faster, at a significant discount (commonly around half the normal price; check current pricing).

```python
sync_client = anthropic.Anthropic()
batch = sync_client.messages.batches.create(
    requests=[
        {"custom_id": f"ticket-{i}",
         "params": {"model": MODEL, "max_tokens": 10,
                    "system": "Reply with one word: billing, bug, account or other.",
                    "messages": [{"role": "user", "content": t}]}}
        for i, t in enumerate(tickets)
    ]
)
print(batch.id, batch.processing_status)
# later: poll the batch, then read results and match them back by custom_id
```

OpenAI's Batch API works similarly with an uploaded JSONL file. Results can come back in any order, so the `custom_id` is how you join them to your inputs.

## Choosing

| Situation | Use |
|-----------|-----|
| User waiting, one request | Single call, streamed |
| User waiting, several independent calls | `gather` a few concurrent calls |
| Thousands of items, need results in minutes | Bounded concurrency under rate limits |
| Thousands of items, can wait hours | Batch API, cheaper |

Concurrency also costs local resources (open connections, memory for results) and can starve other features that share the same API key and rate limits. Consider a separate key or project for bulk jobs.

Typical shape of results: sequential takes roughly 100 x average latency; a semaphore of 10 cuts it about tenfold; 50 helps further only if your rate limit allows, and on a low tier you will start seeing `RateLimitError` (HTTP 429). Total tokens and cost are identical in every run: concurrency changes speed, not price. Wrap each call so errors are captured rather than cancelling the whole run:

results = await asyncio.gather(*(classify(t) for t in texts), return_exceptions=True)
failed = [r for r in results if isinstance(r, Exception)]

## Check yourself

1. Why does concurrency speed up LLM workloads even in single-threaded Python?

<details>
<summary>Answer</summary>

The calls spend almost all their time waiting on the network. asyncio lets one thread keep many requests waiting at once, so throughput rises without needing more CPU.
</details>

2. What does a semaphore add to `asyncio.gather`?

<details>
<summary>Answer</summary>

A cap on how many requests are in flight at once, keeping you under rate limits instead of firing everything immediately.
</details>

3. When is a batch API the better choice than concurrent calls?

<details>
<summary>Answer</summary>

When no one is waiting for the results and you can tolerate a delay of minutes to hours: backfills, nightly jobs, evaluation runs. You get a lower price and avoid fighting your real-time rate limits.
</details>
