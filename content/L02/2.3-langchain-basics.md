# LangChain basics

Once you have called two providers by hand, you notice the differences are mostly cosmetic. One calls the system prompt `system`, the other `instructions`. Token counts live under different field names. Tool formats differ slightly. Orchestration libraries such as LangChain exist to smooth over that, and to give you reusable pieces for prompts, parsing and chaining. The price is a layer of code between you and the API that you need to be able to see through.

## What LangChain wraps

| You write | LangChain gives you | Underneath |
|-----------|---------------------|------------|
| Provider-specific client code | A common chat model interface (`invoke`, `stream`, `batch`) | The same HTTP calls to the provider |
| f-strings for prompts | Prompt templates with named variables | String formatting into messages |
| `json.loads` and checks | Output parsers and `with_structured_output` | Provider structured output or parsing |
| Glue code between steps | Runnables you compose with `|` | Function calls in sequence |

The model itself is unchanged. LangChain is an orchestration layer, not a model, and every call still becomes an ordinary request to OpenAI, Anthropic, Google or a local server.

## Chat models and messages

```python
# pip install langchain langchain-anthropic langchain-openai
from langchain.chat_models import init_chat_model
from langchain_core.messages import SystemMessage, HumanMessage

claude = init_chat_model("anthropic:claude-sonnet-4-5", temperature=0)   # example ids
gpt = init_chat_model("openai:gpt-5-mini")

msgs = [
    SystemMessage("You answer in one sentence."),
    HumanMessage("What does HTTP 409 mean?"),
]
for model in (claude, gpt):
    reply = model.invoke(msgs)          # an AIMessage
    print(reply.content)
    print(reply.usage_metadata)         # {'input_tokens': ..., 'output_tokens': ..., ...}
```

Same code, two providers. The `usage_metadata` field is normalised, which is handy for cost tracking. `model.stream(msgs)` yields chunks the same way for both.

## Prompt templates and parsers

A template turns variables into a list of messages. A parser turns the model's message into something your code wants.

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    ("system", "You write release notes for {audience}. Max {n} bullet points."),
    ("human", "Changes:\n{diff_summary}"),
])

chain = prompt | claude | StrOutputParser()

notes = chain.invoke({
    "audience": "non-technical customers",
    "n": 3,
    "diff_summary": "Fixed CSV export timeout; added dark mode; upgraded auth library",
})
print(notes)
```

## Runnables and composition

Prompts, models and parsers are all **runnables**: objects with `invoke`, `stream`, `batch` and async versions (`ainvoke`, ...). The `|` operator pipes the output of one into the next. That gives you, for free:

- `chain.batch([...inputs])` to run many inputs with concurrency.
- `chain.stream(...)` to stream the final step's output.
- Plain Python functions in a chain via `RunnableLambda`.

```python
from langchain_core.runnables import RunnableLambda

shout = RunnableLambda(lambda s: s.upper())
loud_chain = prompt | claude | StrOutputParser() | shout
```

## The same feature, raw

Here is the release-notes chain with the Anthropic SDK only:

```python
import anthropic
client = anthropic.Anthropic()

def release_notes(audience: str, n: int, diff_summary: str) -> str:
    resp = client.messages.create(
        model="claude-sonnet-4-5", max_tokens=400, temperature=0,
        system=f"You write release notes for {audience}. Max {n} bullet points.",
        messages=[{"role": "user", "content": f"Changes:\n{diff_summary}"}],
    )
    return "".join(b.text for b in resp.content if b.type == "text")
```

Compare honestly:

| | Raw SDK | LangChain |
|---|---------|-----------|
| Lines for one call | About the same | About the same |
| Switching provider | Rewrite call code | Change one string |
| Batching, streaming, retries | You write them | Built in |
| Seeing the exact request | Obvious | Needs tracing or debug logging |
| Dependencies and upgrades | One SDK | Several packages that move quickly |
| Provider-only features | Immediately available | Sometimes lag or need passthrough options |

Neither is "right". The rule for this path: use the framework when it saves real work, and always be able to say which API calls it is making for you.

## Try it

Build a chain that takes a product review and returns a one-line summary plus a sentiment word. Run it on three reviews with `chain.batch`, then switch the model to a different provider by changing only the model string. Finally, write the same thing with a raw SDK and count the lines.

```python
prompt = ChatPromptTemplate.from_messages([

chain = prompt | init_chat_model("anthropic:claude-haiku-4-5") | StrOutputParser()
reviews = ["Fast shipping, great fit.", "Broke after a week.", "Nice colour but runs small."]
for r in chain.batch([{"review": x} for x in reviews]):
    print(r, "\n---")
```

Swapping to `init_chat_model("openai:gpt-5-mini")` changes nothing else. The raw version is a loop of SDK calls, slightly more code once you add concurrency yourself. The output is free text here; module 2.4 shows how to get typed fields instead.

## Check yourself

1. What does LangChain send to the provider when you call `chain.invoke`?

<details>
<summary>Answer</summary>

An ordinary API request: the template is filled into messages, sent through the provider's API, and the response is passed through the parser. There is no extra model or magic; it is the same call you would write by hand.
</details>

2. Name one advantage and one cost of using the framework over a raw SDK.

<details>
<summary>Answer</summary>

Advantage: a common interface, so switching providers or adding batching and streaming is cheap. Cost: an extra layer that hides the exact request, adds dependencies, and can lag behind new provider features.
</details>

3. What makes a prompt, a model and a parser composable with `|`?

<details>
<summary>Answer</summary>

They all implement the runnable interface (`invoke`, `stream`, `batch` and async versions), so the output of one can be fed as the input of the next.
</details>
