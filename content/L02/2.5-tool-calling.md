# Tool calling

A model on its own can only produce text. It cannot check today's exchange rate, look up an order or send an email. Tool calling (also called function calling) closes that gap with a simple division of labour: **the model decides which function to call and with what arguments; your code runs it** and hands back the result. The model never executes anything itself.

## The loop

```
1. You send: messages + tool definitions
2. Model replies: "call get_order(order_id='A-1192')"     stop_reason = tool_use
3. Your code runs get_order("A-1192")
4. You send: the whole conversation + the tool result, tagged with the call's id
5. Model replies with a final answer (or asks for another tool)
```

Steps 2-4 can repeat. The loop ends when the model answers without asking for a tool.

## Defining a tool

A tool is a name, a description and a JSON Schema for its arguments.

```python
tools = [{
    "name": "get_order",
    "description": "Look up an order by id. Returns status, items and delivery date.",
    "input_schema": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "description": "Order id such as A-1192"},
        },
        "required": ["order_id"],
    },
}]
```

## The full loop with the Anthropic SDK

```python
import json
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-5"  # example id

def get_order(order_id: str) -> dict:
    fake_db = {"A-1192": {"status": "shipped", "eta": "2026-11-09"}}
    if order_id not in fake_db:
        raise KeyError(f"no order {order_id}")
    return fake_db[order_id]

REGISTRY = {"get_order": get_order}

def run(user_text: str) -> str:
    messages = [{"role": "user", "content": user_text}]
    for _ in range(5):                                  # hard cap on rounds
        resp = client.messages.create(model=MODEL, max_tokens=800,
                                      tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")

        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            try:
                output = REGISTRY[block.name](**block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": json.dumps(output)})
            except Exception as e:
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": f"Error: {e}", "is_error": True})
        messages.append({"role": "user", "content": results})
    return "Stopped: too many tool rounds."

print(run("Where is my order A-1192?"))
```

Details that matter:

- The assistant turn containing the `tool_use` blocks must go back into history unchanged, followed by a user turn with the matching `tool_result` blocks.
- Every result carries the **id** of the call it answers. With several calls in one turn, ids are how the model matches results to requests.
- Errors go back to the model as results (`is_error`), so it can apologise, retry with a corrected argument or ask the user. Crashing the loop helps no one.
- Cap the number of rounds so a confused model cannot loop forever.

OpenAI's APIs follow the same pattern with different field names: tools declared with a `parameters` schema, the model returns function calls with a `call_id`, and you send back outputs that reference that id.

## Several calls, and calls that depend on each other

| Pattern | Example | What your code does |
|---------|---------|---------------------|
| Parallel | "Weather in Paris and Rome?" -> two calls in one turn | Run both (concurrently if you like), return both results in one user turn |
| Repeated | Same tool with different arguments | Same as parallel |
| Sequential | "Refund my last order" -> `list_orders`, then `refund(order_id=...)` from the first result | Loop: each round's result informs the next request |

The loop above handles all three because it processes every `tool_use` block and keeps going until the model stops asking.

## When the call is bad

Models sometimes produce arguments that are wrong: a missing field, an invented id, a date in the wrong format, or a tool name you never defined. Treat the arguments like any user input:

- Validate against the schema (Pydantic is convenient) before running.
- Return a clear error message as the tool result instead of raising.
- Never assume a requested call is safe to run; that is the subject of the next module.

## LangChain's view

LangChain turns a typed Python function into a tool definition and normalises tool calls across providers:

```python
from langchain_core.tools import tool
from langchain.chat_models import init_chat_model

@tool
def get_order_tool(order_id: str) -> dict:
    """Look up an order by id. Returns status and delivery date."""
    return get_order(order_id)

model = init_chat_model("anthropic:claude-sonnet-4-5").bind_tools([get_order_tool])
msg = model.invoke("Where is order A-1192?")
print(msg.tool_calls)   # [{'name': 'get_order_tool', 'args': {...}, 'id': ...}]
```

You still run the loop (or use a prebuilt one). Under the hood it sends exactly the JSON you wrote by hand above.

## Try it

Add a second tool, `get_weather(city: str)`, returning a fake temperature. Ask "Is my order A-1192 shipped, and what's the weather in Pune?" Print every request and response block. How many model calls happen, and how many tool calls are in the first response?

<details>
<summary>Reference</summary>

Usually two model calls: the first response contains two `tool_use` blocks (one per tool, often in parallel), your code runs both and sends two `tool_result` blocks in one user turn, and the second response is the final answer. Some models call the tools one at a time instead, giving three model calls; the loop handles both. If you sent results in two separate user turns or dropped the assistant turn, the API returns an error about unmatched tool use ids.
</details>

## Check yourself

1. Who executes the function in tool calling?

<details>
<summary>Answer</summary>

Your application. The model only produces the tool name and arguments; your code decides whether to run it, runs it, and returns the result.
</details>

2. Why does every tool result need the id of the call it answers?

<details>
<summary>Answer</summary>

A single turn can contain several calls, even to the same tool. The id tells the model which result belongs to which request.
</details>

3. A tool raises an exception. What should your loop do?

<details>
<summary>Answer</summary>

Catch it and return a tool result describing the error (marked as an error), so the model can recover, try other arguments or tell the user. Also cap the rounds so repeated failures cannot loop forever.
</details>
