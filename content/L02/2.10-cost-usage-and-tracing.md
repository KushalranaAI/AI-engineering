# Cost, usage and tracing

A user reports that the assistant gave a weird answer yesterday afternoon. Another team asks why the AI bill tripled this month. If all you have is `print()` output in a terminal that has since closed, you cannot answer either question. LLM features need the same observability as any service, plus a few extras: tokens, cost, and the chain of model and tool calls behind each answer.

## What to record for every call

| Field | Why |
|-------|-----|
| trace id, step name | Join this call to the request it belongs to |
| model (exact id returned) | Behaviour and price depend on it, and fallbacks change it |
| input, output (and cached / reasoning) tokens | What you are billed for |
| latency, time to first token | User experience and timeouts |
| stop reason | Truncation and tool requests |
| retries, error type | Reliability |
| tool calls (name, args, duration, ok/error) | Most bugs in tool flows live here |
| estimated cost | Budgets and per-feature accounting |
| prompt version | Which instructions produced this output |

Whether to log the full prompt and response text is a policy decision: invaluable for debugging, but it may contain personal data. Many teams log text in a restricted store with retention limits, and metadata everywhere.

## Estimating cost

Cost is tokens times price, per direction:

```python
# Example prices per million tokens; look up current numbers for your models.
PRICES = {
    "claude-sonnet-4-5": {"in": 3.00, "out": 15.00},
    "claude-haiku-4-5": {"in": 1.00, "out": 5.00},
}

def estimate_cost(model: str, input_tokens: int, output_tokens: int) -> float:
    p = PRICES[model]
    return (input_tokens * p["in"] + output_tokens * p["out"]) / 1_000_000
```

Worked example: a chat turn with 6,000 input tokens (system prompt, history, tool results) and 400 output tokens, at $3 / $15 per million, costs 0.018 + 0.006 = $0.024. At 50,000 turns a day that is about $1,200 a day. Notice that input dominates here: long histories and verbose tool results are often the biggest line item. Cached input and batch requests are usually billed at lower rates; reasoning tokens are billed as output.

## Think in traces

One user request can involve a router call, two tool calls, a drafting call and a checking call. Logging each in isolation makes it hard to see the whole. A **trace** groups them: one trace per request, made of **spans** (one per step), each with a start time, duration, parent and attributes. This is the same model used by OpenTelemetry for ordinary distributed systems.

```python
import json, logging, time, uuid
from contextlib import contextmanager

log = logging.getLogger("llm")

@contextmanager
def span(trace_id: str, name: str, **attrs):
    start = time.perf_counter()
    record = {"trace_id": trace_id, "span": name, **attrs}
    try:
        yield record                      # the step adds fields such as tokens
        record["ok"] = True
    except Exception as e:
        record.update(ok=False, error=type(e).__name__)
        raise
    finally:
        record["ms"] = round((time.perf_counter() - start) * 1000)
        log.info(json.dumps(record))

trace_id = str(uuid.uuid4())
with span(trace_id, "draft_reply", model=MODEL, prompt_version="support-v7") as s:
    resp = client.messages.create(model=MODEL, max_tokens=500, messages=msgs)
    s.update(in_tok=resp.usage.input_tokens, out_tok=resp.usage.output_tokens,
             stop=resp.stop_reason,
             cost=estimate_cost(MODEL, resp.usage.input_tokens, resp.usage.output_tokens))
```

One JSON line per span is easy to search, and any log tool can then answer "show me trace X" or "sum cost by prompt version".

## Questions a trace should answer

- Which step failed, and with what error?
- Which call used the most tokens? (Often a tool result that returned far too much data.)
- Which tool did the model choose, with what arguments?
- Where did the seconds go: queueing, TTFT, generation, or a slow tool?
- Did a retry or fallback happen?

## Framework tracing

You do not have to build all of this yourself. LangChain emits events through **callbacks** for every model call, tool call and chain step, and tracing platforms consume them. LangSmith is LangChain's own; Langfuse, Arize Phoenix and others accept OpenTelemetry-style traces from many frameworks and raw SDKs. Turning one on usually takes a few environment variables, after which each `chain.invoke` appears as a tree of spans with inputs, outputs, tokens and timings.

Use a tracing tool for exploration and debugging, and keep your own structured logs or metrics for the numbers you alert on (error rate, cost per day, p95 latency).

Instrument the tool-calling loop from module 2.5 so that one user question produces one trace id, with a span per model call and per tool call. Run three questions, then answer from the logs alone: total cost per question, slowest step, and how many model calls each question needed.

<details>
<summary>Reference</summary>

Create the trace id at the start of `run()`. Wrap each `client.messages.create` in `span(trace_id, f"model_call_{i}", ...)` recording tokens, stop reason and cost; wrap each tool execution in `span(trace_id, f"tool:{block.name}", args=block.input)`. Then, for example with `jq`:

```bash
jq -s 'group_by(.trace_id) | map({trace: .[0].trace_id,
  cost: (map(.cost // 0) | add), calls: (map(select(.span|startswith("model"))) | length),
  slowest: (max_by(.ms) | .span)})' llm.log
```

Typical finding: the second model call costs more than the first because it carries the tool results, and slow answers are usually slow tools, not the model.

## Check yourself

1. Why record the model id returned in the response rather than the one you requested?

<details>
<summary>Answer</summary>

Aliases can resolve to new snapshots, and fallbacks may serve the request with a different model. The returned id is what actually produced the output and what you were billed for.
</details>

2. What is the difference between a log line per call and a trace?

<details>
<summary>Answer</summary>

A trace links all the calls and tool executions that served one request, with parent-child relationships and timings, so you can see the whole flow and find the failing or expensive step.
</details>

3. In a long chat, why does input often cost more than output even though output tokens are priced higher?

<details>
<summary>Answer</summary>

Every turn resends the system prompt, history and tool results, so input token counts grow far larger than the short replies. Volume outweighs the higher per-token output price.
</details>
