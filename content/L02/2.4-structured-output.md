# Structured output

Most model output in real systems is read by code, not people: a ticket category, extracted invoice fields, a list of actions. "Please reply in JSON" works most of the time, and "most of the time" means your parser crashes a few times a day. Structured output means giving the API a schema and getting back data that is guaranteed, or at least checked, to fit it.

## Three levels of strictness

| Approach | What you get | Failure mode |
|----------|--------------|--------------|
| Ask for JSON in the prompt | Usually JSON | Prose around it, missing fields, trailing commas |
| JSON mode | Valid JSON | Valid JSON in the wrong shape |
| Schema-constrained output | JSON matching your schema | Correct shape, possibly wrong values |

Schema-constrained output works by restricting which tokens the model may produce at each step so the result always parses against the schema. Use it whenever code consumes the output.

## Define the schema once, in Pydantic

```python
from enum import Enum
from pydantic import BaseModel, Field

class Priority(str, Enum):
    low = "low"
    normal = "normal"
    urgent = "urgent"

class Ticket(BaseModel):
    category: str = Field(description="One of: billing, bug, account, other")
    priority: Priority
    summary: str = Field(description="One sentence, under 20 words")
    order_id: str | None = Field(default=None, description="Order id if the user gave one")
    tags: list[str] = []
```

Required fields, optional fields, enums, lists and nested models all map to JSON Schema (`Ticket.model_json_schema()` shows it). Field descriptions are sent to the model, so write them as instructions.

## Provider-native: OpenAI

```python
from openai import OpenAI
client = OpenAI()

email = "Hi, I was charged twice for order A-1192. Please fix ASAP!"
resp = client.responses.parse(
    model="gpt-5-mini",  # example id
    input=[
        {"role": "system", "content": "Turn support emails into tickets."},
        {"role": "user", "content": email},
    ],
    text_format=Ticket,
)
ticket: Ticket = resp.output_parsed
print(ticket.priority, ticket.order_id)
```

## Provider-native: Anthropic

Anthropic supports structured outputs directly in recent API versions; check the current docs for the parameter. A long-standing approach that works everywhere tool calling works is to define one tool whose input schema is your model and force the model to call it:

```python
import anthropic
client = anthropic.Anthropic()

resp = client.messages.create(
    model="claude-sonnet-4-5",  # example id
    max_tokens=500,
    system="Turn support emails into tickets.",
    messages=[{"role": "user", "content": email}],
    tools=[{
        "name": "record_ticket",
        "description": "Record the ticket extracted from the email.",
        "input_schema": Ticket.model_json_schema(),
    }],
    tool_choice={"type": "tool", "name": "record_ticket"},
)
block = next(b for b in resp.content if b.type == "tool_use")
ticket = Ticket.model_validate(block.input)
```

## Through LangChain

```python
from langchain.chat_models import init_chat_model

model = init_chat_model("anthropic:claude-sonnet-4-5")
extractor = model.with_structured_output(Ticket)
ticket = extractor.invoke(email)   # a Ticket instance
```

LangChain picks the provider's native mechanism (structured output or a forced tool) for you.

## Valid is not correct

A schema guarantees shape, not truth. All of these pass validation:

- `priority: "low"` for an email that says "ASAP".
- `order_id: "A-1192"` when the email said "A-1129".
- `category: "shipping"` when your description listed four allowed values (a free `str` is not an enum).

So validate in two layers. Pydantic validation catches shape and simple rules: use enums instead of described strings, add `Field(pattern=...)` or a validator for ids. Then business checks catch meaning: does that order id exist for this customer?

## Generate, validate, then decide

```python
from pydantic import ValidationError

def extract_ticket(email: str, attempts: int = 2) -> Ticket | None:
    feedback = ""
    for _ in range(attempts):
        try:
            t = extractor.invoke(email + feedback)
        except ValidationError as e:
            feedback = f"\n\n(Previous output was invalid: {e.errors()[:3]})"
            continue
        if t.order_id and not order_exists(t.order_id):
            feedback = f"\n\n(Order id {t.order_id} does not exist; re-read the email.)"
            continue
        return t            # accept
    return None             # reject: send to a human queue
```

Possible outcomes: **accept**, **retry** with the error as feedback, **repair** in code when the fix is mechanical (trim whitespace, lowercase an enum), or **reject** and route to a fallback. Never let an unvalidated object reach your database.

## Try it

Write a Pydantic model for a job posting (title, company, remote: bool, salary_min and salary_max as optional ints, skills: list[str]). Extract it from three postings you paste in, including one with no salary. Then add a validator that rejects `salary_min > salary_max`.

<details>
<summary>Reference</summary>

```python
from pydantic import BaseModel, model_validator

class Job(BaseModel):
    title: str
    company: str
    remote: bool
    salary_min: int | None = None
    salary_max: int | None = None
    skills: list[str]

    @model_validator(mode="after")
    def check_range(self):
        if self.salary_min and self.salary_max and self.salary_min > self.salary_max:
            raise ValueError("salary_min greater than salary_max")
        return self
```

The posting without a salary should give `None` for both fields, not invented numbers. If the model invents a salary, tighten the field descriptions ("null if not stated"). The validator turns a semantic rule into a check that triggers your retry path.
</details>

## Check yourself

1. Why is "reply only with JSON" in the prompt not enough for production?

<details>
<summary>Answer</summary>

It is a request, not a constraint. The model can add prose, skip fields or use the wrong types. Schema-constrained output or at least validation is needed before code consumes the result.
</details>

2. The output validates against the schema but the amount field is wrong. What kind of failure is this and how do you catch it?

<details>
<summary>Answer</summary>

A semantic failure: correct shape, wrong value. Catch it with business checks (cross-check against the source text or your database, range rules, validators) and test sets, not with the schema.
</details>

3. Why use an enum instead of a string field with a description listing allowed values?

<details>
<summary>Answer</summary>

An enum is enforced by the schema and validation, so the model cannot return an unlisted value. A description is only guidance.
</details>
