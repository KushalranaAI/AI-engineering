# Other orchestration options

LangChain is popular, not standard. Several other tools take quite different views of what "orchestrating LLM calls" means, and plenty of strong teams use no framework at all. You do not need to master them all now. You need to know what each is for, so that when a project's shape calls for one, you recognise it.

## The landscape

| Option | Core idea | Shines when |
|--------|-----------|-------------|
| Raw provider SDK + your code | Plain functions and control flow | Small apps, maximum control, one provider |
| LangChain | Common interfaces and composable runnables | Swapping providers, quick pipelines, big integration catalogue |
| LlamaIndex | Your data first: loading, indexing, querying | Document-heavy apps and retrieval (Level 4) |
| LangGraph | Workflow as a graph with explicit state | Branches, loops, retries, human approval, long-running flows |
| DSPy | Declare inputs and outputs; let an optimiser build prompts | Pipelines you can score, where you want prompts tuned automatically |

Provider-specific agent SDKs (from OpenAI, Anthropic, Google and others) are another option, covered in the agents levels.

## LlamaIndex: data-centred

LlamaIndex's abstractions are built around documents: readers that load files, indexes that organise them, and query engines that answer questions over them.

```python
# pip install llama-index   (uses OpenAI models by default; configurable)
from llama_index.core import SimpleDirectoryReader, VectorStoreIndex

docs = SimpleDirectoryReader("./policies").load_data()
index = VectorStoreIndex.from_documents(docs)
print(index.as_query_engine().query("How many days do customers have to return items?"))
```

Four lines hide chunking, embedding, storage, retrieval and prompting. That is great for speed and a reason to come back after Level 4, when you know what each hidden step does.

## Graphs and state machines: LangGraph

Chains are straight lines. Real flows loop ("revise until the check passes, at most three times"), branch, pause for a human, and must survive a crash halfway. A **state machine** handles this: an explicit state object, nodes that update it, and edges (some conditional) that decide what runs next.

```python
# pip install langgraph
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    draft: str
    attempts: int
    approved: bool

def write(state: State) -> dict:
    draft = llm_write(state["question"], previous=state.get("draft"))
    return {"draft": draft, "attempts": state["attempts"] + 1}

def check(state: State) -> dict:
    return {"approved": llm_check(state["draft"])}

def route(state: State) -> str:
    if state["approved"] or state["attempts"] >= 3:
        return END
    return "write"

g = StateGraph(State)
g.add_node("write", write)
g.add_node("check", check)
g.add_edge(START, "write")
g.add_edge("write", "check")
g.add_conditional_edges("check", route)
app = g.compile()

result = app.invoke({"question": "Draft a refund policy summary", "draft": "", "attempts": 0, "approved": False})
```

(`llm_write` and `llm_check` stand for your own model calls.) The graph makes the loop and its exit condition explicit, and LangGraph adds checkpointing so a flow can pause for human input and resume later. You will use this style heavily for agents.

## DSPy: declare, then optimise

DSPy treats prompts as parameters to be learned rather than strings to be hand-written. You declare a **signature** (inputs and outputs), compose modules, and give an optimiser a few labelled examples and a metric; it searches for instructions and few-shot examples that score well.

```python
# pip install dspy
import dspy

dspy.configure(lm=dspy.LM("openai/gpt-5-mini"))   # example model id

class Triage(dspy.Signature):
    """Classify a support ticket."""
    ticket: str = dspy.InputField()
    category: str = dspy.OutputField(desc="billing, bug, account or other")

triage = dspy.Predict(Triage)
print(triage(ticket="I was charged twice this month").category)
```

The payoff comes when you run an optimiser against a metric on your examples. The cost is a different mental model and less direct control over the exact prompt text.

## Choosing

Compare options on the things that will hurt later:

| Criterion | Question to ask |
|-----------|-----------------|
| Development speed | How fast to a working first version? |
| Abstraction overhead | How many layers between me and the HTTP request? |
| Debuggability | When it misbehaves, can I see the exact prompt and response? |
| Portability | Can I switch model providers easily? |
| Dependencies | How many packages, how often do they break on upgrade? |
| State | Do I need loops, persistence, pause and resume? |
| Control | Can I use new provider features on day one? |

Rough guidance:

- A few calls with fixed steps: raw SDK, or a thin LangChain layer if you want provider flexibility.
- Document question-answering: LlamaIndex or LangChain retrieval components, once you understand retrieval.
- Loops, branches, human approvals, long-running jobs: a graph framework such as LangGraph.
- A pipeline with a clear metric and labelled data, where prompt tuning matters: try DSPy.
- Hard performance, security or compliance needs: a small custom layer you fully own.

Mixing is normal: raw SDK calls inside LangGraph nodes, or LlamaIndex retrieval feeding a hand-written workflow.

## Try it

Rebuild the "draft, check, revise at most twice" flow from module 2.7 three ways: plain Python, LangChain runnables, and LangGraph. For each, note lines of code, how you would see the exact prompt sent on the second revision, and how you would add "pause for human approval before sending".

<details>
<summary>Reference</summary>

Plain Python: a `for` loop with a break; easy to read and debug with prints or logs; pausing for a human means persisting state to a database yourself and resuming from it. LangChain runnables: compact for the linear part, but loops are awkward (you end up writing a Python loop around the chain anyway). LangGraph: more setup lines, but the loop is a conditional edge, the state is explicit, and pausing for approval is a built-in pattern with a checkpointer. Seeing the exact prompt is trivial in plain Python and needs tracing or callbacks in the frameworks. The lesson: the more state and looping a flow has, the more a graph framework earns its overhead.
</details>

## Check yourself

1. What does a graph framework give you that a linear chain does not?

<details>
<summary>Answer</summary>

Explicit shared state, conditional edges that allow loops and branches, and (in LangGraph) checkpointing so a run can pause, wait for a human, and resume.
</details>

2. How does DSPy's approach differ from writing prompts by hand?

<details>
<summary>Answer</summary>

You declare the inputs and outputs of each step and a metric; an optimiser then generates and selects instructions and examples that score well, instead of you hand-tuning prompt text.
</details>

3. Name two criteria that argue for using no framework at all.

<details>
<summary>Answer</summary>

Any two of: a simple flow with few steps, a need to see and control every request exactly, using new provider features immediately, minimising dependencies, or strict security and compliance review of all code.
</details>
