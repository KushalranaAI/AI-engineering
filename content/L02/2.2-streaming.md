# Streaming

A 600-token answer can take ten seconds or more to generate. Without streaming, the user stares at a spinner for all of it. With streaming, the first words appear in well under a second and the rest arrives as the model writes it. Total time is the same; the experience is completely different.

## What users actually feel

| Measure | Meaning | What drives it |
|---------|---------|----------------|
| Time to first token (TTFT) | Delay before anything appears | Network, queueing, prompt length (prefill), reasoning time |
| Output speed | Tokens per second once text flows | Model size, provider load |
| Total latency | Time until the last token | TTFT + output tokens / speed |

Rough worked example: TTFT 0.6 s, 60 tokens/s, 600 output tokens. Total is about 0.6 + 10 = 10.6 s. Streamed, the user starts reading at 0.6 s and reads roughly as fast as text arrives. Non-streamed, they wait 10.6 s for a wall of text.

Streaming does not help when your code needs the whole output before doing anything, for example parsing a JSON object to update a database. It helps whenever a human is reading.

## How it works on the wire

Providers send **server-sent events** (SSE): a long-lived HTTP response where the server pushes small JSON events. You get events such as "message started", "text delta", "message finished, here is the usage". The SDKs wrap this for you.

Anthropic:

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-5"  # example id

with client.messages.stream(
    model=MODEL,
    max_tokens=800,
    messages=[{"role": "user", "content": "Explain Python's GIL for a backend engineer."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    final = stream.get_final_message()   # full message, assembled for you

print()
print(final.stop_reason, final.usage.output_tokens)
```

OpenAI Chat Completions, where you assemble the pieces yourself:

```python
from openai import OpenAI

client = OpenAI()
parts: list[str] = []
stream = client.chat.completions.create(
    model="gpt-5-mini",  # example id
    messages=[{"role": "user", "content": "Explain Python's GIL for a backend engineer."}],
    stream=True,
)
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        piece = chunk.choices[0].delta.content
        parts.append(piece)
        print(piece, end="", flush=True)
full_text = "".join(parts)
```

## Keep a complete record

The stream is for the screen; your application still needs the finished message. Save the assembled text, the stop reason and the usage to your history and logs. If you only print deltas, you lose the record and often the token counts, which usually arrive in the last event.

## When streams go wrong

Streams fail in more ways than single responses do, because they stay open longer.

- **User cancels.** They close the tab or press stop. Stop reading and close the stream so you stop paying for tokens nobody will see. Decide whether to keep the partial answer in history (usually yes, marked as interrupted).
- **Connection drops mid-answer.** You have a partial message and no final event. Do not save it as if it were complete. Either retry the whole request or show what arrived with a clear "interrupted" marker.
- **Cut off by the limit.** The stream ends normally but with stop reason `max_tokens`. The text just stops; flag it.
- **Error event mid-stream.** Some providers send an error event (for example, overloaded) after the stream starts. Your loop must handle that, not just HTTP errors at the start.

```python
received = []
try:
    with client.messages.stream(model=MODEL, max_tokens=800, messages=msgs) as stream:
        for text in stream.text_stream:
            received.append(text)
            send_to_ui(text)
        final = stream.get_final_message()
        status = "truncated" if final.stop_reason == "max_tokens" else "complete"
except anthropic.APIConnectionError:
    status = "interrupted"
save_turn("".join(received), status=status)
```

## Streaming through your own API

Your backend usually relays the stream to a browser. In FastAPI, return a `StreamingResponse` that yields chunks as they come from the provider. Watch for proxies and load balancers that buffer responses, which silently turns your stream back into one slow blob.

## Try it

Stream a long answer (ask for a 500-word explanation). Measure TTFT and total time with `time.perf_counter()`, and compute output tokens per second from the final usage. Then run the same request without streaming and compare the time until you see any text.

<details>
<summary>Reference</summary>

```python
import time
start = time.perf_counter()
first = None
with client.messages.stream(model=MODEL, max_tokens=1000, messages=msgs) as stream:
    for text in stream.text_stream:
        if first is None:
            first = time.perf_counter() - start
    final = stream.get_final_message()
total = time.perf_counter() - start
print(f"TTFT {first:.2f}s, total {total:.2f}s, "
      f"{final.usage.output_tokens / (total - first):.0f} tok/s")
```

Typical result: TTFT under a second, total several seconds. The non-streamed call shows nothing until roughly the streamed total time, so the perceived wait is many times longer even though the work is identical.
</details>

## Check yourself

1. Does streaming make a response finish sooner?

<details>
<summary>Answer</summary>

No, total generation time is about the same. It reduces perceived latency because the user sees text after the time to first token instead of after the whole response.
</details>

2. Your stream breaks after 300 tokens. What should you store in the conversation history?

<details>
<summary>Answer</summary>

Not a normal assistant turn. Either retry and store the complete answer, or store the partial text clearly marked as interrupted so neither the user nor later logic treats it as a finished reply.
</details>

3. When is streaming pointless?

<details>
<summary>Answer</summary>

When nothing can use the output until it is complete, such as a background job that parses a JSON object, or short outputs where TTFT is most of the total anyway.
</details>
