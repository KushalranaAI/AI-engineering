# First calls and conversation state

Calling a model looks like calling any other HTTP API: send JSON, get JSON back. Two things surprise people. The response holds much more than the text, and the API has no memory at all. Every chat app that seems to remember you is resending the whole conversation on every turn.

## The shape of a request

Every major provider takes the same basic ingredients:

| Piece | What it is | Example |
|-------|------------|---------|
| model | which model and version | a dated snapshot id from the provider's model list |
| system / instructions | standing rules for the whole conversation | "You are a terse SQL tutor." |
| messages | the turns so far, each with a role | `user`, `assistant` (and tool turns later) |
| limits | caps such as max output tokens | `max_tokens=500` |

Here is a single call with the Anthropic SDK. The OpenAI SDK has the same structure under different names.

```python
# pip install anthropic   (reads ANTHROPIC_API_KEY from the environment)
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-5"  # example id; check the provider's current model list

resp = client.messages.create(
    model=MODEL,
    max_tokens=300,
    system="You are a concise tutor for Python developers.",
    messages=[{"role": "user", "content": "What is a generator, in two sentences?"}],
)

print(resp.content[0].text)          # the text block
print(resp.stop_reason)              # "end_turn", "max_tokens", "tool_use", ...
print(resp.usage.input_tokens, resp.usage.output_tokens)
print(resp.id, resp.model)
```

The OpenAI equivalent with the Responses API:

```python
from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY
resp = client.responses.create(
    model="gpt-5-mini",  # example id
    instructions="You are a concise tutor for Python developers.",
    input="What is a generator, in two sentences?",
)
print(resp.output_text)
print(resp.usage.input_tokens, resp.usage.output_tokens)
```

## Read the whole response

Treating the API as `prompt -> str` hides the information you need when something goes wrong.

- **Stop reason.** `max_tokens` means the answer was cut off. Your code should notice that rather than show half a sentence to a user.
- **Usage.** Input and output token counts are what you pay for. Log them from day one.
- **Model.** The exact model that answered. Aliases can move to new snapshots.
- **Content blocks.** A response is a list of blocks (text, tool calls, sometimes thinking), not one string. `content[0].text` is fine for a demo, not for production.

## The API remembers nothing

The model sees only what is in the current request. To hold a conversation you keep the history and send all of it each time:

```python
history: list[dict] = []

def chat(user_text: str) -> str:
    history.append({"role": "user", "content": user_text})
    resp = client.messages.create(
        model=MODEL, max_tokens=500,
        system="You are a helpful assistant.",
        messages=history,
    )
    reply = resp.content[0].text
    history.append({"role": "assistant", "content": reply})
    return reply

chat("My name is Priya.")
print(chat("What is my name?"))   # works only because turn 1 is resent
```

Two consequences follow. Cost grows with every turn, because turn 20 resends turns 1-19 as input tokens. And you, not the provider, decide what the model sees: you can trim, summarise or drop old turns. (Some providers offer server-side conversation storage as a convenience, but the model still processes the full context each time.)

## App state is not model context

Your application holds plenty the model never sees: the user's account, their order history in Postgres, the full chat log. The **context** is only what you put in this request. Keep the two apart in your head:

| Application state | Model context |
|-------------------|---------------|
| Lives in your database or memory | Lives only inside one request |
| Can be huge | Limited by the context window and your budget |
| You query it | You choose a slice of it to send |

A common bug is assuming the model "knows" something because it is in your database. It knows it only if you sent it.

## Keys stay on the server

- Load keys from environment variables, a `.env` file kept out of git, or a secret manager.
- Never put a provider key in browser JavaScript or a mobile app. Anyone can read it and spend your money. The browser calls your backend, and your backend calls the model.
- Use separate keys per environment and rotate them if one leaks.

```python
import os
from dotenv import load_dotenv   # pip install python-dotenv

load_dotenv()                    # .env is listed in .gitignore
assert "ANTHROPIC_API_KEY" in os.environ
```

## Try it

Write a terminal chat loop that keeps history, prints each reply, and after each turn prints the input and output token counts. Chat for five turns and watch the input count. Then cap history to the last four messages and compare.

<details>
<summary>Reference</summary>

```python
history = []
while True:
    text = input("> ")
    if text in {"quit", "exit"}:
        break
    history.append({"role": "user", "content": text})
    resp = client.messages.create(model=MODEL, max_tokens=400, messages=history[-4:])
    reply = "".join(b.text for b in resp.content if b.type == "text")
    history.append({"role": "assistant", "content": reply})
    print(reply)
    print(f"[in={resp.usage.input_tokens} out={resp.usage.output_tokens} stop={resp.stop_reason}]")
```

Without the cap, input tokens climb every turn because the whole conversation is resent. With `history[-4:]` the count levels off, but the model forgets anything older, such as your name from turn 1. Note that the slice must start with a `user` message; Anthropic requires that the first message is from the user.
</details>

## Check yourself

1. A user says your bot "forgot" what they said ten minutes ago. Name the most likely cause.

<details>
<summary>Answer</summary>

The app did not include that earlier turn in the request, for example because history was trimmed, lost when a server restarted, or stored per process instead of per user. The model only sees what is sent in each call.
</details>

2. Why check `stop_reason` on every response?

<details>
<summary>Answer</summary>

It tells you why generation ended. `max_tokens` means the output was truncated, and `tool_use` means the model wants a tool run, not that it has answered. Ignoring it leads to half answers or silently dropped tool calls.
</details>

3. Why must a frontend never call the provider API directly with your key?

<details>
<summary>Answer</summary>

Anything shipped to a browser or app can be extracted. A leaked key lets anyone run requests billed to you and bypass your app's limits and checks. Route calls through your backend, which holds the key.
</details>
