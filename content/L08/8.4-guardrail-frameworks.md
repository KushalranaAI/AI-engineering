# Guardrail frameworks: NeMo Guardrails, LlamaFirewall, Bedrock Guardrails

In 8.3 you wrote input and output checks by hand: a moderation call, a regex for card numbers, a "stay on topic" prompt.
That works for a prototype. In production you want detectors someone else has tested against thousands of attacks, one place
to define policy, logs of every decision and a way to update them. **Guardrail frameworks** provide that. This lesson
compares three that you will meet in real jobs. Features change quickly, so treat the descriptions as a map and check the
current documentation before you commit.

## Why use a framework

Hand-written checks drift: every service rewrites the same filters slightly differently, nobody tests them, and a new
jailbreak style slips past all of them. A framework gives you:

- **Tested detectors** for jailbreaks, injection, toxicity, PII and topic.
- **One policy** applied consistently across apps.
- **Observability**: what was blocked, why, how often.
- **A place in the request flow**: before the model, after it, around tools and retrieval.

None of this removes the need for the structural defences in 8.2 and 8.6 (least privilege, approvals, sandboxes).

## NeMo Guardrails

**NeMo Guardrails** is an open-source toolkit from NVIDIA. You put a configuration around an LLM; the configuration
defines **rails**, programmable checks at several points: **input** rails (before the model), **output** rails (after),
**dialog** rails (what conversation flows are allowed), plus rails for retrieval and for tool execution. Rails are written
in **Colang**, a small language for describing user intents and bot behaviour, and configured in YAML. Built-in rails include
a self-check on input (a model call that decides whether the user's message violates policy) and on output. You run it
in-process from Python and it can sit in front of any model. The next lesson (8.5) goes deep.

Strengths: flexible, programmable dialogue control, works with any model. Costs: self-check rails add model calls
(latency and money), and there is a learning curve for Colang.

## LlamaFirewall

**LlamaFirewall** is an open-source framework from Meta aimed at **agents**. It is layered, with scanners that you
combine:

- **PromptGuard 2**: a small classifier model that detects jailbreak and prompt-injection attempts in user input and in
  untrusted content such as tool results. Fast, because it is a compact model and not a general LLM call.
- **AlignmentCheck**: a check that audits an agent's reasoning and actions against the user's original goal, to catch
  goal hijacking (for example, an injected instruction that makes the agent start exfiltrating data). Meta describes it as
  experimental.
- **CodeShield**: static analysis for code the model generates, flagging insecure patterns before the code runs.

Strengths: fits agents and coding assistants, fast detectors. Costs: narrower scope than a general dialogue-policy tool, and
the more advanced scanners are newer and still maturing.

## Amazon Bedrock Guardrails

**Amazon Bedrock Guardrails** is a managed AWS service. You define a guardrail in the console, CLI or infrastructure
code, with policies for:

- **Content filters** for categories such as hate, insults, sexual content, violence and misconduct, plus prompt-attack
  detection, each with an adjustable strength.
- **Denied topics** described in natural language ("investment advice").
- **Word filters** for specific words and phrases.
- **Sensitive-information filters** for PII types and custom regex, which can block or mask.
- **Contextual grounding checks** that score whether an answer is supported by the source and relevant to the query,
  which targets hallucination in RAG.

You attach a guardrail to Bedrock model calls, or call the **ApplyGuardrail** API on any text, so it can protect models
hosted elsewhere or text that never touches a model. Strengths: no infrastructure to run, integrates with IAM and audit
logging, covers PII and grounding. Costs: priced per text unit, runs on AWS, and customisation is bounded by what the
policies allow.

## Comparing them

| | NeMo Guardrails | LlamaFirewall | Bedrock Guardrails |
|---|---|---|---|
| Form | open-source library | open-source library | managed service |
| Runs | in your process | in your process | AWS API call |
| Best at | dialogue and topic control | agent hijacking, injection, insecure code | content, PII, denied topics, grounding |
| Customise by | Colang + YAML + prompts | choosing and tuning scanners | policy settings |
| Extra cost | model calls for self-checks | small classifier inference | per-request fee |

They combine well. A common stack: Bedrock Guardrails or a PII filter for content and privacy, LlamaFirewall scanners on
untrusted tool results in an agent, and NeMo rails where tight conversation control matters.

## Limits

Every guardrail framework has **false positives** (blocking legitimate users) and **bypasses** (attackers who rephrase,
encode or split an attack across turns). So: measure both on your own data, tune thresholds, test with adversarial
inputs (8.9), and keep the real guarantees outside the model: permission checks, approval for irreversible actions and
sandboxing. Treat a guardrail as a filter that lowers risk, not as a wall.

## Try it

You run a customer-support RAG bot on AWS that can look up orders and issue small refunds. Pick a combination of
frameworks and say what each covers.

<details>
<summary>Reference</summary>

Input: Bedrock Guardrails (or ApplyGuardrail) for prompt-attack detection, denied topics (legal and medical advice) and
PII masking. Retrieval and tool results: a PromptGuard-style scanner on retrieved text and tool output to catch planted
instructions. Output: contextual grounding check on answers, plus a NeMo output rail if you need to enforce brand and
refusal wording. Outside all of them: the refund tool's amount limit and a human approval above a threshold.
</details>

## Check yourself

1. Which of the three is designed around agents and what does it scan?

<details>
<summary>Answer</summary>

LlamaFirewall. Its scanners cover jailbreak and injection detection (PromptGuard 2), goal-hijacking checks on agent
behaviour (AlignmentCheck) and insecure generated code (CodeShield).
</details>

2. What does the ApplyGuardrail API let you do that attaching a guardrail to a model call does not?

<details>
<summary>Answer</summary>

Evaluate any text against a guardrail without invoking a model, so you can protect other providers' models, retrieved
content, or user input and output at any point in your own pipeline.
</details>

3. Why keep permission checks and approvals outside the guardrail framework?

<details>
<summary>Answer</summary>

Guardrails are probabilistic and can be bypassed or give false positives. Code-enforced permissions and human approvals
give guarantees that do not depend on a classifier being right.
</details>
