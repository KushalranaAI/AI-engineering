# Threat modelling AI apps

A classic web app has a clear line: your code is trusted, user input is not, and you validate at the boundary. An LLM app blurs that line. The model reads text from anywhere (users, web pages, PDFs, emails, tool results) and every token it reads can influence what it says and does next. Before you pick defences, you need a map of where untrusted text enters, what the model can reach, and how data can leave. That map is a threat model.

## What changes when you add a model

| Capability you give the model | New risk it brings |
|---|---|
| Reads untrusted content (uploads, web, email, retrieved chunks) | That content can carry instructions the model may follow |
| Sees private data (system prompt, user records, other documents) | The model can repeat it to someone who shouldn't see it |
| Calls tools | An attacker can steer which tool runs and with what arguments |
| Takes actions (send, write, pay, execute) | Mistakes or manipulation now have real-world side effects |
| Remembers across sessions | A bad input can persist and affect later conversations |

The danger grows with each column you add. A chatbot that only answers from public docs has a small blast radius. An agent with email access, a CRM tool and web browsing has a large one.

## Trust boundaries

A trust boundary is any point where data moves between parties that deserve different levels of trust. Draw your app as boxes and arrows and mark every place text crosses into the model's context or out of it:

```
 user ──► app server ──► [ context window ] ──► model output ──► tool executor ──► CRM / email / DB
            ▲                 ▲      ▲                                   │
            │                 │      └── retrieved chunks (vector DB) ◄──┘ (tool results)
         system prompt     memory store
```

For each arrow, ask three questions:

1. **Who controls this text?** You, the signed-in user, another user, or an anonymous third party (a web page author, an email sender)?
2. **What can the model do after reading it?** Which tools, which data?
3. **Where can output go?** Back to this user only, to another user, to an external URL, into a database?

Retrieved documents and tool results are the boundaries people miss most often. A support ticket written by a customer and stored in your database is still customer-controlled text when your agent reads it a week later.

## Model output is untrusted too

The second rule of AI threat modelling: **treat what the model produces as untrusted input to the next system.** A tool call is a request, not a command. Generated SQL is a string from an unreliable author. A URL in a markdown answer is something a browser will fetch. Validate it the way you would validate a form submission.

```python
from pydantic import BaseModel, Field

class RefundRequest(BaseModel):
    order_id: str = Field(pattern=r"^ORD-\d{8}$")
    amount_cents: int = Field(gt=0, le=50_000)

def execute_refund(raw_args: dict, user) -> str:
    args = RefundRequest.model_validate(raw_args)      # shape check
    order = db.get_order(args.order_id)
    if order is None or order.customer_id != user.id:   # authorisation in code, not in the prompt
        return "error: order not found for this customer"
    if args.amount_cents > order.total_cents:
        return "error: refund exceeds order total"
    return queue_refund_for_approval(order, args.amount_cents)
```

Nothing here depends on the model behaving. If it is tricked into asking for someone else's order, the check fails.

## A simple process

1. List assets: secrets, customer data, money-moving actions, reputation.
2. Draw the data flow with trust boundaries as above.
3. For each boundary, list what could go wrong. The OWASP Top 10 for LLM Applications is a good checklist: prompt injection, sensitive information disclosure, improper output handling, excessive agency, system prompt leakage, vector and embedding weaknesses and so on.
4. Rate each by likelihood and impact, then decide on controls. Prefer controls that live in code (permissions, validation, approvals) over controls that live in the prompt.
5. Revisit whenever you add a tool or data source. Each one changes the model.

## Try it

Threat-model this app in five bullet points: an internal assistant that answers HR questions from a policy wiki, can look up the asking employee's leave balance, and can draft (not send) emails to HR.

<details>
<summary>Reference</summary>

- **Untrusted inputs:** the employee's question, and wiki pages, which any editor can change. A malicious wiki edit is indirect injection.
- **Private data:** leave balances. Risk: the model is asked for a colleague's balance. Control: the lookup tool takes no employee id; it uses the authenticated user's id from the session.
- **Actions:** drafting emails only, so impact is limited, but drafts could contain leaked data or links. Control: the user reviews and sends; render no auto-loading images or links in drafts.
- **Output handling:** answers rendered as markdown could include external image URLs that leak data in the query string. Control: strip or allowlist external URLs.
- **Logging:** questions may contain health or personal details; restrict log access and retention.
</details>

## Check yourself

1. Why is a document in your own vector database still a trust boundary?

<details>
<summary>Answer</summary>

Because who wrote the text matters, not where it is stored. If customers, external websites or any broad group of editors authored it, it can contain instructions, and the model reads it with the same attention as your prompt.
</details>

2. What does "model output is untrusted" mean for a tool call?

<details>
<summary>Answer</summary>

The tool executor must validate the arguments, check that the current user is authorised for that action on that resource, and enforce limits, exactly as an API would for a request from an unknown client.
</details>

3. Which three capabilities together make an app most dangerous?

<details>
<summary>Answer</summary>

Exposure to untrusted content, access to private data or powerful tools, and a channel to send data or effects outside. Remove any one and most exfiltration attacks stop working.
</details>
