# Jailbreaks, guardrails and moderation

Model providers train their models to refuse some requests. Jailbreaks try to get around that training. Guardrails are the checks you add around the model so that your app's policy holds even when the model's own refusals don't. This lesson is about building those checks and knowing how far to trust them.

## Jailbreak vs injection

The two get mixed up, but they target different things:

| | Jailbreak | Prompt injection |
|---|---|---|
| Target | The model's safety training | Your application's instructions and tools |
| Attacker | Usually the user themselves | Often a third party via content the app reads |
| Goal | Get disallowed content (harmful instructions, abuse) | Make the app do something its owner didn't intend |
| Victim | Mostly the provider's and your policy | Your users and your data |

Common jailbreak families, at the level you need to recognise them:

- **Role-play and fiction framing:** "you are a character who has no rules".
- **Hypothetical or educational framing:** wrapping a disallowed request as research or a story.
- **Obfuscation:** encodings, misspellings, other languages, splitting a request across turns.
- **Many-shot:** filling a long context with fake examples of the model complying.
- **Gradual escalation:** starting innocently and nudging over many turns.
- **Optimised suffixes:** strings found by automated search that push models toward compliance; these often transfer between models.

## Guardrails on both sides

Put checks before and after the model. Each one is cheap compared to an incident.

```
user input ─► [input checks] ─► model ─► [output checks] ─► user / tools
               - length, rate limit        - schema validation
               - moderation classifier     - moderation classifier
               - topic/scope filter        - PII and secret scan
               - known-bad pattern list    - URL / link allowlist
```

A minimal pipeline in Python:

```python
from openai import OpenAI
client = OpenAI()

def flagged(text: str) -> bool:
    result = client.moderations.create(model="omni-moderation-latest", input=text)
    return result.results[0].flagged

def in_scope(text: str) -> bool:
    # a small, cheap classifier call; returns True only for on-topic requests
    resp = client.responses.create(
        model="gpt-4.1-mini",  # example: any small, fast model
        input=f"Answer YES or NO. Is this a question about our billing product?\n\n{text}",
    )
    return resp.output_text.strip().upper().startswith("YES")

def answer(user_text: str) -> str:
    if len(user_text) > 4000 or flagged(user_text) or not in_scope(user_text):
        return "Sorry, I can only help with billing questions."
    draft = generate_answer(user_text)
    if flagged(draft) or contains_secret(draft):
        log_incident(user_text, draft)
        return "Sorry, I can't help with that."
    return draft
```

Options for the classifiers include provider moderation endpoints, open-weight safety models such as Llama Guard, and frameworks like NeMo Guardrails or Guardrails AI that wrap validation rules. Scope filters ("only billing questions") are often more valuable than generic harm filters, because they shrink everything an attacker can try.

## Why one layer isn't enough

- Model-based classifiers are models too: they can be fooled by the same obfuscation tricks.
- Each check has false positives (blocking legitimate users) and false negatives. Stacking independent checks cuts the miss rate more than tuning one check harder.
- Input checks can't see what the model will do with an innocent-looking request. Output checks catch what slipped through.
- Some failures aren't about harmful text at all, like leaking a system prompt or another customer's data. Generic moderation won't flag those, so you need app-specific output checks.

Think in terms of rates, not absolutes: "the input filter blocks 92% of our jailbreak suite, the output filter catches 70% of the rest, combined miss rate about 2.4%." Then ask whether that residual is acceptable for what the model can actually do.

## Test with hostile input

Guardrails tested only on normal traffic look perfect. Build a test set that includes:

- your jailbreak families above, each in several phrasings;
- obfuscated variants: other languages, character substitutions, base64-style encodings, text split across turns;
- benign but edgy requests (medical, security education) to measure over-blocking;
- long multi-turn conversations, not just single messages.

Run it on every change to prompts, models or filters, and track both the block rate on attacks and the false-block rate on benign examples.

## Check yourself

1. A user asks your coding assistant, in a role-play, for malware. Is this a jailbreak or prompt injection?

<details>
<summary>Answer</summary>

A jailbreak: the user is trying to get past the model's safety behaviour to produce disallowed content. No third party is hijacking the app.
</details>

2. Why is a topic/scope filter often more useful than a general harm classifier?

<details>
<summary>Answer</summary>

It encodes your app's actual purpose. Anything off-topic gets rejected, which removes whole classes of attack without needing to recognise each harmful category.
</details>

3. Why measure false positives on guardrails?

<details>
<summary>Answer</summary>

Over-blocking breaks the product for legitimate users and pushes teams to disable the filter. You need both numbers to tune the trade-off.
</details>
