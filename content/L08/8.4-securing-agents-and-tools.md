# Securing agents and tools

An agent is only as dangerous as its tools. A model that can only produce text can embarrass you; a model that can delete records, send money or run shell commands can hurt you. The OWASP list calls this "excessive agency": giving a model more functionality, permissions or autonomy than the task needs. Securing an agent mostly means trimming those three things and putting checks in code that the model can't talk its way past.

## Least privilege, three ways

| Dimension | Too much | Enough |
|---|---|---|
| Functionality | A generic `run_sql(query)` tool | `get_order(order_id)` and `list_my_orders()` |
| Permissions | One service account with admin rights | Per-user, short-lived tokens scoped to the task |
| Autonomy | Acts without review | Reads freely, asks before changing anything |

Narrow tools are safer *and* easier for the model to use correctly. A tool that takes a free-form query lets an injected instruction become an arbitrary query; a tool with a typed id does not.

## Classify every tool

Sort tools by what they can change:

- **Read-only:** search, fetch, list. Still need authorisation (whose data?) and size limits.
- **Reversible writes:** create a draft, add a label, stage a change.
- **Consequential or irreversible:** send messages, modify or delete records, make payments, execute code, change permissions.

The class drives the controls. Read tools run freely; reversible writes run with logging; consequential ones need human approval and tighter limits.

## Checks that live outside the model

Wrap every tool call in a policy layer that the harness enforces:

```python
from dataclasses import dataclass

@dataclass
class ToolPolicy:
    risk: str               # "read" | "write" | "consequential"
    allowed_roles: set[str]
    max_calls_per_run: int

POLICIES = {
    "search_tickets": ToolPolicy("read", {"agent", "support"}, 50),
    "add_ticket_note": ToolPolicy("write", {"support"}, 20),
    "issue_refund": ToolPolicy("consequential", {"support_lead"}, 1),
}

def guarded_call(run, user, name: str, args: dict):
    policy = POLICIES.get(name)
    if policy is None:
        return {"error": f"unknown tool {name}"}
    if user.role not in policy.allowed_roles:
        return {"error": "not permitted for this user"}
    if run.calls[name] >= policy.max_calls_per_run:
        return {"error": "call limit reached for this tool"}
    validated = SCHEMAS[name].model_validate(args)          # types, ranges, formats
    if policy.risk == "consequential":
        if not run.await_approval(user, name, validated):    # human sees exact arguments
            return {"error": "rejected by user"}
    run.calls[name] += 1
    result = TOOLS[name](validated, user=user)               # tool re-checks resource ownership
    audit_log(run.id, user.id, name, validated, result)
    return result
```

Note the tool runs with **the user's identity**, not a powerful service identity. If the user couldn't do it through your normal UI, the agent shouldn't be able to either.

## Approvals that mean something

A confirmation dialog only helps if a person can judge it:

- Show the exact action and arguments ("Send email to finance@... with this body"), not "The agent wants to use send_email".
- Ask rarely. If every step needs a click, people approve without reading.
- Approvals should be per action, not "allow everything for this session", for irreversible steps.

## Runaway limits

Agents can loop: retrying a failing call, or being steered into repeated actions. Cap steps per run, wall-clock time, tokens and money, and per-tool call counts. Hitting a limit should stop the run and tell the user, not silently continue.

## Generated code, SQL, commands and URLs

Anything the model writes that another system will interpret is untrusted:

- **Code and shell:** run only in a sandbox (container, microVM or a hosted sandbox) with no host credentials, no network or an allowlist, and CPU, memory and time limits.
- **SQL:** use a read-only database role, restrict to specific views, set statement timeouts and row limits. Better still, offer parameterised query tools instead of raw SQL.
- **URLs:** fetch through an allowlist or a proxy that blocks internal addresses (cloud metadata endpoints, private IP ranges) to avoid server-side request forgery.
- **API calls:** validate against a schema and the user's permissions before sending.

## Try it

An agent has one tool, `execute_sql(query: str)`, connected as the database owner, to answer analytics questions. List four changes that reduce risk without killing usefulness.

<details>
<summary>Reference</summary>

1. Connect with a read-only role that can only see an analytics schema or curated views, not raw PII tables.
2. Set a statement timeout and a row limit on results.
3. Parse the SQL and reject anything other than a single SELECT (as a backstop, not the main control; the role is the main control).
4. Apply row-level security or filters for the user's tenant.
5. Log every query with the user id for audit; optionally offer a few parameterised tools for common questions.
</details>

## Check yourself

1. Why should tools run with the end user's identity rather than a shared service account?

<details>
<summary>Answer</summary>

So the agent can never access more than the user could directly. If the model is manipulated into requesting another user's data, the normal authorisation checks reject it.
</details>

2. What makes an approval prompt useless?

<details>
<summary>Answer</summary>

Vague descriptions that hide the real arguments, and asking so often that people click through without reading.
</details>

3. Why does an internal URL allowlist matter for a web-fetch tool?

<details>
<summary>Answer</summary>

Without it, a manipulated agent can request internal services or cloud metadata endpoints from inside your network (server-side request forgery) and return the results.
</details>
