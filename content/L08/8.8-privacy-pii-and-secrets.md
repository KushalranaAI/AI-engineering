# Privacy, PII and secrets

LLM apps are very good at spreading data around. A single user message can end up in the prompt, the provider's servers, your request logs, your tracing tool, a memory store, a vector index, an eval dataset and a support engineer's screen. Each copy is a place to leak from and a thing you must be able to delete. The goal of this module is simple to state: send as little sensitive data as possible, to as few places as possible, for as short a time as possible.

## Know what you're protecting

| Category | Examples | Typical handling |
|---|---|---|
| Direct identifiers | Name, email, phone, national id, address | Mask or pseudonymise when the model doesn't need them |
| Credentials and secrets | API keys, passwords, session tokens, private keys | Never in prompts; block in output and logs |
| Financial | Card numbers, bank accounts, salaries | Tokenise; strict access control |
| Special categories | Health, religion, biometrics, sexual orientation | Extra legal duties in many jurisdictions; minimise hard |
| Private conversations | Support chats, emails, DMs | Purpose-limit and set retention |
| Confidential business data | Contracts, roadmaps, source code | Check provider terms and deployment model |

Start with a data inventory: for each feature, list which of these flow into the model and why.

## Redact and minimise before the model

Ask whether the model needs the real value. To summarise a complaint it needs the complaint, not the customer's card number. Detect and replace with placeholders, and restore afterwards only if the output needs them:

```python
import re
from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

analyzer, anonymizer = AnalyzerEngine(), AnonymizerEngine()
SECRET_PATTERNS = [re.compile(r"sk-[A-Za-z0-9_-]{20,}"), re.compile(r"AKIA[0-9A-Z]{16}")]

def scrub(text: str) -> str:
    for p in SECRET_PATTERNS:
        text = p.sub("[SECRET]", text)
    findings = analyzer.analyze(
        text=text, language="en",
        entities=["EMAIL_ADDRESS", "PHONE_NUMBER", "CREDIT_CARD", "IBAN_CODE", "PERSON"],
    )
    return anonymizer.anonymize(text=text, analyzer_results=findings).text

print(scrub("Hi, I'm Priya Shah, card 4111 1111 1111 1111, email priya@example.com"))
# -> "Hi, I'm <PERSON>, card <CREDIT_CARD>, email <EMAIL_ADDRESS>"
```

Detectors miss things (names in unusual formats, ids specific to your business) and over-match others, so measure them on your own data and add custom recognisers. Treat redaction as reducing exposure, not guaranteeing zero.

## Keep it out of logs, traces and datasets

Most leaks come from the copies you forgot about:

- **Logs and traces:** observability tools capture full prompts and completions by default. Scrub before export, or log ids and hashes instead of text; restrict who can view raw traces.
- **Memory stores:** don't let an agent "remember" card numbers or health details. Filter what gets written.
- **Vector indexes:** embeddings of sensitive text are still sensitive. Text can be partly reconstructed from embeddings, and the source chunk usually sits next to the vector anyway.
- **Eval datasets:** production failures are great test cases, but scrub them before they land in a repo that the whole company can clone.

## Retention, deletion, residency

Questions to answer for every store and every provider:

- **Retention:** how long is it kept? Providers typically keep API data for a limited period for abuse monitoring unless you have a zero-retention arrangement; check the current terms for your account.
- **Deletion:** when a user asks to be deleted, can you find and remove them from logs, memories, indexes and fine-tuning data? Provenance ids make this possible.
- **Residency:** which country or region processes and stores the data? Many providers and clouds offer regional endpoints.
- **Training:** is your data used to train the provider's models? For business APIs the default is commonly no, but confirm it in the contract, not a blog post.
- **Access:** who at your company and at the provider can read it?

## Controls for regulated deployments

Banks, hospitals and governments usually need more than a public API key:

- **Private connectivity:** reach the model through a private network link (for example cloud private endpoints for models hosted in your cloud account) so traffic never crosses the public internet.
- **No public egress** from the app's network, so even a compromised component can't send data out.
- **Contractual terms:** zero data retention, no training on your data, a data processing agreement, and agreed regions.
- **Self-hosting open-weight models** when data cannot leave your infrastructure at all.

## Secrets never go to the model

The model doesn't need an API key to call an API; your tool code does. Keep credentials in a secret manager, inject them in the tool executor, and return only results:

```
model ──► tool_call: get_invoice(id="INV-123") ──► executor adds auth header from vault ──► API
model ◄── {"amount": 120, "status": "paid"}  (no token anywhere in the context)
```

Then anything the model is tricked into revealing simply doesn't include the secret. Also scan outputs and logs for secret patterns as a backstop.

## Try it

Your support bot logs every full conversation to a tracing tool that all engineers can access, keeps them forever, and copies failed conversations into an eval set in Git. List four changes.

<details>
<summary>Reference</summary>

1. Scrub PII and secrets before traces are exported; keep raw text only in a restricted store if needed.
2. Restrict raw-trace access to a small on-call group, with access logged.
3. Set a retention period (for example 30 days) and automatic deletion.
4. Scrub and review conversations before adding them to the eval set; store the eval set with access controls; record source ids so user deletion requests can reach it.
</details>

## Check yourself

1. Why isn't PII detection a guarantee?

<details>
<summary>Answer</summary>

Detectors are pattern and model based. They miss unusual formats and domain-specific identifiers and flag false positives. Measure them on your data and combine with minimisation and access control.
</details>

2. Why are embeddings of sensitive text still sensitive?

<details>
<summary>Answer</summary>

Text can be partially reconstructed from embeddings, and the original chunk is usually stored alongside the vector. The index needs the same protection as the source.
</details>

3. How should an agent call an authenticated API without seeing the key?

<details>
<summary>Answer</summary>

The model emits a tool call with only business arguments; the tool executor fetches the credential from a secret manager and adds it to the request. The key never enters the context window or the logs.
</details>
