# AI system design

The AI system-design round is usually 45 to 60 minutes with a vague brief: "design a coding assistant", "design
document processing for an insurer". The interviewer is grading your process as much as the final diagram. A
reliable structure keeps you from freezing or, more often, from drawing a giant architecture in the first five
minutes.

## A structure for the hour

| Minutes | Phase | What you produce |
|---------|-------|------------------|
| 0-8 | Requirements | Users, use cases, scale, latency, quality bar, cost, freshness, privacy, reliability |
| 8-15 | Baseline | The simplest system that could work, and how you'd measure it |
| 15-35 | Architecture | Components, data flow, model choices, context layer |
| 35-45 | Scale and failure | Bottlenecks, fallbacks, security, cost |
| 45-55 | Evals and monitoring | Offline evals, online signals, rollout |
| Last 5 | Trade-offs | What you'd change with more time or different constraints |

## From vague brief to assumptions

Turn every unknown into a stated assumption with a number. For "an enterprise support assistant":

- 5,000 agents, 50,000 customer tickets a day, peak 10 requests/second.
- Suggested reply within 4 seconds; first token under 1 second.
- Knowledge base of 200k articles, updated daily; answers must cite articles.
- Customer data can't leave the company's cloud region.
- Target: agents accept 60% of drafts with light edits.

Say them out loud and ask "does that sound right?" The interviewer will correct the ones that matter, which tells you
where the question is going.

## Simplest thing first

Baseline: retrieval over the knowledge base plus one model call that drafts a reply with citations. Only then add
pieces, each tied to a requirement:

| Add | Because |
|-----|---------|
| Hybrid retrieval + reranker | Product codes and error numbers in tickets |
| Routing (small model for easy tickets) | Cost at 50k tickets/day |
| Semantic cache | Many near-identical questions |
| Tool calls (order lookup) | Replies need live account data |
| Agent loop | Only if multi-step investigation is common; usually not |
| Fine-tune | Only if tone or format still fails evals after prompt work |

## The full stack, briefly

Make sure the final picture touches each layer at least in a sentence: model selection and routing; context (RAG,
history, tools); caches; databases (operational, vector, object storage); inference (provider or self-hosted);
observability (traces, cost); evals (offline set, online sampling, feedback); security (auth, permissions on
retrieval, prompt injection from tickets, PII redaction); deployment (CI/CD, canary for prompt changes).

## Enterprise constraints

"You can't use a public API" is a common twist. Options: a managed model platform inside your cloud account (the big
cloud providers all host frontier and open models with regional deployment), or self-hosted open-weight models.
Compare on identity integration, data residency, available models, GPU capacity and cost. A quick capacity estimate
shows maturity:

```python
peak_rps = 10
tokens_out = 300          # per reply
tok_per_sec_per_gpu = 1500  # example aggregate throughput for a mid-size model with batching
gpus = peak_rps * tokens_out / tok_per_sec_per_gpu
print(f"~{gpus:.0f} GPUs at peak, before headroom and redundancy")  # ~2, so plan 3-4
```

The throughput number is an assumption you state, not a fact; the interviewer cares that you know which quantities
drive the estimate.

## Practice systems

- **Support assistant**: retrieval quality, citations, live data tools, human in the loop.
- **Coding assistant**: repository context (indexing, symbol search), latency for completions vs chat, sandboxed
  execution, evals by running tests.
- **Research agent**: planning, web tools, source tracking, step and cost limits.
- **Document intelligence at scale**: batch pipelines, OCR and vision models, schema extraction, confidence-based
  human review, throughput and cost per page.

## Common weak answers

- Drawing components before asking a single question.
- Naming tools ("Pinecone, LangChain, GPT") without saying why.
- No evals: nothing tells you the system works.
- No numbers, so scale discussion stays vague.

## Practice drill

Run the hour structure on one of the four practice systems each day for four days, timed and recorded. After each,
score yourself: did you state numeric assumptions, start simple, justify each addition, and cover evals?

## Check yourself

1. Why state assumptions as numbers?

<details>
<summary>Answer</summary>

Numbers drive design decisions (caching, routing, GPU count) and let the interviewer correct you precisely. Vague
assumptions lead to vague designs.
</details>

2. What should justify each component you add beyond the baseline?

<details>
<summary>Answer</summary>

A specific requirement or measured failure: a latency target, a cost limit, a type of query that baseline retrieval
misses. Components without a reason are a red flag.
</details>

3. Name two ways to meet a "no public API" constraint.

<details>
<summary>Answer</summary>

A managed model service deployed in your own cloud account and region, or self-hosted open-weight models on your own
GPUs, each compared on residency, identity, capacity and cost.
</details>
