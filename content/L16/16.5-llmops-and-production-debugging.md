# LLMOps and production debugging

These questions check whether you have ever been responsible for an AI system after launch. The interviewer
describes an incident and watches how you think. There is rarely one right answer; there is a right **order**:
stabilise, scope, isolate, fix, prevent.

## Example questions

- "p95 latency went from 3 seconds to 12 at 10am. Walk me through it."
- "Our model bill tripled this month with flat traffic. Why might that be?"
- "Our main model provider is down. What happens to users right now, and what should happen?"
- "Would you move this workload from an API to self-hosted inference?"

## A method you can say out loud

| Step | What you do | Example for a latency spike |
|------|-------------|-----------------------------|
| Stabilise | Protect users first | Fail over to a backup model, shed low-priority traffic |
| Scope | Which requests, since when | All routes or one? One region? Long prompts only? |
| Changes | What changed near the start | Deploy, prompt change, provider status, traffic shape |
| Isolate | Break the request into spans | Retrieval 200 ms, LLM 11 s, tools 300 ms: it's the model call |
| Fix | Smallest safe fix | Roll back the prompt that doubled output length |
| Prevent | Stop it recurring | Alert on output tokens, max_tokens cap, eval on length |

The **Isolate** step is where tracing earns its keep. A strong candidate asks for a per-span breakdown before
guessing.

## Signals and what they tell you

| Signal | A sudden change usually means |
|--------|------------------------------|
| Latency (p50 vs p95) | p95 only: queueing, rate limits, a few huge prompts. Both: provider or model change |
| Error rate by type | 429: rate limits/capacity. 5xx: provider or server. Timeouts: slow upstream |
| Tokens in / out per request | Context bloat (retrieval returning more), verbose prompt change, agent loops |
| Cost per request | Usually tokens × price; also routing sending traffic to a pricier model |
| Retrieval hit rate / eval score | Data or index problem, or model quality drift |
| Cache hit rate | A key change or deploy invalidated the cache |

The cost question is a classic. Flat traffic but triple cost means tokens per request or price per token changed.
Likely culprits: a prompt edit that added long examples, retrieval returning more chunks, an agent taking more
steps, a fallback route silently sending traffic to the expensive model, or a cache that stopped hitting.

```python
import pandas as pd

df = pd.read_parquet("llm_requests.parquet")  # one row per call from your traces
daily = df.groupby([df.ts.dt.date, "model", "route"]).agg(
    calls=("id", "count"), in_tok=("input_tokens", "mean"),
    out_tok=("output_tokens", "mean"), cost=("cost_usd", "sum"))
print(daily.tail(20))  # which model/route grew, and was it calls or tokens per call?
```

## Resilience patterns

- **Timeouts and retries** with exponential backoff and jitter; never retry non-idempotent tool actions blindly.
- **Fallbacks**: a second provider or smaller model; a cached or canned answer as the last resort.
- **Graceful degradation**: turn off reranking or agent mode under load rather than fail.
- **Load balancing and autoscaling**: for self-hosted inference, scale on queue depth or GPU utilisation, not CPU.
- **Rate limiting and budgets**: per user and per tenant, so one customer can't burn the monthly bill.

## Alert, roll back or investigate

- **Page someone**: user-facing errors or latency breaching the SLO, spend rate far above budget.
- **Roll back immediately**: a deploy or prompt change correlates with a drop in eval scores or a rise in errors.
  Rolling back is cheap; investigating with users suffering is not.
- **Investigate during working hours**: slow drifts, such as a gradual fall in feedback scores.

## API vs self-hosted under pressure

Interviewers like this one with constraints: "1M requests a day, strict data residency, 300 ms budget for a
classification step." A strong answer: a small open-weight model self-hosted in-region can meet residency and
latency for a narrow task, at a GPU cost that is justified at that steady volume; keep a hosted frontier model for
the hard, low-volume requests if the contract allows. State the operations cost you are taking on: on-call, upgrades,
capacity planning.

## Common weak answers

- Jumping to a cause ("the provider is slow") without scoping.
- Proposing fixes that need a week while users are failing now.
- "Add more retries" during a rate-limit incident, which makes it worse.

## Practice drill

Write five incident cards (latency spike, cost tripled, provider outage, eval drop after deploy, cache hit rate
fell to zero). Draw one at random and talk through all six steps in eight minutes.

## Try it

Error rate jumps to 30%, all HTTP 429, starting right after a marketing email went out. What do you do in the first
15 minutes?

<details>
<summary>Reference</summary>

Stabilise: route overflow to a fallback provider or model, queue non-urgent requests, show users a "busy, retrying"
state instead of an error. Make sure retries use backoff with jitter so they don't amplify the spike. Scope: confirm
it is a traffic surge against your rate limit, not a provider incident. Then request a quota increase, and afterwards
add capacity planning for campaigns and an alert on approaching the limit.
</details>

## Check yourself

1. Cost tripled, traffic flat. What two quantities do you inspect first?

<details>
<summary>Answer</summary>

Tokens per request (input and output) and which model each request went to. Cost is calls × tokens × price, so with
flat calls one of the other two changed.
</details>

2. Why can retries make an outage worse?

<details>
<summary>Answer</summary>

Without backoff and jitter, every client retries at once, multiplying load on an already saturated upstream and
burning your own rate limit.
</details>

3. When should you roll back before finding the root cause?

<details>
<summary>Answer</summary>

When a recent change correlates with user-facing harm. Rollback restores service quickly; the investigation
continues afterwards.
</details>
