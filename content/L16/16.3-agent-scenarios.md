# Agent scenarios

Agent questions test judgment more than knowledge. Anyone can draw an LLM in a loop with some tools. Interviewers
want to see that you know when **not** to build an agent, how to keep one from doing damage, and how to debug one
that works on your laptop but misbehaves in production.

## Example questions

- "Design an agent that handles refund requests for an online shop."
- "Would you use one agent or several for a research assistant? Why?"
- "Your agent passes every test but in production it sometimes loops for 40 steps and costs $3 a run. What do you do?"

## Workflow or agent: say it first

The first decision in any agent design is how much autonomy the task needs. Put it on a spectrum and justify where
you land:

| Option | When it fits | Refund example |
|--------|-------------|----------------|
| Single LLM call | One step, no tools | Classify the request |
| Fixed workflow | Steps known in advance | Classify, look up order, check policy, draft reply |
| Agent with tools | Steps depend on what it finds | Customer has three orders and a vague complaint |
| Multi-agent | Clearly separate skills or parallel work | Rarely needed for refunds |

A strong answer for refunds: a workflow for the common 80% of cases (clear order, clear policy), with an agent
handling ambiguous ones, and a human approving any refund above a threshold. That shows you treat autonomy as a cost.

## What a strong design covers

- **Tools:** few, narrow, well described, with validated arguments. `issue_refund(order_id, amount)` with a cap,
  not `run_sql(query)`.
- **Permissions:** least privilege per tool, read-only by default, separate credentials for write actions.
- **Human checkpoints:** approval before irreversible or expensive actions (money, emails to customers, deletes).
- **Memory:** short-term state in the run; long-term facts in a store the agent queries, not an ever-growing prompt.
- **MCP:** a standard way to expose tools to many clients; mention it when integrations will be reused.
- **Budgets:** hard limits on steps, tokens, wall-clock time and spend per run.
- **Observability:** a trace of every step: prompt, tool call, arguments, result, tokens.

## The failure scenarios

Be ready to name the cause and the guard for each:

| Failure | Typical cause | Guard |
|---------|--------------|-------|
| Runaway loop | Tool returns an error the model keeps retrying; no stop condition | Step cap, repeated-call detection, clear error messages |
| Wrong tool | Overlapping tools, vague descriptions | Fewer tools, sharper descriptions, routing step |
| Tool failure | Timeouts, bad arguments | Validate inputs, retry with backoff, return useful errors |
| Different path each run | Sampling, ambiguous instructions | Lower temperature, explicit plan, evaluate on many runs |
| Token blow-up | Whole tool outputs appended to context | Truncate or summarise tool results |
| Context decay | Long runs bury the original goal | Restate goal, summarise history, sub-agents with clean context |
| Over-broad permissions | Convenience during development | Scoped credentials, approvals, audit log |

## Debugging from the trajectory

For "works in tests, fails in production", the strong answer is: pull the traces of failing runs and read them step
by step. Look for the first step where the agent went wrong, then ask whether production inputs differ from your
test inputs (longer, messier, different language), whether a tool behaves differently with real data, or whether
context grew past what you tested.

```python
from collections import Counter

def loop_signals(trace: list[dict]) -> dict:
    calls = [(s["tool"], str(s["args"])) for s in trace if s["type"] == "tool_call"]
    repeats = [c for c, n in Counter(calls).items() if n >= 3]
    errors = sum(1 for s in trace if s.get("error"))
    return {"steps": len(trace), "repeated_calls": repeats, "tool_errors": errors}
```

Run something like this over a day of traces and the pattern usually jumps out: the same failing call repeated, or
one tool erroring on a production data shape.

## Common weak answers

- "I'd use a multi-agent framework" before establishing the task needs one.
- No limits on steps or spend.
- Giving the agent broad credentials "so it can figure it out".
- Debugging by tweaking the prompt without reading the trace.

## Practice drill

Pick three tasks (refunds, meeting scheduling, code review). For each, in five minutes, say where on the autonomy
spectrum it belongs, list its tools with permissions, and name the one action that needs human approval.

## Try it

An agent that books meetings sometimes double-books. Traces show it calls `create_event` twice in one run. Propose
two fixes.

<details>
<summary>Reference</summary>

Make the tool idempotent: accept a client-generated request id and ignore duplicates. Return a clear success result
so the model doesn't think the first call failed (often it retries because the tool returned something ambiguous or
timed out). Optionally check availability inside the tool before creating, and require confirmation for the write.
</details>

## Check yourself

1. Why is "fixed workflow" often the better answer than "agent"?

<details>
<summary>Answer</summary>

It is cheaper, faster, predictable and easier to test. If the steps are known in advance, autonomy adds cost and
failure modes without benefit.
</details>

2. Name three hard limits every production agent should have.

<details>
<summary>Answer</summary>

Maximum steps, maximum tokens or spend per run, and a wall-clock timeout. Approval gates on consequential actions
are a fourth.
</details>

3. What is the first artefact you look at when an agent misbehaves in production?

<details>
<summary>Answer</summary>

The trajectory trace of a failing run: each model step, tool call, argument and result, to find the first wrong
step.
</details>
