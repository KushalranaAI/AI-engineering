# Fine-tuning questions

Fine-tuning comes up in interviews far more often than it comes up at work. The questions are rarely "write the
training loop". They are "should we tune?", "what does LoRA buy you?" and "the tuned model got worse in production,
why?". Interviewers want to hear that you treat tuning as an expensive last resort with a clear measurement plan.

## Example questions

- "We're building a support bot for our product. Should we fine-tune or use RAG?"
- "Explain LoRA and QLoRA to me as an engineering choice."
- "How would you serve a fine-tuned 8B model for 200 requests per second?"
- "The tuned model scored well offline but production accuracy dropped. What do you check?"

## Prompt, RAG or tune: from the brief

Answer from the product brief, not from preference. A table you can reproduce on a whiteboard:

| The problem is... | Reach for | Why |
|-------------------|-----------|-----|
| Model lacks private or changing facts | RAG | Fresh, citable, no retraining |
| Model ignores instructions or format | Better prompt, structured output | Cheap, fast to iterate |
| Format or style still unstable after prompt work | Fine-tune (SFT) | Bakes behaviour in, shortens prompts |
| A big model works but is too slow or costly | Distil into a small tuned model | Lower latency and cost |
| Narrow task with a checkable answer | Possibly RFT | Reward from an automatic grader |

For the support bot: RAG for product knowledge, because it changes every release. Tuning only if, after prompt and
retrieval work, tone or a strict output format still fails a measured eval, and even then, combined with RAG.

**Weak answer:** "Fine-tune it on our docs so it knows the product." Facts baked into weights go stale, can't be
cited, and still hallucinate.

## LoRA and QLoRA as trade-offs

| | Full fine-tune | LoRA | QLoRA |
|---|---|---|---|
| Weights trained | All | Small low-rank adapters | Same adapters, base in 4-bit |
| GPU memory | Highest | Much lower | Lowest |
| Quality on narrow tasks | Best ceiling | Usually close | Usually close, small risk |
| Artefact | Full model copy | Small adapter file | Small adapter file |
| Serving | One model per tune | Many adapters on one base | Same as LoRA |

Back-of-envelope memory is a good signal of real experience. For an 8B model: weights alone in 16-bit are about 16
GB; in 4-bit about 5 GB. Full fine-tuning with an Adam-style optimiser needs several times the weight memory for
gradients and optimiser state, which is why LoRA or QLoRA on a single GPU is the common choice.

```python
def weight_gb(params_b: float, bits: int) -> float:
    return params_b * 1e9 * bits / 8 / 1e9

print(weight_gb(8, 16), weight_gb(8, 4))  # 16.0 4.0 (plus overhead, activations, KV cache)
```

## Serving the tuned model

Cover: an inference server such as vLLM with continuous batching; multi-LoRA serving if you have several tunes;
quantisation to fit cheaper GPUs, with a re-run of evals afterwards; autoscaling on queue depth; and a gateway that
can route back to the old model.

## "Accuracy dropped after deployment"

Walk the path from training to serving, in order:

1. **Template and tokenizer.** Is production using the exact chat template and special tokens from training? This is
   the most common cause.
2. **Inference settings.** Temperature, max tokens, stop sequences, system prompt different from eval.
3. **Quantisation.** Was the served model quantised after evaluation? Re-run evals on the served artefact.
4. **Serving changes.** Wrong adapter version loaded, adapter not applied, merged weights from a different base.
5. **Distribution shift.** Production inputs differ from the training and test data (length, language, new topics).
6. **Eval gaps.** The offline test set never covered the failing cases; maybe it leaked from training.

A strong answer ends with the fix to the process: evaluate the exact served artefact through the real endpoint
before rollout, and sample production traffic into the eval set.

## Practice drill

Have someone read you three product briefs. For each, in two minutes, decide prompt, RAG, tune or a mix, name the
metric that would prove it, and one cost you would incur.

## Try it

A team tuned a 7B model to output JSON invoices. Offline: 97% valid. In production: 81%. The served model is a
4-bit GGUF in a local runtime. List your first three checks.

<details>
<summary>Reference</summary>

1. Re-run the offline eval against the served 4-bit artefact through the same runtime: quantisation or the runtime's
default template may explain the gap. 2. Compare the prompt actually sent in production (chat template, system
prompt, stop tokens, max tokens) with the training format. 3. Sample failing production inputs and check whether
they look unlike the training data (longer invoices, other languages). Constrained decoding with a JSON schema is a
cheap safety net either way.
</details>

## Check yourself

1. Why is fine-tuning a poor way to add product knowledge?

<details>
<summary>Answer</summary>

Knowledge changes, and retraining on every change is slow and costly. Tuned-in facts can't be cited or easily
corrected, and the model still makes things up. Retrieval keeps facts fresh and traceable.
</details>

2. What does QLoRA change compared with LoRA?

<details>
<summary>Answer</summary>

It loads the frozen base model in 4-bit precision while training the same small adapters, cutting memory so larger
models fit on smaller GPUs, at a small risk to quality.
</details>

3. What is the single most common cause of a tuned model behaving worse in production?

<details>
<summary>Answer</summary>

A mismatch between the training and serving prompt format: chat template, special tokens or system prompt.
</details>
