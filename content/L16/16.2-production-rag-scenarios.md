# Production RAG scenarios

"Design a RAG system" is the most common AI design question there is, and the most common weak answer is a demo:
embed documents, put them in a vector database, retrieve top 5, call the model. Interviewers have heard it a hundred
times. What separates candidates is everything around that loop: messy ingestion, scale, services, failure handling
and debugging.

## Example questions

- "Design a question-answering system over 20 million internal documents for 30,000 employees."
- "Our documents are scanned PDFs with tables and diagrams. How would you ingest them?"
- "The RAG system worked well for a week, then answers got worse. How do you investigate?"

## What a strong design covers

Split the system into services with clear jobs. Keep the request path stateless so it scales horizontally, and put
state in stores built for it.

```
               ┌──────────── offline / async ─────────────┐
 sources ──► queue ──► ingestion workers ──► parse/OCR ──► chunk ──► embed ──► vector + keyword index
   (S3, wiki,    (retry,          (layout-aware,               (versioned     (+ metadata, ACLs)
    tickets)      dead-letter)     table extraction)            model id)
               └──────────────────────────────────────────┘
 user ──► API gateway (auth, rate limit) ──► orchestrator (stateless)
                                               ├─► retrieval service (hybrid + rerank, ACL filter)
                                               ├─► LLM inference (provider or self-hosted, fallback model)
                                               └─► cache (embeddings, frequent answers)
 everything ──► traces, metrics, eval sampling ──► dashboards + alerts
```

| Topic | What to say |
|-------|-------------|
| Ingestion | Layout-aware parsing, OCR or a vision model for scans, tables kept as tables, change detection so only edited docs re-index |
| Storage | Raw files in object storage, chunks and metadata in a database, vectors in a vector index, keyword index for exact terms |
| Access control | Filter by the user's permissions **at retrieval**, never after generation |
| Scale | Shard the index, cache embeddings for repeat queries, autoscale stateless services, batch embedding jobs |
| Reliability | Queues with retries and dead-letter for ingestion, timeouts and a fallback model for generation |
| Security | IAM roles per service, private networking to the model endpoint, secrets in a manager, encryption at rest |
| Operations | SLAs for latency and freshness, CI/CD that runs a retrieval eval before deploy |

You will not have time to say all of this. Lead with the request path, then let the interviewer steer you to the
parts they care about, and offer the rest as one-line headlines.

## Common weak answers

- Naming a vector database as if that were the design.
- No answer for permissions: "everyone can see everything" fails in any enterprise.
- Ignoring updates: documents change, and a stale index is the most common real failure.
- Scaling the LLM call but not the ingestion pipeline.

## The debugging case

"Quality dropped after a week" is a test of method. The strong answer isolates stages instead of guessing:

1. **Confirm and scope.** Which queries, which users, since when? Check eval scores and user feedback over time.
2. **What changed?** Deploys, prompt edits, model version (providers update aliases), embedding model, index rebuilds,
   new document sources.
3. **Retrieval or generation?** For failing questions, look at what was retrieved. Right chunks plus wrong answer
   points to generation; wrong chunks points to retrieval or data.
4. **Data.** New documents that crowd out old ones, duplicates, a broken parser on a new file type, a partial
   re-index mixing two embedding models.
5. **Infrastructure.** Timeouts silently returning fewer chunks, a cache serving stale answers, rate limits
   triggering a weaker fallback model.

A small script that compares retrieval hit rate on a fixed question set between two dates is often the fastest
way in:

```python
def hit_rate(results: dict[str, list[str]], gold: dict[str, str], k: int = 5) -> float:
    return sum(gold[q] in ids[:k] for q, ids in results.items()) / len(gold)

before = hit_rate(retrieve_all(index="snapshot-oct-01"), gold)
after = hit_rate(retrieve_all(index="live"), gold)
print(f"hit@5 before={before:.2f} after={after:.2f}")  # a big drop points at data or index, not the LLM
```

## Practice drill

Set a 25-minute timer. Out loud, design the 20-million-document system above. Spend 5 minutes on requirements, 10 on
the architecture, 5 on scale and security, 5 on failure modes. Record it, then check: did you mention permissions,
updates and evaluation without being asked?

## Try it

A RAG assistant over HR policies starts giving outdated holiday rules. Retrieval hit rate on your test set is
unchanged. Where do you look?

<details>
<summary>Reference</summary>

The test set probably doesn't contain questions about the changed policy, so it can't see the problem. Look at
ingestion: was the new policy document indexed, and was the old one deleted or marked superseded? If both are present,
retrieval may rank the old one higher. Fixes: delete or version-filter superseded documents, add effective-date
metadata and prefer the latest, and add questions about recently changed documents to the eval set.
</details>

## Check yourself

1. Why should the orchestration service be stateless?

<details>
<summary>Answer</summary>

So any instance can serve any request, which makes horizontal scaling, rolling deploys and failure recovery simple.
Conversation history, indexes and caches live in stores designed for durability and sharing.
</details>

2. Where must document permissions be enforced, and why there?

<details>
<summary>Answer</summary>

At retrieval, as a filter on the query. If unauthorised chunks reach the prompt, the model can leak them in the
answer, and no post-processing reliably removes that.
</details>

3. What is the first split you make when debugging a bad RAG answer?

<details>
<summary>Answer</summary>

Retrieval versus generation: check whether the right evidence was retrieved. That halves the search space
immediately.
</details>
