# What vision models get right and wrong

Vision models are impressive in demos and inconsistent in production. The gap is predictable: they are strong at
tasks that resemble describing an image, and weak at tasks that resemble measuring one. Knowing which is which lets
you decide what to ship as-is, what needs a safeguard, and what needs a different tool.

## Strengths

| Task | Typical reliability | Notes |
|---|---|---|
| Reading clear printed text in an image | High | Screenshots, signs, clean scans |
| Describing a scene or UI | High | "What is on this screen?" |
| Extracting named fields from a document | Good | Invoice number, date, total on a clean invoice |
| Classifying an image | Good | "Is this a receipt or a contract?" |
| Reading a chart's trend and labels | Good, coarse | "Sales rose through Q3" |
| Exact chart values without printed numbers | Weak | Estimates from bar heights |

## Repeat failures

These show up across models and vendors, though each new generation improves:

- **Counting**: "How many people are in this crowd?" or "how many items on the shelf?" Off by a few is common past a
  dozen objects.
- **Spatial and geometric reasoning**: left vs right, which object is behind which, distances, angles, whether two
  lines intersect.
- **Dense small text**: fine print, footnotes, pages of tiny tables after downscaling.
- **Table alignment**: reading every cell but assigning a value to the wrong row or column, especially without
  gridlines.
- **Fine visual comparison**: spotting a small difference between two near-identical images.

## Invented detail

The most dangerous failure is not "I can't read that" but a confident wrong answer. Give a model a blurry receipt and
ask for the total, and it may return a plausible number that appears nowhere in the image. It may read a label that
is not there, or "complete" a partially hidden word.

## Why it happens

The model does not measure the image. It sees a set of patch embeddings, and generates text that is a likely
description given those patches and your question. When the evidence is thin, "likely" fills the gap: totals look like
totals, dates look like dates. Counting requires tracking discrete objects across many patches, which a single pass of
attention does unevenly. Nothing in the process checks the answer against the pixels.

## Ask "how reliably?"

"Can this model read invoices?" is a demo question. The engineering question is: how often is it exactly right on
**my** invoices, at **my** resolution, in **my** formats? Build a small labelled set and score exact matches:

```python
import json

cases = json.load(open("vision_cases.json"))   # [{"image": "...", "type": "table", "question": "...", "expected": "..."}]
results = []
for c in cases:
    got = ask_vision_model(c["image"], c["question"]).strip()
    results.append({**c, "got": got, "ok": got == c["expected"]})

by_type = {}
for r in results:
    by_type.setdefault(r["type"], []).append(r["ok"])
for t, oks in by_type.items():
    print(f"{t:12} {sum(oks)}/{len(oks)}")
```

Group cases by type (clean print, handwriting, dense table, counting) so you learn which categories are safe and which
are not. An overall 90% can hide a 40% on handwriting.

## Safeguards

| Problem | Safeguard |
|---|---|
| Small text misread | Higher detail, or crop the region and send it at full resolution |
| Free-form answers hard to check | Structured output with a schema; validate types and ranges |
| Totals and sums | Extract line items and recompute the total in code; flag mismatches |
| Counting | Use a detector model, or ask the model to list items with positions, then count the list |
| Invented values | Ask for "null if not visible"; run a second verification pass ("is this value visible in the image?") |
| Residual risk | Route low-confidence or high-value cases to human review |

The pattern is the same as with text: do not trust a single generation for anything precise; check it with code or a
second pass, and keep a human where errors are expensive.

## Try it

Build a ten-image test set: a crowded shelf (count items), a dense table, a low-resolution receipt, a handwritten note,
and six of your own. Write the exact expected answer for each. Run one vision model and score exact matches by
category.

<details>
<summary>Reference</summary>

Expect near-perfect results on clean printed text, misses on the shelf count (often off by a few), some cell
misalignments in the dense table, and at least one invented digit on the low-res receipt rather than an admission it
cannot read it. Handwriting varies widely. The useful output is the per-category score: it tells you which tasks need
cropping, recomputation or review before shipping.

## Check yourself

1. Why is "the model got 9 of 10 demo invoices right" weak evidence for production?

<details>
<summary>Answer</summary>

Ten curated examples do not represent your real resolution, formats, handwriting and scan quality, and one sample per
category says nothing about rates. You need a labelled set from real traffic, scored by category.
</details>

2. A model returns an invoice total of 1,284.50 but the line items sum to 1,248.50. What does this suggest and what
   should the system do?

<details>
<summary>Answer</summary>

A misread or transposed digit in either the total or a line item. Recompute in code, flag the mismatch, and send the
document to review (or re-read the relevant crops at higher resolution) instead of storing either value silently.
</details>

3. Why does a vision model invent values rather than say it cannot read them?

<details>
<summary>Answer</summary>

It generates the most plausible text given the patches and the question; it does not verify against the pixels. When
evidence is weak, plausible-looking values still score highly. Explicit "null if not visible" instructions and
verification passes reduce, but do not eliminate, this.
</details>
