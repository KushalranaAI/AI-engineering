# Deep research and long-running tasks

A "deep research" agent takes a question, searches and reads for many minutes across dozens of sources, and returns a
report. The same shape appears in due-diligence tools, literature reviews and competitive analysis. The engineering is
less about the model and more about planning, source quality, memory across a long run, and producing something a
human can check.

## Why long runs differ

| Short task | Long research run |
|---|---|
| One prompt, one answer | Dozens to hundreds of model and tool calls |
| Fits in one context window | Reads far more text than any window holds |
| Errors visible immediately | Early mistakes compound silently |
| Cost in cents | Cost can reach dollars per run; needs a budget |

So the design needs explicit structure: a plan, a memory outside the context window, stopping rules and a report
format.

## Decompose, then go wide before deep

Break the question into sub-questions that can be investigated independently, often in parallel:

```
Q: "Should we move our document pipeline from OCR to a vision-language model?"
  1. How accurate are current VLMs vs OCR on scanned invoices? (benchmarks, vendor docs)
  2. What do they cost per page at our volume?
  3. What latency do teams report in production?
  4. What failure modes are documented (hallucinated fields, tables)?
  5. What do migrations look like (case studies)?
```

If the question is too vague to decompose ("what's happening in AI?"), ask the user to narrow it first; decomposing
a vague question produces a vague report.

For each sub-question, **search broadly** first: many queries, many candidate results, read only titles and snippets.
Then pick the few most promising sources and read them closely. Discard the rest on purpose, and record why.

## Reading critically

Rank sources by what kind of evidence they are:

| Type | Example | Weight |
|---|---|---|
| Primary | Paper with the experiment, official docs, filings, datasets | Highest |
| Secondary | Reputable analysis, survey articles | Medium |
| Marketing | Vendor blog claiming "10x better" | Low; check for evidence |
| Stale | Anything older than the facts it describes allow | Check the date |

When sources disagree, do not average them. Prefer the stronger evidence, or report the disagreement explicitly
("Vendor A reports 98% field accuracy; the independent benchmark measured 91% on scanned documents"), or say the
question is unresolved.

## Claims tied to sources

Store findings as structured notes, each with its source and the exact supporting passage:

```python
from dataclasses import dataclass

@dataclass
class Finding:
    sub_question: int
    claim: str
    source_url: str
    quote: str           # the passage that supports the claim
    source_type: str     # primary / secondary / marketing
    retrieved_at: str

notes: list[Finding] = []
```

At writing time the model may only make claims backed by a `Finding`, and cites it. A verification pass then checks
each sentence against its quote: does the passage actually say this?

## Notes, summaries and stopping

A run that reads 80 pages cannot keep them all in context. Keep the findings list and short per-sub-question
summaries; drop raw page text once its findings are extracted. Each step's prompt includes the plan, the current
summaries and what is still missing, not the whole history.

Stop when:

- every sub-question has an answer supported by adequate sources;
- new searches keep returning sources you have already seen (saturation);
- the remaining uncertainty is not something more searching can resolve (the data does not exist publicly);
- or the budget (time, tokens, dollars) is hit, in which case the report says so.

## An auditable report and its failure modes

A report a human can audit has a fixed structure:

1. The question (and how it was interpreted).
2. The short answer.
3. Evidence per sub-question, with citations.
4. Contradictions found and how they were weighed.
5. Gaps and open questions.

Characteristic failures to test for:

- **Drift**: the run wanders into a related but different question.
- **Thin synthesis**: confident conclusions from one or two weak sources.
- **Citation mismatch**: a real URL attached to a sentence it does not support.
- **Recency errors**: outdated facts presented as current.

Spot-check citations on a sample of reports regularly; citation mismatch is the failure readers notice last and
trust least once they do.

## Try it

Run the same research question through a research agent (a hosted deep-research feature or your own loop) twice: once
with a 5-minute budget and once with 30 minutes. Compare number of sources, number of distinct claims, contradictions
surfaced, and citation accuracy on ten randomly chosen claims from each.

<details>
<summary>Reference</summary>

The longer run usually cites more sources and surfaces more nuance and contradictions, but returns diminish quickly:
many extra sources repeat earlier findings. Citation accuracy does not automatically improve with time and can get
worse as more material is synthesised. The useful conclusion is where your quality curve flattens, which sets the
default budget.
</details>

## Check yourself

1. Why should raw page text be dropped from the working context once findings are extracted?

<details>
<summary>Answer</summary>

Long runs read far more than fits in the window. Keeping structured findings and summaries preserves what matters,
keeps cost down, and avoids the model losing the plan in a sea of raw text.
</details>

2. Two sources give different numbers for the same metric. What are acceptable ways to handle it?

<details>
<summary>Answer</summary>

Prefer the stronger evidence (primary, independent, recent) and say why; or report both with their context; or mark
the point as unresolved. Averaging hides the disagreement and is not acceptable.
</details>

3. Name three stopping conditions for a research run.

<details>
<summary>Answer</summary>

All sub-questions answered with adequate evidence; saturation (new searches return known sources); remaining
uncertainty cannot be reduced by searching; plus a hard budget limit, reported in the output.
</details>
