# What a multimodal model is

Everything you learned about text LLMs still holds when a user uploads a photo or a voice note. A multimodal model is
not a different kind of machine: it is the same transformer, fed tokens that happen to come from pixels or sound. The
engineering questions are mostly about how those tokens get made, what they cost, and what gets lost on the way.

## Everything becomes tokens

A text model reads a sequence of token embeddings. A multimodal model adds **encoders** that turn other inputs into
embeddings of the same width, then interleaves them with the text:

```
[text: "What is wrong with this invoice?"]  → 9 text tokens
[image: invoice.png]                         → vision encoder → ~1,000 image tokens
                                             → projected into the LLM's embedding space
→ one sequence → the same transformer → text tokens out
```

The vision encoder cuts the image into patches; an audio encoder slices sound into short frames. A small projection
layer maps their outputs into the space the language model already understands. From the transformer's point of view,
it is just a longer prompt.

## Native model or stitched pipeline

There are two ways to build "it understands images":

| | Native multimodal | Stitched pipeline |
|---|---|---|
| How | One model trained on mixed text, image and audio data | A separate OCR, captioning or speech-to-text model converts input to text, then a text-only LLM reads it |
| Keeps | Layout, colour, tone of voice, who is speaking over whom | Only what the converter chose to write down |
| Debuggable | Harder: one opaque step | Easier: you can read the intermediate text |
| Cost | Media tokens can be expensive | Converter is often cheap; LLM sees short text |

A pipeline throws information away at the conversion step. OCR flattens a two-column page into one stream and forgets
which number sat under which header. A transcript records the words "that's fine" but not the sigh before them. A
native model sees the page or hears the sigh. Pipelines are still often the right call: they are cheaper, easier to
inspect, and good enough when the source is clean.

You can usually tell which one a product uses by asking it about something only the raw input carries: "what colour is
the highlighted cell?" or "did the speaker sound annoyed?".

## Text is still the hub

Even with native models, the reasoning happens in token space and the output is nearly always text. Image generation
and speech output usually come from separate models or decoders bolted onto the end. "Any-to-any" in a launch post
mostly means many inputs, text out, plus a few output modalities through extra components. Read the API docs for the
exact list of input and output types before designing around a claim.

## What carries over

- **Context window**: images and audio consume it, often fast.
- **Tokenisation and pricing**: you pay per token; media just produces lots of them.
- **Sampling**: temperature and friends behave the same.
- **Failure modes**: hallucination, sensitivity to prompt wording, and position effects in long context all apply,
  with new variants (inventing text that is not in a blurry image).

A minimal call looks like any chat call with an extra content part:

```python
import base64
from openai import OpenAI

client = OpenAI()
img = base64.b64encode(open("chart.png", "rb").read()).decode()

resp = client.chat.completions.create(
    model="gpt-4o-mini",  # any vision-capable model
    messages=[{
        "role": "user",
        "content": [
            {"type": "text", "text": "What was revenue in Q3? Answer with the number only."},
            {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{img}"}},
        ],
    }],
)
print(resp.choices[0].message.content, resp.usage.prompt_tokens)
```

Check `prompt_tokens`: the image alone will usually dwarf the question.

## Try it

Take a bar chart with labelled axes. Send it as an image to a vision model, and separately run OCR on it (for example
`pytesseract`) and send only the extracted text to a text-only model. Ask both: "Which quarter had the highest value,
and roughly by how much did it exceed the lowest?"

<details>
<summary>Reference</summary>

The OCR text contains the axis labels and maybe the numbers printed on bars, but not the bar heights or which label
belongs to which bar. If values are not printed, the text-only model must guess or refuse. The vision model can
compare bar heights and answer, though its "roughly by how much" will be an estimate, not a measurement. The
difference is the information the OCR step threw away: geometry and position.
</details>

## Check yourself

1. A support tool transcribes calls and summarises them with a text LLM. A manager asks it which customers sounded
   frustrated. Why might it do badly?

<details>
<summary>Answer</summary>

It is a stitched pipeline. The transcript keeps the words but drops tone, pace, pauses and volume, which are the main
signals of frustration. The LLM can only infer emotion from word choice. An audio-native model, or adding
prosody features, would help.
</details>

2. Why does the same context window hold far fewer documents when they are sent as page images rather than text?

<details>
<summary>Answer</summary>

Each image becomes hundreds to thousands of tokens depending on resolution, while the same page as text might be a few
hundred tokens. Both share the one context window and the per-token bill.
</details>

3. A vendor says its model is "any-to-any". What do you check before relying on that?

<details>
<summary>Answer</summary>

The exact input and output modalities the API supports, whether outputs like speech or images come from the same model
or separate ones, and the pricing and limits per modality. Most models accept several inputs but return text.
</details>
