# Realtime voice agents

A chat assistant that takes three seconds is fine. A voice agent that leaves three seconds of silence feels broken:
people start repeating themselves, talk over it, or hang up. Building voice agents is mostly about latency and
turn-taking, with the LLM as one component in a tightly timed loop.

## The latency budget

Natural conversation has gaps of a few hundred milliseconds between turns. Past roughly a second of silence after the
user stops, the agent feels slow. Measure **end of user speech → first audible sound of the reply**, and split it:

| Stage | Example budget (cascade) |
|---|---|
| Endpointing (deciding the user has finished) | 200-500 ms |
| Network, client to server | 30-100 ms |
| Final transcription | 100-300 ms |
| LLM time to first token | 200-600 ms |
| TTS time to first audio | 100-300 ms |
| Network back + playback buffer | 50-150 ms |
| **Total** | **~0.7-2 s** |

These are illustrative ranges; your numbers depend on region, models and load. Notice endpointing: the wait to be sure
the user is done is often the largest single item.

## Cascade vs speech-to-speech

| | Cascade: STT → LLM → TTS | Speech-to-speech realtime API |
|---|---|---|
| Latency | Sum of stages, minus overlap | Usually lower |
| Control | Pick each model; edit text between steps | Fewer knobs |
| Debugging | Inspect transcript and reply text | Harder; audio in, audio out |
| Hears tone | No (transcript only) | Yes |
| Cost | Often lower, easier to predict | Audio tokens both ways |
| Guardrails | Run text checks before TTS | Must hook into the session's events |

Cascades remain common in production because each part can be swapped, logged and guarded. Speech-to-speech wins on
naturalness and latency when its control and cost are acceptable.

## Overlapping the stages

The cascade is only as slow as its serial parts. Overlap them:

- Stream audio to STT while the user talks, so the final transcript is ready almost instantly at endpoint.
- Stream LLM tokens, cut them into sentences, and send the **first sentence** to TTS immediately.
- Start playback as soon as the first audio chunk arrives.

```python
async def respond(transcript: str):
    buffer = ""
    async for token in llm.stream(messages + [{"role": "user", "content": transcript}]):
        buffer += token
        if buffer.rstrip().endswith((".", "?", "!")):
            await tts_queue.put(buffer)      # TTS worker synthesises and plays in order
            buffer = ""
    if buffer:
        await tts_queue.put(buffer)
```

## Turn-taking

**Voice activity detection (VAD)** detects whether speech is present in each audio frame. **Endpointing** decides the
turn is over, usually after some silence (say 500 ms). That is hard: people pause mid-thought, slow speakers leave long
gaps, and background chatter looks like speech. Short thresholds interrupt users; long ones add dead air. Some systems
add a small model that judges from the words whether the sentence sounds finished.

**Barge-in**: when the user speaks during the agent's reply, stop playback immediately, cancel the pending LLM and TTS
work, and listen.

**Partial transcripts** let you start early (retrieve, prefetch) but never commit irreversible actions on them.

**Honest state after a cut-off**: if the agent planned three sentences and the user interrupted after one, the
conversation history must record only what was actually played. Otherwise the model believes it told the user
something they never heard.

```python
def on_barge_in(played_text: str):
    playback.stop(); llm_task.cancel(); tts_queue.clear()
    history[-1]["content"] = played_text + " [interrupted]"
```

## Silence, noise and drops

- **Dead air**: if processing will exceed the budget, play a short holding phrase ("let me check that").
- **User silence**: re-prompt once, then close politely.
- **Network loss**: reconnect with session state; do not restart the conversation.
- **Noise and crosstalk**: use noise suppression and echo cancellation (so the agent does not hear itself and
  barge-in on its own voice), and tune VAD sensitivity on real call audio.

## Tools mid-conversation

A three-second database lookup is three seconds of silence. Options: say a filler line while the tool runs, start the
tool on partial transcripts when intent is clear, and set strict tool timeouts. Decide in advance what the agent says
when a tool fails or returns nothing ("I can't see that order right now; can I take your number and call back?").

For debugging, log per session: the raw audio (with consent), transcripts with timestamps, turn boundaries,
barge-in events, and per-stage latency. A bad call is almost impossible to reconstruct from text logs alone.

## Try it

Build a minimal cascade: microphone → streaming STT → LLM → TTS → speaker. Log timestamps at end of speech, final
transcript, first LLM token, first TTS audio and playback start. Run ten turns and compute the median end-to-end
delay and its biggest component.

<details>
<summary>Reference</summary>

Most first versions land between 1.5 and 3 seconds, with endpointing silence and LLM time to first token as the
biggest items, and non-streamed TTS next if the whole reply is synthesised at once. The usual fixes, in order:
sentence-level TTS streaming, a shorter endpoint threshold, a faster or smaller LLM for the first sentence, and
co-locating services in one region.
</details>

## Check yourself

1. Why is endpointing often the largest item in a voice latency budget?

<details>
<summary>Answer</summary>

The system must wait for some silence to be confident the user has finished. That wait is pure added latency, and
making it shorter risks cutting users off mid-thought.
</details>

2. After a barge-in, why must you edit the stored assistant message?

<details>
<summary>Answer</summary>

The model's history would otherwise contain text the user never heard, so later turns may refer to it ("as I
mentioned...") and confuse the user. Store only what was actually played.
</details>

3. Give two reasons a team might choose a cascade over a speech-to-speech API.

<details>
<summary>Answer</summary>

Any two of: inspectable text at each step for debugging and logging, text guardrails before speaking, freedom to
choose and swap each model, and more predictable or lower cost.
</details>
