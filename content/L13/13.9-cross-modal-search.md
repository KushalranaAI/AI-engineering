# Cross-modal search

"Find photos of a red bicycle leaning against a wall" over a folder of 50,000 untagged images. "Show me products that
look like this photo." Both are cross-modal search: the query is one modality and the results are another. The
machinery is the vector search you already know; the new part is an embedding space shared by text and images.

## One shared space

A text embedding model puts similar sentences near each other. A **joint embedding model** puts an image and a
caption that describe the same thing near each other too:

```
embed_image(photo_of_red_bike.jpg)        → [0.12, -0.40, 0.08, ...]
embed_text("a red bicycle against a wall") → [0.11, -0.38, 0.10, ...]   close
embed_text("a bowl of noodles")            → [-0.52, 0.07, 0.33, ...]   far
```

Once both live in one space, cosine similarity works across modalities: text-to-image, image-to-text, and
image-to-image all become the same nearest-neighbour query.

## How CLIP-style models learn it

CLIP trains two encoders, one for images and one for text, on a very large set of image-caption pairs from the web.
Each training batch holds N pairs. The model computes all N × N similarities and is trained (with a contrastive loss)
so that each image is most similar to its own caption and less similar to the other N - 1, and vice versa. Over
hundreds of millions of pairs, concepts like "red", "bicycle" and "wall" become directions that both encoders agree
on. Later variants (SigLIP and others) change the loss and data but keep the idea.

## Searching across modalities

```python
import numpy as np, torch
from PIL import Image
from transformers import CLIPModel, CLIPProcessor

model = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")
proc = CLIPProcessor.from_pretrained("openai/clip-vit-base-patch32")

paths = ["img/001.jpg", "img/002.jpg", "img/003.jpg"]
with torch.no_grad():
    imgs = proc(images=[Image.open(p) for p in paths], return_tensors="pt")
    img_vecs = model.get_image_features(**imgs)
    img_vecs = img_vecs / img_vecs.norm(dim=-1, keepdim=True)

    q = proc(text=["a red bicycle against a wall"], return_tensors="pt", padding=True)
    q_vec = model.get_text_features(**q)
    q_vec = q_vec / q_vec.norm(dim=-1, keepdim=True)

scores = (img_vecs @ q_vec.T).squeeze(1).numpy()
for i in np.argsort(-scores):
    print(paths[i], round(float(scores[i]), 3))
```

For a real collection, store the image vectors in your vector database with metadata, exactly as for text chunks.
Image-to-image search ("more like this") just uses an image vector as the query.

## Or caption everything first

The alternative: run a vision model over every image, generate a detailed caption, and index the captions with text
embeddings (plus BM25).

| | Joint embeddings (CLIP-style) | Caption, then text search |
|---|---|---|
| Indexing cost | Cheap, fast encoder | One vision-LLM call per image |
| Query types | Text, image, "more like this" | Text only (unless you also embed images) |
| Exact words, text in image, numbers | Weak | Better, if the caption includes them |
| Explainability | A similarity score | A readable caption you can inspect |
| Re-indexing on model change | Re-embed images | Re-caption (expensive) |

Many systems combine both: joint embeddings for visual similarity, captions or OCR text for keyword matches, fused
with reciprocal rank fusion.

## Where it fails

- **Fine-grained detail**: two similar car models, two near-identical product SKUs.
- **Text inside images**: CLIP-style models read a little text but are unreliable for codes or prices.
- **Counting and relations**: "three dogs" vs "two dogs", "cup on the left of the laptop".
- **Unfamiliar domains**: X-rays, circuit boards, satellite imagery, internal part photos that look nothing like web
  pictures. A domain-specific or fine-tuned encoder may be needed.
- **Negation**: "a street with no cars" often returns streets full of cars.

## Test on your own collection

Public zero-shot benchmarks are measured on general web-like photos. Build 30-50 real queries for your collection,
mark the relevant images for each, and measure recall at 10. Compare at least two encoders and the caption baseline.
Your ranking may well differ from the leaderboard's.

## Try it

Index 200 of your own photos with a CLIP-style model. Write ten plain-language queries, five visual ("sunset over
water") and five specific ("receipt from a pharmacy", "whiteboard with a diagram"). Then caption the same photos with
a vision model, index the captions, and compare which approach finds the right image in the top 5.

<details>
<summary>Reference</summary>

Joint embeddings usually win or tie on visual, scene-level queries and are far cheaper to index. Captions usually win
on queries that depend on text in the image or specific objects the caption happened to mention ("pharmacy",
"diagram"). The misses in each column tell you whether a hybrid is worth the extra indexing cost.
</details>

## Check yourself

1. Why can a text query be compared directly with an image vector in CLIP but not with vectors from an ordinary text
   embedding model?

<details>
<summary>Answer</summary>

CLIP's image and text encoders were trained together so their outputs share one space. An ordinary text embedding
model's space has no relation to any image encoder's, so distances between them are meaningless.
</details>

2. Users search a parts catalogue by serial number printed on the part. Joint embeddings perform badly. Why, and what
   do you add?

<details>
<summary>Answer</summary>

CLIP-style embeddings capture overall visual meaning, not exact characters. Add OCR or captions and a keyword (BM25)
index for the serial numbers, and fuse with the visual results.
</details>

3. What does the contrastive training objective push together and apart?

<details>
<summary>Answer</summary>

It pulls each image towards its own caption (and vice versa) and pushes it away from the other captions in the batch.
</details>
