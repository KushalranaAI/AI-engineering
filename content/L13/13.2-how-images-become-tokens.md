# How images become tokens

When you attach a screenshot, the bill and the context window jump. That is not overhead: the image genuinely became
hundreds or thousands of tokens. Knowing how that happens lets you predict cost, and lets you decide what resolution
and crop to send instead of uploading whatever the phone camera produced.

## Patches and the vision encoder

Most vision encoders follow the Vision Transformer (ViT) recipe:

1. Resize the image to a size the encoder supports.
2. Cut it into a grid of square **patches**, typically 14 or 16 pixels on a side.
3. Flatten each patch and project it to a vector. Each vector is one "visual token".
4. Run the encoder, then project the outputs into the language model's embedding space.

```
224 × 224 image, 16-px patches → (224/16)² = 14 × 14 = 196 patches
448 × 448 image, 16-px patches → 28 × 28 = 784 patches     (2× side, 4× tokens)
```

Token count follows **pixel area**, not file size. A heavily compressed 4K JPEG and a lossless 4K PNG cost the same; a
crisp 600 × 400 crop costs a fraction of either. Some models merge neighbouring patches to reduce the count, but the
scaling is the same: double the side, roughly quadruple the tokens.

## What providers actually charge

Each provider resizes and counts differently, so always read their docs and check `usage` in the response. Two
illustrative schemes (treat as examples, they change):

| Scheme | How it counts | 1,024 × 1,024 image |
|---|---|---|
| Area-based (one provider's rule of thumb: tokens ≈ width × height / 750, after downscaling to a max size) | Proportional to pixels | ≈ 1,400 tokens |
| Tile-based "high detail" (one provider: base 85 + 170 per 512-px tile, after resizing so the short side is 768) | Image is scaled, cut into 512-px tiles, each billed | 768 × 768 → 4 tiles → 765 tokens |
| Tile-based "low detail" | One fixed small thumbnail | 85 tokens |

Back-of-envelope: 1,000 product photos a day at ~1,000 tokens each is a million input tokens per day from images alone,
before any text. At an example rate of $3 per million input tokens that is $90 a month; at "low detail" it might be a
twelfth of that. Whether low detail is acceptable is a quality question you answer with tests.

## Tiles and detail levels

High-detail modes exist because a single downscaled thumbnail loses small text. The provider splits a big image into
tiles, encodes each at full encoder resolution, and often adds a low-res overview so the model knows how the tiles fit
together. You pay per tile. A detail setting is usually a request parameter:

```python
{"type": "image_url",
 "image_url": {"url": data_url, "detail": "low"}}   # or "high" / "auto"
```

## What resizing destroys

Every pipeline resizes something, either you or the provider. Downscaling hits, in order:

- **Small text**: 9-pt text on a full-page scan becomes a few pixels tall and unreadable.
- **Thin lines**: table borders and chart gridlines vanish, so rows and columns blur together.
- **Dense tables**: neighbouring cells merge.
- **Chart labels and tick marks**: the axis becomes impossible to read precisely.

Aspect ratio matters too. Squashing a long receipt into a square, or letterboxing it into one, wastes most of the
pixels you pay for. Very tall images (a full scrolled web page) are often better split into several sections.

## Images crowd the context

Image tokens sit in the same window as your system prompt, history and retrieved documents. Ten full screenshots in a
chat history can be 15,000 tokens that get re-sent every turn. Strategies:

- Send an image once, extract what you need into text, and drop the image from later turns.
- Use prompt caching for images that must stay in context.
- Keep only the latest screenshot in agent loops that see the screen repeatedly.

## Full, cropped or overview

| Option | Good for | Risk |
|---|---|---|
| One large, high-detail image | Unknown layout, need to read anything anywhere | Most tokens |
| Several crops of known regions | Forms and documents with fixed layout | Miss content outside crops |
| Small overview | Classification, scene description | Small text lost |
| Overview, then crop on demand | Agents and large documents | Extra round trip |

Cropping is the cheapest quality upgrade available: the region that matters, at full resolution, often beats the
whole page at any detail setting.

## Try it

Take one screenshot containing a small table. Send it three ways: full resolution, half resolution, and cropped to the
table only. Record `usage.prompt_tokens` and whether the model reads every cell correctly.

<details>
<summary>Reference</summary>

Typical pattern: full resolution reads correctly but costs the most; half resolution costs roughly a quarter as many
image tokens (area scaling, subject to the provider's minimums and tiling) and starts misreading digits; the crop
costs the least and is as accurate as full resolution, because the table keeps its original pixel density. Subtract
a text-only call's tokens to isolate the image's share.
</details>

## Check yourself

1. Why does recompressing a JPEG to half the file size not reduce its token cost?

<details>
<summary>Answer</summary>

Tokens depend on the number of patches, which depends on pixel dimensions after the provider's resizing. Compression
changes bytes, not width and height.
</details>

2. A form has a signature box in the bottom-right corner. Users complain the model misses whether it is signed. What
   do you try first?

<details>
<summary>Answer</summary>

Crop the signature box and send it at full resolution alongside (or instead of) the full page. Its detail is being
lost in downscaling; a crop is cheaper than raising detail on the whole page.
</details>

3. An agent takes a screenshot every step for 30 steps. What happens to cost, and how do you fix it?

<details>
<summary>Answer</summary>

If every screenshot stays in history, each call re-sends all previous images, so cost grows roughly quadratically.
Keep only the latest one or two screenshots, summarise older steps as text, and lower resolution where possible.
</details>
