# Entity memory: structured entity extraction

Vector memory (6.7) is good at "things like this". It is poor at exact lookups: "what is Priya's phone number", "what
did the customer order", "which flight is booked". Those questions want a record, not a similar sentence. **Entity
memory** keeps a structured record for each person, organisation, product or order the conversation mentions, and
updates it as new facts arrive.

## Entities and attributes

An entity has a type, a name and attributes. You extract them with structured output (see 2.4):

```python
from pydantic import BaseModel

class Fact(BaseModel):
    attribute: str          # "phone", "diet", "role"
    value: str
    confidence: float       # 0-1

class Entity(BaseModel):
    name: str               # "Priya Sharma"
    type: str               # person | org | product | order | place
    aliases: list[str] = []  # ["my sister", "Priya"]
    facts: list[Fact]

class Extraction(BaseModel):
    entities: list[Entity]

result = llm_structured(
    "Extract entities and facts stated in the message. Do not infer facts that were not said.\n\n" + message,
    schema=Extraction,
)
```

The instruction "do not infer" matters: an extractor that guesses will fill your store with plausible fiction.

## An entity store

The store can be as simple as a table keyed by entity id, a JSON document per user, or a small graph if
relationships matter ("Priya works at Infosys; Infosys is in Pune"). Start with a table:

```sql
CREATE TABLE entity (id TEXT PRIMARY KEY, user_id TEXT, type TEXT, name TEXT, aliases JSONB);
CREATE TABLE entity_fact (entity_id TEXT, attribute TEXT, value TEXT,
                          confidence REAL, updated_at TIMESTAMPTZ, source TEXT,
                          PRIMARY KEY (entity_id, attribute));
```

New facts are **upserted**: the same `(entity, attribute)` pair gets its value replaced and `updated_at` refreshed.
Unlike vector memory, there is exactly one current answer per attribute.

## Aliases and references

People rarely use full names. "My sister", "she" and "Priya" can all be one entity. Resolve them in two steps: match
names and aliases against the existing store (exact and fuzzy), and when a message uses a pronoun or relation, give
the extractor the last few turns and the known entity list so it can say which one is meant. When two records turn
out to be the same person, merge them and keep the union of aliases. A wrong merge is worse than a missed one, so
prefer asking ("Is Priya your sister?") when unsure.

## Injecting only what is relevant

Do not paste the whole store into the prompt. Look at the entities mentioned in the current message (by name or
alias) and inject only those records:

```text
<entities>
Priya Sharma (person, user's sister): phone 98xxxx1234; diet vegetarian (said 2026-03-02)
</entities>
```

This keeps tokens low and gives the model exact values to quote. Pair it with vector memory: entities for exact
facts about named things, vectors for fuzzy recall of what was discussed.

## Staleness and conflicts

Every fact needs `updated_at` and `source`. When a new value disagrees with the stored one, decide the rule: the
newest statement usually wins for things that change (address, job), but for something that should be stable (date
of birth) a conflict is a signal to ask. Lower confidence for facts the user only implied.

## Try it

A user says: "Book a table for my brother Arjun's birthday on the 14th. He's vegan now, by the way." Earlier, the store
says Arjun is vegetarian. Write the update.

<details>
<summary>Reference</summary>

Resolve "my brother Arjun" to the existing Arjun entity (add alias "my brother" if missing). Upsert the fact
`diet = vegan` with a new `updated_at` and source, replacing `vegetarian`. Create an event or episode record for
the birthday booking separately (6.9); the date belongs to the event, not to Arjun's attributes.
</details>

## Check yourself

1. When would you pick entity memory over vector memory?

<details>
<summary>Answer</summary>

When you need exact, current values for named things (a phone number, an order status, a diet) rather than a fuzzy
recall of similar past statements.
</details>

2. Why upsert facts by (entity, attribute) instead of appending them?

<details>
<summary>Answer</summary>

So there is one current value per attribute and a later lookup cannot return an old and a new value together.
</details>

3. Why is a wrong entity merge worse than a missed one?

<details>
<summary>Answer</summary>

A wrong merge mixes two people's facts and spreads the error everywhere the record is used; a missed merge only
leaves a duplicate that can be fixed later.
</details>
