# Short-term memory: buffers, windows and token bloat

A model has no memory between calls. Everything it "remembers" about the conversation is text you send again on
every turn. **Short-term memory** is the policy for which earlier messages you resend. Get it wrong in one
direction and the assistant forgets what the user said two minutes ago. Get it wrong in the other and every
reply is slower and costlier than the last.

This lesson starts the memory strand of Level 6. We look at the simplest layer first, then add layers in the
next lessons: summaries, vector recall, entities, episodes, facts, procedures and reflections.

## Conversation buffer

The conversation buffer keeps every message verbatim.

```python
history = []
def turn(user_text):
    history.append({"role": "user", "content": user_text})
    reply = llm(system=SYSTEM, messages=history)
    history.append({"role": "assistant", "content": reply})
    return reply
```

Recall is perfect. The costs are not. At turn *n* you send roughly *n* messages, so the **total** tokens paid over
a conversation of N turns grow with N²: 10 turns of 200 tokens each cost about 11,000 input tokens in total; 50
turns cost about 255,000. Latency rises too, and eventually the window overflows.

## Sliding window

Keep only the last *k* turns:

```python
def window(history, k=6):
    return history[-2 * k:]       # k user/assistant pairs
```

Cost per turn is flat and predictable. The price is amnesia: at turn 20 the model no longer knows the user's name,
their budget or the constraint they gave in turn 2. Windows work for chit-chat and short tasks, and fail for
anything with a goal.

## Token buffer

Counting messages is a poor proxy for size; one pasted log can outweigh twenty chat lines. A **token buffer** trims
by tokens, dropping the oldest turns until the history fits a budget:

```python
def token_buffer(history, budget, count):
    kept, used = [], 0
    for msg in reversed(history):             # newest first
        n = count(msg["content"])
        if used + n > budget:
            break
        kept.append(msg); used += n
    return list(reversed(kept))
```

This is the budget thinking from 6.1 applied to history: give history a fixed share (say 4,000 tokens) and let the
rest of the window serve instructions, retrieval and output.

## Token bloat

**Token bloat** is the creeping growth of the prompt for reasons that have nothing to do with the user's question:

- the same long system prompt resent every turn;
- tool results kept in full long after they were used;
- assistant replies that restate the question;
- history that nobody ever trims.

Measure it instead of guessing: log tokens per section per turn (the inspector from 6.1) and plot them. A healthy
agent has a flat or slowly rising curve. A bloated one climbs steeply. Prompt caching (6.17) softens the price of the
repeated prefix but does not remove the latency or the context-rot problems of a huge window.

## Pinning what must stay

Trimming from the front will eventually drop the thing that matters most. Exempt a small set of items from trimming:
the system prompt, the user's stated goal, and any hard constraints ("budget is ₹20,000", "no peanuts"). Store them
in a **pinned** block that is always included, and let the rest slide. What falls off the edge is not necessarily
lost: the next two lessons turn it into a summary (6.6) or a searchable memory (6.7).

## Try it

A travel assistant has a 3,000-token history budget. At turn 12 the user asks, "Does that hotel fit my budget?" The
budget (₹40,000) was stated at turn 2. Compare the three strategies.

<details>
<summary>Reference</summary>

A **sliding window of the last 4 turns** has already dropped turn 2, so the model cannot know the budget and will
guess or ask again. A **token buffer** drops the oldest turns first, so it fails the same way once the history
exceeds 3,000 tokens. A **pinned goal block** ("budget ₹40,000, dates 12-16 Dec") survives under either strategy.
The fix is to pin durable constraints, not to enlarge the window.
</details>

## Check yourself

1. Why does a conversation buffer get expensive faster than the conversation grows?

<details>
<summary>Answer</summary>

Each turn resends all earlier turns, so the input tokens per turn grow linearly and the total across the conversation
grows roughly with the square of its length.
</details>

2. What does a token buffer fix that a sliding window does not?

<details>
<summary>Answer</summary>

A window counts messages, so a few huge messages can still blow the budget. A token buffer counts tokens, so the
history always fits the budget you set whatever the message sizes.
</details>

3. Name two causes of token bloat besides long user messages.

<details>
<summary>Answer</summary>

Any two of: a long system prompt resent each turn, old tool results kept in full, verbose assistant replies, and
history that is never trimmed or summarised.
</details>
