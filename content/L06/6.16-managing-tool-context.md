# Managing tool context

Tools take up context in two ways. Their **definitions** (name, description, JSON schema) are sent on every call,
whether used or not. Their **results** pile up in the history as the agent works. In a tool-heavy agent these two
together often outweigh everything else in the window. This lesson is about keeping both under control.

## Tools take space too

A single well-documented tool definition is typically 100-400 tokens. Connect a few MCP servers and you can have 50
or more tools, which is easily 10-20k tokens before the user has said anything. Count them:

```python
import json, tiktoken
enc = tiktoken.get_encoding("o200k_base")   # approximate; use your provider's counter for billing-accurate numbers

def tool_tokens(tools: list[dict]) -> list[tuple[str, int]]:
    sizes = [(t["name"], len(enc.encode(json.dumps(t)))) for t in tools]
    return sorted(sizes, key=lambda x: -x[1])

# [('create_jira_issue', 610), ('search_confluence', 420), ...]  total: 14,300
```

Large tool catalogues hurt more than cost: with many similar tools, the model is more likely to pick the wrong one.

## Showing only relevant tools

Expose a subset per task or per step instead of the whole catalogue. Options, from simplest:

| Approach | How | Trade-off |
|----------|-----|-----------|
| Static per agent | Each agent or mode gets a fixed small set | Simple; needs good task routing |
| Per state | The harness picks tools by workflow stage (e.g. no `send_email` until a draft exists) | Predictable; doubles as a safety control |
| Retrieved | Embed tool descriptions, pick top-k for the user's request | Scales to hundreds of tools; can miss the right one |
| Tool search tool | Give the model one `find_tools(query)` tool that returns definitions to load | Model decides; adds a step |

```python
def select_tools(query_vec, tool_index, always=("finish", "ask_user"), k=6):
    scored = sorted(tool_index, key=lambda t: -cosine(query_vec, t["vec"]))
    chosen = {t["name"] for t in scored[:k]} | set(always)
    return [t["schema"] for t in tool_index if t["name"] in chosen]
```

One caution: changing the tool list between calls can break prompt caching, since tool definitions usually sit at
the start of the prompt. Prefer changing tools at stage boundaries rather than every turn.

## Filtering big results

Never pass raw API, search or database output straight back to the model. Build a result shaper per tool:

- **Select fields**: return the 6 fields the task needs, not the 80 the API sends.
- **Limit rows** and say so: `{"rows": [...20], "total": 4312, "truncated": true}`. The model should know there is
  more.
- **Paginate**: accept `page` or `cursor` arguments so the model can ask for more deliberately.
- **Summarise prose**: for long pages, extract the parts relevant to the current question.
- **Make errors short and actionable**: "No customer with email x. Try search_customers(name=...)" beats a stack
  trace.

## Full results kept outside

When you shrink a result, keep the full version somewhere the agent can reach:

```python
import uuid
RESULTS: dict[str, str] = {}   # use a real store (Redis, files, S3) in production

def run_tool(name: str, args: dict, max_chars: int = 2000) -> str:
    raw = TOOLS[name](**args)
    text = raw if isinstance(raw, str) else json.dumps(raw)
    if len(text) <= max_chars:
        return text
    ref = f"res_{uuid.uuid4().hex[:8]}"
    RESULTS[ref] = text
    return json.dumps({"preview": text[:max_chars], "full_result_ref": ref, "chars": len(text),
                       "hint": "call read_result(ref, offset) for more"})
```

The agent sees a preview and a reference; if it needs a detail, it calls `read_result`. This turns a 50k-token blob
into a few hundred tokens without losing anything permanently.

## Clearing old observations

In a 40-step loop, the result from step 3 is rarely needed at step 38, yet it is resent every turn. Ways to clear
it:

- **Replace old tool results with stubs** once they are a few steps old: `"[result of search('pricing') cleared;
  ref res_91ab]"`. Keep the call itself so the history still makes sense. Some providers now offer built-in
  context-editing features that do this for you.
- **Fold findings into state**: when the agent extracts the fact it needed, record it in the task state (6.4) and
  drop the raw result.
- **Hand bulky exploration to a sub-agent** (6.18) that returns only a short conclusion.

## Try it

Your agent has 45 tools from three MCP servers and averages 30 steps per task. Each tool result is around 3k tokens.
Estimate the context used by tools at step 30 with no management, then design changes that bring it below 15k.

<details>
<summary>Reference</summary>

Unmanaged: 45 definitions × ~300 = ~13.5k, plus 30 results × 3k = 90k, so about 100k tokens of tool context at step
30, resent on every call. Managed: expose 8 tools per stage (~2.4k); cap each result at ~800 tokens with a reference
to the full output; keep the last 5 results in full and stub older ones (~50 tokens each). That gives
2.4k + 5 × 800 + 25 × 50 ≈ 7.7k, with key findings recorded in task state. Verify that task success holds on a test set.
</details>

## Check yourself

1. Besides cost, why is a large tool catalogue a problem?

<details>
<summary>Answer</summary>

The model is more likely to choose the wrong tool or mix up similar ones, and definitions crowd out useful context.
</details>

2. Why include `"truncated": true` and a total count in a shortened result?

<details>
<summary>Answer</summary>

So the model knows it is seeing a partial view and can page or narrow the query, instead of wrongly concluding that
the 20 rows shown are everything.
</details>

3. What is the risk of changing the exposed tool set on every turn?

<details>
<summary>Answer</summary>

Tool definitions usually sit at the start of the prompt, so changing them invalidates the prompt cache and raises
cost and latency. Change tools at stage boundaries instead.
</details>
