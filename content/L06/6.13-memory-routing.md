# Memory routing with intent classification

By now you can build eight kinds of memory. The temptation is to load all of them on every turn. Resist it. A user who
types "thanks!" does not need their order history, a vector search and three reflections. Loading everything costs
tokens and latency, and, worse, irrelevant memory distracts the model (the context rot of 6.1). A **memory router**
decides, per turn, which memories to read and how much space each gets.

## Not every turn needs every memory

| User says | Memory that helps |
|-----------|-------------------|
| "thanks, that's great" | none |
| "what's my sister's number?" | entity memory |
| "what did we decide last time?" | episodic memory |
| "recommend something I'd like" | semantic facts and preferences |
| "and the second one?" | short-term buffer only |
| "do it the way we did the Goa trip" | episodic plus procedural |

Routing is the same idea as the router in system design (9.3) and the tool selection in 6.16: a small decision up front
saves a lot of work downstream.

## Classify the intent first

Label the incoming message with an **intent** from a small, fixed set. Three ways to do it, from cheapest:

1. **Rules and keywords** ("last time", "remember when") for the obvious cases.
2. **An embedding classifier**: embed example messages per intent, pick the nearest. Milliseconds, no model call.
3. **A small LLM** with structured output when intents are subtle or messages are long.

```python
from pydantic import BaseModel
from typing import Literal

class Route(BaseModel):
    intent: Literal["smalltalk", "followup", "personal_fact", "past_event",
                    "preference", "howto", "new_task"]
    confidence: float

route = llm_structured(
    "Classify the user's latest message. Use the last two turns for context.\n" + context,
    schema=Route, model="small-fast-model", temperature=0,
)
```

## A routing table

Map each intent to the stores to read and a token budget for each. Keep the table in config, not in a prompt:

```python
ROUTES = {
    "smalltalk":     {"stores": [], "budget": 0},
    "followup":      {"stores": ["buffer"], "budget": 1500},
    "personal_fact": {"stores": ["entity", "buffer"], "budget": 800},
    "past_event":    {"stores": ["episodic", "buffer"], "budget": 1200},
    "preference":    {"stores": ["semantic", "vector"], "budget": 600},
    "howto":         {"stores": ["procedural", "reflections"], "budget": 800},
    "new_task":      {"stores": ["semantic", "entity", "reflections", "buffer"], "budget": 2000},
}
FALLBACK = ROUTES["new_task"]           # used when confidence < 0.6

def memory_for(route):
    plan = ROUTES[route.intent] if route.confidence >= 0.6 else FALLBACK
    return [STORES[s].read(query, budget=plan["budget"]) for s in plan["stores"]]
```

When the classifier is unsure, **fail towards more memory, not less**. A little extra context costs tokens; missing
context costs a wrong answer.

## Routing writes

The same idea applies on the way out. A new piece of information goes to the right place: a phone number to the entity
store, "we decided on IndiGo" to the episode log, "always keep replies short" to the preference facts, a one-off
remark nowhere. A single extraction call can return both the intent and a write plan, but keep the write rules
conservative; wrongly storing is harder to undo than wrongly skipping.

## Measuring the router

A router can be wrong in two ways: it can skip a memory the answer needed (quality drops) or load memory nobody used
(tokens wasted). Measure both:

- **Routing accuracy**: label 100-200 real messages with the right intent and compare.
- **Memory used**: for each answer, how much of the injected memory was actually referenced? A judge model (7.8)
  can estimate it.
- **Savings**: tokens and latency per turn against a baseline that loads everything.
- **Answer quality** on the eval set, with and without routing. Routing is a win only if quality holds.

## Try it

Your assistant serves 20,000 turns a day. Loading all memory adds about 2,500 tokens per turn. Your classifier labels
45% of turns "smalltalk" or "followup" (needing about 300 tokens) and 55% as needing about 1,500. What is the saving,
and what do you watch?

<details>
<summary>Reference</summary>

Baseline: 20,000 × 2,500 = 50M tokens. Routed: 0.45 × 300 + 0.55 × 1,500 = 960 tokens average, so 19.2M tokens, a saving
of about 62% of memory tokens. Watch routing accuracy and eval quality: if the 45% includes turns that really needed
episodic or entity memory, you have traded money for wrong answers. Raise the confidence threshold or widen the fallback.
</details>

## Check yourself

1. Why not load every memory type on every turn?

<details>
<summary>Answer</summary>

It wastes tokens and time, and irrelevant memory can distract the model and lower answer quality.
</details>

2. What should the router do when its confidence is low?

<details>
<summary>Answer</summary>

Fall back to a broader set of memory stores, because a little extra context is cheaper than missing the context the
answer needed.
</details>

3. Give two metrics for judging a memory router.

<details>
<summary>Answer</summary>

Any two of: routing accuracy against labelled messages, the share of injected memory the answer used, tokens and
latency saved against loading everything, and answer quality on the eval set.
</details>
