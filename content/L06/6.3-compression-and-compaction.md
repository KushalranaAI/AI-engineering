# Compression and compaction

Selection decides what goes in. Compression makes what goes in smaller. For long conversations and long agent
runs you will eventually hit the budget no matter how well you select, and you have to replace detailed text with
shorter text. Done well, the model barely notices. Done badly, the agent forgets the goal, repeats work or quotes a
number that was mangled in a summary.

## Summaries that keep the goal

A generic "summarise this conversation" prompt keeps the topic and loses the things that matter for continuing the
work. Ask for a structured summary instead:

```python
COMPACT_PROMPT = """You are compacting the history of a task so work can continue.
Write these sections. Be specific; keep names, ids and numbers exactly as written.

GOAL: the user's original goal, in their words if possible
CONSTRAINTS: rules, preferences and limits the user stated
DECISIONS: choices made so far and why
DONE: completed steps and their results
OPEN: unfinished work, open questions, next step
"""

def compact(client, model: str, messages: list[dict], keep_last: int = 6) -> list[dict]:
    old, recent = messages[:-keep_last], messages[-keep_last:]
    if not old:
        return messages
    transcript = "\n".join(f"{m['role']}: {m['content']}" for m in old)
    resp = client.chat.completions.create(
        model=model,
        messages=[{"role": "system", "content": COMPACT_PROMPT},
                  {"role": "user", "content": transcript}],
    )
    summary = resp.choices[0].message.content
    return [{"role": "user", "content": f"<summary_of_earlier_work>\n{summary}\n</summary_of_earlier_work>"}] + recent
```

Keep the most recent turns verbatim: they carry tone and fine detail the next reply depends on. Trigger compaction
on a token threshold (say 70% of the history budget), not on every turn, so you are not paying for summaries
constantly. Note that tool-call messages usually need to stay paired with their results, so cut on a turn boundary.

## Shrinking tool output

Tool results are often the biggest single source of bloat. Compact them **before** they enter the history:

| Output | Compaction |
|--------|------------|
| Web page (20k tokens) | Extract the paragraphs relevant to the current sub-question |
| SQL result (5,000 rows) | Row count, column names, first 20 rows, aggregates |
| Log file | Error lines plus a few lines of surrounding context |
| JSON API response | Only the fields the task needs |

Deterministic compaction (code that selects fields or lines) is cheaper and safer than an LLM summary. Use a model
only when the content is unstructured prose.

## Rolling and layered summaries

- **Rolling summary**: keep one running summary, and each time you compact, merge the newly dropped turns into it.
  Simple, but errors accumulate: a detail dropped once is gone for good.
- **Hierarchical summary**: summarise chunks (for example each phase of a task), then summarise the summaries. The
  top level gives the big picture; lower levels can be pulled back in when needed. This suits very long runs and
  long documents.

## Keeping exact data exact

Summaries paraphrase. Paraphrase is fatal for order ids, amounts, file paths, dates and code. Rule: **anything that
must stay exact lives outside the summary**, in a structured record the harness maintains.

```python
state = {
    "order_id": "A-77812",
    "refund_amount": "149.00 EUR",
    "files_changed": ["api/routes.py", "tests/test_routes.py"],
}
# Render state verbatim into the prompt every turn; summaries refer to it instead of restating values.
```

This also gives you something to test: after compaction, the exact values are still present byte for byte.

## What you lose

Every compression throws something away. The trade-off:

| Approach | Tokens saved | Risk |
|----------|--------------|------|
| Drop oldest turns | High | Loses goals and constraints stated early |
| Rolling summary | High | Drift and lost details over many rounds |
| Structured summary + exact state | High | Small; costs an extra model call |
| Field selection on tool output | Medium-high | Needs code per tool |
| No compression | None | Cost, latency and context rot |

Measure, don't assume: run the same long task with and without compaction and compare success rate and tokens.

## Try it

Write a compaction test. Build a 40-turn synthetic conversation where turn 2 states a constraint ("never email the
customer directly"), turn 10 introduces order id A-77812, and turn 25 moves the delivery date from 2026-11-28 to 2026-12-03. Compact it with your
structured prompt, then check programmatically that the constraint, the exact order id and the *latest* date
survive.

```python
summary_msgs = compact(client, MODEL, conversation, keep_last=6)
text = summary_msgs[0]["content"]
assert "A-77812" in text                       # exact id kept
assert "email" in text.lower()                 # constraint kept
assert "2026-12-03" in text and "2026-11-28" not in text   # only the latest date
```

If the id or date assertion fails, move those values into a structured state record instead of trusting the
summary. Run the test a few times; summaries are not deterministic.

## Check yourself

1. Why ask for a sectioned summary (goal, constraints, decisions, done, open) instead of a free-form one?

<details>
<summary>Answer</summary>

Free-form summaries keep the topic but drop what is needed to continue: the original goal, constraints and pending
work. Named sections force the model to preserve exactly those.
</details>

2. When should you compact tool output with code rather than with an LLM?

<details>
<summary>Answer</summary>

When the output is structured (JSON, tables, logs). Selecting fields, rows or error lines in code is cheaper,
deterministic and can't invent or alter values.
</details>

3. What is the main weakness of a rolling summary over a long run?

<details>
<summary>Answer</summary>

Errors compound: each merge can drop or distort details, and once something is lost from the summary it can't be
recovered unless the original was stored elsewhere.
</details>
