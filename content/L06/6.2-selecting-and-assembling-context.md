# Selecting and assembling context

Most chat code builds the prompt by accident: append each message to a list, send the list. Context engineering
means building the window **on purpose**, in one function you own, from separate sources that you rank, trim and
label. The goal is the smallest context that still lets the model make this particular decision well.

## The sources

| Source | Example | Changes how often |
|--------|---------|-------------------|
| Instructions | Role, rules, output format | Rarely |
| Tool definitions | Names, descriptions, schemas | Per task or step |
| Long-term memory | "User prefers metric units" | Across sessions |
| Retrieved knowledge | Top 5 chunks for this question | Every turn |
| Conversation history | Last few turns | Every turn |
| Tool results | Output of the last search | Every step |
| Application state | Current plan, open ticket id, user's plan tier | Every step |

## Always, sometimes or never

For each piece of information, choose one of four treatments:

- **Always present**: short, stable and needed on almost every call. Core instructions, the user's goal, hard
  constraints.
- **Retrieved on demand**: large or only occasionally relevant. Docs, past tickets, older memories. Fetch when the
  current step needs them.
- **Summarised**: needed in gist but not word for word. Older conversation, long tool outputs.
- **Excluded**: stale, duplicated, superseded or irrelevant. Old drafts, a search result the agent already rejected.

A useful test: "If I removed this, would the next model call make a worse decision?" If not, it goes.

## Ranking what goes in

When candidates exceed the budget, rank them. Four signals cover most cases:

- **Relevance** to the current step (retrieval score, or a reranker).
- **Importance**: constraints and user corrections outrank background.
- **Recency**: newer facts usually supersede older ones.
- **Reliability**: your own database outranks a web page; a verified tool result outranks the model's earlier guess.

## Assembling it in code

```python
from dataclasses import dataclass

@dataclass
class Item:
    section: str      # "memory", "docs", "history", ...
    text: str
    score: float      # combined relevance/importance/recency/reliability
    tokens: int
    source: str = ""

BUDGET = {"memory": 800, "docs": 6000, "history": 6000, "tool_results": 6000}

def pick(items: list[Item], section: str) -> list[Item]:
    chosen, used, seen = [], 0, set()
    for it in sorted((i for i in items if i.section == section), key=lambda i: -i.score):
        key = it.text.strip().lower()
        if key in seen or used + it.tokens > BUDGET[section]:
            continue                      # skip duplicates and overflow
        chosen.append(it); used += it.tokens; seen.add(key)
    return chosen

def build_messages(instructions: str, goal: str, state: dict, items: list[Item], user_msg: str):
    docs = "\n".join(f'<doc source="{d.source}">{d.text}</doc>' for d in pick(items, "docs"))
    mem = "\n".join(f"- {m.text}" for m in pick(items, "memory"))
    history = [{"role": "user", "content": h.text} for h in pick(items, "history")]  # simplified
    system = (
        f"{instructions}\n\n<goal>{goal}</goal>\n<state>{state}</state>\n"
        f"<memory>\n{mem}\n</memory>"
    )
    user = f"<documents>\n{docs}\n</documents>\n\n<question>{user_msg}</question>"
    return system, history + [{"role": "user", "content": user}]
```

The details will differ, but the shape matters: one place that decides, per section, what makes the cut.

## Order and labels

The model has to tell instructions from evidence from user data. Help it:

- Put **instructions first** and keep them in the system prompt. Put the **question last**, close to where the model
  starts writing.
- Wrap each kind of content in clear delimiters (XML-style tags work well across providers) and attach the
  **source** to each document.
- Say explicitly that documents and tool results are **data to use, not instructions to follow**. This is not a
  security boundary (Level 8 covers why), but it reduces confusion.
- Keep stable sections at the top and changing ones lower down. This also helps prompt caching (module 6.17).

## Removing the junk

Before sending, run cheap checks:

- **Duplicates**: the same chunk retrieved twice, the same fact in memory and in history.
- **Stale facts**: an address the user corrected three turns ago. Keep the correction, drop the original.
- **Contradictions**: when two sources disagree, either resolve it in code (newest wins, or most reliable wins) or
  include both with dates and sources so the model can reason about it.
- **Irrelevant matches**: chunks below a relevance threshold after reranking.

## Try it

A support agent's next call has these candidates: system rules (900 tokens), 14 tool definitions (5,000), user
profile (300), 8 retrieved help articles (9,000, two near-identical), 30 turns of history (12,000, including a
corrected shipping address), and the last order lookup result (1,500). Your working budget is 12,000. Decide the
treatment for each.

<details>
<summary>Reference</summary>

- System rules: always, 900.
- Tools: keep only the 3-4 relevant to an order question, about 1,500.
- User profile: always, 300 (with the corrected address only).
- Help articles: deduplicate, rerank, keep the top 3, about 3,000.
- History: last 4-6 turns verbatim (about 2,500) plus a 500-token summary of the rest that records the address
  correction and any decisions.
- Order lookup: keep, 1,500, since it is the current evidence.
Total about 10,200, leaving headroom for output. The old address, duplicate article and unused tools are excluded.
</details>

## Check yourself

1. Give one example each of context that should be always present, retrieved, and excluded.

<details>
<summary>Answer</summary>

Always: the core instructions and the user's stated goal. Retrieved: product documentation relevant to the current
question. Excluded: a search result the agent already judged irrelevant, or a superseded fact.
</details>

2. Why put the user's question at the end of the prompt rather than the start?

<details>
<summary>Answer</summary>

It sits right before generation, after the evidence, so the model reads the documents with the task in mind just
before answering. It also keeps the stable parts at the top, which suits prompt caching.
</details>

3. Two retrieved documents give different refund windows. What can the assembler do?

<details>
<summary>Answer</summary>

Resolve it in code if there is a clear rule (newest policy version, most authoritative source), or include both with
their dates and sources so the model can explain the conflict. Never silently include both without labels.
</details>
