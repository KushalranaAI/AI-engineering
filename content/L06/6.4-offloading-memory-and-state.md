# Offloading memory and state

Compression shrinks what is in the window. Offloading moves things **out** of the window entirely and brings them
back only when needed. This is how a person works on a big project: you don't hold every detail in your head, you
keep notes, a task list and files, and you look things up.

## Places outside the window

| Store | Good for | Example |
|-------|----------|---------|
| Scratchpad (in-run) | Working notes for the current task | "Tried endpoint v1, returns 404" |
| Files | Plans, drafts, large outputs | `plan.md`, `findings.json` |
| Database / key-value store | Structured task state | `{task_id, step, status, result}` |
| Vector or memory store | Facts to recall by meaning | User preferences, past resolutions |
| Task tracker | Progress across many runs | A list of todo items with status |

The model reaches these through tools (`write_note`, `read_note`, `search_memory`) or the harness injects them
automatically at the start of each call.

## Active vs stored

Split information into two groups:

- **Active context**: what the next decision needs. The goal, the current subtask, the latest observation, the
  relevant constraint.
- **Stored context**: everything else that might matter later. Raw tool outputs, finished subtasks, research notes,
  earlier drafts.

The window should hold the active set plus **pointers** to the stored set: "full search results saved as
`results/q3.json`", "notes on vendor pricing in `notes/pricing.md`". A pointer costs a few tokens; the content it
points to might cost thousands.

## Persisting plans and progress

Long tasks need a record that survives compaction, crashes and new sessions. Keep it in a structured file the agent
updates as it goes:

```python
import json
from pathlib import Path

STATE = Path("run_state.json")

def load_state() -> dict:
    if STATE.exists():
        return json.loads(STATE.read_text())
    return {"goal": "", "plan": [], "done": [], "decisions": [], "facts": {}}

def save_state(state: dict) -> None:
    tmp = STATE.with_suffix(".tmp")
    tmp.write_text(json.dumps(state, indent=2))
    tmp.replace(STATE)              # atomic swap so a crash can't leave half a file

def complete_step(state: dict, step: str, result: str) -> None:
    state["plan"] = [s for s in state["plan"] if s != step]
    state["done"].append({"step": step, "result": result[:500]})   # short result; full output stored elsewhere
    save_state(state)

def state_block(state: dict) -> str:
    return (f"<goal>{state['goal']}</goal>\n<next_steps>{state['plan'][:5]}</next_steps>\n"
            f"<done>{[d['step'] for d in state['done']]}</done>\n<facts>{state['facts']}</facts>")
```

Each turn, the harness renders `state_block` into the prompt. The model sees a compact view of the whole task, while
the detailed history lives on disk.

## Note-taking agents

Instead of the harness deciding everything, you can give the agent tools to manage its own notes:

```python
tools = [
    {"name": "write_note", "description": "Save a fact or finding you will need later. Use short titles.",
     "parameters": {"type": "object", "properties": {"title": {"type": "string"}, "body": {"type": "string"}},
                    "required": ["title", "body"]}},
    {"name": "list_notes", "description": "List titles of saved notes.", "parameters": {"type": "object", "properties": {}}},
    {"name": "read_note", "description": "Read one saved note by title.",
     "parameters": {"type": "object", "properties": {"title": {"type": "string"}}, "required": ["title"]}},
]
```

Instruct the agent to write a note whenever it learns something it will need after the current step, and to check
its notes before redoing research. Watch for two failure modes: writing too much (notes become a second bloated
history) and never reading them back. Logging note reads and writes makes both visible.

## Remembering vs making room

These two ideas use the same stores but solve different problems:

- **Memory** (Level 5) is about *keeping* information across sessions so the agent knows the user next week.
- **Offloading** is about *freeing space* during one long task so the window holds only what is active.

A design can use one store for both, but ask the right question for each item: "will this matter in a future
session?" versus "does this need to be in the window right now?"

## Try it

Take an agent that researches a topic with a web search tool. Change it so that every search result is saved to a
file and only a three-line summary plus the file path goes into the history. Add a `read_file` tool. Compare peak
context size and answer quality on a 15-search task.

<details>
<summary>Reference</summary>

Wrap the search tool: run the search, write the full result to `results/<n>.json`, return to the model
`{"summary": "...3 lines...", "path": "results/7.json", "n_results": 10}`. Peak context typically drops by an order of
magnitude because raw pages never accumulate. Quality should hold if the summaries name what each result contains;
if the agent needs a detail, it calls `read_file` on the path. If quality drops, the summaries are too thin: make
them mention the specific entities and numbers found.
</details>

## Check yourself

1. What should stay in the active window when a large tool result is offloaded?

<details>
<summary>Answer</summary>

A short summary of what the result contains and a pointer (file path or id) so the agent can fetch the full content
again if needed.
</details>

2. Why write the state file with a temp file and an atomic rename?

<details>
<summary>Answer</summary>

So a crash during writing can't leave a truncated or corrupt state file. The old version stays intact until the new
one is fully written.
</details>

3. How does offloading differ from long-term memory?

<details>
<summary>Answer</summary>

Long-term memory keeps information to use in future sessions. Offloading moves information out of the window during
the current task to free space, retrieving it later in the same run.
</details>
