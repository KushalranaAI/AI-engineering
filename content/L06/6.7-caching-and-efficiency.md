# Caching and efficiency

Most of a typical prompt is the same on every call: system instructions, tool definitions, few-shot examples, a
reference document. In an agent loop the growing history is also identical up to the newest turn. Without caching,
you pay full price to process those tokens again on every request. Prompt caching lets the provider reuse that work,
and it rewards one habit above all: **put what doesn't change first**.

## Paying for the same tokens

Example: a support agent with a 6k-token system prompt and tools, and a 20k-token policy document, handling 50k
requests a day.

```
26k fixed tokens × 50,000 requests = 1.3B input tokens/day just for the fixed part
```

With caching, those tokens are billed at a steep discount on a cache hit (providers have offered reads at a small
fraction of the normal input price) and the model starts responding sooner because it skips reprocessing the
prefix. Exact discounts, minimum lengths and cache lifetimes vary by provider and change over time; check the
current docs.

## How prompt caching works

Caching is **prefix-based**. The provider stores the processed state of the start of your prompt. A later request
gets a hit only if its prompt begins with exactly the same tokens. One changed character early on, and everything
after it is a miss.

| Provider style | How you use it |
|----------------|----------------|
| Automatic (e.g. OpenAI) | Repeated prefixes above a minimum length are cached automatically; you just keep them stable |
| Explicit (e.g. Anthropic) | You mark cache breakpoints in the request; cache writes may cost a bit more than normal input |
| Explicit cache objects (e.g. Gemini) | You create a cached content object with a lifetime and reference it |

Caches expire after a short idle period (minutes, sometimes extendable), so caching pays off most at steady
traffic.

## Layout for cache hits

Order the prompt from most stable to least stable:

```
1. System instructions        (changes on deploy)
2. Tool definitions           (changes on deploy or per stage)
3. Large reference material   (changes rarely)
4. Long-term memory / user profile   (changes per user)
5. Conversation history       (grows each turn; prefix stays the same)
6. Current turn / fresh tool results  (always new)
```

Common cache killers:

- A **timestamp** or request id in the system prompt ("Current time: 14:03:22"). Move it to the end, or round it to
  the day.
- **Reordering** tools or documents between calls (for example from an unordered set). Sort them deterministically.
- **Rewriting history**: if you edit or summarise earlier messages every turn, the prefix changes every turn.
  Compact in occasional larger steps instead.
- **Non-deterministic JSON** serialisation of tool schemas. Use `sort_keys=True`.

## Stable vs changing

Keep task state that changes every step (current plan item, latest observation) out of the system prompt. Put it
in the latest message, near the end. This both protects the cache and keeps the freshest information close to
where the model generates.

```python
import anthropic
client = anthropic.Anthropic()

resp = client.messages.create(
    model="claude-sonnet-4-5",      # example model id
    max_tokens=1024,
    system=[
        {"type": "text", "text": SYSTEM_RULES},
        {"type": "text", "text": POLICY_DOC, "cache_control": {"type": "ephemeral"}},  # cache up to here
    ],
    tools=TOOLS,                    # tools are part of the cached prefix too
    messages=history + [{"role": "user", "content": f"<state>{task_state}</state>\n{user_msg}"}],
)
u = resp.usage
print(u.input_tokens, u.cache_creation_input_tokens, u.cache_read_input_tokens)
```

## Trimming tokens

Caching makes repeated tokens cheaper, not free, and it does nothing for context rot. Still cut:

- Verbose instructions that say the same thing three ways.
- Few-shot examples that no longer change results (test removing them).
- Pretty-printed JSON where compact JSON works.
- Boilerplate in retrieved chunks (headers, navigation text).

## Measure it

Log per request: input tokens, cached tokens, output tokens, latency (time to first token and total), and cost. Then
track the **cache hit rate** (cached input tokens divided by total input tokens).

| Metric | Healthy sign | Warning sign |
|--------|--------------|--------------|
| Cache hit rate | High and stable at steady traffic | Near zero: something in your prefix changes every call |
| Time to first token | Drops after warm-up | Unchanged: caching not taking effect |
| Cost per task | Falls after layout change | Rises: cache writes without reads |

## Try it

Your app's system prompt starts with `f"Today is {datetime.now().isoformat()}. You are a helpful assistant..."`,
followed by 8k tokens of instructions and tools. Your dashboard shows a cache hit rate near 0%. Fix it and explain
what you expect to see.

<details>
<summary>Reference</summary>

The timestamp changes every request, so the very first tokens differ and nothing after them can be reused. Move the
date to the final user message (or use only the date, not the time, if it must stay in the system prompt), make sure
tools are serialised in a fixed order, and if your provider uses explicit caching, mark a breakpoint after the
instructions and tools. Expect the hit rate to rise sharply at steady traffic, cached-token counts to appear in the
usage field, and time to first token and cost per request to drop.
</details>

## Check yourself

1. Why does a single changed token near the start of the prompt ruin caching?

<details>
<summary>Answer</summary>

Caching matches on exact prefixes. Everything after the first differing token is a different prefix, so none of it
can be reused.
</details>

2. Where should fast-changing task state go, and why?

<details>
<summary>Answer</summary>

At the end, in the latest message. It keeps the stable prefix intact for caching and puts fresh information next to
where the model generates.
</details>

3. Caching cuts cost. Why still trim tokens?

<details>
<summary>Answer</summary>

Cached tokens still cost something and still occupy the window, so they add to distraction and context rot. Caching
fixes price and latency, not quality.
</details>
