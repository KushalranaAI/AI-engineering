# Long-term memory: vector store memory

Short-term memory and summaries only help inside one conversation. Long-term memory survives across sessions: the
assistant that remembers on Friday that you asked about a visa on Monday. The standard way to build it reuses
what you learned in Level 4. Store memories as embeddings, and retrieve them by meaning when they might matter.

This is RAG over the agent's own experience rather than over company documents. The same machinery applies, but the
design questions differ: what is worth writing, how to rank what comes back, and how to stop the store becoming a
junk drawer.

## Memories as embeddings

A memory record is more than text:

```python
memory = {
    "id": "m_0192",
    "user_id": "u_42",
    "text": "User is vegetarian and avoids onion and garlic (Jain diet).",
    "type": "preference",           # preference | fact | event | decision
    "created_at": "2026-03-02T10:14:00Z",
    "last_used_at": "2026-04-11T18:02:00Z",
    "importance": 0.8,              # 0-1, set when written
    "source": "chat:2026-03-02",
    "embedding": embed("User is vegetarian and avoids onion and garlic (Jain diet)."),
}
```

The metadata earns its keep later: `user_id` for isolation, `created_at` and `last_used_at` for recency and decay
(6.14), `importance` for ranking, `source` so you can show where a belief came from.

## What deserves to be stored

Writing every message turns memory into a second, worse transcript. A **write policy** decides what to keep. A
common approach is to ask a small model, after each turn or session, to extract durable items:

```python
EXTRACT = """From this exchange, list facts about the user worth remembering in future conversations: stable
preferences, constraints, goals, and decisions. Skip small talk and anything temporary. Return JSON:
[{"text": "...", "type": "preference|fact|decision", "importance": 0.0-1.0}] or [] if nothing qualifies."""
```

"I'm in a hurry today" is not a memory. "I'm allergic to peanuts" is.

## Recall that mixes signals

Plain similarity is not enough. A very similar but two-year-old memory can be less useful than a slightly less similar
one from last week. The *Generative Agents* paper (Stanford and Google, 2023) popularised scoring each memory as a
weighted sum of **relevance, recency and importance**:

```python
import math, time

def score(mem, query_vec, now, half_life_days=30, w=(1.0, 0.5, 0.5)):
    rel = cosine(query_vec, mem["embedding"])
    age_days = (now - mem["last_used_at_ts"]) / 86400
    rec = 0.5 ** (age_days / half_life_days)         # exponential decay, see 6.14
    return w[0] * rel + w[1] * rec + w[2] * mem["importance"]

top = sorted(memories_for_user, key=lambda m: -score(m, qv, time.time()))[:5]
```

Retrieve a handful (3-5), insert them in a labelled `<memory>` block, and record `last_used_at` so useful memories
stay fresh.

## Updates, duplicates and contradictions

Over months the user changes city, quits a diet, switches jobs. If you only append, retrieval returns both "lives in
Pune" and "lives in Bengaluru". On write, search for similar existing memories and let a model decide:
**add**, **update** (replace the old text), **ignore** (a duplicate) or **delete** (now false). Keep the old record
marked as superseded if you need history.

## Isolation and privacy

Memory holds personal data, so treat it as such: filter by `user_id` at query time in the store itself (not after
retrieval), never share a memory index across tenants, tell users what is remembered, and offer a way to view and
delete it. Do not store secrets or sensitive categories you do not need. This overlaps with 8.7 and 8.8.

## Try it

A shopping assistant has these memories for one user: "prefers size M" (written 14 months ago), "prefers size L
after weight change" (written 2 weeks ago), "likes blue shirts". The query is "show me a shirt for the wedding".
Which should be recalled, and what should happen on the write that stored "size L"?

<details>
<summary>Reference</summary>

Recall "prefers size L" and "likes blue shirts" (relevant to shopping for a shirt, and recent or important); the
old size M memory should not be recalled. On the write of "size L" the system should have found the near-duplicate
"size M", decided it is contradicted, and updated or superseded it, so retrieval cannot surface both.
</details>

## Check yourself

1. Why combine similarity with recency and importance when recalling memories?

<details>
<summary>Answer</summary>

Similarity alone can return old or trivial memories that happen to be worded like the query. Recency favours what is
still true and importance favours what matters, so the mix returns more useful memories.
</details>

2. What problem do add/update/delete decisions at write time solve?

<details>
<summary>Answer</summary>

They stop duplicates and contradictions piling up, so a later recall does not return two conflicting versions of the
same fact.
</details>

3. Where should the per-user filter be applied, and why?

<details>
<summary>Answer</summary>

In the vector store query itself, so only that user's memories are ever retrieved. Filtering after retrieval risks
leaking other users' data into logs or into the prompt if the filter is skipped.
</details>
