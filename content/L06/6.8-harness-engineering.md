# Harness engineering

Give the same model the same task in two different setups and you can get a clean success in one and a confused
mess in the other. The difference is the **harness**: everything around the model that turns it into an agent. When
an agent fails, check the harness before blaming the model. It is also the part you control completely.

## What a harness is

| Part | Question it answers |
|------|---------------------|
| Loop | How do model calls and tool calls alternate, and when does it stop? |
| System prompt | What role, rules and working style does the agent follow? |
| Tool set | What can it do, and how are results shaped? |
| Context management | What enters the window each turn (6.1-6.7)? |
| State | Where are plan, progress and results kept? |
| Permissions | What needs approval, what is forbidden? |
| Environment | What files, services and checks can it see and run? |

Coding agents such as Claude Code, Codex CLI or Cursor's agent mode are mostly harness: they use general models, and
their quality comes largely from the loop, tools, context handling and environment conventions around them.

## Designing the loop

```python
def run(task: str, max_steps=40, max_tokens=400_000, max_seconds=1800):
    state = load_or_init_state(task)
    used, start = 0, time.monotonic()
    for step in range(max_steps):
        if used > max_tokens or time.monotonic() - start > max_seconds:
            return finish(state, reason="budget")
        resp = call_model(build_context(state))            # context assembled fresh each turn
        used += resp.usage.input_tokens + resp.usage.output_tokens
        if not resp.tool_calls:
            if verify(state):                               # harness checks before accepting "done"
                return finish(state, reason="done")
            state.add_feedback("Verification failed: " + state.last_check_output)
            continue
        for call in resp.tool_calls:
            if needs_approval(call) and not ask_human(call):
                state.add_result(call, "Denied by user. Choose another approach.")
                continue
            try:
                state.add_result(call, run_tool(call))     # shaped, size-limited result
            except Exception as e:
                state.add_result(call, f"Error: {e}. Fix the arguments or try a different tool.")
        save_state(state)
    return finish(state, reason="max_steps")
```

Key decisions in this loop: errors are fed back as text the model can act on, the model cannot declare itself done
without passing `verify`, and three independent limits stop runaway runs.

## What the harness enforces

Split responsibilities on purpose:

- **The model decides**: which tool next, what arguments, how to phrase the result, how to fix a failing test.
- **The harness enforces**: fixed steps that must always happen (run tests before commit), permission checks,
  human approval for risky actions, budgets, safe defaults (read-only unless granted write).

If a rule must hold every time, put it in code. Prompts are suggestions; code is a guarantee.

## Work across many windows

Some tasks are too big for one context window no matter how well you compact: building a feature across dozens of
files, a multi-day research project. Structure them as many short sessions:

1. **Setup run**: read the request, explore the environment, write a plan and a task list to files, set up how to
   run checks.
2. **Working runs**: each one starts fresh, reads the progress notes and task list, picks **one** task, completes and
   verifies it, records what changed, and commits.
3. Repeat until the list is empty.

Each run begins with a small, clean context instead of the dregs of the previous one.

## Durable artifacts as the source of truth

Between runs, conversation history is the worst possible record: long, noisy, gone after compaction. Use artifacts
instead:

- `PROGRESS.md`: what was done, what was learned, what is next.
- `tasks.json`: each task with a status, so the agent can't silently skip or forget one.
- **git commits**: small, described, revertable. `git log` is a free progress record.
- **tests**: the executable definition of "done".

## Checks the agent can run

An agent that can verify its own work is far more reliable than one that just says it's finished. Give it tools to
run tests, linters, type checkers and, for UIs, end-to-end checks such as a headless browser. Have the harness run
them before marking a task complete, and feed failures back into the loop.

## A legible environment

Agents read your repository like a new hire with no memory. Help them:

- A short **AGENTS.md** (or equivalent instruction file) at the root: how to build, test and lint, project
  conventions, things never to touch. Keep it short; it is loaded every session.
- A clear directory layout and descriptive file names.
- Docs written to be read by agents: concrete commands and paths, not tribal knowledge.

## Sub-agents

When a subtask needs lots of exploration (search a codebase, read 30 pages), run it in a **sub-agent** with a fresh
context and a narrow brief. It does the messy work and returns a condensed result, maybe 1-2k tokens. The main
agent's context stays clean. The cost is extra tokens overall and the risk that the summary leaves out something the
main agent needed, so write sub-agent briefs that say exactly what to return.

## Try it

Write an AGENTS.md (under 40 lines) for a small Python project of yours, and a `tasks.json` with five tasks for a
feature. Then describe what the harness should do at the start and end of each working run.

## Check yourself

1. An agent keeps claiming tasks are finished when tests fail. Is that a model problem or a harness problem?

<details>
<summary>Answer</summary>

Mostly a harness problem. The harness should run the checks itself and refuse to accept "done" until they pass,
feeding the failures back to the model.
</details>

2. Why start each working run with a fresh context and progress files rather than continuing one long conversation?

<details>
<summary>Answer</summary>

A fresh context avoids accumulated noise and rot, and progress files, task lists, commits and tests are a compact,
reliable record that survives across windows.
</details>

3. When is a sub-agent worth its extra cost?

<details>
<summary>Answer</summary>

When a subtask needs a lot of exploration or reading whose detail the main agent doesn't need, so a short condensed
result can replace thousands of tokens in the main context.
</details>
