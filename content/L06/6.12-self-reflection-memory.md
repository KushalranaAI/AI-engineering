# Self-reflection memory: agent postmortems

After a bad match, a cricket team sits down and asks what went wrong and what to change. Engineering teams do the
same after an outage and call it a postmortem. An agent can do it too. **Self-reflection memory** has the agent write a
short, honest account of how a task went, store it, and read the relevant ones before trying a similar task again.
The idea comes from the *Reflexion* paper (Shinn et al., 2023), which showed agents improving across attempts by
learning from verbal feedback rather than from weight updates.

## Reflection after a task

Trigger a reflection when something is worth learning from: a failed task, a task that needed many retries, a user
correction, or (less often) a surprising success. The prompt gives the model the task, the trace of what it did, and the
outcome:

```python
REFLECT = """You attempted this task:
{task}

Steps you took (with results):
{trace}

Outcome: {outcome}

Write a postmortem as JSON:
{"what_happened": "...", "root_cause": "...", "lesson": "one sentence, actionable next time",
 "applies_when": "the kind of task where this lesson matters"}
Be specific. If the failure was bad luck rather than a mistake, say so and leave lesson empty."""
```

The `applies_when` field is the retrieval key. The "bad luck" escape hatch prevents the agent from drawing a false
lesson from noise.

## Storing lessons

Save each reflection with the task type, outcome, date and a pointer to the trace, and embed `applies_when + lesson` so
it can be found by similar tasks later. Reflections are a natural fit for the vector memory from 6.7, with a type of
`lesson`.

## Using lessons on the next attempt

Before starting a task, retrieve the top two or three lessons whose `applies_when` matches and put them in the prompt:

```text
<lessons_from_past_attempts>
- When booking multi-city flights, check visa requirements before searching fares (failed 2026-03-04: booked a
  flight to a country needing a visa the user lacked).
</lessons_from_past_attempts>
```

Keep the block short. Ten stale lessons are noise, and a context budget (6.1) applies here as everywhere.

## Does it help?

Reflection feels clever, so measure it. Run your eval set (7.9) on the same tasks **with and without** the lesson
memory and compare success, steps and cost. Common outcomes:

- It helps on recurring task types with clear failure modes (tool-use mistakes, missed checks).
- It does nothing on one-off tasks.
- It can **hurt**: a confident wrong lesson ("always use the cheaper API") is applied where it does not belong. This is the
  main risk, and it is why the next point matters.

## Keeping evidence

Every lesson should link to the trace it came from, so a person can check it. Review the highest-impact lessons
(the ones retrieved most often) periodically, and retire any that evidence does not support. Where a lesson keeps
recurring, promote it to a rule in the playbook (6.11) after review, and delete the individual reflections that it
replaces.

## Try it

An agent that books meeting rooms double-booked a room twice in a week. Its reflection says: "Lesson: always
double-check." Why is that a poor lesson, and what would a good one look like?

<details>
<summary>Reference</summary>

"Double-check" is vague: it says nothing about what to check or when, so it cannot change behaviour. A good lesson:
"Before confirming a booking, re-read the room's calendar after the write call and compare the returned
slot with the requested one; the availability search result can be stale within seconds (failed on runs 812, 840)."
It names the action, the reason and the evidence.
</details>

## Check yourself

1. What is the purpose of the `applies_when` field in a reflection?

<details>
<summary>Answer</summary>

It describes the kind of task the lesson is relevant to, and it is what you embed and search on so the lesson is
retrieved only when a similar task comes up.
</details>

2. How would you test whether reflection memory actually improves the agent?

<details>
<summary>Answer</summary>

Run the same evaluation tasks with and without the stored lessons and compare success rate, steps and cost, ideally
on tasks that are new to the lessons so you do not just measure memorisation.
</details>

3. How can reflection make an agent worse?

<details>
<summary>Answer</summary>

It can store a confident but wrong lesson drawn from bad luck or a one-off case, then apply it where it does not hold.
Keeping evidence, requiring specific lessons and reviewing frequently used ones limits this.
</details>
