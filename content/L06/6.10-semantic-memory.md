# Semantic memory: distilled facts and patterns

After a week with a new colleague you do not remember every lunch, but you know they prefer tea, hate morning
meetings and always read the document before the call. You have distilled many episodes into general knowledge.
**Semantic memory** does the same for an agent: it turns piles of events into a compact set of facts and patterns
that are cheap to store, cheap to inject and stable over time.

## From many episodes to one fact

Episodic memory (6.9) keeps what happened. Semantic memory keeps what is generally true.

| Episodes | Distilled fact |
|----------|----------------|
| Booked window seats on 5 of 5 flights | Prefers window seats |
| Asked for shorter answers three times | Likes brief replies |
| Ordered Jain food on every request | Follows a Jain diet |

Distilling saves tokens (one line instead of five stories) and survives the point where old episodes are archived.

## Behavioural patterns

Facts about preference are one kind. **Patterns** describe how someone works: "orders late in the evening", "checks
prices on two sites before booking", "needs code samples, not theory". Store a pattern with the evidence behind it:

```python
fact = {
    "user_id": "u_42",
    "statement": "Prefers window seats on flights.",
    "kind": "preference",
    "confidence": 0.9,              # grows with consistent evidence
    "evidence_count": 5,
    "evidence_ids": ["ep_0301", "ep_0309", "ep_0322", "ep_0402", "ep_0410"],
    "first_seen": "2026-03-01", "last_confirmed": "2026-04-10",
}
```

Confidence and evidence count let you act sensibly: use a pattern seen five times as a default, and one seen once only
as a hint.

## Consolidation jobs

Distillation is a background job, not part of the live reply. Run it nightly or after every N sessions:

1. Fetch episodes since the last run.
2. Ask a model to propose new facts and updates to existing ones, given the current fact list.
3. For each proposal, require evidence ids. Reject proposals that cite none.
4. Apply: add new facts, raise confidence on confirmed ones, lower or retire those the new evidence contradicts.

```python
CONSOLIDATE = """You maintain a list of stable facts about a user. Given existing facts and recent session
summaries, return JSON edits: add, update (with new confidence), or retire. Every edit must cite the
session ids that support it. Do not state anything the sessions do not support."""
```

This mirrors how people consolidate memory during sleep, and it is why the job is sometimes called "sleep-time
compute".

## Provenance and correction

A semantic memory is a belief about a person, and beliefs can be wrong. Keep the evidence links, show the user what
the agent believes ("Here is what I've learned about your preferences"), and let them correct or delete items. A user
correction should beat any inferred fact and should be marked so a later consolidation run cannot overwrite it.
Sensitive inferences (health, religion, finances) deserve extra care; do not infer them unless the product needs it,
and if you store them, treat them under the privacy rules in 8.8.

## Facts, episodes and entities together

Each layer answers a different question:

- *Entity memory* (6.8): exact attributes of a named thing.
- *Episodic memory* (6.9): what happened, when.
- *Semantic memory* (this lesson): what is generally true and how this user behaves.

Retrieval picks among them (6.13). Semantic facts are usually cheap enough to include a short list by default.

## Try it

You have these session summaries: Mar 1, "asked for a short answer"; Mar 8, "asked for a short answer"; Mar 15, "asked
for a detailed walkthrough of a new topic". Should the agent record "prefers brief replies"? How?

<details>
<summary>Reference</summary>

Not as an unconditional fact. Two of three sessions support brevity, but the third shows depth is wanted for new
topics. Record a conditional pattern with moderate confidence: "Prefers brief replies for familiar topics; wants
detail for new ones (3 sessions)". Citing all three sessions makes it checkable and lets a later run refine it.
</details>

## Check yourself

1. Why distil episodes into facts at all?

<details>
<summary>Answer</summary>

Facts are far smaller and stay useful after the original episodes are archived or forgotten, so they cost fewer
tokens to inject and last longer.
</details>

2. What should a consolidation job require for every fact it writes?

<details>
<summary>Answer</summary>

Evidence: references to the sessions or episodes that support it, so the fact can be checked, trusted at the right
level and corrected.
</details>

3. If a user corrects a stored belief, how should the system treat it?

<details>
<summary>Answer</summary>

The correction takes priority over inferred facts and is flagged as user-provided, so later automatic consolidation
cannot overwrite it.
</details>
