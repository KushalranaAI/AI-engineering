# Summary memory: abstractive, progressive, summary buffer

When old turns fall off the edge of a window (6.5), they are gone. **Summary memory** keeps a compressed version of
them instead. You trade exact wording for a much smaller footprint, which is often a good deal for a conversation
and a dangerous one for numbers.

## Abstractive summaries

An **extractive** summary copies the important sentences. An **abstractive** summary rewrites the content in new,
shorter words, which is what an LLM does naturally. For memory, abstractive is usually better because it can merge
ten turns into two lines.

```python
SUMMARISE = """Summarise the conversation so far in under 120 words. Keep: the user's goal, decisions made,
constraints, names, numbers and unresolved questions. Drop pleasantries and anything already resolved.

Existing summary:
{summary}

New messages:
{messages}

Updated summary:"""
```

The instruction does the real work. A summary prompt that does not say what to keep will happily keep the jokes and
drop the budget.

## Progressive summarisation

Re-summarising the whole history every time is expensive. **Progressive** (rolling) summarisation folds only the
newest batch into the existing summary:

```python
def fold(summary: str, new_msgs: list[dict]) -> str:
    return llm(SUMMARISE.format(summary=summary, messages=render(new_msgs)), temperature=0)
```

The summary stays a roughly constant size however long the conversation runs. The cost is one extra model call every
few turns, which you can make with a small, cheap model and run after the reply is sent so the user never waits for it.

## Summary buffer

The best-known pattern combines the two ideas: a **summary of older turns plus the most recent turns verbatim**, with
a token limit that decides when the oldest verbatim turns get folded into the summary.

```python
def build_history(summary, recent, limit, count):
    while sum(count(m["content"]) for m in recent) > limit:
        oldest = recent.pop(0)
        summary = fold(summary, [oldest])
    return summary, recent
# prompt: system + "Conversation so far: " + summary + recent messages
```

Recent turns stay exact, which is what follow-up questions ("and the second one?") depend on; older ones are
remembered in outline.

## What summaries lose

Summaries are lossy, and the loss is not random.

- **Drift.** A summary of a summary of a summary slowly changes meaning, like a game of telephone.
- **Dropped specifics.** Ids, amounts, dates and names are the first things to go, and the ones most needed later.
- **Invention.** A model asked to summarise can add a plausible detail that was never said.

Defences: keep exact data in **structured fields** outside the prose (an order id, a budget, a date; see the
entity memory in 6.8), tell the summariser to keep numbers and names verbatim, and spot-check summaries against the
transcript. A cheap test: ask questions whose answers are in the dropped turns and see if the summary answers them.

## When to summarise

Trigger on a **token threshold** (history over 3,000 tokens) or a **topic change**, not on every turn. Run it in the
background. And always keep the raw transcript in storage, even when the prompt only carries the summary; you will
want it for debugging, for the vector memory in 6.7 and for episodes in 6.9.

## Try it

A user planning a wedding has chatted for 40 turns. The summary says: "User planning a wedding in Jaipur, budget
around 12 lakh, guest count about 250." At turn 41 they ask, "What was the exact budget I gave for decor?" Why might
the assistant fail, and what would you change?

## Check yourself

1. What is the difference between a progressive summary and a summary buffer?

<details>
<summary>Answer</summary>

A progressive summary describes how it is updated: each batch of new turns is folded into the existing summary. A
summary buffer describes what goes in the prompt: that summary plus the most recent turns verbatim.
</details>

2. Which kinds of information do summaries tend to lose first, and how do you protect them?

<details>
<summary>Answer</summary>

Exact numbers, ids, dates and names. Protect them by saving them in structured fields outside the summary and by
telling the summariser to keep them verbatim.
</details>

3. Why run summarisation after the reply has been sent?

<details>
<summary>Answer</summary>

It is an extra model call that the current answer does not depend on, so doing it in the background keeps it off the
user's waiting time.
</details>
