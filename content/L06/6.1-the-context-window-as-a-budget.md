# The context window as a budget

A model sees only what you send it on this call: the system prompt, the conversation so far, retrieved chunks, tool
definitions, tool results and any state you paste in. That bundle is the **context window**. Windows are now large,
often hundreds of thousands of tokens, which makes it tempting to put everything in. Don't. Treat the window like a
budget: each token costs money and latency, and it can also make the answer worse.

## More is not better

Adding text has three costs:

| Cost | What happens |
|------|--------------|
| Money | You pay for input tokens on every call, and an agent makes many calls |
| Latency | Time to first token rises with prompt length |
| Quality | Irrelevant or conflicting text pulls attention away from what matters |

The first two are easy to see. The third is the one that hurts quietly.

## How long context goes wrong

- **Context rot.** Accuracy on the same task tends to fall as the input gets longer, even when the needed fact is
  still in there. Long-context benchmarks show this across model families.
- **Distraction.** Text that looks relevant but isn't (an old version of a policy, a similar product) gets used.
- **Contradictions.** History says "the deadline is Friday", a later tool result says "Monday". The model may pick
  either one.
- **Lost in the middle.** Models tend to use facts at the start and end of a long prompt more reliably than facts
  buried in the middle.
- **Cost growth.** In an agent loop the whole history is resent every turn, so total tokens grow roughly with the
  square of the number of steps.

That last point is worth working through. Each step adds about 2,000 tokens of tool output, and the window is
resent on every call:

```
step 1:  2k   step 10: 20k   step 30: 60k
total input over 30 steps ≈ 2k × (1 + 2 + ... + 30) = 2k × 465 ≈ 930k tokens
```

A run you thought cost 60k tokens actually costs close to a million.

## Look at the real prompt

You can't manage what you can't see. Before tuning anything, log the exact payload sent to the model and measure
each section.

```python
import json, tiktoken

enc = tiktoken.get_encoding("o200k_base")  # an approximation; use your provider's token counter for exact numbers

def count(x) -> int:
    return len(enc.encode(x if isinstance(x, str) else json.dumps(x)))

def context_report(system: str, messages: list[dict], tools: list[dict]) -> dict:
    report = {"system": count(system), "tools": count(tools)}
    for m in messages:
        key = m.get("role", "?")
        if m.get("role") == "tool":
            key = "tool_results"
        report[key] = report.get(key, 0) + count(m.get("content", ""))
    report["total"] = sum(report.values())
    return report

# e.g. {'system': 1800, 'tools': 6200, 'user': 900, 'assistant': 3100, 'tool_results': 41000, 'total': 53000}
```

A report like the example above usually tells you the story at once: tool results take 77% of the window, and most
of them are old pages the agent already used.

When you read the dump, mark each piece as one of: needed now, needed later, never needed. Anything in the last two
groups is a candidate for removal or for storage outside the window.

## Splitting the budget

Give each section a rough limit, the same way you would plan memory in a service. A starting point for a 32k
working budget (you rarely want to fill the whole window):

| Section | Budget | Notes |
|---------|--------|-------|
| System instructions | 2k | Stable; cache it |
| Tool definitions | 3k | Only tools for this task |
| Retrieved knowledge | 8k | Top chunks after reranking |
| Long-term memory | 1k | A few relevant facts |
| Conversation history | 8k | Recent turns verbatim, older ones summarised |
| Tool results / working state | 8k | Current step's observations |
| Headroom for output | 2k | Reasoning and answer |

These numbers are not rules. They are a plan you can check against the report, and when one section overflows you
decide deliberately what to cut instead of letting the oldest messages fall off the end.

## Try it

Take any chat or agent app you have built. Log the full request for a long conversation (20+ turns or 15+ tool
calls). Produce a per-section token report and list the three biggest sections. For each, say whether it is needed
now, needed later, or never needed.

<details>
<summary>Reference</summary>

A typical result for a tool-using agent: tool results are the largest section (often over half), followed by
conversation history and tool definitions. Most old tool results are "needed later" at best: the agent already
extracted what it wanted, so they can be summarised or moved to external storage with an id. Tool definitions for
tools irrelevant to the current task are "never needed" on this call. Older history turns are usually "needed later"
and can be compacted into a summary that keeps goals and decisions. A good next step is to set per-section limits
and re-run the same conversation to compare answer quality and token totals.
</details>

## Check yourself

1. Why does total input grow faster than linearly in a long agent run?

<details>
<summary>Answer</summary>

Each call resends the whole history, and the history grows every step. If each step adds roughly the same amount,
the total sent across n steps is proportional to 1 + 2 + ... + n, which grows with n².
</details>

2. A fact is definitely in the prompt but the model ignores it. Name two context-related reasons.

<details>
<summary>Answer</summary>

It may be buried in the middle of a long prompt (lost in the middle), or it may be contradicted or crowded out by
similar but wrong text elsewhere (distraction or conflicting context). Very long inputs also degrade accuracy in
general.
</details>

3. What is the first thing to do when an agent's quality drops as conversations get longer?

<details>
<summary>Answer</summary>

Look at the actual payload sent to the model and measure tokens per section. Without that you are guessing; with it
you can see which part of the context grew and whether it is useful.
</details>
