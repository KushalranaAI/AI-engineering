# Managed building blocks: build or buy

Every cloud AI platform now sells more than models: managed retrieval, hosted agents, guardrails, evaluation, fine-tuning. Each one promises to save you weeks. Some do. The trick is to decide **layer by layer**, not to adopt or reject the whole platform as a package.

## What's on the shelf

| Layer | What the managed version does | Examples |
|-------|-------------------------------|----------|
| Retrieval | Ingests documents, chunks, embeds, stores and retrieves from config | Bedrock Knowledge Bases, Vertex AI Search, Azure AI Search |
| Agents / workflows | Hosts an agent loop with tools, memory and orchestration | Bedrock Agents / AgentCore, Vertex AI Agent Engine, Foundry Agent Service |
| Guardrails | Content filters, denied topics, PII redaction, grounding checks | Bedrock Guardrails, Azure AI Content Safety |
| Evaluation | Runs metric suites or LLM judges over datasets | Platform evaluation services |
| Fine-tuning | Adapts a supported base model on your data, sometimes distillation | Platform customisation jobs |

Names and features change quickly; the categories don't.

## Managed retrieval vs your own stack

A managed knowledge base is attractive: point it at a bucket, pick an embedding model, done. Compare it with the Level 4 stack on what you actually need:

| Question | Managed KB | Your own stack |
|----------|-----------|----------------|
| Custom chunking for odd documents | A few built-in strategies, sometimes a hook | Anything |
| Hybrid search, reranking, query rewriting | Some options, fixed recipe | Full control |
| Seeing *why* a passage was retrieved | Limited | Every score is yours |
| Retrieval eval depth | You can still evaluate end to end, but tuning levers are few | Tune each stage |
| Cost at your corpus size | Often includes a vector store with a minimum monthly cost | Depends on what you run |
| Time to first working version | Hours | Days |

If your documents are clean and your questions ordinary, managed retrieval may simply pass your evals. If you've already found that your corpus needs custom parsing, it probably won't.

## Managed agents

Hosted agent runtimes assume a particular shape: tools described in their schema, memory in their store, orchestration by their loop. That's fine for standard tool-calling assistants. It gets awkward when you need custom control flow, unusual approval steps, or detailed traces of every decision, which is exactly what you built by hand in Level 5.

## Guardrails, evals and fine-tuning

- **Managed guardrails** are good at broad content categories and PII redaction. They don't know your business rules. Keep them as one layer, alongside your own checks from Level 10.
- **Managed evaluation**: ask whether its metrics answer *your* questions. A generic "helpfulness" score doesn't replace the task-specific cases in your Level 7 suite.
- **Managed fine-tuning**: check which base models are allowed, where the resulting weights live, and whether you can export them. Often the custom model only runs on that platform, sometimes only on provisioned capacity, which affects cost and exit.

## Judging a candidate

Score each layer separately:

```python
CRITERIA = ["control", "transparency", "eval_depth", "cost_at_volume",
            "auditability", "portability", "time_to_value"]

def decide(layer: str, scores: dict[str, int], weights: dict[str, float]) -> str:
    total = sum(scores[c] * weights[c] for c in CRITERIA)   # scores: -2 (build wins) .. +2 (buy wins)
    return f"{layer}: {'buy' if total > 0 else 'build'} ({total:+.1f})"

print(decide("retrieval",
    {"control": -2, "transparency": -1, "eval_depth": -1, "cost_at_volume": 0,
     "auditability": 0, "portability": -1, "time_to_value": 2},
    {"control": 1.5, "transparency": 1, "eval_depth": 1, "cost_at_volume": 1,
     "auditability": 1, "portability": 1, "time_to_value": 1}))
```

The numbers are a thinking aid, not an oracle; the value is in writing the reasons down.

## Count the exit cost first

A prompt moves to another provider in minutes. A managed knowledge base's index, an agent definition in a platform's console, or a guardrail policy usually has to be rebuilt by hand. Before adopting, write one line per component: "to leave, we would need to …". If that line is long, you're taking on real lock-in; make sure the benefit is worth it.

## When buying is the honest call

- A small team with no one to own the infrastructure.
- A standard use case where the managed component already clears your quality bar.
- A compliance deadline that the managed service already meets (audit logs, certifications).
- Plumbing that doesn't differentiate your product.

A useful rule: **buy the plumbing nobody will ever notice; build the layer your users judge you on.**

## Try it

Rebuild one component of an existing app on its managed equivalent (for example, replace your Level 4 retrieval with a managed knowledge base over the same documents). Compare quality on your eval set, cost per month, and the knobs you lost.

## Check yourself

1. Why decide build or buy per layer rather than per platform?

<details>
<summary>Answer</summary>

Each layer has different value and risk. Buying managed retrieval doesn't commit you to managed agents or guardrails, and the right answer often differs between layers.
</details>

2. What should you check before adopting managed fine-tuning?

<details>
<summary>Answer</summary>

Which base models can be tuned, where the resulting weights live, whether you can export them, and what capacity (and therefore cost) the custom model requires to run.
</details>

3. Give two situations where buying a managed component is the right call.

<details>
<summary>Answer</summary>

Any two of: a small team with no owner for the infrastructure; a standard use case already meeting your quality bar; a compliance deadline the service already satisfies; plumbing that doesn't differentiate the product.
</details>
