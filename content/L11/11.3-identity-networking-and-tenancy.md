# Identity, networking and tenancy

A security reviewer looking at your AI service asks three questions. Who is allowed to call the model? Which path does the data take? Can one customer ever see another customer's data? Managed platforms let you answer all three with tools the company already trusts, but only if you set them up deliberately.

## Cloud identity instead of API keys

An API key is a long-lived shared secret. Anyone who has it is "you", it ends up in logs and laptops, and revoking it breaks everything that uses it. Cloud identity replaces it:

| Cloud | Workload identity |
|-------|-------------------|
| AWS | IAM role attached to the EC2 instance, ECS task or Lambda |
| Google Cloud | Service account attached to the workload; workload identity federation for outside callers |
| Azure | Managed identity, authorised through Microsoft Entra ID |

The code never sees a secret. The SDK fetches short-lived credentials from the environment, and they rotate automatically.

## Least privilege

Grant only the models and actions the service needs. On AWS a policy for a RAG service might look like this:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:eu-central-1::foundation-model/example.chat-model-v1",
        "arn:aws:bedrock:eu-central-1::foundation-model/example.embed-model-v2"
      ]
    }
  ]
}
```

This service can call exactly two models, in one region, and cannot create fine-tuning jobs, change guardrails or read knowledge bases. A different team gets a different role. (Converse calls are authorised by these same invoke permissions. Cross-region inference profiles need extra resources in the policy; check the docs for your setup.)

## Auditing

Regulated environments need to answer "who invoked which model, when?" months later. The control-plane audit log (CloudTrail, Cloud Audit Logs, Azure Monitor activity logs) records API calls and the identity behind them. Logging the prompts and responses themselves is a separate, opt-in feature on most platforms. Turn it on only with a clear retention policy, since those logs now contain user data.

## Private connectivity

By default your service reaches the platform's public endpoint over the internet (TLS-encrypted, but still public routing). Private connectivity keeps traffic inside the provider's network:

- **AWS:** an interface VPC endpoint (PrivateLink) for `com.amazonaws.<region>.bedrock-runtime`.
- **Google Cloud:** Private Service Connect / Private Google Access.
- **Azure:** Private Endpoints for the AI resource.

What it buys you: no public egress needed from your subnets, endpoint policies that limit which principals may use it, and a clean answer for the reviewer. What it costs: an hourly charge per endpoint per availability zone plus data processing fees, and more networking to debug (DNS is the usual culprit).

## Tenant isolation

If you serve several customers from one platform, decide how hard the walls are:

| Approach | Isolation | Cost and effort |
|----------|-----------|-----------------|
| Separate account/project per tenant | Strongest; separate quotas, keys, bills | High |
| Shared account, per-tenant roles and KMS keys | Strong for data at rest | Medium |
| Shared everything, tenant filter in code | Weakest; one bug leaks data | Low |

The most common leak is in retrieval, not the model. Every vector query must carry a tenant filter that the caller cannot override, ideally enforced by the data layer (separate indexes or row-level security) rather than an optional parameter.

```python
def search(tenant_id: str, query_vec, k: int = 5):
    # tenant_id comes from the authenticated session, never from the request body
    return index.query(vector=query_vec, top_k=k, filter={"tenant_id": tenant_id})
```

## Encryption and your own keys

Platforms encrypt stored data (fine-tuned models, knowledge bases, logs) by default with provider-managed keys. **Customer-managed keys** (KMS on AWS, Cloud KMS, Azure Key Vault) let you control and revoke the key yourself, and give each tenant its own key so deleting a key makes that tenant's data unreadable.

## Try it

Invoke a model from a private subnet with no NAT gateway or internet route, through a private endpoint. Then prove from logs that it worked and which identity made the call.

<details>
<summary>Reference</summary>

On AWS: create an interface VPC endpoint for `bedrock-runtime` in the VPC with private DNS enabled, launch an instance in a private subnet with no internet route and an instance role that allows `bedrock:InvokeModel` on one model, and run a `converse` call. It succeeds because the regional hostname resolves to the endpoint's private IPs. Confirm in CloudTrail that the event shows your role as the caller and, if VPC endpoint logging details are present, the endpoint id. As a negative test, remove the endpoint and the call should time out.
</details>

## Check yourself

1. Why is a role attached to the workload safer than an API key in an environment variable?

<details>
<summary>Answer</summary>

The role yields short-lived, automatically rotated credentials scoped by policy, tied to an auditable identity. A key is long-lived, shared, easily leaked, and revoking it breaks every user.
</details>

2. Where do multi-tenant AI systems most often leak data, and how do you prevent it?

<details>
<summary>Answer</summary>

In retrieval: a query that returns another tenant's chunks. Prevent it by taking the tenant id from the authenticated session and enforcing the filter in the data layer (separate indexes, row-level security), not as an optional parameter.
</details>

3. What does private connectivity cost you?

<details>
<summary>Answer</summary>

Endpoint hourly and data-processing charges, plus more networking complexity, especially private DNS and endpoint policies to debug.
</details>
