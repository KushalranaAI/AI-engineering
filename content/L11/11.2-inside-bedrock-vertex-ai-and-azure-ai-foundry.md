# Inside Bedrock, Vertex AI and Azure AI Foundry

The three big cloud AI platforms look different on the surface: different consoles, different SDKs, different names. Underneath they are the same product. Once you see the common shape, a document from any of them reads as a variation on something you know.

## The shape they share

Each platform gives you:

1. **A model catalog** of closed models (from the cloud's own lab and partners) and open-weight models.
2. **One invocation style** for all of them, plus sometimes a provider-native format.
3. **One identity system**: your cloud IAM decides who may call which model.
4. **One network boundary**: calls stay inside your cloud account and can use private endpoints.
5. **One bill**: usage lands on the cloud invoice, with the cloud's tagging and budgets.

## Same ideas, different words

| Idea | Bedrock (AWS) | Vertex AI (Google Cloud) | Azure AI Foundry (Microsoft) |
|------|---------------|--------------------------|------------------------------|
| Catalog | Model catalog / model access | Model Garden | Model catalog |
| Unified chat call | Converse API | Gen AI SDK `generate_content` | Model inference / chat completions |
| Identity | IAM roles and policies | Service accounts, IAM | Microsoft Entra ID, managed identity |
| Reserved capacity | Provisioned throughput | Provisioned throughput | Provisioned throughput units |
| Isolation unit | AWS account | Project | Subscription / resource / project |

Names and features change, so treat this table as a map, not a spec.

## Reading a catalog like a model card

For each model you care about, check:

- **Provider and version.** Is the id pinned to a dated snapshot, or an alias that moves?
- **Regions.** Is it in *your* region? Is it only available through cross-region routing?
- **Lifecycle.** Platforms mark versions as legacy and publish retirement dates. Put those dates in your calendar.
- **Features.** Tool calling, structured output, image input, prompt caching and batch can each differ from the vendor's own API.

## Calling a model on Bedrock

Bedrock's Converse API uses one request format for every chat model in the catalog. Authentication comes from your AWS credentials (a role on the machine), not an API key in code.

```python
import boto3

client = boto3.client("bedrock-runtime", region_name="eu-central-1")

def ask(model_id: str, question: str) -> dict:
    resp = client.converse(
        modelId=model_id,
        messages=[{"role": "user", "content": [{"text": question}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0.2},
    )
    return {
        "text": resp["output"]["message"]["content"][0]["text"],
        "usage": resp["usage"],              # inputTokens, outputTokens, totalTokens
        "latency_ms": resp["metrics"]["latencyMs"],
    }

for model in ["example.closed-model-id", "example.open-weight-model-id"]:
    print(model, ask(model, "Summarise our refund policy in two sentences."))
```

Swapping models is a string change: same auth, same network path, same bill. That is the main thing a platform buys you. The equivalent on Vertex uses the Google Gen AI SDK with `vertexai=True`, a project and a location; on Foundry you point an inference client at your resource's endpoint and authenticate with Entra ID.

Where a platform also offers a **provider-native** format (for example sending a vendor's own request body through `invoke_model`), it is useful for features the unified API doesn't expose yet, at the cost of portability within the catalog.

## Back-of-envelope comparison

Prices below are invented for illustration; read the real price page for your region.

| Model (example) | Input $/M tok | Output $/M tok | Cost for 1,000 calls of 1,500 in / 300 out |
|-----------------|---------------|----------------|--------------------------------------------|
| Large closed model | 3.00 | 15.00 | 1.5M × 3 + 0.3M × 15 = **$9.00** |
| Mid open-weight model | 0.50 | 1.50 | 1.5M × 0.5 + 0.3M × 1.5 = **$1.20** |

Whether the cheaper model is good enough is an eval question, not a pricing question.

## What the platform does not give you

The platform hosts and meters models. It does not write good prompts, design retrieval, decide what "correct" means, or make your product behave well. Everything from Levels 3 to 8 is still your job; you have just moved where the model runs.

## Try it

Pick one cloud catalog and send the same eval prompt to one proprietary model and one open-weight model there. Record answer quality (your rubric), latency and cost per thousand calls.

<details>
<summary>Reference</summary>

A minimal script loops over 20 eval questions, calls `converse` for each model, stores `usage`, `metrics.latencyMs` and the text, then scores answers with your Level 7 judge or by hand. Multiply the summed input and output tokens by the region's list prices and scale to 1,000 calls. A typical finding: the open model is several times cheaper and somewhat faster, close on easy questions, and weaker on multi-step or long-context ones. The decision depends on which kind dominates your traffic.

## Check yourself

1. What stays the same when you swap between two models in one platform catalog?

<details>
<summary>Answer</summary>

Authentication (IAM), the network path, the billing and usually the request format. Only the model id (and possibly some feature support) changes.
</details>

2. Why check a catalog entry's region and lifecycle, not just its benchmark scores?

<details>
<summary>Answer</summary>

A model you can't use in your permitted region is useless to you, and a version scheduled for retirement will force a migration and re-evaluation on the platform's timetable.
</details>

3. When might you use a provider-native request format instead of the unified API?

<details>
<summary>Answer</summary>

When you need a model feature the unified API does not yet expose. You trade away the ability to swap models in the catalog with just an id change.
</details>
