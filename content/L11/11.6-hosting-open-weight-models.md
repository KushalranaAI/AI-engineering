# Hosting open-weight models

"We'll use an open model" can mean anything from calling a per-token API to racking your own GPUs. Think of it as a ladder: each rung up gives you more control and lower cost at high volume, and asks for more engineering in return.

## The hosting ladder

| Rung | What you do | Examples | You pay for |
|------|-------------|----------|-------------|
| Model hub | Find, read and download weights | Hugging Face | Nothing (storage, bandwidth) |
| Serverless inference API | Call a hosted open model per token | Together, Fireworks, Groq, Replicate; also the cloud platforms' catalogs | Tokens |
| GPU compute platform | Bring your own serving code; they schedule and scale GPUs | Modal, Baseten, RunPod | GPU-seconds or hours |
| Your own servers | Run everything on GPUs you rent or own | EC2/GKE/AKS GPU nodes, on-prem | GPU hours, plus your time |

## Picking a checkpoint you can trust

On a hub, read the **model card**: who published it, what it was trained for, evaluation results, and known limits. Then check:

- **Licence.** Apache 2.0 and MIT are permissive; some families have custom licences with usage restrictions or user-count thresholds. Gated models require accepting terms first.
- **Provenance.** Prefer the original publisher's repository over random re-uploads. A fine-tune from an unknown account may be anything.
- **File format.** Prefer `safetensors`. Older pickle-based checkpoints can execute code when loaded.
- **Quantised variants.** Note who made them and how; quality can differ.

## Serving it yourself with vLLM

A naive server runs one request at a time and leaves the GPU mostly idle, because generating each token reads all the weights from memory. Serving engines such as **vLLM** and **TGI** fix that with:

- **Continuous batching:** new requests join the running batch at each step instead of waiting for the batch to finish.
- **Paged KV cache:** the attention cache is stored in fixed-size blocks, so memory isn't wasted on padding and many sequences fit at once.
- **Prefix caching:** requests that share a prompt prefix (a long system prompt) reuse its cached computation.

```bash
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 8192 --gpu-memory-utilization 0.90
```

That starts an OpenAI-compatible server on port 8000, so existing client code only needs a new base URL:

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="unused")
r = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "Explain continuous batching in one sentence."}],
)
print(r.choices[0].message.content)
```

**Ollama** is the easy local option for laptops and prototypes; vLLM or TGI is the usual choice for serving real traffic.

## Sizing the GPU

Memory decides which GPU you need:

```
weights   = parameters × bytes per parameter
            8B × 2 bytes (bf16) ≈ 16 GB;  8B × 0.5 bytes (4-bit) ≈ 4-5 GB
KV cache  = 2 × layers × kv_heads × head_dim × bytes × tokens
            Llama-3-8B-like: 2 × 32 × 8 × 128 × 2 B ≈ 128 KB per token
            8,192-token context ≈ 1 GB per sequence
```

So an 8B model in bf16 on a 24 GB GPU leaves room for only a handful of full-length sequences at once; a 48 or 80 GB card serves far more concurrent users. Long contexts eat memory fast.

## Per token vs per GPU-hour

Example numbers, for illustration only:

```
GPU rental:            $2.00 / hour
Batched throughput:    1,500 output tokens/s at full load  → 5.4M tokens/hour
Cost at 100% busy:     $2.00 / 5.4M ≈ $0.37 per M output tokens
Cost at 15% busy:      ≈ $2.47 per M output tokens
Serverless price for a similar model: say $0.60 per M tokens
```

Renting wins only when the GPU is kept busy. Steady high traffic favours GPU-hours; spiky or low traffic favours per-token pricing.

**Cold starts:** scale-to-zero platforms save money when idle, but the first request must wait while a container starts and loads several gigabytes of weights, which can take tens of seconds or more. Keep one warm replica for interactive traffic.

## What you gain, what you owe

Running open weights yourself gets you steady unit costs at high volume, data that stays inside your own network, and a model that only changes when you decide. In return you own uptime, scaling, security patches, and upgrades. And never assume open or closed is better: run your eval set on both before deciding.

## Try it

Serve one small open model (around 1-8B parameters) three ways: through a serverless provider, on a GPU platform, and locally with Ollama or vLLM. Compare setup time, latency for the same 20 prompts, and the estimated cost of 1,000 requests.

<details>
<summary>Reference</summary>

Serverless: minutes to set up (API key, base URL), low latency, cost = tokens × listed price. GPU platform: an hour or so to wrap vLLM in their deployment format; the first call may hit a cold start; cost = GPU-seconds used, which for 1,000 sequential requests is usually higher than serverless unless you batch them. Local: free per request but slow on a laptop and unsuitable for shared traffic. Expect serverless to win for this small, bursty test, and the GPU platform to win only for sustained, concurrent load.
</details>

## Check yourself

1. Why does continuous batching raise throughput so much?

<details>
<summary>Answer</summary>

Decoding one sequence is limited by reading the weights from memory; batching lets many sequences share each weight read. Continuous batching keeps the batch full by adding new requests at every step instead of waiting for the slowest one.
</details>

2. Roughly how much GPU memory do the weights of a 70B model need in bf16?

<details>
<summary>Answer</summary>

About 140 GB (70B × 2 bytes), before any KV cache, so it needs several GPUs or quantisation.
</details>

3. When does paying per GPU-hour beat paying per token?

<details>
<summary>Answer</summary>

When traffic keeps the GPU busy enough that the hourly rate divided by tokens served falls below the per-token price, which in practice means steady, high-volume load.
</details>
