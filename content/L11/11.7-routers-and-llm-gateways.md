# Routers and LLM gateways

Once two teams use three providers, you get three sets of keys, three dashboards, three retry implementations and nobody knows the total bill. An **LLM gateway** (or router) puts one endpoint in front of all of them. It is useful, and it is also one more thing on the critical path.

## What a gateway does

- **Holds the credentials** for every provider, so apps don't.
- **Accepts one request format** (usually OpenAI-style chat completions) and translates it per provider.
- **Routes** each request to a model by rule.
- **Fails over** when a provider errors, times out or throttles.
- **Controls spend** with per-team keys, budgets and rate limits.
- **Records** usage, latency, errors and cost in one place.

## Hosted or self-hosted

| Option | Examples | Trade-off |
|--------|----------|-----------|
| Hosted router | OpenRouter, Portkey | Nothing to run; your prompts pass through another company |
| Self-hosted proxy | LiteLLM proxy | You run it; data stays in your network |
| Cloud platform routing | Bedrock / Vertex / Foundry features | Inside your cloud; limited to that catalog |
| Framework gateway | Built into an agent or app framework | Convenient; tied to the framework |

Regulated teams usually self-host or rely on the cloud platform for the same reasons covered in 11.1's comparison of consumption paths.

## Routing and failover in code

LiteLLM's Python `Router` shows the idea. Two deployments share a logical name, with a fallback group if both fail:

```python
from litellm import Router

router = Router(
    model_list=[
        {"model_name": "chat", "litellm_params": {
            "model": "bedrock/example.chat-model-v1", "aws_region_name": "eu-central-1"}},
        {"model_name": "chat-backup", "litellm_params": {
            "model": "azure/example-deployment", "api_base": "https://example.openai.azure.com",
            "api_key": "os.environ/AZURE_API_KEY"}},
    ],
    fallbacks=[{"chat": ["chat-backup"]}],
    num_retries=1,
    timeout=20,
)

resp = router.completion(model="chat", messages=[{"role": "user", "content": "Hello"}])
print(resp.model, resp.usage)
```

The app asks for `"chat"`; the router decides who answers. Typical rules on top of this: send long-context requests to a model with a bigger window, cap cost per task type, keep EU tenants on EU regions, or send risky categories to the strongest model.

## Spend controls

A self-hosted proxy can issue **virtual keys**: one per team or feature, each with its own budget, allowed models, and rate limit. When the search team's batch job goes wild, it hits its own ceiling instead of exhausting the shared quota that the customer-facing chat depends on.

## The gateway is now critical

Every model call now depends on the gateway. Treat it like any tier-one service:

- Run at least two replicas behind a load balancer, with health checks.
- Give it its own timeouts, shorter than the client's.
- Have a **bypass**: a config flag that lets the app call one provider directly if the gateway is down.
- Watch the latency it adds (should be a few milliseconds, not hundreds).

## What a gateway can't hide

One request format does not make providers interchangeable:

| Difference | Effect |
|------------|--------|
| Tool-calling formats and reliability | A tool schema that works on one model fails or is ignored on another |
| Structured output support | Strict JSON schema mode on one, best-effort on another |
| Context and output limits | A request that fits one model is rejected by the fallback |
| Prompt behaviour | A prompt tuned for model A is worse on model B |

So a fallback model needs its own eval run, and ideally its own prompt version.

## Caching at the gateway

The gateway sees every request, so it's a natural place for exact-match and semantic caches. Be strict about exclusions: never serve cached answers for requests containing personal data, user-specific context, tool calls with side effects, or anything time-sensitive. Scope cache keys by tenant.

## When it earns its place

Worth it: several providers, several teams, spend worth governing, or a real need for failover. Not worth it: one team, one provider, modest spend. Then a thin wrapper in your code (as in Level 9) is the honest answer.

And remember: **changing a routing rule changes which model answers your users** with no application code change. Put routing config through the same eval gate as prompts.

## Try it

Route traffic for two providers through one gateway (LiteLLM proxy or Router works). Break the first provider on purpose by giving it a wrong model id or an unreachable endpoint, and confirm the fallback answers within your latency budget.

<details>
<summary>Reference</summary>

Configure two deployments and a fallback as above, with a short timeout on the primary (e.g. 5 seconds) and `num_retries` set low. Break the primary and send 20 requests. Check that every request succeeds, that `resp.model` names the backup, and measure p95 latency: it should be roughly the primary's failure time plus a normal backup call. If the primary *hangs* rather than errors, the timeout dominates; that is why the gateway timeout must sit well inside your total budget. Then run your eval subset against the backup to see what quality your users get during an outage.
</details>

## Check yourself

1. Why does a gateway need a bypass plan?

<details>
<summary>Answer</summary>

It sits on the critical path of every model call. If it fails, everything fails, so you need a way to call a provider directly while it is restored.
</details>

2. Name two provider differences a gateway can't hide.

<details>
<summary>Answer</summary>

Any two of: tool-calling formats and reliability, structured output support, context and output limits, and how a given prompt performs on each model.
</details>

3. Why should routing configuration go through the eval gate?

<details>
<summary>Answer</summary>

A routing change swaps the model that answers users, which can change quality as much as a model or prompt change, without any code changing.
</details>
