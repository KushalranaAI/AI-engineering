# Portability and migration

Sooner or later you will move a workload: a model is retired, a cheaper one appears, procurement switches clouds, or a customer demands a region your platform doesn't serve. Whether that takes a week or a quarter is decided long before, by how you built the system.

## What travels and what doesn't

| Travels easily | Travels with effort | Barely travels |
|----------------|---------------------|----------------|
| Application code behind an abstraction | Prompts (need re-tuning per model) | Managed knowledge base indexes |
| Eval datasets and judge rubrics | Embeddings (must be regenerated with the new model) | Agent definitions in a platform console |
| Raw documents and metadata | Fine-tuning data (but not the tuned weights, often) | Guardrail policies in a platform format |
| Traces you exported | Gateway routing rules | Platform-specific APIs used deep in the code |

Your **eval suite** is the most portable and most valuable asset: it is how you prove the new setup is as good as the old one.

## Keep an abstraction in place

Application code should ask for a capability, not a vendor:

```python
# llm.py — the only module that knows about providers
from dataclasses import dataclass
import yaml

@dataclass
class ModelConfig:
    provider: str       # "bedrock" | "vertex" | "azure" | "openai_compatible"
    model_id: str
    region: str | None = None
    prompt_version: str = "prod"

def load(task: str) -> ModelConfig:
    with open("models.yaml") as f:
        return ModelConfig(**yaml.safe_load(f)[task])

def complete(task: str, messages: list[dict]) -> str:
    cfg = load(task)
    client = CLIENTS[cfg.provider]          # thin adapters, one per provider
    return client.chat(cfg, messages)
```

```yaml
# models.yaml — a model swap is a change here, reviewed and eval-gated
answer:    { provider: bedrock, model_id: example.chat-model-v1, region: eu-central-1 }
summarise: { provider: openai_compatible, model_id: example-open-8b }
```

A gateway (11.7) can play the same role. Either way, the rule is: no vendor SDK imports outside one module.

## The real cost of lock-in

Price is the obvious cost. The others matter more:

- **Model availability:** you get only what your platform's catalog offers in your region.
- **Feature pace:** managed catalogs often trail the model makers' own APIs by days to months.
- **Negotiating position:** if you can't leave, you can't negotiate.
- **Proof of safety:** moving means repeating security review, data-handling sign-off and evals.

## Migration is an evaluation exercise

Plan a move like this:

```
1. Freeze a baseline: run the full eval suite on the current system; record quality, latency, cost.
2. Rebuild on the target: same documents, re-embedded; prompts adapted; same eval suite.
3. Compare offline; fix gaps (often prompt tweaks or chunking differences).
4. Shadow traffic: send a copy of live requests to the new stack, compare outputs, users see the old one.
5. Canary: route 5% → 25% → 100% through the gateway, watching online metrics.
6. Keep the old path warm until the new one has run cleanly for an agreed period; then retire it.
```

Each step has a numeric pass bar decided in advance, not "looks fine".

## Catalog lag and deprecation

Platforms retire model versions on their own schedule, often with a few months' notice. Defend against it:

- Pin dated model versions; never rely on a moving alias in production.
- Track retirement dates for every model id in `models.yaml`, with a reminder well ahead.
- Keep an evaluated **second choice** for each task, so a forced migration is a config change plus a confirmation run.

## Two platforms, honestly

Running two platforms in parallel behind a gateway buys resilience against an outage or a catalog gap, access to the best model per task, and bargaining power. It costs two security reviews, two sets of quotas and budgets, two eval runs per change, and two bodies of operational knowledge. It's justified for critical workloads or real regional needs; for most teams, one platform plus a tested exit plan is the better deal.

## Try it

Write the exit plan for your current app: list each component, where it lives, what it would take to move it to another platform, and how you'd prove the move didn't hurt quality.

## Check yourself

1. Why is the eval suite the most important thing to keep portable?

<details>
<summary>Answer</summary>

It is the evidence that the migrated system is at least as good as the old one. Without it, a migration is a guess.
</details>

2. Why pin dated model versions instead of using aliases?

<details>
<summary>Answer</summary>

An alias can point to a new model at any time, changing behaviour without a release. A pinned version only changes when you change it, after evaluation.
</details>

3. What does running two platforms in parallel actually cost?

<details>
<summary>Answer</summary>

Duplicated security review, quotas, budgets, evaluation on every change, and operational knowledge, on top of the gateway that switches between them.
</details>
