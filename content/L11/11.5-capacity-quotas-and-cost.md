# Capacity, quotas and cost

On a managed platform, capacity is not infinite and not automatic. Each account gets quotas per model and region, and raising them is an approval process. Cost is easier to see than on a shared API key, but only if you tag and budget it. This lesson is about sizing both before launch day.

## On-demand vs provisioned

| | On-demand | Provisioned / reserved throughput |
|---|---|---|
| Pricing | Per input and output token | Per hour per capacity unit, often with a 1- or 6-month commitment |
| Limits | Shared quotas (requests and tokens per minute) | Dedicated capacity sized by the units you buy |
| Good for | Spiky or small traffic, experiments | Steady high traffic, latency guarantees, some custom models |
| Risk | Throttling at peak | Paying for idle capacity |

Committed capacity changes both the price curve and the rate limit: you stop competing with other customers for the shared pool.

## Reading quotas

Typical quota dimensions (names differ per platform):

- **Requests per minute** per model per region.
- **Tokens per minute**, sometimes counting input and output differently, sometimes reserving `max_tokens` up front, so an oversized `max_tokens` eats quota you never use.
- **Concurrent requests** for long or streaming calls.
- Separate, often lower, limits for new models and smaller regions.

Do the arithmetic before launch:

```
peak traffic       = 40 requests/s  = 2,400 RPM
tokens per request = 2,000 in + 300 out
TPM needed         = 2,400 × 2,300 ≈ 5.5M tokens/minute
```

If the default quota is a fraction of that, you need a quota request with evidence: current traffic graphs, growth forecast, and what happens to the business if requests are throttled.

## Handling bursts

Don't assume the platform will absorb a spike. Design for it:

- **Queue** non-interactive work (summaries, enrichment) and drain it at a controlled rate.
- **Backpressure**: when you're near the limit, reject or delay low-priority traffic early instead of letting everything time out.
- **Batch endpoints** for offline jobs: usually cheaper and on separate quotas.
- **Retry with jittered backoff** on throttling errors, with a cap.

## Cost per request, end to end

The model call is rarely the only charge.

```python
PRICES = {  # example prices, USD — replace with your region's price sheet
    "chat_in": 1.00 / 1e6, "chat_out": 4.00 / 1e6,
    "embed_in": 0.02 / 1e6, "rerank_per_query": 0.001,
    "guardrail_per_1k_chars": 0.0005,
}

def cost_per_request(q_tokens=30, ctx_in=2000, out=300, guard_chars=3000):
    return (
        q_tokens * PRICES["embed_in"]
        + PRICES["rerank_per_query"]
        + ctx_in * PRICES["chat_in"] + out * PRICES["chat_out"]
        + guard_chars / 1000 * PRICES["guardrail_per_1k_chars"]
    )

print(f"${cost_per_request():.4f} per request")   # ≈ $0.0057
```

In this example the model call is $0.0032, and the reranker and guardrail add nearly 80% on top of it. Small per-request components matter at volume.

## Attribution and budgets

A shared API key gives you one number on one invoice. A platform lets you split it:

- Use **separate accounts/projects** or **cost allocation tags** (on AWS, application inference profiles can carry tags) per team, feature or tenant.
- Set **budgets with alerts** at, say, 50%, 80% and 100% of the monthly figure, plus a daily anomaly alert.
- Add an in-app spend cap per request and per user, because the billing alert arrives hours later. A runaway agent loop should be stopped by your code, and confirmed by the budget alert.

## Which pricing model wins

Example workload: 200,000 requests a day, 2,000 input and 300 output tokens each. All prices are illustrative.

| Option | Assumption | Monthly cost |
|--------|------------|--------------|
| On-demand closed model | $1/M in, $4/M out | 200k × 30 × ($0.002 + $0.0012) ≈ **$19,200** |
| Provisioned throughput | 2 units at $15/hour | 2 × 15 × 720 ≈ **$21,600** |
| Open-weight model, self-hosted | 2 GPUs at $2.50/hour + ~$3,000 of engineer time | 2 × 2.5 × 720 + 3,000 ≈ **$6,600** |

At this volume provisioned capacity only wins if you need its guaranteed throughput or latency. Self-hosting wins on price *if* the open model passes your evals and someone can run it. At a tenth of the traffic, on-demand wins easily. Always price at your real volume, not the example on the pricing page.

## Try it

Take a week of your app's real (or realistic) traffic logs. Price it three ways: on-demand, committed capacity, and an open-weight model on rented GPUs. Find the daily volume where each option becomes cheapest.

<details>
<summary>Reference</summary>

From the logs, compute requests per day and average input and output tokens, plus the peak-to-average ratio. On-demand cost is linear in volume. Provisioned and self-hosted are step functions: a fixed cost per unit or GPU, sized for *peak* load, plus fixed ops effort for self-hosting. Plot all three against volume; the crossover points are where the lines meet. Typical shape: on-demand cheapest at low volume, self-hosted cheapest at high steady volume, provisioned justified mainly by latency or throughput guarantees. Note the peak ratio: spiky traffic pushes the crossovers higher because fixed capacity sits idle.
</details>

## Check yourself

1. Why might a large `max_tokens` setting cause throttling even if responses are short?

<details>
<summary>Answer</summary>

Some platforms reserve tokens-per-minute quota based on `max_tokens` when the request starts, so an oversized value consumes quota that the short response never uses.
</details>

2. Why add an in-app spend cap if you already have a cloud budget alert?

<details>
<summary>Answer</summary>

Billing data and alerts lag by hours. A per-request or per-user cap in code stops a runaway loop immediately; the budget alert is the backstop.
</details>

3. Why must fixed-capacity options be sized for peak rather than average traffic?

<details>
<summary>Answer</summary>

Requests at peak still have to be served. Capacity bought for the average would throttle at peak, so you pay for capacity that sits idle off-peak, which raises the effective price per token.
</details>
