# Three ways to get a model

Until now you have probably called a model the easy way: sign up, get an API key, `pip install` the vendor SDK. Plenty of companies can't do that. A bank's security team will ask where the prompt goes, who can read it, which country it is processed in, and how access is revoked when you leave. The answers depend far more on *how* you consume the model than on *which* model it is.

## The three paths

| Path | What it looks like | Typical example |
|------|--------------------|-----------------|
| **Vendor public API** | You call the model maker's endpoint with an API key | OpenAI API, Anthropic API, Gemini API |
| **Managed platform in your cloud** | The same (or similar) models, invoked inside your AWS, Azure or Google Cloud account | Amazon Bedrock, Azure AI Foundry, Vertex AI |
| **Open weights** | You download the weights; you or an inference provider runs them | Llama, Qwen, Mistral, Gemma on vLLM, or on Together / Fireworks |

One point people miss: **open weights no longer mean running GPUs.** Bedrock, Vertex and Foundry all list open-weight models in their catalogs, and serverless inference providers sell them per token. "Open" describes the licence and portability of the weights, not who operates the hardware.

## Why regulated teams avoid the public API

A public API is usually fine technically. The problem is everything around it:

- **Identity.** A shared API key is a secret in an environment variable. The company already has a cloud identity system with roles, audit logs and offboarding. A managed platform plugs into it.
- **Contracts.** The company has an enterprise agreement and a data processing addendum with its cloud provider. Adding a new vendor means a new procurement and security review, which can take months.
- **Network.** Traffic to a public API leaves the corporate network. A managed platform can be reached over private connectivity.
- **Region.** The regulator may require processing in a specific country.

These constraints are decided before anyone runs an eval. That is why "we'll use the best model" often becomes "we'll use the best model available in our Bedrock region".

## Comparing the paths

| | Public API | Cloud platform | Open weights (self or provider) |
|---|---|---|---|
| Identity | API key | Cloud IAM roles | Varies: keys for providers, your IAM if self-hosted |
| Data handling | Vendor terms | Cloud contract you already have | Fully yours if self-hosted |
| Region choice | Limited | Per-region catalog | Anywhere you can get GPUs |
| Capacity | Vendor rate limits | Quotas, provisioned throughput | Your hardware or provider limits |
| Price per token | List price | Usually close to list price | Can be much lower at high utilisation |
| Ops effort | Lowest | Low | Low (provider) to high (self) |
| New model arrival | Day one | Days to months later | Whenever weights are released |

## Where the gateway fits

In Level 9 you met the model gateway: one layer between your code and providers. A managed platform relates to it in three ways:

1. **The platform is your gateway.** Bedrock's unified API already gives you many models behind one identity and one bill. A small team may need nothing else.
2. **The platform sits behind your gateway.** A LiteLLM proxy or an internal service routes to Bedrock *and* a public API *and* a self-hosted vLLM.
3. **The platform is one of several providers.** The gateway routes by region, cost or capability across Bedrock and Vertex.

```python
# The same app code, three backends, chosen by config (sketch)
BACKENDS = {
    "public":   {"kind": "openai",  "model": "example-frontier-model"},
    "platform": {"kind": "bedrock", "model": "example.bedrock-model-id", "region": "eu-central-1"},
    "open":     {"kind": "openai",  "base_url": "http://vllm.internal:8000/v1", "model": "example-open-model"},
}
```

If your code can switch between these by configuration, choosing a path later becomes much cheaper.

## Try it

Take an app you built against a public API (your Level 4 RAG app is ideal). List every component that would change if it had to run inside a company's cloud account with no public egress.

<details>
<summary>Reference</summary>

A typical list:

- **Auth:** the API key goes; the service gets an IAM role or service account with permission to invoke specific models.
- **Client code:** vendor SDK calls become platform calls (for example Bedrock's Converse API), or go through a gateway that hides the difference.
- **Model ids:** the platform has its own ids and may lag behind the vendor's latest model.
- **Network:** calls go through a private endpoint; the embedding model and any reranker must also be reachable privately.
- **Secrets:** fewer of them; whatever remains moves to the cloud's secret store.
- **Region:** the chosen region must offer both the chat model and the embedding model.
- **Logging and cost:** usage now shows up in cloud billing and audit logs instead of a vendor dashboard.
- **Evals:** must be re-run, because even the "same" model can behave slightly differently through another serving stack.
</details>

## Check yourself

1. Why do open-weight models not imply operating GPUs?

<details>
<summary>Answer</summary>

Managed platforms and serverless inference providers host popular open-weight models and charge per token. "Open" refers to the weights being available and portable, not to who runs the hardware.
</details>

2. Give two reasons a regulated company might reject a public API even if its model scores best.

<details>
<summary>Answer</summary>

Any two of: it doesn't integrate with the company's identity and audit system; it requires a new vendor contract and security review; traffic leaves the private network; processing can't be pinned to the required region.
</details>

3. Name the three ways a managed platform can relate to a model gateway.

<details>
<summary>Answer</summary>

It can act as the gateway itself, sit behind your own gateway, or be one of several providers that a gateway routes between.
</details>
