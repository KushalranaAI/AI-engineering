# Observability before optimization

Every flag in the next six modules trades one thing for another: chunked prefill trades TTFT for smoother ITL, bigger batches trade latency for throughput, quantization trades quality for memory. If you cannot see those numbers move, you are tuning by superstition. So build the dashboard first, record a baseline, and only then touch a setting.

## The four numbers

| Metric | Definition | What drives it | Users feel it as |
|--------|------------|----------------|------------------|
| **TTFT** (time to first token) | Request arrival to first output token | Queue wait + prefill | "Is it doing anything?" |
| **ITL / TPOT** (inter-token latency, time per output token) | Gap between output tokens; TPOT is the per-request average, ITL the individual gaps | Decode step time, batch size, prefills stealing steps | Reading speed of the stream |
| **Throughput** | Output (and input) tokens per second across all requests; also requests per second | Batch size, GPU, engine | Your cost per token |
| **Queue depth** | Requests waiting to be scheduled | Arrival rate vs capacity | Rising TTFT, then timeouts |

End-to-end latency ≈ TTFT + ITL × (output tokens − 1). Queue depth is the leading indicator: it rises before latency does, which is why it is also the right signal for autoscaling (12.10).

## What the engine exposes

vLLM serves Prometheus metrics on `/metrics` of the same port; SGLang does with `--enable-metrics`; llama.cpp with `--metrics`. Look before you graph:

```bash
curl -s localhost:8000/metrics | grep -E '^vllm:' | cut -d'{' -f1 | sort -u
```

In recent vLLM versions you will find, among others (names drift, so trust your own output over this list):

- `vllm:num_requests_running`, `vllm:num_requests_waiting`: batch size and queue depth.
- `vllm:kv_cache_usage_perc` (older: `gpu_cache_usage_perc`): how full the KV cache is.
- `vllm:time_to_first_token_seconds`, `vllm:inter_token_latency_seconds` (older: `time_per_output_token_seconds`), `vllm:e2e_request_latency_seconds`: histograms.
- `vllm:prompt_tokens_total`, `vllm:generation_tokens_total`: counters for throughput.
- `vllm:num_preemptions_total`, prefix cache query and hit counters.

## Prometheus and Grafana

Run both with Docker Compose next to the engine. The scrape config is short:

```yaml
# prometheus.yml
global:
  scrape_interval: 5s
scrape_configs:
  - job_name: vllm
    static_configs:
      - targets: ["host.docker.internal:8000"]   # or the service name in compose
  - job_name: sglang
    static_configs:
      - targets: ["host.docker.internal:30000"]
```

Then build panels from these PromQL queries:

```promql
# p95 TTFT over the last minute (histograms → quantiles)
histogram_quantile(0.95, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[1m])))

# p99 inter-token latency
histogram_quantile(0.99, sum by (le) (rate(vllm:inter_token_latency_seconds_bucket[1m])))

# output tokens per second
sum(rate(vllm:generation_tokens_total[1m]))

# queue depth and batch size
sum(vllm:num_requests_waiting)
sum(vllm:num_requests_running)

# KV cache fullness
max(vllm:kv_cache_usage_perc)
```

Two caveats. Histogram percentiles are only as precise as the bucket boundaries, so a p99 of "between 2 and 5 s" is what the buckets can tell you. And percentiles cannot be averaged across replicas; aggregate the buckets with `sum by (le)` first, as above. Both projects ship example Grafana dashboards in their repos; import one, then trim it to the panels you actually read.

A useful layout: a top row with p50/p95/p99 TTFT and ITL, a middle row with token throughput and requests per second, a bottom row with saturation (running, waiting, KV cache %, preemptions). Add GPU utilisation and memory from NVIDIA's DCGM exporter if you have it, but note that "GPU utilisation 100%" only means a kernel was running, not that the chip was efficient.

## Measure from the client too

The server's TTFT starts when the engine receives the request. It misses the network, TLS, any gateway, and queues in front of the engine (a load balancer, an API server's own backlog). Your load-test client (12.4) should record its own TTFT and ITL from the streamed chunks. When client and server numbers diverge, the gap is time spent outside the engine, and that is a finding in itself.

## Try it

With your dashboard up, send 50 identical requests one at a time, then 50 at once. Describe what moves on each panel.

<details>
<summary>Reference</summary>

Sequential: running stays at 1, waiting at 0, TTFT and ITL are at their minimum, throughput is low. Concurrent: running jumps to 50 (if it fits), throughput rises several times, ITL rises a little because each step handles more sequences, and TTFT rises because the 50 prefills compete. If the KV cache cannot hold all 50, you will see waiting requests and possibly preemptions.
</details>

## Check yourself

1. Which metric tells you first that a server is falling behind?

<details>
<summary>Answer</summary>

Queue depth (waiting requests). It grows as soon as arrivals exceed capacity, before TTFT percentiles catch up.
</details>

2. Why can't you average the p99 of three replicas to get the fleet p99?

<details>
<summary>Answer</summary>

Percentiles don't combine linearly. You must merge the underlying histogram buckets (or raw samples) and compute the percentile on the combined distribution.
</details>

3. Server-side TTFT is 200 ms but users see 1.5 s. Where do you look?

<details>
<summary>Answer</summary>

Outside the engine: the network, gateway or load balancer, an API layer queueing requests before forwarding them, or the client itself. Compare client-side timestamps hop by hop.
</details>
