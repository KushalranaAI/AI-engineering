# Deploying vLLM and SGLang

In Level 11 you started vLLM with one command. Now you will run it the way you would in production: pinned versions, every flag chosen on purpose, and a second engine, SGLang, serving the same model so you can compare them later. Both expose an OpenAI-compatible API, so the client code never changes.

## The hardware paths

| Path | Hardware | Model | Rough cost |
|------|----------|-------|------------|
| Laptop, no GPU | 16 GB RAM, any recent CPU | 0.5-3B, GGUF 4-bit with llama.cpp, or vLLM's CPU backend | Free, slow |
| One small GPU | A rented 24 GB card (L4, A10-class, RTX 4090) | 7-8B in BF16 (tight) or 4-bit | Often under $1 per hour on community clouds |
| One big GPU | A rented 80 GB H100 or A100 | 7-8B with lots of KV room, or 70B in 4-bit | A few dollars per hour |

Prices vary by provider and month; the point is that a few hours of one GPU is enough for everything in this level. Stop the instance when you finish.

## vLLM, flag by flag

```bash
pip install "vllm==<pinned version>"     # or the official Docker image with a fixed tag
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --dtype bfloat16 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 256 \
  --max-num-batched-tokens 8192 \
  --tensor-parallel-size 1 \
  --port 8000
```

- `--max-model-len`: the longest prompt plus output you accept. Lower it if startup fails with "not enough KV cache for one sequence".
- `--gpu-memory-utilization`: the fraction of GPU memory vLLM may take. Weights and overhead come out first; the rest becomes KV cache.
- `--max-num-seqs`: the most sequences in one batch. Too high and you preempt constantly; too low and the GPU idles.
- `--max-num-batched-tokens`: the token budget per scheduler step, shared by prefill chunks and decodes (see 12.5).
- `--tensor-parallel-size`: number of GPUs per replica.

Flags change between releases, so read `vllm serve --help` for your pinned version. Then read the startup log. It reports the memory used by weights and, crucially, how many tokens of KV cache it allocated and the maximum concurrency that implies for your `max-model-len`. Compare that line with your estimate from 12.1. If they disagree by a lot, one of you is wrong, and it is worth finding out who.

The first requests after startup can be slow: the engine captures CUDA graphs and warms kernels. Health-check `/health`, then send a few warm-up requests before you measure anything.

## SGLang, same model

```bash
pip install "sglang[all]==<pinned version>"   # or the official Docker image
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-7B-Instruct \
  --context-length 8192 \
  --mem-fraction-static 0.85 \
  --tp 1 \
  --enable-metrics \
  --port 30000
```

The names differ (`--mem-fraction-static` vs `--gpu-memory-utilization`, `--tp` vs `--tensor-parallel-size`) but the ideas match. SGLang's distinctive features are RadixAttention, a tree-shaped prefix cache (12.7), and a scheduler designed around structured, multi-call programs. Check the server arguments page in its docs for your version.

Both servers answer the same client:

```python
from openai import OpenAI
for base in ["http://localhost:8000/v1", "http://localhost:30000/v1"]:
    c = OpenAI(base_url=base, api_key="unused")
    r = c.chat.completions.create(model="Qwen/Qwen2.5-7B-Instruct",
        messages=[{"role": "user", "content": "Name three uses of a KV cache."}],
        max_tokens=100)
    print(base, r.usage)
```

## The cheap path

No GPU? You can still do most of this level.

```bash
# llama.cpp: build it or download a release, then
llama-server -m qwen2.5-1.5b-instruct-q4_k_m.gguf -c 8192 -np 8 --metrics --port 8080
```

`-c` is the total context shared by `-np` parallel slots, so 8 slots of 1,024 tokens here. `--metrics` exposes a Prometheus endpoint, so the observability work in 12.3 carries over. vLLM also has a CPU backend (installed from source or a CPU image); it is slower but runs the same scheduler you will read in 12.5. The absolute numbers will be small, but the shapes (TTFT growing with prompt length, ITL rising with batch, the queueing knee) are the same.

## Make it reproducible

Write a `launch.sh` and a `versions.txt`: engine version or image digest, model repo and revision hash, GPU model, driver and CUDA version. A benchmark without these is an anecdote.

## Try it

Start vLLM with `--max-model-len 32768` and then with `8192` on the same GPU, and record the KV cache capacity and maximum concurrency from the startup log each time.

<details>
<summary>Reference</summary>

The KV cache capacity in tokens stays about the same, because it depends on free memory, not on the context limit. The reported maximum concurrency changes roughly fourfold, because it is capacity divided by `max-model-len`. Lowering the context limit doesn't create memory; it promises the scheduler that no single sequence will need more than that.
</details>

## Check yourself

1. You raise `--gpu-memory-utilization` from 0.80 to 0.95. What changes?

<details>
<summary>Answer</summary>

Weights stay the same size, so all the extra memory goes to KV cache, letting more sequences or longer contexts run at once. The risk is out-of-memory errors if anything else on the GPU needs memory.
</details>

2. Why send warm-up requests before measuring?

<details>
<summary>Answer</summary>

The first requests pay one-off costs such as CUDA graph capture, kernel selection and memory allocation, which would inflate the latency you report.
</details>

3. What must a benchmark record to be reproducible?

<details>
<summary>Answer</summary>

Engine version, model and revision, GPU type, driver and CUDA version, every launch flag, and the exact workload (lengths, seed, concurrency).
</details>
