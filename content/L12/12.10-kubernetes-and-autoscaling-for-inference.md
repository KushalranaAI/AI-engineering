# Kubernetes and autoscaling for inference

A single GPU box goes a long way. Once you need several replicas, rolling upgrades and scaling with traffic, most teams reach for Kubernetes. The parts that differ from a normal web service are exactly the parts that hurt if you treat an inference server like one: GPUs as resources, very slow cold starts, and load that CPU metrics cannot see.

## GPUs in Kubernetes

GPUs become schedulable through NVIDIA's device plugin (usually installed by the GPU Operator or your cloud's GPU node pool). A pod asks for whole GPUs:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: vllm}
spec:
  replicas: 1
  selector: {matchLabels: {app: vllm}}
  template:
    metadata: {labels: {app: vllm}}
    spec:
      nodeSelector: {gpu-pool: l4}            # your node pool label
      containers:
      - name: vllm
        image: vllm/vllm-openai:<pinned tag>
        args: ["--model", "Qwen/Qwen2.5-7B-Instruct", "--max-model-len", "8192"]
        ports: [{containerPort: 8000}]
        resources:
          limits: {nvidia.com/gpu: 1}
        readinessProbe:
          httpGet: {path: /health, port: 8000}
          periodSeconds: 10
        startupProbe:
          httpGet: {path: /health, port: 8000}
          failureThreshold: 90                 # allow up to ~15 minutes to load
          periodSeconds: 10
        volumeMounts:
        - {name: model-cache, mountPath: /root/.cache/huggingface}
        - {name: shm, mountPath: /dev/shm}
      volumes:
      - name: model-cache
        persistentVolumeClaim: {claimName: hf-cache}
      - name: shm
        emptyDir: {medium: Memory, sizeLimit: 8Gi}
```

Notes that save days: pin the image tag; give a generous **startup probe** so Kubernetes doesn't kill a pod that is still loading weights; mount shared memory (tensor parallelism uses it); put weights on a shared volume or bake them into a node-local cache rather than downloading 16-140 GB from the internet on every start; and set `nodeSelector`/tolerations so GPU pods land on GPU nodes and nothing else squats there.

## Scale on queue depth, not CPU

The standard Horizontal Pod Autoscaler scales on CPU or memory. An inference pod's CPU is busy mostly with tokenization and HTTP; it can sit at 15% while the GPU is saturated and requests pile up. GPU utilisation is not much better: it reads near 100% whenever any kernel runs, even at batch size 1.

Scale on signals that measure work waiting for the GPU:

- **Waiting requests** (`vllm:num_requests_waiting`): the most direct sign that replicas are behind.
- **KV cache usage**: a leading indicator that admission is about to stall.
- **TTFT p95** against your SLO: useful but lagging, and noisy at low traffic.

KEDA makes this a short manifest. It queries Prometheus and drives the HPA for you:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: vllm}
spec:
  scaleTargetRef: {name: vllm}
  minReplicaCount: 1
  maxReplicaCount: 8
  cooldownPeriod: 900
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus.monitoring:9090
      query: sum(vllm:num_requests_waiting)
      threshold: "8"          # target waiting requests per replica
```

With the default averaging, desired replicas ≈ total waiting / 8. Pick the threshold from your load test: the queue length at which p95 TTFT starts breaching the SLO. The Kubernetes HPA with a Prometheus adapter does the same job if you prefer fewer components. Check KEDA's Prometheus scaler docs for current fields.

## Cold starts and warm pools

Scaling out an inference service is slow:

| Step | Typical range |
|---|---|
| Provision a GPU node (if none free) | 2-10 minutes |
| Pull a 10+ GB engine image | 1-5 minutes uncached |
| Load weights (16 GB from local disk vs internet) | seconds to many minutes |
| Engine warm-up, CUDA graph capture | tens of seconds |

A spike that lasts five minutes is over before a new replica is ready. So: keep at least one warm replica for interactive traffic (`minReplicaCount: 1`), scale up early on queue depth and scale down slowly (long cooldown, so you don't pay the startup again ten minutes later), pre-pull images on GPU nodes, keep a small buffer of idle GPU nodes if your budget allows, and shed or queue load gracefully (Level 9) while capacity arrives.

## Routing across replicas

A Kubernetes Service balances connections round-robin. For LLM traffic that is wasteful twice: it ignores how loaded each replica is (one may have 200 waiting requests, another none), and it scatters conversations so prefix caches miss (12.7). Better routers read each replica's queue and KV usage and prefer the replica that already holds a request's prefix. Options include the SGLang router, the Kubernetes Gateway API Inference Extension and the llm-d project; check their current status, as this space is young.

## Try it

On a local cluster (kind or minikube) without GPUs, deploy llama.cpp's server with `--metrics` as the "model", Prometheus, and KEDA scaling on a queue metric (llama.cpp exposes a deferred/queued requests gauge; check the name on its `/metrics`). Fire a burst of 200 requests and watch replicas scale out and back.

<details>
<summary>Reference</summary>

Replicas should rise within a scrape interval or two of the queue building, then the new pods take time to load the model before they help, which you will see as a lag between replicas "running" and queue depth falling. After the burst, replicas stay up until the cooldown expires. If CPU-based HPA were used instead, it might not scale at all, since the server's CPU barely changes with queue length.
</details>

## Check yourself

1. Why is CPU utilisation a poor autoscaling signal for a GPU inference server?

<details>
<summary>Answer</summary>

The work happens on the GPU; CPU only handles HTTP and tokenization, so it stays low while requests queue up for the GPU.
</details>

2. Why scale down slowly?

<details>
<summary>Answer</summary>

Starting a replica takes minutes (node, image, weights, warm-up). Removing replicas quickly means paying that start-up cost again at the next bump in traffic, with users waiting meanwhile.
</details>

3. What two pieces of information should an LLM-aware router use that round-robin ignores?

<details>
<summary>Answer</summary>

Each replica's current load (queue depth, KV cache usage) and which replica already has the request's prefix cached.
</details>
