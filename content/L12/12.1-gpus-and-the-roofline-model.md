# GPUs and the roofline model

Most inference decisions (which GPU, how many users per card, whether quantization or batching will help) come from three numbers on a datasheet and one small model of how work meets hardware. Get these right and you can predict a server's behaviour before you rent it.

## Three numbers on the datasheet

| Number | What it is | Example: H100 SXM | Example: L4 |
|--------|------------|-------------------|-------------|
| Memory (HBM / VRAM) | Where weights and KV cache live | 80 GB | 24 GB |
| Memory bandwidth | How fast the chip can read that memory | about 3.35 TB/s | about 0.3 TB/s |
| Dense BF16 tensor FLOP/s | How fast it can multiply matrices | about 990 TFLOP/s | about 120 TFLOP/s |

Datasheets often quote FLOP/s "with sparsity", which is double the dense number. Use the dense figure; inference rarely uses structured sparsity. Treat all of these as approximate and check the vendor page for your exact card.

**HBM** (high-bandwidth memory) sits next to the compute die. It is big compared with on-chip caches, but every byte the compute cores need has to travel from it, and that trip is usually the bottleneck.

## What has to fit

```
weights     = parameters × bytes per parameter
              8B × 2 bytes (BF16) = 16 GB
KV cache    = 2 × layers × kv_heads × head_dim × bytes × tokens
              Llama-3.1-8B: 2 × 32 × 8 × 128 × 2 B = 128 KiB per token
overhead    = activations, CUDA graphs, framework: budget a few GB
```

On an 80 GB H100 with 90% handed to the engine: 72 GB − 16 GB weights − ~3 GB overhead ≈ 53 GB of KV cache ≈ 400,000 tokens. At 4,000 tokens per conversation that is about 100 sequences at once. On a 24 GB card the same model leaves only a few GB for KV cache, which is why 4-bit weights are popular on small GPUs. The `2 ×` is for keys and values; `kv_heads` is smaller than the number of query heads in models using grouped-query attention, which is a big reason modern models are cheaper to serve.

## The roofline model

Any piece of work has an **arithmetic intensity**: FLOPs performed per byte moved from memory. A GPU has a **ridge point**: peak FLOP/s divided by bandwidth. For the H100, 990e12 / 3.35e12 ≈ **295 FLOPs per byte**.

- Intensity below the ridge: the cores wait for memory. You are **memory-bound**; time ≈ bytes / bandwidth.
- Intensity above the ridge: memory keeps up. You are **compute-bound**; time ≈ FLOPs / FLOP/s.

Plot attainable FLOP/s against intensity and you get a sloped line (bandwidth limit) that flattens into a roof (compute limit). That is the whole model.

## Prefill vs decode, worked

A forward pass costs about **2 × parameters FLOPs per token** (one multiply and one add per weight). For an 8B model, 16 GFLOP per token.

**Decode, one stream.** Each step produces one token but must read all 16 GB of weights. Intensity = 16 GFLOP / 16 GB = **1 FLOP per byte**, far below 295. Time per step ≈ 16 GB / 3.35 TB/s ≈ 4.8 ms, so the ceiling is about **210 tokens/s** for a single stream, and real engines reach perhaps 60-80% of that. The compute units are idle more than 99% of the time.

**Decode, batch of B.** The weights are read once and used for B tokens, so intensity rises to roughly B. This is why batching is nearly free throughput: 64 streams cost little more time per step than one. KV cache reads grow with batch and context, so in practice decode stays memory-bound even at large batches.

**Prefill of a 2,000-token prompt.** All prompt tokens go through in one pass: 2,000 × 16 GFLOP = 32 TFLOP against 16 GB of weights, an intensity of about 2,000. That is **compute-bound**: ≈ 32 ms at peak, more like 60 ms at realistic utilisation.

So prefill time scales with prompt length and FLOP/s; decode time scales with bytes read and bandwidth. Time to first token is mostly prefill (plus queueing); inter-token latency is decode. Every optimisation in this level attacks one of the two.

## Tensor parallelism, intuitively

When a model doesn't fit, or you want each token faster, **tensor parallelism** (TP) splits every weight matrix across N GPUs. Each GPU reads 1/N of the weights per step, so you get N times the memory and roughly N times the bandwidth. The price: after each split layer, the GPUs must combine partial results (an all-reduce), twice per transformer layer. Over NVLink this is cheap; over PCIe or across machines it can erase the gain. Rule of thumb: use TP within one machine, and replicas (or pipeline parallelism) across machines.

## Try it

Estimate, for Llama-3.1-70B (80 layers, 8 KV heads, head dim 128) in FP8 weights on two H100s with tensor parallel size 2: weight memory per GPU, KV cache per token, KV tokens that fit, and the single-stream decode ceiling.

<details>
<summary>Reference</summary>

Weights: 70 GB total, 35 GB per GPU. KV per token: 2 × 80 × 8 × 128 × 2 bytes = 320 KiB (BF16 cache), split across the two GPUs. Free memory: about 2 × (72 − 35 − 3) ≈ 68 GB, so roughly 68e9 / 327,680 ≈ 200,000 tokens. Decode: each GPU reads 35 GB per step at 3.35 TB/s ≈ 10.4 ms, a ceiling near 95 tokens/s per stream before communication overhead. An FP8 KV cache would halve the per-token figure and double capacity.
</details>

## Check yourself

1. Why does adding a second concurrent request barely slow down decode on a large GPU?

<details>
<summary>Answer</summary>

Decode is memory-bound: the step time is dominated by reading the weights. A second request reuses the same weight read, adding only its own small FLOPs and KV reads.
</details>

2. A prompt of 8,000 tokens hits an H100. Which resource bounds its time to first token?

<details>
<summary>Answer</summary>

Compute. Prefill pushes thousands of tokens through each weight read, so its arithmetic intensity is far above the ridge point and time scales with FLOPs.
</details>

3. Why doesn't tensor parallelism across two separate servers usually pay off?

<details>
<summary>Answer</summary>

TP needs an all-reduce after every split layer. Across a network those transfers are slow enough to cancel the extra bandwidth; it works best over fast links inside one machine.
</details>
