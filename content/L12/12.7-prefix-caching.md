# Prefix caching

If two requests start with the same 3,000 tokens, the keys and values for those tokens are identical. Computing them twice is waste. **Prefix caching** keeps the KV blocks of earlier requests and lets later requests with the same beginning skip that part of prefill. When it hits, TTFT drops sharply and the GPU has more compute left for everyone else. When it misses, it costs almost nothing. The engineering question is which workloads hit, and how to make them hit more.

## Two implementations

**vLLM: hashed blocks.** Each full block (say 16 tokens) gets a hash computed from its tokens *and the hash of the block before it*, so a hash identifies an entire prefix, not just 16 tokens in isolation. When a request arrives, the engine walks its blocks from the start, looking up each hash in the block pool's cache map (the one you saw in `block_pool.py` in 12.6). Matching blocks get their reference count raised and are reused; computation starts at the first miss. Freed blocks stay in the map until the LRU free queue reclaims them. Only full blocks are cached, so the last partial block is always recomputed. In recent versions this is on by default (`--enable-prefix-caching`; check your version).

**SGLang: RadixAttention.** Cached prefixes live in a radix tree keyed by token sequences. Lookup finds the longest matching path; insertion splits nodes where requests diverge; eviction removes least-recently-used leaves. The scheduler can also order the waiting queue by longest cached prefix, so requests that share a prefix run close together while it is still cached.

The outcome is similar. The tree makes partial matches and scheduling by prefix natural; the hashed blocks fit neatly into the paged allocator.

## Which workloads it helps

| Workload | Shared prefix | Benefit |
|---|---|---|
| Long system prompt or tool definitions on every call | Thousands of tokens, all users | Large |
| Multi-turn chat | Each turn repeats the whole history | Large, per conversation |
| Agent loops | Same instructions + growing scratchpad on every step | Large |
| Few-shot classification | Same examples, different input at the end | Large |
| RAG with the same document asked many questions | The document, if placed first | Large |
| RAG with different chunks per query | Only the system prompt | Small |
| Unique one-off prompts (summarise this upload) | None | None |

Quick estimate: if 70% of each prompt's tokens are a cached prefix, prefill work drops by about 70%, and TTFT for those requests drops by close to that once queueing is excluded. Decode speed does not change: prefix caching is a prefill optimisation.

## Keeping the hit rate high

1. **Stable content first.** Put the system prompt, tool schemas and few-shot examples at the very beginning; put anything that varies (timestamp, user name, request id) after them. A single changed token early in the prompt invalidates every block after it. "Today is 2026-11-06 14:03:22" at the top of a system prompt quietly gives you a hit rate of zero.
2. **Deterministic formatting.** The same text must tokenize the same way. Serialise tool schemas with sorted keys; keep whitespace fixed.
3. **Route by prefix.** With several replicas, round-robin spreads a conversation across all of them, and each one caches only a fraction of it. Send a session (or a shared system prompt) to the replica that already holds it, by consistent hashing on a session or prefix key, or with a cache-aware router (SGLang has a router with cache-aware balancing, and newer Kubernetes routing projects do this too). Balance against load, so one hot prefix doesn't melt one replica.
4. **Leave room.** If the KV cache is always full of running sequences, cached blocks are evicted before anyone reuses them. Watch the hit rate as you raise concurrency.

Measure it: vLLM exposes prefix cache query and hit counters on `/metrics`, and the hit rate is `rate(hits) / rate(queries)`. Put it on your dashboard next to TTFT.

This is the self-hosted version of the prompt caching that hosted APIs sell at a discount; the same "stable prefix first" rule applies to both.

## Try it

Build two workloads of 500 requests each: (a) a 2,000-token fixed system prompt followed by a 50-token question, (b) the same but with the current timestamp on the first line. Load test both with prefix caching on, and compare TTFT p50 and the cache hit rate.

<details>
<summary>Reference</summary>

Workload (a) should show a hit rate near the prefix share (about 95% of prompt tokens after the first request) and a TTFT several times lower than (b). Workload (b) shows a hit rate near zero, because the timestamp changes the very first block and every later block hash depends on it.
</details>

## Check yourself

1. Why does vLLM include the previous block's hash when hashing a block?

<details>
<summary>Answer</summary>

So that a block is only reused when everything before it also matches. Keys and values depend on all earlier tokens, so identical 16-token blocks after different histories are not interchangeable.
</details>

2. Does prefix caching speed up inter-token latency?

<details>
<summary>Answer</summary>

Not directly. It skips prefill work for shared prefixes, cutting TTFT and freeing compute. Decode still reads the same weights and KV per step.
</details>

3. Why can round-robin load balancing hurt the prefix cache?

<details>
<summary>Answer</summary>

Successive requests for the same conversation or prompt land on different replicas, each of which must compute and cache the prefix separately, so each replica's hit rate drops.
</details>
