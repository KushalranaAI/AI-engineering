# Schedulers: continuous batching and chunked prefill

The model's forward pass is the same in every engine. What separates a good serving engine from a slow one is mostly the **scheduler**: the loop that decides, every few milliseconds, which requests take part in the next GPU step and how many tokens each contributes. This module is about reading that loop.

## Static vs continuous batching

**Static batching** collects a batch, runs it until every sequence finishes, then starts the next. One request generating 2,000 tokens holds the whole batch hostage while others that finished after 50 tokens sit as padding, and new arrivals wait outside.

**Continuous batching** (also called iteration-level scheduling, introduced by the Orca paper) reschedules at every decode step. A sequence that emits its end token leaves immediately and frees its KV cache; a waiting request joins on the next step. Because decode is memory-bound (12.1), adding sequences to a step costs little, so keeping the batch full is close to free throughput. Gains of several times over static batching are typical on mixed-length traffic.

## What one scheduling step does

Stripped down, a modern scheduler looks like this:

```python
def schedule_step(running, waiting, kv, token_budget):
    batch = []
    # 1. keep running sequences going: each decode needs 1 token of budget
    for req in running:
        if not kv.can_append(req):
            victim = running.pop()          # lowest priority, usually newest
            kv.free(victim); waiting.appendleft(victim)   # preempt: recompute later
            continue
        batch.append((req, 1)); token_budget -= 1
    # 2. admit waiting requests while budget and KV blocks last
    while waiting and token_budget > 0 and len(batch) < MAX_SEQS:
        req = waiting[0]
        n = min(req.remaining_prompt_tokens, token_budget)   # chunked prefill
        if not kv.can_allocate(req, n):
            break
        waiting.popleft(); running.append(req)
        batch.append((req, n)); token_budget -= n
    return batch                             # one forward pass over all of it
```

Three limits shape every step: the **token budget** (vLLM `--max-num-batched-tokens`), the **sequence cap** (`--max-num-seqs`), and **free KV blocks**. Priorities and fairness rules sit on top.

## Reading the real code

Clone both repos at the tag you deployed and read with the dashboard open.

**vLLM (V1 engine).** Start at `vllm/v1/core/sched/scheduler.py` and find `schedule()`. Things to notice: the V1 scheduler does not split "prefill phase" and "decode phase"; each request simply has a number of computed tokens and a target, and the scheduler hands out tokens from one budget, running requests first, then waiting ones. When allocating KV blocks fails, it preempts a running request and puts it back in the waiting queue to be recomputed. Follow the call into `vllm/v1/core/kv_cache_manager.py` to see how blocks are requested (you will reread this in 12.6).

**SGLang.** Open `python/sglang/srt/managers/scheduler.py`. Find the event loop and `get_next_batch_to_run`, then the prefill admission logic (a helper that adds requests while budget remains) in `schedule_policy.py`. Notice the scheduling policy option: besides first-come-first-served, SGLang can order waiting requests by longest cached prefix, which raises cache hits (12.7). Also notice the overlap mode, which prepares the next batch on the CPU while the GPU runs the current one.

File paths move between releases; if one is missing, search the repo for `def schedule` or `max_num_batched_tokens`. Write a one-page note: what is in the batch, in what order requests are admitted, and what happens when memory runs out. That note is worth more than any blog post.

## Chunked prefill

Without it, a 16,000-token prompt arriving at a busy server forms a huge prefill step. Every decoding user waits for it, so their ITL spikes from 30 ms to several hundred. With **chunked prefill**, the prompt is cut into pieces that fit the token budget and each piece rides along with the ongoing decodes. The long prompt's TTFT gets a little worse (it is spread over several steps); everyone else's token stream stays smooth.

The budget is the knob:

| `max-num-batched-tokens` | Effect |
|---|---|
| Small (e.g. 2,048) | Short steps, smooth ITL, slower prefill, so higher TTFT for long prompts |
| Large (e.g. 16,384) | Fast prefill, lower TTFT, but decodes stall behind big steps, so ITL p99 rises |

There is no universally right value. Pick the SLO that matters (chat users feel ITL; a batch summariser only cares about throughput), then sweep the budget with the load test from 12.4 and read the trade-off off your dashboard. vLLM V1 enables chunked prefill by default; SGLang controls the chunk with `--chunked-prefill-size`. Check the docs for your version.

## Try it

With a steady load of 64 chat streams running, inject one 16,000-token prompt every 10 seconds. Run once with a token budget of 2,048 and once with 16,384, and compare p99 ITL of the chat streams and TTFT of the long prompts.

<details>
<summary>Reference</summary>

With the small budget, chat p99 ITL barely moves, while each long prompt takes several steps to prefill, raising its TTFT. With the large budget, the long prompt prefills in one or two big steps (lower TTFT for it), but every chat stream sees a visible ITL spike each time it arrives, which shows up in p99.
</details>

## Check yourself

1. Why does continuous batching help most when output lengths vary widely?

<details>
<summary>Answer</summary>

With static batching, short sequences finish early and leave idle slots until the longest one ends. Continuous batching refills those slots every step, so the GPU stays busy.
</details>

2. What does the scheduler do when it cannot allocate KV blocks for a running sequence?

<details>
<summary>Answer</summary>

It preempts a sequence (usually the lowest priority or newest), frees its blocks and requeues it. In vLLM V1 the preempted request is later recomputed from its tokens.
</details>

3. A chat product has bad p99 ITL whenever long documents are uploaded. Which knob do you try first?

<details>
<summary>Answer</summary>

Make sure chunked prefill is on and lower the per-step token budget, so long prompts are split into smaller pieces that don't stall decoding streams. Then confirm on the dashboard that TTFT for long prompts is still acceptable.
</details>
