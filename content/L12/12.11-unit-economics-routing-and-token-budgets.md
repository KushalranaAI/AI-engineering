# Unit economics, routing and token budgets

A fast server is not automatically a profitable product. Inference is a variable cost that grows with every request, every retry and every extra agent step, and it can quietly exceed what a customer pays. This module turns your benchmark numbers into business units, then gives you two controls: a router that sends each request to the cheapest model that is good enough, and a token budget that caps what any request may spend.

## From GPU-hours to cost per task

All numbers below are examples; plug in your own.

```
GPU price:                          $2.50 / hour
Sustained output at your SLO:       2,000 tokens/s  (from the 12.4 load test, not peak)
                                    = 7.2M output tokens / hour
Cost at 100% busy:                  $2.50 / 7.2M  ≈ $0.35 per 1M output tokens
Average utilisation over the day:   40%  (nights, weekends, headroom)
Effective cost:                     ≈ $0.87 per 1M output tokens
```

Input tokens are not free on your own GPU: they cost prefill compute. The honest way is to measure requests per second at your SLO for *your* traffic mix, which prices input and output together:

```
Requests/s at SLO (your traffic mix):  5   → 18,000 requests / hour
Cost per request at 40% utilisation:  $2.50 / (18,000 × 0.4) ≈ $0.00035
```

Now climb to the units the business uses:

- **Per task.** A support task might be 1 classification call, 1 retrieval rewrite, 4 agent steps with growing context, and a retry on 10% of steps: about 7 calls, and later calls are larger because context accumulates. Cost per task is the sum, not "one request".
- **Per user.** Tasks per user per month × cost per task. A heavy 5% of users often costs as much as the other 95% together.
- **Margin.** Compare with the price. A $10/month plan with a power user running 2,000 agent tasks at $0.01 each is a $10 loss.

## How inference breaks the margin

The usual culprits, in rough order: long outputs (output tokens dominate decode time), context that grows every turn or agent step, retries and self-consistency sampling, agent loops with no step cap, idle GPUs (utilisation is the denominator in every line above), and a frontier model used for tasks a small one handles. Self-hosting only beats per-token APIs when utilisation is high; find the break-even volume where your effective $/1M tokens drops below the API's price for equivalent quality, and keep the hosted API as overflow above it.

## Your own model router

A router picks a model per request. Start simple and measured:

```python
ROUTES = {   # from your own eval and load-test numbers
  "small-8b-selfhosted": {"cost_per_1k": 0.0004, "p95_ttft_ms": 250, "quality": 0.78},
  "mid-hosted":          {"cost_per_1k": 0.003,  "p95_ttft_ms": 600, "quality": 0.86},
  "frontier-hosted":     {"cost_per_1k": 0.02,   "p95_ttft_ms": 1200, "quality": 0.93},
}

def route(req, difficulty: float):
    need = 0.75 + 0.2 * difficulty          # harder request → higher quality bar
    ok = [(n, r) for n, r in ROUTES.items()
          if r["quality"] >= need and r["p95_ttft_ms"] <= req.latency_slo_ms]
    if not ok:
        return "frontier-hosted"            # or reject / degrade, per product rules
    return min(ok, key=lambda x: x[1]["cost_per_1k"])[0]
```

The hard part is `difficulty`. Options, from cheapest: rules (task type, input length, tenant tier), a small classifier trained on which requests the small model got wrong in your eval logs, or a cascade (Level 9) that tries the small model and escalates when a check fails (schema invalid, low confidence, verifier says no). Quality numbers must come from your own eval set per task category, not a leaderboard. Log every routing decision with cost, latency and outcome, then review weekly: the share of traffic on each model is your biggest cost lever.

## A token budget per request

A budget is a set of hard caps enforced in code before and during each call:

| Part | Example cap | Enforced by |
|---|---|---|
| System + tools | 1,500 | Prompt review, tests |
| Conversation history | 3,000 | Summarise or drop oldest turns |
| Retrieved context | 2,500 | Fewer/shorter chunks, rerank first |
| User input | 2,000 | Truncate or reject with a message |
| Output | 600 | `max_tokens` |
| Agent steps per task | 8 | Loop counter |
| Total tokens per task | 40,000 | Running tally, stop or escalate |

```python
def fit(parts: dict[str, str], caps: dict[str, int], count) -> dict[str, str]:
    out = {}
    for name, text in parts.items():
        toks = count(text)
        # TODO: if over cap, summarise history, drop lowest-ranked chunks,
        #       or truncate input, then recount
        out[name] = text
    return out
```

Count with the serving model's own tokenizer, since counts differ between models. Record the per-request tally in your logs and on the dashboard: a slowly rising average prompt size is an early warning that costs and TTFT are about to rise together. Budgets also protect the server: a hard cap on input and output length is what lets you set `max-model-len` and predict KV usage (12.6).

## Try it

Using your own load test results, compute cost per request, per task (assume 6 calls per task with the context doubling every two calls) and per user (40 tasks per month) at 30% and 70% utilisation. Find the utilisation at which you break even with a hosted API you would otherwise use.

<details>
<summary>Reference</summary>

Cost per request scales inversely with utilisation, so going from 30% to 70% cuts it by more than half. Per-task cost is dominated by the last, largest calls, so trimming history or summarising context usually saves more than switching GPU. The break-even utilisation is effective self-hosted $/token equal to the API's $/token; below it, the API is cheaper and simpler.
</details>

## Check yourself

1. Why must cost per request use sustained throughput at the SLO rather than peak throughput?

<details>
<summary>Answer</summary>

You cannot sell peak throughput: at peak, latency breaks the SLO. The usable capacity is the load at which latency targets still hold, which is lower and makes each request more expensive.
</details>

2. A router saves 60% on paper but complaints rise. What went wrong most likely?

<details>
<summary>Answer</summary>

Its quality estimates or difficulty signal were wrong for some request categories, sending hard requests to the small model. Routing needs per-category evals and outcome logging, plus a fallback when checks fail.
</details>

3. Name two ways a per-request token budget helps the inference server itself, not just the bill.

<details>
<summary>Answer</summary>

Capped inputs and outputs make KV cache usage and latency predictable, so you can set context limits and concurrency safely; and they stop runaway prompts or loops from monopolising batch slots and hurting other users' latency.
</details>
