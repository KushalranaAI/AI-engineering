# Load testing and tail latency

One request tells you how fast the model is. A load test tells you how many people you can serve before they notice. The goal is a capacity statement you can defend: "this replica handles 12 requests per second at p95 TTFT under 800 ms and p95 ITL under 60 ms, for chat-shaped traffic".

## Closed vs open load

- **Closed loop (fixed concurrency):** N virtual users; each sends a request, waits for the full answer, sends the next. When the server slows down, users send less, so the queue never explodes. Good for finding throughput at a given concurrency.
- **Open loop (fixed arrival rate):** requests arrive at R per second (often Poisson-distributed) whether or not earlier ones finished. This is how real users behave, and it is the only way to see a queue build up.

Use both. Closed loop at rising concurrency finds the throughput curve; open loop at rising rates finds the knee where latency bends upward.

## Traffic that looks like yours

A fixed 512-in, 128-out prompt flatters every engine. Real chat has short questions and long histories; RAG has 3,000-token prompts and 200-token answers; summarisation is long-in, short-out; agents repeat a long prefix. Sample input and output lengths from your logs, or use a public conversation dataset, and always cap output with `max_tokens` plus `ignore_eos` (where supported) so every run generates the same number of tokens.

## Tools

**vLLM's benchmark** works against any OpenAI-compatible server (check `vllm bench serve --help` for current flags):

```bash
vllm bench serve \
  --backend openai-chat --base-url http://localhost:8000 \
  --endpoint /v1/chat/completions \
  --model Qwen/Qwen2.5-7B-Instruct \
  --dataset-name random --random-input-len 1024 --random-output-len 256 \
  --num-prompts 4000 --max-concurrency 1000 --request-rate inf \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,95,99 \
  --seed 42 --save-result
```

SGLang ships `python -m sglang.bench_serving` with similar options; NVIDIA's `genai-perf` and general tools like `locust` or `k6` also work. A small asyncio client is worth writing once, because you control exactly what is measured:

```python
import asyncio, time, numpy as np
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="x", timeout=600)

async def one(prompt):
    t0 = time.perf_counter(); first = None; stamps = []
    stream = await client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct", stream=True, max_tokens=256,
        messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        now = time.perf_counter()
        if chunk.choices and chunk.choices[0].delta.content:
            first = first or now; stamps.append(now)
    itl = np.diff(stamps) if len(stamps) > 1 else np.array([])
    return first - t0, itl, stamps[-1] - t0

async def main(n=1500, concurrency=1000):
    sem = asyncio.Semaphore(concurrency)
    async def guarded(i):
        async with sem: return await one(f"Request {i}: explain paging in 200 words.")
    res = await asyncio.gather(*[guarded(i) for i in range(n)])
    ttft = [r[0] for r in res]; itl = np.concatenate([r[1] for r in res])
    for name, xs in [("TTFT", ttft), ("ITL", itl)]:
        print(name, {p: round(float(np.percentile(xs, p)) * 1000) for p in (50, 95, 99)}, "ms")

asyncio.run(main())
```

At 1,000+ concurrent streams the client itself becomes a suspect. Raise the open-file limit (`ulimit -n 65536`), make sure the HTTP client's connection pool allows that many connections, run the client on a different machine from the server if you can, and watch its CPU. A saturated client reports server latency that does not exist.

## Percentiles, never the mean

Latency distributions under load are skewed: most requests are fine, a few wait behind a long prefill or a preemption. Suppose 95 requests get TTFT 300 ms and 5 get 6 s. The mean is 585 ms, which describes nobody. The p50 is 300 ms (typical user), p95 is right at the edge, p99 is 6 s (the users who leave). At scale, 1% is a lot of people: at 10 requests per second, 1% is over 8,000 bad experiences a day.

Report p50, p95 and p99 for TTFT, ITL and end-to-end latency, plus throughput (output tokens/s and requests/s), and the error and timeout count. A run where 3% of requests time out and are left out of the percentiles is lying to you.

## Finding the knee

Ramp concurrency (or rate): 1, 8, 32, 128, 256, 512, 1,000, 1,500. Plot throughput and p95 TTFT against it. Throughput rises then flattens; TTFT stays flat then shoots up. The knee is where the queue starts growing faster than it drains: the waiting-requests panel from 12.3 leaves zero right there. Your sellable capacity is the highest load that still meets the SLO, not the peak throughput.

## Try it

Run the ramp above against your server and fill a table: concurrency, output tokens/s, p50/p95/p99 TTFT, p95 ITL, errors. Mark the knee.

<details>
<summary>Reference</summary>

Expect throughput to grow almost linearly at low concurrency (decode is memory-bound, batching is nearly free), flatten once the KV cache or the token budget is saturated, and TTFT p99 to jump once requests start waiting. ITL creeps up steadily with batch size. The knee is usually well below the concurrency where throughput peaks.
</details>

## Check yourself

1. Why can a closed-loop test hide an overloaded server?

<details>
<summary>Answer</summary>

Each virtual user waits for its answer before sending again, so a slow server automatically receives fewer requests and the queue stays bounded. Real users keep arriving regardless.
</details>

2. Your mean TTFT improved but complaints rose. How?

<details>
<summary>Answer</summary>

A change can speed up typical requests while making the tail worse (for example, larger batches that occasionally stall behind long prefills). The mean improves while p99 degrades.
</details>

3. Name two ways the load generator can distort results.

<details>
<summary>Answer</summary>

Running out of CPU, connections or file descriptors, which adds client-side delay; and dropping timeouts or errors from the statistics. Running on the same machine as the server also steals resources.
</details>
